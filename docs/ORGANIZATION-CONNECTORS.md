# Organization connectors

Organization connectors are staged behind `METRO_CONNECTORS_ENABLED` on api.metro.box. Leave it unset until a separately approved rollout. Existing agents continue using their local connectors. Merging the setup API and page does not enroll or update agents, import their connectors, or activate organization connectors.

## Agent enrollment

An organization admin opens the selected agent's **Server** page, clicks **Enroll with organization**, checks the agent and organization in the confirmation, then clicks **Enroll agent**. The page uses the existing WorkOS login to create a one-use, ten-minute ticket with `POST /api/servers/<id>/enrollment`, then gives it to that agent's captured daemon origin at `POST /api/enrollment`. The ID is the central server row, not the local daemon agent ID, EC2 instance ID or slug. No token handling or separate sign-in is needed.

Before minting, the page checks the captured daemon's `/api/mode` response for its organization and enrollment-compatible version (beta.288 or later). This gives old daemons an Update notice without attempting their unsupported POST route.

The page holds the ticket only in memory. A retry in the same dialog reuses an unexpired ticket so the daemon can recover an interrupted confirmation while its pending key still exists. If the daemon already finished and discarded its pending record, a lost browser reply can instead produce a definite consumed-ticket refusal. The page explains this and discards the ticket; the next explicit retry obtains a fresh one and may replace the existing enrollment identity. Closing the dialog discards the ticket too; starting again obtains a fresh ticket. Account or agent changes abort the request and invalidate the dialog's operation, including a switch away and back. Closing or aborting cannot undo enrollment already received by the daemon, so an interrupted request is not reported as an unchanged agent. A successful response must match the captured organization and central server ID.

Enrollment does not enable delivery or live tools, assign or move connectors, or change API/live rollout flags. Starting enrollment clears a saved Sync On setting and its receipt, even if the exchange later fails; check the Server page status and explicitly enable sync again only after confirming enrollment. It replaces an existing enrollment identity if the agent was already enrolled. Setup-off and old-daemon failures are explained without displaying remote response text. The daemon registers its signing and sealing public keys with `POST /api/agents/enroll`. Its private keys stay in Metro's protected agent directory, never in the agent's readable view, a bundle or an export.

The daemon saves a candidate in `agent-key.pending.json` (0600) **before** contacting the API, flushing the file and directory to disk. This recovery record includes a hash of the ticket, not the ticket itself, and the expected agent identity once known. Only a matching signed `/api/agents/session` confirmation promotes it to the active `agent-key.json`. The active file is flushed before the pending copy is removed. A confirmation failure keeps the pending private key and leaves the previous active file unchanged.

Retrying the same ticket first checks whether that candidate already committed remotely. If so it finishes locally without consuming the ticket again. A different ticket always goes through enrollment with a new key, after preserving any recovered old identity. Only an explicit missing-key response permits a retry of the enrollment exchange: outages, clock errors and inconsistent identities are reported without consuming another ticket. Unreadable pending files are never overwritten. A fresh ticket may be required if the previous one expired before enrollment committed.

Only one enrollment request per daemon directory can run at a time. Overlapping requests return 409 rather than saving keys out of order. An organization change during a request also returns 409. Enrollment belongs to the organization that initiated it, never the new owner.

`agent-key.json` is preferred over the old `box-key.json`. The legacy file is read only when the new file is absent. A damaged new file does not resurrect an old key.

## Deployment compatibility

Migration `0006_agent_keys` renames the old table in place. It preserves key material, assignments, secrets, audit rows and applied migration history. The `box_keys` compatibility view lets the previous API remove keys during an organization move while Fly replaces its machines. It does not support old enrollment upserts. Keep the feature off throughout the deployment and any rollback to the old API.

Enrollment uses `/api/agents/enroll`, `/api/agents/session`, `Authorization: MetroAgent ...` and the `metro-agent-request/v1` signing domain. API and daemon versions must match this protocol. Old routes and signatures are not aliases. Infrastructure addresses containing `box` are not renamed.

Connector Activity removal also requires two releases. Deploy all reader/writer/UI removal first while keeping `connector_events`. Verify that every old API writer and in-flight request has stopped before a separately approved drop release: an old audit insert can fail after the provider rotates a token and roll back its replacement. The prepared SQL stays outside the active journal in `apps/api/drizzle/pending/0010_drop_connector_events.sql`. Follow the [two-release procedure](../README.md#removing-connector-activity-storage-in-two-releases) to activate it later with the next contiguous, increasing journal entry. It deletes only Activity history, not credentials, assignments, keys, nonce guards, migration mappings, refresh intents, local migration journals/maps/receipts, the namespace ledger, sync receipt or unrelated history. There is no local Activity table to drop. Do not roll back to Activity-writing API code after the drop.

## Secrets and rollout

Secrets in Postgres are sealed with AES-256-GCM under one `METRO_CONNECTORS_KEY` Fly secret, with organization and connector identity as additional authenticated data. The browser never receives them. Do not replace an existing key: there is no key rotation or re-sealing flow yet.

OAuth sign-in, the organization setup page, assignments and policies are implemented. Central refresh and memory sync are separately gated from setup. Enabling the setup switch alone does not migrate existing per-agent connector configuration. No tool call is relayed through api.metro.box.

## Central refresh and signed delivery

The staged `POST /api/agents/connectors` endpoint requires both `METRO_CONNECTORS_ENABLED=true` and `METRO_CONNECTORS_DELIVERY_ENABLED=true`. Neither is enabled by default. A browser or a user bearer token cannot fetch credentials. The enrolled agent signs each request with its private key. Durable database nonces prevent replay across API processes and restarts.

OAuth refresh is serialized by a database row lock, not an in-process lock. The service rereads the encrypted current token under that lock and preserves a rotating refresh token. A forced refresh names an opaque prior credential revision so simultaneous retries do not refresh the newly issued token twice. An invalid grant requires sign-in again; a transient provider failure must not erase the saved refresh token.

Only current, same-organization assignments can be delivered. Authorization, assignment and policy checks run again after slow refresh work. Connector-level and assignment policies are combined without allowing either to weaken the other. Delivery includes the target URL, access header, policy and opaque revision, never an OAuth refresh token or client secret. The full payload is sealed to the enrolled agent's X25519 key and bound to its organization, agent ID, key ID and random request ID.

Snapshots have a lease of at most 90 seconds. This limits how long Metro can retain the delivery; it does not shorten a vendor's access token or API key lifetime. Tokens with an earlier expiry cannot be used beyond it. Credential lifetime is measured from the API's snapshot issue time, then reduced by monotonic request time, so an allowed clock difference cannot extend it. Responses are bounded, not silently truncated, and are not cacheable.

Connector Activity and its event API are removed. Enrollment, refresh, delivery and migration no longer write an Activity log. This does not remove authorization nonces, assignments, operation mappings or refresh intents. Verify receipt on the daemon, not from an API response being prepared.

## Permissions and tool catalogue

Read and Write come only from the vendor's `readOnlyHint`: true means Read, anything else means Write. Unknown tools count as Write; names do not determine the group. Each policy layer resolves a named tool override before its group default. The organization and agent layers then combine with the stricter result winning: Block, then Ask, then Allow. A named Allow or Ask exception remains effective when its own layer's group defaults are Block, but cannot weaken the other layer. Older agents receive a conservative flattened fallback and may enforce stricter permissions until updated.

Organization admins save a full organization policy with `PUT /api/connectors/<id>` and an agent policy with `PUT /api/connectors/<id>/agents/<agent>/policy`, each using `{ policy }`. The separate agent-policy route fails with 404 on an older API without changing the assignment or clearing its restrictions. Clients never retry that write through the legacy assignment route, which retains its `readOnly` and empty-body behavior. Saved named overrides are retained even when absent from the current catalogue.

Updated daemons request exact policy layers using the signed `policy_layers=1` query. Their redundant flat fallback is compact Block for both groups; effective permissions are recomputed from the complete layers and provider groups. Older daemons receive the unchanged conservative flat shape. Unusually large combined policies or snapshots can make the largest connector payloads unavailable with no credentials and a Block-only fallback, rather than interrupting unrelated smaller connectors. Stored policies are not rewritten or partially allowed, and the existing encrypted-delivery size cap is unchanged.

An organization member can read `GET /api/connectors/<id>/tools` for a connector in that organization, including blocked or unassigned connectors. The response contains tool metadata only, never credentials. Endpoint path segments, including those revealed by recursively decoded separators, and their encoded forms are redacted from text. For tool names only, an exact terminal `mcp` or `sse` segment is assumed to be public protocol routing, including its encoded forms; no other path segment is exempt. Explicit header, OAuth and query credentials always take precedence, even when their value is `mcp` or `sse`. A tool name containing a protected value causes generic refusal instead of returning or renaming it. This catalogue request does not grant permissions, create an assignment or execute `tools/call`. OAuth refresh remains central through the existing row-lock and imported-grant ownership paths; discovery does not enable the connector's policy.

## Staged daemon memory sync

An organization admin can enable **Sync org connectors** on the selected agent's **Server** page after updating its daemon to beta.289 or later. The protected `org-connector-sync.json` setting in Metro's agent directory stores only a version, boolean and opaque organization/enrollment binding, never connector credentials. The save takes effect without a service restart and survives daemon restarts. An explicit saved setting, including Off, overrides `METRO_CONNECTORS_SYNC_ENABLED`. Only when no saved file exists does `METRO_CONNECTORS_SYNC_ENABLED=true` retain its previous behavior. With neither opt-in present, sync is off. An unreadable, invalid or different-identity setting fails off, not back to the environment.

The setting is bound to the current owner, enrolled central agent ID and enrollment key. Owner or enrollment invalidation clears a saved On setting. An observed identity mismatch also clears it, so returning to the old owner cannot silently restore that opt-in. A fresh admin action is needed after enrollment replacement. Legacy environment-only deployments keep their separate environment opt-in; they still cannot retain an old identity's receipt or in-flight snapshot. A scope token prevents a delayed page write from succeeding after invalidation, even if the owner changes away and back, or the daemon restarts.

With sync enabled and the agent enrolled in its current organization, the daemon retrieves an encrypted snapshot at start, immediately after enabling, and every minute. Overlapping polls share a request. The snapshot lives in an isolated memory store only, never `connectors.json`, the plugin configuration, a policy file, the agent view, a bundle or an export.

Turning sync Off cancels in-flight delivery, clears memory and removes organization tool publication while leaving local connectors alone. Memory is also cleared on sync failure, lease expiry, owner change, enrollment-key change or shutdown. A response that was already in flight before an owner change cannot install credentials afterward, even if the organization changes back. Both monotonic elapsed time and wall time bound the lease, so a slow response or a backward clock adjustment cannot extend it.

Memory sync alone is still a preparation stage, not the relay cutover. Existing per-agent connector setup, OAuth, tool policies and relay behavior stay unchanged when only memory sync is opted into. No organization connector is published as a live tool unless the separate runtime switch below is also enabled.

### Safe receipt status

`GET /api/connectors/sync` and `PUT /api/connectors/sync` require a current WorkOS bearer for an admin of this daemon's organization. Monitor and agent tokens cannot read or change them. PUT accepts only the boolean `enabled` and current opaque `scope`; it cannot alter live tools. An older daemon gets an Update notice before any unsupported call. A failed or interrupted page save is not proof that the daemon stayed unchanged; refresh status to reconcile it.

Status reports the effective setting and its source, local confirmed enrollment, and a receipt derived only from an authenticated, decrypted, validated snapshot accepted by this running daemon. Before the first receipt it says Waiting, never healthy or zero connectors. A received empty snapshot explicitly reports zero. Counts include total, ready and unavailable connectors, not names, URLs, headers, credentials, revisions or vendor errors. Last received and lease expiry are daemon timestamps, with the lease shortened by delivery time and any earlier credential expiry. Counts are cleared on expiry or failure; a last-success timestamp is historical, not current access. Status is memory-only and resets on restart or identity change. Refreshing status reads the current state; it does not make a central delivery request.

Off, not enrolled, waiting, received, expired and unavailable are distinct states. An enrollment badge is local confirmation, not a fresh central key-validity check. API delivery is still a separately approved prerequisite: enabling this switch alone cannot turn it on, and a rejected delivery shows Unavailable. Only the daemon's validated snapshot establishes receipt.

This control never changes `METRO_CONNECTORS_LIVE_ENABLED`. To avoid accidentally activating tools on a server with that legacy flag already set, the page/API refuse an On save while it is true; Off remains available. Such deployments show a warning instead of claiming live tools are off. Default and pilot deployments leave the live flag unset or false.

## Opt-in local tool runtime

`METRO_CONNECTORS_LIVE_ENABLED=true` on the daemon opts assigned organization connectors into its local relay. It also requires effective daemon sync, both API flags and a current enrollment. All flags remain off by default. This code does not set them, enroll or update agents, move connectors, or reload a running plugin.

The daemon publishes local and organization connectors through one combined path. Local server keys stay unchanged. Organization relay IDs and plugin server keys are source-qualified and collision-safe, even when a local connector has the same name or ID. Local setup, sign-in, copy, bundle and export remain local-only. Organization credentials, target URLs and credential revisions never enter plugin or policy files. Only names, IDs, effective policies and tool read/write groups are published.

Before each organization vendor request, including an auth retry and each tool-discovery request, the daemon completes a fresh signed API delivery check. It then synchronously rechecks its current identity, assignment, lease, availability and effective tool policy immediately before sending. This is a control-plane check, not a central tool proxy: tool arguments and results still travel directly between the daemon and the vendor. A policy edit immediately after the API's check can still race a request already being sent; there is no cross-network atomic revocation guarantee.

Discovery uses the same bounded HTTP MCP helper as local connectors. Read/write groups stay in memory, unknown tools count as write, and stale discovery cannot restore removed access. Organization relay POSTs accept the MCP tool protocol and its handshake only, not arbitrary resource or prompt methods that could bypass tool policy. Caller credentials are stripped, vendor credentials are injected only at dispatch, and redirects remain refused.

An upstream 401 or 403 permits one central refresh and one retry, using the revision of the credential actually rejected. Discovery has one OAuth refresh budget for its entire scan, shared across all pages; a relay request has one auth retry. The retry rechecks the policy. An approval is scoped to that exact request and may cover its credentials-only retry, not duplicate batch entries or later calls. Removal or policy changes revoke obsolete approvals. API failures, expired leases, owner/key changes and revocation fail closed and abort active organization streams without disabling local connectors. A vendor refusal becomes 424, never the daemon's own 401; missing assignments and temporary failures keep distinct statuses. The runtime never signs out or rewrites a local connector.

A new relay request recovers a missing or expired memory receipt through one shared fresh signed delivery instead of waiting for the next minute poll. Existing sessions remain invalidated, and stale credentials are never extended. Discovery still has four slots, a 60-second success cache and a 30-second failure cache. Debug logs identify only sanitized `receipt_open`, `tool_discovery`, `discovery_backoff` and `discovery_capacity` stages and statuses, without URLs, headers, tokens or bodies. New or renamed plugin servers still need `/reload-plugins --force` or an agent restart; a stale client cannot use a removed server merely because it still displays it. Per-request checks also consume the existing signed-request nonce budget, so a pilot must measure control-plane load and rate-limit behavior.

Production activation and pilot, automatic plugin reload and key rotation remain separate rollout work. The explicit per-connector migration below can opt in one verified replacement without changing the global live switch. Merging this code does not run that migration, transfer production credentials or change existing connectors.

## Explicit connector migration

The agent's Connectors page has an admin-only **Move to organization** entry. It opens the source preview and durable migration status before any mutation. `GET /api/connectors/migration-preview` requires an organization admin and effective daemon sync (the saved switch or legacy environment opt-in). No new flag is introduced. Do not enable sync just to view a production preview: that same switch starts the memory-sync runtime described above. An older daemon gets an Update notice rather than an unsupported mutation.

`GET /api/connectors/migrations` returns safe operation status. `POST` on the same route requires a local source ID, action, current opaque sync scope and expected migration operation ID, explicitly null before preparation. Request-settlement confirmation also requires the exact outstanding-request receipt. Both routes require an admin bearer for the daemon's current organization, never the agent or monitor token. The scope binds writes to the current daemon/enrollment operation, including changes away and back; the operation ID prevents an old page from changing a later migration of the same source. The page captures its account, organization, agent and daemon origin; switching any of them invalidates the dialog and its outstanding responses. Confirmation dialogs also retain the operation and receipt shown when opened. Closing a dialog cannot undo a request already received. Refresh and explicit Reconcile recover uncertain migration operations; the page never automatically retries a mutation.

The preview reads protected local settings without changing them. It does not verify a server, register an OAuth client, refresh a token, enroll an agent, publish tools, copy credentials, create a connector, change a policy or assignment, or delete anything. Its browser response contains only IDs, names, URL origins, authentication categories, complete valid policies and fixed reason codes. Full URLs, paths, queries, headers, tokens, client credentials and secret-derived fingerprints are excluded. Invalid settings block preparation rather than silently becoming an unauthenticated connector.

The client then reads the current organization's existing connector metadata. A name conflict is not merged or renamed. A shared origin is only a possible duplicate service, not proof of the same endpoint or login; different names or origins can still hide a duplicate. Failed organization reads do not become an empty, conflict-free list. The preview is an advisory snapshot, not a reservation, verification result or authority to change anything. Closing it needs no rollback because it changes no connector state.

### Move all with existing credentials

**Move all to organization** is the normal path on an updated agent. One owner confirmation starts sequential per-connector `move` requests over the existing migration API. Each request automatically freezes the source, prepares or reuses its destination, transfers supported authentication, verifies the destination, and checks fresh encrypted delivery before switching the original alias. The page shows Moved, Retry or a specific blocker. A failure does not prevent the next eligible connector from being attempted. Nothing is merged by name or service, and only the original agent receives the migration assignment. Exact names, group policies and per-tool rules are retained.

The browser receives status, never a credential export. Closing the dialog or changing account, organization, agent or daemon aborts the UI and stops the unstarted remainder of the batch. An accepted request may still finish. Its durable source operation is retained; reopening reads its current progress and Retry continues the same operation. There is no background browser retry loop and already moved connectors are skipped. Older agents expose their existing recovery flow but receive no unsupported Move request. No global fallback, sync setting or production flag changes.

For a Move, the daemon saves **Freezing** before capturing a transferable payload. This durable record stops new local calls and refreshes, including after restart. Existing streams, tool calls and refreshes drain first. A refresh request remains in the protected journal until its final token values have been saved and flushed, not merely until its HTTP body arrived. The final grant-inclusive source stamp is saved with a separate `captured` flag so a pre-capture abort remains resumable even after changing phase. Uncertain vendor writes require inspection. An uncertain local refresh requires explicit recovery that confirms remote abort, discards the old local grant, and requires local sign-in; a durable Recovering phase and receipt make every step resumable.

OAuth handover copies the actual bearer grant from `config.auth`, including dynamically registered client identity, client secret, access/refresh tokens, expiry, issuer, token endpoint, original scope and resource. It does not substitute a manual `config.client`, register a replacement, request consent, or discover new provider bindings during transfer. The existing runtime's client authentication is `none` or `client_secret_post`; other authentication methods, key/device-bound grants, unsafe endpoints and unrecognized grant fields block explicitly. Public HTTPS and guarded DNS/redirect checks apply to the MCP endpoint and OAuth endpoints. Providers can still refuse a valid-looking portable grant because of tenant, client, IP or other policy; Metro does not claim universal portability.

An imported grant keeps its exact effective resource, including an existing resource equal to the confidential transport URL. This value and the full transport path/query stay inside encrypted payloads and sealed storage, never in browser sign-in URLs. That is distinct from a **new interactive sign-in**, which still requires a validated query-free public resource. Future central sign-in discovers public authorization metadata only when requested, checks the original issuer/token endpoint, and retains the original client without automatic registration. A client whose registration cannot use the central callback needs a separately configured sign-in.

The atomic database commit of the imported connector and migration snapshot is the ownership transfer point. From then on central is the sole refresh owner. Before refreshing, central commits an encrypted refresh intent; a second row-locked transaction makes the provider request and saves any rotated grant. A crash, lost provider reply or failed commit leaves a durable uncertain state instead of automatically sending the same refresh token again. This applies to both migration verification and subsequent organization delivery. Expired access with a usable refresh token does not itself require new consent. An ambiguous refresh or invalid grant requires explicit central sign-in.

A prepared destination from the older fresh-sign-in flow can be reused only while it is pristine, unassigned and unchanged, with no tokens and no sign-in started. Otherwise Move reports a conflict without overwriting its credentials or making another destination. Import retries reconcile the same source, operation and destination. After central may own an imported grant, rollback is refused on both servers and hidden in the recovery controls. Recovery finishes forward; there is no reverse handover and no restoration of stale local tokens. A confirmed abort before handover resumes the unchanged local source.

### Legacy preparation and recovery

Prepare first durably records an opaque operation ID and the organization, enrolled agent, signing key, source ID, source name and exact policy in `<agents dir>/connector-migrations.json`. It is a protected 0600 file outside the agent view, bundles and exports; writes flush the file and directory. A separately flushed `connector-migrations.initialized` marker prevents a missing ledger from being mistaken for a never-migrated source. It contains no target URL, credential or private key. A protected source stamp detects settings changes but is not returned to the page. The original local connector remains in `connectors.json`. Its setup, rename, policy, sign-in, delete and replacement/import paths are locked during migration; ordinary local requests and token refresh remain usable until cutover. Copy and bundle output exclude migration-held sources so preparation cannot create another rotating-token owner.

The daemon uses signed `POST /api/agents/connector-migrations` calls. The API consumes durable request nonces and keeps a separate durable source-to-destination operation mapping for retries. Begin reserves a new destination and returns its receiving public key to the daemon. The private receiving key is sealed under the existing API secret key. The daemon encrypts preparation directly for that key, bound to organization, agent, enrollment key, operation, source and destination. No browser, bundle or log carries the payload. The API seals the full URL and static credential in the new destination and keeps it unassigned. Name conflicts never merge into an existing shared connector.

Header/API-key and unauthenticated connectors use their existing local configuration. OAuth sends only the fresh-sign-in intent and an explicitly saved manual client, never the local access token, refresh token or dynamically registered client. The operator signs in centrally through the existing organization OAuth flow, then reconciles readiness. A manually registered provider must allow `https://api.metro.box/api/connectors/callback`, or use a separately registered client. An expired OAuth handoff needs a new sign-in against the same prepared destination, not a second migration. Even fresh sign-in can invalidate an older grant at some providers; retaining old tokens is not an OAuth rollback guarantee.

All representable read, write, `ask` and per-tool overrides are preserved. An empty assignment policy is neutral, so it cannot silently tighten a named exception. Organization management exposes the full policy and refuses replacing a custom policy with its simple read-only toggle. Unsupported tool names, invalid settings, private or non-HTTPS destinations, and a non-OAuth connector retaining an unused manual OAuth client block preparation explicitly. All three authentication methods accept arbitrary public HTTPS transport paths, percent-encoded segments and queries through the same endpoint validator. The exact saved transport stays sealed and is used for MCP verification and delivery, never as an implicit browser-visible OAuth audience. User information, fragments, trailing-dot hosts, invalid URL encoding, private/special addresses and redirects remain refused; DNS answers are still checked at dispatch. This does not add stdio, legacy SSE or new authentication protocols. Resolve the stated setup limitation or keep that source local; do not remove restrictions to make it pass. Prepared destinations cannot be edited, deleted or assigned through ordinary management before cutover, except for their required fresh sign-in and verification.

### Public OAuth resource and confidential transport

OAuth preparation selects a distinct, query-free public resource identifier. Automatic discovery requests only the endpoint origin’s unauthenticated protected-resource metadata, without its saved path or query. A published resource must identify that origin and cover the transport on a path-segment boundary. Authorization-server issuer metadata must agree with the selected issuer. Invalid, confidential, mismatched, redirected, oversized or unavailable metadata fails closed; only a genuine 404 is treated as absent.

For providers with path-scoped metadata or no published resource, the admin independently enters **Public OAuth resource** before Prepare. It is explicitly browser-visible, never prefilled from the saved endpoint, and must contain no credentials or query. This allows a confidential query-bearing transport to use its documented public audience without replacing the transport with its origin. If automatic preparation reports a missing resource, roll that preparation back before preparing again with the public value. The optional value travels in the sealed payload and is bound into the retained source stamp; changing it requires a new preparation. Older daemons do not receive the new field.

The prepared public audience, transport, client and authorization-server configuration are immutable under the destination stamp. OAuth uses the public audience for authorization, code exchange and refresh; MCP verification still uses the original sealed transport. A fresh grant also retains its audience with the sealed tokens. Grant refresh does not change the preparation stamp. Older grants without a validated public audience require fresh sign-in rather than falling back to the private transport or silently omitting the resource parameter. Clearing a grant keeps the prepared transport, public audience and client configuration.

Sign-in handoffs bind the initiating admin, organization, connector, generation, client, authorization server, transport and audience. Changing that configuration invalidates an old completion before token exchange and again before saving. Browser callback errors and provider failures use fixed messages, not raw provider descriptions or endpoint values. Organization verification displays the public hostname rather than echoing a provider-supplied server title. No credential is returned in management responses or migration preview.

### Verify and switch one connector

In the legacy recovery flow, Cutover is a separate explicit operator action. Move performs this step automatically under the initial confirmation, with the source already frozen. Cutover rechecks the source stamp and destination readiness, then durably fences the source before any organization assignment is created. It waits for existing local relay streams, discovery, OAuth and refresh work to finish. A pending operation reports that wait and can be reconciled; it does not replay a tool call or claim that aborting a request reverses a vendor write.

The API checks current enrollment, source mapping, destination settings, verification and policy under its transaction before creating the exact agent assignment with migration provenance. An already completed request reconciles that assignment instead of making another. Afterward the daemon must accept a fresh authenticated, decrypted delivery containing that ready destination and the expected policy. Only then does it save Active and route the original local relay ID and plugin server key through the organization runtime. It does not publish a second organization server for the same destination on that agent.

This per-connector action needs effective sync and approved API delivery, but does not set `METRO_CONNECTORS_LIVE_ENABLED` or enable unrelated organization tools. Unmigrated sources keep their normal path. Sync Off, failed delivery, expired leases, owner/enrollment changes, removed assignments and policy changes still fail closed. They never resurrect the retired local credential path. The normal fresh policy check and central refresh rules apply to the alias.

### Reconcile and roll back

The protected phases are Freezing, Preparing, Prepared, Cutover pending, Active, Rollback pending, Recovering local sign-in and Rolled back. A lost reply or restart between the database and filesystem steps retains its operation and source fence. Reconcile resumes that same operation. A corrupt or missing initialized protected record fails closed rather than being treated as no migration. A migration from a different enrollment stays blocked until its original enrollment is restored; changing organizations or keys is not permission to take over its destination.

Potentially side-effecting vendor requests have a separate protected per-source journal containing only random request IDs. Preparation captures requests already running locally; later dispatches are flushed before sending. Completed requests clear their entry. An interrupted response or daemon restart leaves an uncertain outcome, not proof that the vendor canceled the operation. New dispatch, cutover and rollback stay fenced. Read-only discovery and MCP session maintenance retain drain leases without becoming uncertain business writes merely because metadata was absent or a cleanup body was discarded.

After checking the vendor, an admin can explicitly **Confirm requests settled** with the typed confirmation. It names both the displayed migration generation and the exact outstanding-request receipt, refuses while current operations are still running, and only clears that fence. It does not retry a vendor tool, undo an effect or continue migration automatically; use a separate Reconcile afterward. This is not an exactly-once guarantee. Vendor background jobs and requests already abandoned before migration tracking began cannot be proven complete by Metro. Inspect those at the vendor before production cutover or rollback.

For connectors without an imported grant, rollback first durably disables the migrated alias and waits for its already-running requests. Imported OAuth grants cannot use this rollback path after ownership transfer. The API removes only the unchanged assignment created by that migration. Ordinary assignment edits, including delete-and-recreate, invalidate that ownership proof; rollback then blocks rather than deleting independently managed access. Other agents' assignments are untouched. The destination is retained even if unshared, never deleted as cleanup.

Only after remote rollback is confirmed does the daemon restore the retained local path. OAuth restoration clears the old local grant and requires fresh local sign-in; none/header configuration remains unchanged. Independently changed source settings are not overwritten. A failed network request leaves Rollback pending and the source stopped until reconciliation succeeds. After Rolled back, a new explicit Prepare uses a new operation generation and destination; delayed requests from the old operation cannot affect it. Keep an operator-controlled encrypted backup before production work, never plaintext credentials in chat, logs or a development checkout.

## Approved pilot checklist

Preparation and a merged PR do not authorize these production steps. The operator must approve the agent and test connector, package update, enrollment, each activation switch and any later credential migration separately.

1. Review and merge the preparation PR only after its tests and security review pass. Publish the matching daemon as a **beta** using the existing publish workflow.
