# HTTP surface of api.metro.box, gateway.metro.box and mcp.metro.box

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code. The daemon's own route table stays in `CLAUDE.md`.

The owner is always the signing organization. The breakdown is the 8 connectors with the most calls (ties by key), then one `{key: '~other', name: 'Other'}` row for the rest, in buckets too. |
| `PUT /api/connectors/<id>/agents/<agent>/events` | bearer, admin | Connector events for one agent (`docs/CONNECTOR-EVENTS.md`): `{events?: [<event name>], senders?: [<sender id or @domain or *>]}`, at least one of the two. `events` is what this agent receives from the connector (default none, 50 names at most; a name newly turned on must be one the connector's server offers, turning one off is always allowed), `senders` the people who can write (normalized like a channel allowlist, `@metro-labs/http/sender-list`, default `["*"]`). 404 when the agent does not have the connector, 409 when the agent has no server (it has no session to receive in). It answers the connector as `GET /api/connectors` does, where each connector now carries `events` (`[{name, title, description, sender}]`: the event types its server offers by webhook, read with its tool list) and each assigned agent `events`, `senders` and `subscriptions` (`[{event, status, error?}]`, status `pending`, `active`, `signed_out` or `error`, kept by mcp.metro.box). `GET /api/connectors/activity` rows carry `kind` (`call` or `event`); an event row's `tool` is the event name and its `outcome` one of `delivered`, `dropped_sender`, `dropped_unverified`, `dropped_paused`, `dropped_unassigned`, `expired`, `skipped`. The stats count calls only. |
| `/api/admin/*` | bearer, operator email | Users, status, organizations, agents. `/api/admin/servers/<id>/deletion` is the same deletion as above for a box of any organization: the view adds `owner` and `organizationName`. |

**How the api signs in to AWS** (`aws/access.ts`, `launch-config.ts`, docs/ISSUING-SERVERS.md): `METRO_AWS_ROLE_ARN` is Metro's own role `metro-api`, taken with the Fly machine's OIDC token (`aws/fly-oidc.ts`, `AssumeRoleWithWebIdentity`), no long-lived key. While `METRO_AWS_ACCESS_KEY_ID` and `METRO_AWS_SECRET_ACCESS_KEY` are set they still sign Metro's own account, so unsetting them is the switch. A row with `agents.aws_connection` is reached through that connection's `metro-access` role (`AssumeRole` with the organization's external id, from `metro-api` only, never from the key). Every credential is `AwsCredentials`: static keys or a provider; role keys are kept per role and external id until 5 minutes before they expire, one mint at a time. Each call site picks the account with `access.reach(config, row.account)`; never pass Metro's own credentials for a connected row.

**The api never answers 502 or 504; an AWS refusal is a 503 (`AWS_REFUSED` in `aws/ec2.ts`).** Cloudflare in front of api.metro.box replaces an origin 502 or 504 with its own `error code: 502` body and drops the CORS headers, so the browser saw only a failed fetch and the page said "Failed to reach Metro." instead of AWS's reason (the Storage section, 2026-10-03). It passes 500, 503 and 4xx through.

## gateway.metro.box (`apps/gateway`, `docs/GATEWAY-SERVER.md`; live since 2026-10-25, no box uses it yet)

The model router as a service: `packages/inference` run for every organization, which records usage and never content. Boxes still route themselves until phase 3 of the plan.

| Route | Auth | Note |
| --- | --- | --- |
| `GET /health` | none | `{status, version, uptime}`. |
| `POST /v1/messages`, `/v1/messages/count_tokens`, `GET /v1/models` | a box's MCP token, or an access key with the `gateway` scope, in `x-api-key` or `Authorization: Bearer` | Anthropic Messages. The caller's credential headers are dropped before anything goes upstream (`dropCredentials`). |

- **Callers** (`callers.ts`, the shared `@metro-labs/connectors/db/bearers` lookup mcp.metro.box uses): a box's token keeps the box's rules (the requested model, the hint headers' lanes); an access key must name `metro` (main order, main effort) or `metro-workers` (workers order, workers effort), anything else is a 400 naming them (`named` in `packages/inference/src/named.ts`), and `GET /v1/models` lists those two. An access key may use every account of the order, subscriptions included (owner's decision, 2026-10-26).
- **Setup** (`setups.ts`): `agentModelSetup` + `agentModelsOf` (stale Codex tokens refreshed, secrets opened) + `deliveredOf`/`setupOf`, cached 10 s per agent; a Codex 401 refreshes through `refreshModelConnection` at the revision used.
- **Usage rows** (`app.ts`, `recorder.ts`): the router's `onCall` hook gives one call per attempt (`packages/inference/src/attempts.ts`: an `AsyncLocalStorage` context per attempt, `UsageScanner` counts into it, `noteFailure` marks a mid-stream error, a `writeHead` wrapper keeps the status, a 429 handed to a backup included); each becomes a `model_calls` row (`kind` `external` for a key), batched every 2 s or 100 rows, never awaited, a missing table logged once. A `/v1/messages` that found no model is one `no_route` row. Counting tokens is not recorded.
- **Cost** (`prices.ts`, `cost_micros`): OpenRouter's own `cost`; Routeway's list prices (`routewayModels`, now in `@metro-labs/connectors/model-lists`, read hourly; every input token at the prompt price); Anthropic API keys from `CLAUDE_PRICES` (per million: input, output, cache read; 5-minute writes 1.25x input, 1-hour 2x; Haiku 5.5 five times above 100,000 prompt tokens; prices from the claude-api skill, cached 2026-10-06; `test/prices.test.ts` fails when a model the Gateway page offers has no price). A Claude subscription, Codex and Bedrock (priced by AWS) have no cost.
- **Usage windows** (`windows.ts`): every 10 s each machine saves a connection's windows when they changed (stamped with the time of the reading, not of the save), then loads the windows of the organizations it served and adopts those newer than its own (`noteUsage`), so a model above 95% of a window is held on both machines. A 429's cooldown stays per machine. The page reads them with `GET /api/models/windows` (members: `{windows: [{connection, label, used, resetAt, detail, at}]}`): `useModelQuery` merges them into the box's `usage` per connection (`withGatewayWindows` in the client's `api/gateway-usage.ts`; a window of the same name from the gateway wins, the box keeps its others and its tally), so the Gateway page, Home and Settings show the gateway's windows. An agent without a server shows its Gateway usage (`GatewayUsage`) above the calls on its Activity tab.
- **Never content**: `quietProviderText()` at start keeps provider error text out of every log line (`providerText` in `packages/inference/src/failures.ts`; the box still logs it); `test/e2e.test.ts` sends a marker in the prompt, the answer and an error and checks no row and no log line holds it.
- Fly app `metro-gateway`, `iad`, two machines of 2 GB (512 MB ran out on 2026-10-27 at 20:13 UTC: both machines were killed twice within two minutes and Fly stopped them, so every agent's model requests failed for about three hours; a request body, up to 64 MB, is held as bytes, text, the parsed object and one or two re-encoded copies while the router reshapes it, and every agent's requests now land here), concurrency by requests (200 soft, 500 hard), port 8440, `apps/gateway/fly.toml` and `Dockerfile`; `.github/workflows/gateway.yml` deploys it on merges that touch it or its packages, with `FLY_GATEWAY_API_TOKEN` (a deploy token for `metro-gateway` only; the repository's `FLY_API_TOKEN` cannot deploy it).

## mcp.metro.box (`apps/mcp`)

The one MCP endpoint every agent uses for its organization connectors (`docs/MCP-SERVER.md`): two tools, `tool_search` (Claude Code's `ToolSearch` design over every assigned connector's tools) and `tool_call` (1 to 10 calls in parallel, run from here through the safe egress, so connector credentials never reach a box). A tool is `<connector key>.<tool>`; the key is the slug of the connector's name, with `-2`, `-3` in connector id order when two assigned connectors share one. The policy is the organization and agent layers (the stricter wins, a per-tool rule beats its group, the group comes from the vendor's `readOnlyHint`, an unknown tool is write), read from Postgres on every call. Block hides a tool from `tool_search` and refuses it; Ask records an `mcp_approvals` row and answers `needs_approval` with its id, the daemon relays it to the owner and posts the answer back, and the agent repeats the same call with `approval: "<id>"`, which works once, for exactly that tool and those arguments (SHA-256 of their canonical JSON), within 10 minutes of the answer. **The row records who made the call** (2026-10-23, `0020`): `origin` `box` for a box's MCP token, `key` with the access key's id in `token`; each caller has its own pending row for the same call (the pending index takes `coalesce(token, '')`, so a box's own request and an old row without origin share a slot), and `POST /v1/approvals` sends `origin` and, for a key, its `keyLabel` (`agentTokenLabels`), never the key or its id. Redeeming is not bound to the caller. Rows from before `0020` have no origin; the store's fallback for a database without those columns went on 2026-10-26. Unanswered requests expire after 24 hours. **Answered rows are kept 7 days**: each machine deletes `mcp_approvals` rows in state `allow`, `deny`, `used` or `expired` whose last change (`answered_at`, else `requested_at`) is more than 7 days old, at start and every hour (`startApprovalPruning` in `prune.ts`, `pruneApprovals` in `approvals.ts`; an unref'd timer, never fatal, one info line with the count). A pending row is never pruned: it expires after 24 hours as before (when its agent next asks or polls), and goes 7 days after that. Two machines pruning at once is fine, since it is one plain `DELETE … WHERE`. `tool_search` ends with a `Call these with tool_call: {...}` line naming the first result, and also answers `structuredContent` `{connectors: [{key, name}], tools: [{name, title, connector, description, inputSchema}], note}` (**the structured copy must hold everything the text does**: Claude Code shows the model only `structuredContent` when a result has one and drops the text, so before 2026-11-06 an agent saw no schema and would not call a write tool; `note` is the text's last line, the call hint or the no-match sentence; every usable connector with its metro.box name; a tool's `title` is the vendor's, else `annotations.title`, else its id in words, `toolTitleOf`), and text names a connector `key (Name)` unless the name is only the key in other letters (`connectorLabel`), and a miss names the connectors and suggests a broader query or `select:`; an unknown tool or connector in `tool_call` answers `not_found` with up to 3 closest names (bigram similarity, `closestNames`) and "Run tool_search first"; a malformed `calls` answers with the expected shape. The two tool definitions and descriptions live in `@metro-labs/http/mcp-server-tools`, shared with the daemon's fallback. **Tool lists are answered from a cache, never by waiting on a vendor that has a list** (2026-10-29, after a dashboard waited 52 to 75 s and one unreachable vendor, Slash, held every `tool_search`; Claude Code's ToolSearch also searches only what it already holds): `ToolLists` (`tool-lists.ts`) keeps each connector's redacted list in memory (the 500 most recently read connectors) and in Postgres (`connector_tools`, so both machines and a restart share it); a list younger than 5 minutes (`TOOL_LIST_TTL_MS`) is used as it is, an older one is answered at once and read again in the background (one flight per connector, which first adopts a fresher row the other machine wrote), and a connector never listed waits 8 s at most (`FIRST_LIST_WAIT_MS`) and then reads `listing` while the read goes on (30 s at most in all). A failed read is kept with its message and not tried again for a minute (`FAILURE_PAUSE_MS`); an older list stays in use meanwhile. `tool_call` checks a tool against the held list and reads it again (8 s at most) when the tool is missing from an old one, and always before a call whose rule depends on the tool's kind (read or write), so an old list never decides a policy. A failure that only concerns the calling agent (`not_found`: unassigned meanwhile) is kept as `unavailable`, since every agent of that connector reads it. `tool_search`'s `structuredContent.connectors` carries each connector it consulted with `status` (`ok`, `listing`, `signin`, `unavailable`) and `error`. **A third tool, `list_connectors`, is served only by mcp.metro.box** (`list.ts`, never in `mcpServerTools`, so a box's daemon, which picks `tool_search` and `tool_call` by name, never shows it to its session; everything stays MCP, no HTTP route, Less 2026-10-29): it answers from the cache without waiting on any vendor (a never-read connector reads `listing` and its read starts), light by default: `structuredContent.connectors: [{key, name, status, error?, listedAt?, toolCount, icons}]`, where `icons` is MCP's Icon shape with a URL, never the image: **first the icons the connector's own server declares** in its initialize answer (`serverInfo.icons`, MCP 2025-11-25; read by `listRemoteServer` with the tool list and kept with it: https only, no user information, no data URI, 4 at most, `mimeType` an image type, `sizes` like `64x64` or `any`, `theme` light or dark; `publicIcons` in `@metro-labs/connectors/catalogue` drops one holding any 8+ character credential form of the connector: a query value, a path segment, the header value or a token, never the connector's own address, since a server at the root of its host (`https://mcp.epost.piston.box/`) serves its icon under that address (SharePoint and ePost lost theirs until 2026-10-29); Less, 2026-10-29: "the icon MCP server declare itself with fallback to google favicon system"), **else** the brand logo metro.box serves, `https://metro.box/brands/<slug>.svg` from `brandIcons` in `@metro-labs/core/brands`, with `theme` light and dark when there are two; else Google's 64 px `t1.gstatic.com/faviconV2` icon of the connector's domain (`checkedFaviconUrl`), but only when Google answers 200 for it, checked once a day per domain by `Favicons` (`@metro-labs/connectors/favicons`, which api.metro.box's `/api/icons` shares) (3 s at most, a failed check retried after 5 minutes, 1,000 domains held), since its 404 still carries a generic globe that browsers draw; no icon is `icons: []`, so a client draws a letter. Asked by the piston.box dashboard, 2026-10-29: three connectors on piston.box all showed the globe. The brand map and `faviconUrl` moved from the client to core for this). `{connector: <key>}` answers that connector only with its `tools`, and `{tools: true}` every connector's: `{name, title, description, readOnly, destructive?: true, ask?: true}`, blocked tools left out, never a schema (that is `tool_search`'s). The text content is one short line per connector (and per tool when asked), never the JSON again. A missing `connector_tools` table (mcp.metro.box deployed before the api migrated) is logged once and the lists stay in memory. One log line per call (agent, connector, tool, outcome, ms), never arguments or results. **Every `tool_call` call is also one `mcp_calls` row** (`call-log.ts`, `recordCall` in `@metro-labs/connectors/db/mcp-calls`; Less, 2026-10-22, for the page's Live activity): owner, agent id, the agent's name and the connector's name and key at that moment, connector id (null for a connector the agent does not have), tool, outcome (`ok`, `vendor_error`, `blocked`, `needs_approval`, `denied`, `not_found`, `signin`, `unavailable`, `invalid`), ms and `at` (when it ended); **never the arguments, the result or an approval preview**. A `tool_call` of several calls writes one row per call as each ends. The insert runs after the call has its answer and is never awaited (`.catch()` that logs), so a failed write never fails or slows a call; a missing table (mcp.metro.box deployed before api.metro.box's release command ran `0018`) is logged once, and the next write that works logs `mcp: recording calls again`. **Rows are kept for good** (Less, 2026-10-22: no expiry, no cap): nothing prunes them, and an agent or connector deleted or moved keeps its rows and the names they were written with (no foreign key). Measured on PGlite: about 33 MB per 100,000 calls (16 MB of rows, 17 MB for the primary key and `(owner, at desc, id desc)`).

**Connector events** (`docs/CONNECTOR-EVENTS.md`, 2026-11-10): for every assignment that wants an event (`connector_agents.events`, agents with a server only), mcp.metro.box keeps one `connector_subscriptions` row and the matching `events/subscribe` on the connector's server (`subscriptions.ts`, every 20 s on both machines, each row claimed with a conditional update, no global lease): a `whsec_` secret of its own sealed under `metro-webhook-secret/v1`, the callback `https://mcp.metro.box/v1/events/<row id>`, a refresh at half the granted time that always passes the stored cursor, a new secret after a new sign-in, a wait on `signed_out`, an unsubscribe when no longer wanted. The webhook (`webhook.ts`) verifies, applies who can write (`events.ts`: the sender at the descriptor's JSON Pointer, the list of `connector_agents.senders`, `verified` false dropped unless the list is `*`, no declared sender only with `*`), and keeps the event sealed in `connector_events` (domain `metro-connector-event/v1`) until the box takes it through `/v1/inbox`, 7 days at most (`startEventPruning`, hourly). Each received event is one `mcp_calls` row of `kind = 'event'`, never its data, sender or cursor. Metro knows no event type by name.

Agent routes check signatures with `AgentAuth` and keep their nonces in Postgres (`agent_nonces`), since they change state and run on two machines. Env: `DATABASE_URL` and `METRO_CONNECTORS_KEY` (Fly secrets on `metro-mcp`, the same values as api.metro.box; without either it refuses to start), `METRO_HTTP_HOST`, `METRO_HTTP_PORT` (default 8430), `METRO_MCP_HOST` (the host agent signatures name and the OAuth issuer, default `mcp.metro.box`), `METRO_APP_URL` (where the consent page lives, default `https://metro.box`). Fly app `metro-mcp`, `iad`, two always-on machines, `apps/mcp/fly.toml` and `apps/mcp/Dockerfile` (built from the repository root).
