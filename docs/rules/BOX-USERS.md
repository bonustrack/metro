# Three users on every box: root, metro, agent (`metro-user/`, `agent-user/`)

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code.

- **Why:** on 2026-09-25 an agent sent mail with the Outlook refresh token it found in `~/.metro`, because the daemon and Claude Code both ran as root. The same day every box moved to three users (Less's call), and on 2026-09-26 the move code, the root paths and the root-job switch went: **a Linux daemon runs only as the system user `metro`, Claude Code only as `agent`, and root is reached only through one checked helper.** A root daemon on Linux is refused: `startClaude` skips all Claude work and `sessionBlocked` says "Metro runs as root; reinstall it as the metro user", so Claude never runs as root. macOS dev (no agent user) keeps plain paths.
- **Layout:** `/var/lib/metro` (metro's home, **711** so the agent can run the CLI in `.npm-global`) holds `.metro` (**700**: `agents/`, keys, credentials, runtime) and `.npm-global` (the CLI, so `metro update` runs without root through `NPM_CONFIG_PREFIX`). `/home/agent` is **711** (the agent sets it after `ensure-agent`), Claude's own files keep their modes. `openMetroHome` in `provision.ts` repairs both modes at every start: with a 700 metro home Claude Code exited at once on every box (2026-09-25). **Every other entry of the metro home is closed** (`closeMetroHome` in `agent-user/metro-home.ts`, at start and on the view sync's 5 s tick: group and other bits off, symlinks left alone), so only `.npm-global` and the folder holding `METRO_CLI_BIN` stay open to the agent; a folder an SDK makes later (`.cache`, `.local`, …) is closed within 5 s. Why: on 2026-10-01 the agent could read the Telegram session under `.cache/metro/serve` (0755 folder, 0644 files). `bun run secret-modes` (`scripts/secret-modes.sh`, on a box as any user, `stat` only, never reads a file) checks these modes, the agent's view files (0600) and, run as the agent, that it cannot list or read Metro's folders.
- **Install (new boxes, `apps/api/src/aws/user-data.ts`):** steps `packages` (with sudo, iptables), `node`, `bun` (`BUN_INSTALL=/usr/local`, nothing under `/root`), `user` (`useradd --system … metro`, in `systemd-journal`), `tailscale` (`--operator=metro`, with a single-use, one-hour, `tag:metro-box` key the api mints per launch from its Tailscale OAuth client, `aws/tailscale-key.ts`; never a shared key), `metro` (the CLI installed as metro into `/var/lib/metro/.npm-global`, `.metro/agents/.node` written 600), `service` (`metro service install --owner <org> --user metro` as root). `STEP_LABELS` in `boot-log.ts` follows the steps. `service install --user metro` (root, Linux, only that user) writes the unit (`User=metro`, `Group=metro`, `WorkingDirectory=/`, `HOME`, `PATH=<prefix>/bin:/usr/local/bin:/usr/bin:/bin`, `NPM_CONFIG_PREFIX`, `OOMPolicy=continue`, the other `METRO_*`), and first installs the root side: a checked copy of its own version in `/usr/local/lib/metro/release` (see The root side follows updates), whose `metro-user/install.ts` writes the helper and the sudo rules from the one source `helper-script.ts` (checked with `visudo -cf`, 0440), enables `metro-imds.service` (see the helper's `imds-block`) and writes `metro-root-upgrade@.service`. **On a box that already has the unit, `service install --user metro` only does that root side** and leaves the service running. **The first launch with this install has not been run end to end yet** (checks to watch: the checked download and Bun running the root copy's `install.ts` in cloud-init, `sudo -u metro -H npm install`, the Bun installer into `/usr/local`, the `metro` group).
- **Sudo rules:** `metro ALL=(agent) NOPASSWD: ALL` and `metro ALL=(root) NOPASSWD: /usr/local/lib/metro/root-helper *`, nothing else. No `Defaults` line (2026-10-26): `Defaults:metro !requiretty` did nothing on Ubuntu's sudo, where `requiretty` is off, and sudo-rs (Ubuntu 26.04) refuses it, so `visudo` failed; a box's root side rewrites the file at its next upgrade. CI's `sudo-rules` job runs `test/metro-user.test.ts` (`visudo -cf` on the real file) on Ubuntu 24.04 and 26.04, while the main gate stays on 24.04, the boxes' Ubuntu (`ubuntu-noble-24.04` in `aws/ec2.ts`). Sudo logs every call; turning that off was refused as audit tampering, keep it.
- **The helper** (`/usr/local/lib/metro/root-helper`, root 0755, `HELPER_VERSION` 3) knows only: `ensure-agent`, `as-agent-scope <max> <high> <cmd…>` (the Claude session's memory scope), `dropin-write`/`dropin-remove` (only `11-metro-vault.conf`, only on a service under `/etc/systemd/system` that a timer starts, whose name starts with a letter or digit and not with `metro`; the content must be exactly `[Service]` and `EnvironmentFile=-<agent home>/.metro/vault.env`, and the job must run as the agent with no command run with root rights: `+`, `!`, `!!` in systemd's `Exec*Ex` flags, or `PermissionsStartOnly`; version 2 let metro add `ExecStart=` or `Environment=` to a root timer job, which was a way to root), `upgrade <version>` (version 3: only a plain version, starts `metro-root-upgrade@<version>.service`), `daemon-reload`, `start-job` (only a service that runs as the agent), `root-crontab`, `root-crontab-drop` (unused by the daemon now, kept so the helper text does not change), `firewall-on`/`firewall-off` (the agent uid only), `trust-ca` (the vault certificate from its fixed path, refused if it holds a key), `untrust-ca`, `install-nss-tools` (these five and the drop-in pair served the secrets vault and are unused since it went, 2026-10-23; like `root-crontab-drop` they stay so the helper text does not change: root installs it and `HELPER_VERSION` versions it), `imds-block` (version 2: chain `METRO_IMDS` in iptables and ip6tables rejects traffic to `169.254.169.254` and `fd00:ec2::254` from every uid but root and `metro`, so the agent reads neither the user data nor the instance role; run at every boot by `metro-imds.service`, before the network, and by the daemon at every start, `metro-user/imds.ts`, which only logs on an older helper).
- **The root side follows updates** (version 3, Less 2026-10-01, design in `docs/ISSUING-SERVERS.md`): at every start the daemon runs the helper's `upgrade <its version>` (`metro-user/root-follow.ts`); root's oneshot unit runs `service root-upgrade <version>` (`packages/cli/src/root-release.ts`, `root-release-io.ts`) from root's own copy `/usr/local/lib/metro/release` with root's node, under `flock`. It installs a version only when it is newer than root's copy, is what the `beta` or `latest` tag points to, matches npm's sha512, and has a Sigstore-signed SLSA provenance from `bonustrack/metro`'s `publish-cli.yml` on `refs/heads/main` naming that tarball (checked with the `sigstore` inside npm next to root's node); then that copy's `install.ts` runs with root's Bun (`--no-install`) and the copy replaces the old one. **Root never runs code from a path metro can write**, and a version string is all metro passes. **Moving the publish workflow, its branch or the repo stops every box's root side from following** until a root run of the new version. **The same root step hardens Tailscale** (`hardenTailscale` in `metro-user/tailscale-guard.ts`, 2026-10-28, after the unpatched "Tailworm" Tailscale SSH report of 2026-10-25): it adds `TS_SSH_DISABLE_FORWARDING=1` to `/etc/default/tailscaled` and restarts `tailscaled` only when the line was missing (once per box; Tailscale SSH stays on, since a launched box has no other way in), and runs `tailscale set --auto-update`. It never fails the step: a box without Tailscale or a failing command only writes a `metro:` note, because a failed root step stops the root side following updates. New boxes get it from `service install --user metro` at the end of cloud-init. The tailnet side is the admin console's: tag the boxes `tag:metro-box`, let only admins SSH to them, with `check`, and never `tag:metro-box` to `tag:metro-box`. A box with an older helper needs one root run, then never again: `npx -y @stage-labs/metro@<version> service install --user metro` (the daemon logs it with its version, `rootStepHint`). `bun run metro-user-check` seeds the root copy from the local tarball, since an unpublished build has no provenance.
- **Everything runs as the agent through `asUser`**: `sudo -n -u agent -- env -i HOME=… PATH=<home>/.local/bin:… <cmd>` (a terminal resize still reaches the program through sudo's pty; **never `runuser`**, which does not pass SIGWINCH on). That covers the session watcher, the runner store's preparation, the login pty, `auth status`, the Terminal tab (the agent's tmux, never a root shell), Files, and every write into the agent's home (`home-fs.ts`, small `sh` scripts with the content on stdin: writing as the agent means a symlink the agent planted, `skills/evil -> /etc`, cannot redirect it). The session command is `env METRO_AGENTS_DIR=<home>/.metro/agents METRO_WEBHOOK_PORT=<port> node <cli> agent`. **Nothing is spawned with the agent's home as cwd** (`EACCES posix_spawn 'sudo'`, 2026-09-25): the session passes `-c` to tmux, Run now does `cd "$HOME"` inside.
- **Reads of the agent's home go through `agent-user/agent-fs.ts`** (`existsSync`, `statSync`, `realpathSync`, `readFileSync`, `readRange`, `readdirNames`, `readdirEntries`, `createReadStream`): the plain read first, and only when it is refused (EACCES/EPERM) the same read as the agent (`cat`, `stat`, `find`, `tail|head`). **A plain read of a path inside the agent's home is used only when the file really lives there** (`escapesHome`: the opened file's `/proc/self/fd` target for content, the real path for metadata); a link out of the home is read as the agent, so metro never reads its own files for the agent and writes them back into the agent's home. Paths the agent chooses outside its home (a scheduled job's script and log file, `schedule-detail.ts`) are read only as the agent (`readAsAgent`). Every read of Claude's files (`claude/*`, `schedule-detail`, `provision`) goes through it: Claude Code writes transcripts 0600 and some session folders 0700, which broke Sessions, the install check and the session start on the first moves.
- **Boot** (`provision.ts`, before the setup and the session watcher): `ensure-agent` through the helper, the home modes, the view sync, then `metro agent --prepare` as the agent (`prepareRunnerStore`, 16 minutes at most), which installs the runner store and the Claude Code it bundles. **A failed prepare blocks nothing**: it is logged, the watcher (and Start) still run `metro agent`, which prepares the store itself, and a session that keeps exiting is paused by the watcher's strikes. A missing Claude Code is not read as a missing login either (`loginNotRuledOut` in `session.ts`). The 30 s cache of the install and login checks (`claudeInstalled`, `claudeAccount`) is forgotten when a prepare ends.
- **The agent reads a key-free copy of the Metro files** (`view.ts`, `<home>/.metro/agents`, 0600, owned by the agent, refreshed every 5 s, rewritten only on change): `agent.json` as `{version, id, key}`, `model.json` as `{route, connections: [{id, provider, model}]}` (from the effective organization route), and `policy.json`, `claude-setup.json`, `system-prompt.md` as they are; an `mcp-token` there (from before 2026-10-14) is removed. Nothing trusts the agent's copies. `connectors.json`, `voice.json`, `agent-key.json` and the legacy `box-key.json` are never copied: the voice provider key and the enrollment private keys stay in Metro's folder, and connector credentials never reach the box.
- **An inbound file reaches the agent as its url only** (the cache is Metro's; `buildMediaNote(…, showPath)`, `surfaceMedia`, `withUrls` in `read-tool.ts`). **A `send` attachment by `path` is read as the agent** (`fromPathAs` in `stations/attach-resolve.ts`), so the daemon never sends a file the agent could not read. **One by `url` is fetched as the agent too** (`fromUrlAs`: `curl` through `sudo -u agent`, http and https only, 5 redirects, the attachment size cap), so the agent cannot use metro's network position (instance metadata) through a send.
- **The Claude session's memory** (`claude/memory.ts`): Tony (8 GB) ran out of memory twice on 2026-09-25 under ~16 Node builds and 30 to 48 headless Chromes, and systemd's default `OOMPolicy=stop` took the daemon and every train down each time. The unit has `OOMPolicy=continue`, and the session's tmux starts in its own scope through the helper (`as-agent-scope`: `MemoryMax` 80% of the box, always leaving 1.5 GiB, never under 1 GiB; `sessionMemoryLimit`; **`MemoryHigh` is the same value, never lower**: until 2026-10-31 it was 90% of the max, and on Lisa a 1.6 GB export held the scope between the two for over two hours, so the kernel's throttle stalled every process in it about 87% of the time, nothing was killed and no message was answered; a scope made before that keeps its old soft limit until its tmux server starts again (the update's session restart reuses a tmux server that is still up, for example while the Terminal tab is open), so from beta.329 the root step of every update lifts it with `systemctl set-property --runtime metro-claude-<n>.scope MemoryHigh=infinity` (`liftSessionSoftLimits` in `metro-user/session-scopes.ts`, after `daemon-reload`, which can put back a value written straight into the cgroup; only a note when it fails)) whenever the tmux server is not already up, so a memory kill takes the heaviest process only and a daemon restart no longer kills the session.
- **Scheduled jobs** (`schedules.ts`, `schedule-detail.ts`, `schedules-api.ts`, the Scheduled tab, `tools/ScheduledPage.tsx`, `tools/Routines.tsx` and `tools/RoutinePage.tsx`, `#/<agent>/scheduled[/<id>]`): the page lists the agent's jobs only (systemd timers under `/etc/systemd/system` running as the agent, and the agent's crontab); root's jobs never show and there is no way back to root. `GET /api/schedules[?id=]` answers the job plus `definition` (`systemctl cat`, or the cron line), `script` (`scriptOf`: among the command's first three absolute paths, the first Markdown file, else the first text file, under 64 KiB, where a job's `claude -p` prompt lives) and `logs` (the last 80 journal lines, or of the file the cron line redirects to, `logFileOf`); `POST {id, action: 'run'}` is Run now (`start-job` through the helper for a timer, the command detached as the agent for a cron line). `agent-user/unit-files.ts` sends the agent's `crontab` through `sudo -u agent` and `daemon-reload`/`start` through the helper. The switch of root jobs to the agent ran on every box on 2026-09-25 and is gone.
- **The daily memory routine is a cron line the daemon owns** (`claude/memory-routine.ts`, `ensureMemoryJob` at boot after the setup and on the Routines switch, `memoryRoutine` in `claude-setup.json`, default on). It sits in a `# metro memory routine: begin/end` block at the END of the agent's crontab (through `agent-user/crontab.ts` `withBlock`), runs `~/.metro/bin/memory-routine ~/.claude/skills/memory/SKILL.md` (a launcher with the agent's PATH, the port and `exec node <METRO_CLI_BIN> memory "$@"`, so `metro memory` follows the skill file the line names, which the Routines page shows as the job's script) at `0 0,12 * * *` (00:00 and 12:00, box clock, UTC on a box Metro launched), and logs to `~/.metro/memory-routine.log`. **One memory job per box, always named `memory-routine`** (Less, 2026-10-01): an agent cron line whose job name (its script's file name) has `memory` in it, like Emma's `memory-upkeep`, is replaced: kept in the crontab as a `# replaced by memory-routine: ` comment, which Off turns back into the line. **A memory job metro cannot name is kept and no second job is added**: a cron line with `memory` only further in its command (run through a shell, a lock or `claude -p`), or an agent timer with `memory` in its name or command (Lisa's `memory-daily`), since the helper cannot switch a timer off. The state is then `own` and the page names that job. No agent user or no `METRO_CLI_BIN` (a dev checkout, compat) means `unavailable` and no crontab write. `metro memory` (`packages/cli/src/memory.ts`) skips without tokens when no transcript changed since `~/.metro/memory-routine.json` `lastRun`, holds `~/.metro/memory-routine.lock`, creates the ten Instinct folders when missing, and runs the runner store's `claude -p` with `headlessEnv` but **no metro MCP server** (a second `/mcp` session would take the chat session's slot), metro's hooks off (`METRO_SESSION=memory`), `--strict-mcp-config`, `--no-session-persistence`, and `--permission-mode dontAsk` with `--tools Read,Write,Edit,Glob,Grep` and only Read, Glob, Grep and `Edit(/<memory>/**)` allowed. **No Bash, ever**: a Bash allow rule overrides Claude Code's own path check for a write inside the cwd (`$HOME`), so `Bash(mv *)` could overwrite any file of the agent. After exit 0 the CLI itself moves `workstreams/active/` notes whose frontmatter `status` is `completed`, `parked` or `abandoned` to `workstreams/completed/` and relinks `MEMORY.md` (`settleWorkstreams`). The window is at most 2 days, the run gets SIGTERM at 50 minutes and SIGKILL 30 s later, and a lock older than 2 hours or held by a dead pid is taken over. **The crontab is read strictly** (`readCrontab`: exit 1 with `no crontab for` is empty, anything else throws), because a failed read once meant an empty crontab and the write after it would have wiped the agent's jobs; the write's status is checked too. `withBlock` cuts a range only when there is exactly one begin before exactly one end, and otherwise only drops the markers and the lines it owns (for the memory block, any line naming the launcher). Measured on Claude Code 2.1.282: in `dontAsk`, writes under `~/.claude` are refused even with an `Edit` rule unless the folder is the cwd's own auto-memory folder, which is why the launcher runs from `$HOME`.
- **What the first migration taught, for anyone moving a box's files by hand** (2026-09-25): copying Tony's 43 GB `work` filled the disk to 97% while a same-disk `mv` is instant; git worktrees keep absolute `gitdir:` paths (the worktree's `.git` file and `.git/worktrees/*/gitdir`); tool and model caches in hidden folders do not follow a move of visible folders; a Bun that lives only under `/root` is invisible to other users.
- `bun run metro-user-check` (Docker Desktop must be running; ask Less before starting it, nothing is installed on his Mac) boots a throwaway ubuntu:24.04 with systemd and a stand-in `tailscale`, installs Metro the way cloud-init does (`install.sh`, then `service install --user metro`), and checks as metro: the service user and health, nothing under `/root`, the unit, the helper version and sudo rules, agent commands, the walls (metro cannot read `/root`, the agent cannot read Metro's folder, metro cannot sudo to root outside the helper), Files, the session scope and start, the agent's jobs and Run now, the helper's refusals, Sessions with a 0600 transcript in a 0700 folder, Memory, Skills, Settings, the terminal resize. It is outside the gate.
- **`bun run secret-boundary-check` (`scripts/secret-boundary-check.sh`) runs ON a box as the agent user** (`sudo -u agent bash …`) and prints PASS or FAIL per check, never a value: first `secret-modes.sh` (the modes), then reads: root and Tailscale state, `/proc` environ, memory and fds of other users' processes, ptrace scope, sudo, metro's journal, secret-looking argv, the Tailscale LocalAPI node key and cert, the admin APIs with the agent key, the agent key through the public address, instance metadata, and a pattern scan of every file of another user the agent can read. Exit 1 on any FAIL.
