# Tool policies and approvals (`policy/`, `mcp/policy-gate.ts`, `mcp/channel-asks.ts`, `approvals/`)

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code.

- **Every metro MCP tool declares `group: 'read' | 'write'` next to its definition** (`ToolDef` in `mcp/tool-def.ts`, `StationTool.group` in core; `destructive: true` for delete, remove and close). Read is `read`, `list_members`, `get_profile`, `list_accounts`, `list_channels`, `tool_search`, xmtp `group_info`; everything else is write, and an undeclared tool counts as write. `mcp/tool-catalog.ts` is the one list: `toolList()` publishes `readOnlyHint`/`destructiveHint`, `channelToolsOf(station)` feeds the page. `test/tool-groups.test.ts` fails on a tool with no group. **Never mark a metro tool `requiresUserInteraction`**: Claude Code never relays such a tool's prompt.
- **A channel account may carry `policy: {read?, write?, tools?: {<tool>: …}}` in `agent.json`** (`allow`, `ask`, `deny`; absent means allow). The parser is tolerant (a bad value is logged and dropped), the API strict (`normalizePolicy`, 400 by name). The bundle and `.metro` exports carry it. `PUT /api/agents/<id>/accounts/<station>/<account>/policy` (member, like the allowlist) reloads the maps only. `list_accounts` shows each account's effective policy.
- **One rules engine** (Less, 2026-11-07, step 1 of `docs/CHANNELS-AS-CONNECTORS.md`): a channel rule has the connectors' shape and is decided by the connectors' function. `ToolPolicy` is `ConnectorPolicy`, and `decide` in `policy/policy.ts` is `decideTool` of `@metro-labs/http/connector-policy`, the function mcp.metro.box calls (a rule on the tool beats its group, nothing set allows). **The daemon is the only place a channel rule is applied.** The guard hook knows no rule (see Gone, below).
- **The rule that applies is the rule of the account that acts** (`channelTargets` in `mcp/policy-gate.ts`). A call with a `line` is always judged by the rule of the line's account, since `send`, `reply`, `react`, `unreact`, `edit`, `delete`, `typing` and the XMTP line tools act on it and never read an `account` argument. When such a call also names an `account`, that account's rule applies as well and the stricter wins (`read` and the group tools do forward it); `list_members` follows its line only. A call with no line is judged by the account it names, else by every account of its station, the strictest winning. **`account` must be text**: `runTool` refuses any other type before scope, rule or train (`givenCall`), and takes `null` and `""` out, so the scope check, the gate and the dispatch read the same call. Why: until 2026-11-10 an added account replaced the line's account in the gate, so `send {line, text, account: 7}` (or another account of the agent with no rule) ran straight through a Block or an Ask, on every box. `test/policy-matrix.test.ts` holds a row per verb.
- **The daemon blocks and asks by itself** (`policyGate` in `runTool`, right after the scope check). A name that is no metro tool is refused before all of it (`unknown tool: <name>`, the first line of `runTool`): until 2026-11-11 an unknown name on a line under Ask asked the owner and took one of the 50 places. A block answers `Blocked by the owner's policy for <station> (<tool>).` and no train call. **An Ask answers at once and nothing runs** (`askOwner` in `mcp/channel-asks.ts`): `Needs the owner's approval for <station> (<tool>). It waits on metro.box, approval id "<id>": <link> Metro posted that link in the chat. Keep working: metro tells you the answer. Once approved, call <tool> again with the same arguments and approval: "<id>".` (no `Metro posted…` sentence when no chat got it). This is the `needs_approval` contract mcp.metro.box uses for connectors: a member of the organization answers on metro.box or nobody does (24 hours, denied), the agent is told, and repeats the same call with `approval: "<id>"`, which runs once. Nothing waits, so the main thread may make an Ask call itself. Why the daemon and not the hook: an agent holds its own key and could call `/mcp` with `curl`, so the daemon has refused unapproved Ask calls since 2026-09-25; until 2026-11-10 only a Claude Code prompt raised by the hook could approve one.
- **What an approval is bound to** (`AskedCall` in `approvals/ledger.ts`): the tool, the SHA-256 of the canonical JSON of the arguments without `approval` (`@metro-labs/http/args-digest`, the digest mcp.metro.box uses), the channel account the rule was decided for (station and account), and the agent that made the call. A speech send is also bound to its live call (below). An approval runs once (`use` marks it before the call is dispatched, in the same synchronous step, so two repeats at the same moment run one call), within 10 minutes of the answer (`APPROVAL_USE_MS`), and the rule is decided again on every call: **a rule that now blocks wins over an approval, and a rule that stops asking withdraws the waiting question and the unused approval**, so a rule moved to Allow cannot leave an approval that would run the same call a second time. It happens at once when the rules are saved (the listener on `setPolicies` at the end of `mcp/channel-asks.ts`: every waiting request and unused approval whose tool and account are no longer on Ask). An agent that was waiting gets one notice, `Withdrawn: <tool> on <station> (<id>). The owner changed the rule. Call <tool> again, without the approval, to see what applies now.`, which promises no outcome: the call may now run, be blocked, be out of scope, or ask under another account's rule. The 24 hours, the 10 minutes, the 50 below and the id pattern are `@metro-labs/http/approval-rules`, shared with `@metro-labs/connectors/db/mcp-approvals`.
- **One waiting request per call.** The same call asked again while its request waits gets the same id and no second question (`…and has not answered yet`). The same call asked again after the owner approved, without the id, is pointed to that approval (`Already approved by the owner for <station> (<tool>), approval id "<id>". Nothing ran yet: call <tool> again…`), not asked twice; that is also how an agent finds an answer whose notice it never got. A denied id answers `Denied by the owner for <station> (<tool>), approval "<id>". Do not repeat it.`
- **An approval that cannot be used says why, then the owner is asked again** (`SPENT` in `mcp/channel-asks.ts`, between the first sentence and the new id): not known here (Metro restarted since), given for another call (another tool, channel or arguments), already used, answered more than 10 minutes ago, expired after 24 hours, or withdrawn before it was used. A value that is not a 5-letter id is said so and never repeated back.
- **Limits** (all in memory, `AskLedger`): 50 requests wait at once; the next call is refused with `50 approval requests are already waiting for the owner. Wait for answers before asking again.` and asks nobody. A call whose preview is over 100,000 characters (`PREVIEW_MAX` in `approvals/preview.ts`) is refused, not asked: the owner would approve what they cannot see. Answered requests are kept for the sentences above, 500 at most (`ASKS_KEPT_MAX`): the oldest answered one goes first, a waiting one never. **A daemon restart forgets every request**: the page no longer lists it, a `yes <id>` in chat gets no link reply, and a repeat with the old id answers "not known here" and asks again. A session restart keeps them (they belong to the module, not to a session).
- **The link** goes where a Claude Code prompt's would go (`ownerPromptLine` in `mcp/owner-route.ts`, which is `relayLine`: the call's chat for a speech send, else the session's last inbound line; never a line outside scope or an account that does not receive; page only while messages are paused). **The last inbound line survives a restart** (2026-11-15): `channels/last-chat.ts` keeps it in `<agents dir>/last-chat.json` (`{"version":1,"line":"metro://…"}`, 0600, written atomically and only when the chat changes, by `noteLastChat` from the inbound relay), boot reads it (`setLastChatFile`), and every new session's relay starts from it, so the first approvals after an update or a session restart (background work, a worker's Claude Code prompt) still reach the chat. It is only a hint: the same checks apply at use (in scope, the account receives, messages not paused), a missing, unreadable or malformed file means no chat is known, and a failed write is a warning (the line stays in memory). The agent view never copies it (only `COPIED` in `agent-user/view.ts` is). `test/last-chat.test.ts`. The message is the one `approvalNotice` in `mcp/permission-prompt.ts` writes: `Approval needed: <agent> wants to run <tool> on <station>.` then `Approve or deny it on metro.box: <link>`. **No argument ever goes in chat**, so nothing an agent puts in a call can reach the owner's chat; the agent's name, the tool and the station are made one line each (`oneLine`) and cut to 60 and 120 characters, and a station is named only when it is a registered one (the line's station, or for `list_channels` the station of the account, never a surplus `line` or `station` argument). **The link** is `approvalLink` of `@metro-labs/http/approval-rules`: `https://metro.box/#/<org id>/<agent row id>/approvals/<id>` (`METRO_APP_URL` changes the origin), where the row is the `server` the box enrolled as (`approvalAgentOf` in `approvals/link.ts`, wired in `boot.ts` from `.owner` and `agent-key.json`), `#/<org id>` before enrollment or when the enrollment belongs to another organization, and `https://metro.box` with no owner. **The page shows everything that will run**: `GET /api/approvals` lists the request as `mcp__metro__<tool>` with the arguments as JSON, whole and in their own order (`previewText` in `approvals/preview.ts`; only the bytes of an inline file are cut, to their first and last 64 characters around `\n⋯ N code points elided ⋯\n`, from which the page reads the size), and the approval card and the approval's own page list every argument in full (`everything` in the client's `api/approval-card.ts`, `approvalFields` of `@metro-labs/core/approval-fields`; `ApprovalCard.tsx`, `approval/ApprovalPage.tsx`). Why (Less, 2026-11-15): an approval is now answered by a signed-in member of the organization, not by whoever controls a chat account, so the chat only points there; until then the chat carried the arguments, fitted to 1,000 characters, and a `Reply "yes <id>"` line.
- **The answer**: the page (`POST /api/approvals/<id>`, any member of the organization) or the 24 hour expiry. **No chat answer counts.** A chat message that looks like `yes <id>` or `no <id>` (`ANSWER_LIKE_RE` in `channels/inbound.ts`, case-insensitive, nothing else on the line) for a request that is waiting gets one reply on its own line, `Approval <id> is answered on metro.box, not in chat: <link>` (`pointToApproval` in `mcp/session.ts`), and still reaches the agent as an ordinary message; an unknown id, a bus replay, an unverified sender and a message with attachments get nothing. The agent then gets a metro notice (`tellAgent` in `mcp/owner-route.ts`): `Approved: <tool> on <station> (<id>). Call <tool> again with the same arguments and approval: "<id>".`, `Denied: <tool> on <station> (<id>).` or `Expired: <tool> on <station> (<id>). The owner did not answer within 24 hours, so it counts as denied.` It goes on the first of the posted line and the session's last chat whose account is still attached and receiving. **A notice is not guaranteed**: with messages paused, or with no such chat (a box that never got a message, or whose last chat was detached or switched off), nothing is delivered, and the waiting sentence then says `Metro cannot tell you the answer right now: to see it, call <tool> again…` in place of `Keep working: metro tells you the answer.` (`canTellAgent`, the test `tellAgent` itself uses). A request withdrawn by a hang-up sends no notice; one withdrawn by a rule change sends the `Withdrawn:` notice above. The chat confirmations (`Approved on the page.`, `Denied on the page.`, `Expired, denied.`) go on the line the link was posted on, as for every prompt. Gone (2026-11-15): the chat answer and its approver, line and `sender_verified` checks, `PERMISSION_REPLY_RE` as a contract, `promptLine`, and the pointer to the right chat (`mcp/approval-elsewhere.ts`, `channels/line-names.ts`, 2026-11-14).
- **A speech send** (`send` with `speech`) is asked only while its call is live and its source is real (`sharedCalls.source` with the caller's scope; otherwise `The call or its authorized source has ended or changed. Nothing was spoken.` and nobody is asked), its question goes to the call's chat, and **hang-up withdraws its request and its unused approval** (`revokeCallAsks`, called with `revokeCallPrompts` from `mcp/call-bridge.ts`). `callId`, `generation` and `sourceId` are in the digest, so an approved speech cannot pay for a chat post, another source or another call.
- **Every gated metro tool's published schema has an optional `approval`** (`withApproval` in `mcp/tool-catalog.ts`, the `APPROVAL_PROPERTY` mcp.metro.box publishes; never on `UNGATED`: `list_accounts`, `create_upload`, `tool_search`, `tool_call`), and `runTool` takes it out before the scope check, the rule and the dispatch, so it never reaches a train (a Claude Code prompt is settled against the call as it was sent, `approval` included). `test/policy-matrix.test.ts` is the daemon's case table; `test/channel-asks.test.ts` and `test/channel-asks-rules.test.ts` drive the contract over real HTTP (chat, page, expiry, single use, another call's id, six repeats at once, a rule change after approval, the 50, a restart, a new session, paused messages); `test/approval-ledger.test.ts` is the state machine; `test/approval-preview.test.ts` the preview written and read; the `the words in chat and for the agent` tests of `test/permission-relay.test.ts` pin the link message (no input, forged tool names, the station named only when real) and `the link names the metro.box row` the link itself and `packages/client/test/approval-card.test.ts` what the card lists; `test/shared-call-security.test.ts` covers speech.
- **Gone** (2026-11-10): the hook's copy of the rules (`packages/cli/hooks/policy.mjs`, its use in `guard.mjs`), the snapshot `<agents dir>/policy.json` and `mcp/policy-snapshot.ts`, the grants (`takeGrant`, `GRANT_TTL_MS`, `NEEDS_APPROVAL` in `approvals/pending.ts`), the hook's `ask` and `deny` answers, and the rule that an Ask on the main thread moves to a worker. The agent view removes the agent's copy of `policy.json` at its first sync (`NEVER_COPIED` in `agent-user/view.ts`); the one an older version left in `<agents dir>` stays where it is, since nothing reads it and it holds rules, no secret. `packages/cli/test/hooks.test.ts` checks that a leftover snapshot changes nothing. The hooks ship in the same package as the daemon, so a new daemon never runs with an old hook; in the seconds of an update where the new hook is on disk and the old daemon still runs, an Ask call is refused (the old daemon wants a grant nothing gives any more).
- **A Claude Code prompt is still relayed** (the auto mode classifier, a tool that is not metro's) **and its answer never authorizes a metro call** (`test/connector-channel-grants.test.ts`): with a rule on Ask, a call the owner approved in a Claude Code prompt still answers `Needs the owner's approval` with the daemon's own id. The relay (`mcp/permission-relay.ts`): the SDK runner sends `notifications/claude/channel/permission_request` `{request_id, tool_name, description (the tool's own), input_preview (JSON of the input)}`, metro holds it, posts the link to the chat the request belongs to (above; never a line outside scope), formatted by `promptNotice` in `mcp/permission-prompt.ts` (a metro tool with the station of its line, any other tool by its name alone, never the description or the input), and answers with `notifications/claude/channel/permission` `{request_id, behavior}` once the page or the expiry answered. A prompt bound to a call goes to the call's chat, and while a shared call is on so does any other prompt. Until 2026-11-15 a prompt went to the owner's direct chat (`approvals/owner-line.ts`, `<state dir>/approval-line.json`, kept since 2026-10-09 so workers' prompts did not land in front of whoever was in the last chat); with no answer in chat and no arguments in the message there is nothing left to protect, so the link goes where the request came from. The old file meant something else (a private chat where an approver wrote, with that sender), so it is not reused: boot removes it and a leftover `approval-line.json.tmp-<pid>` from `<state dir>` (`removeOldOwnerChat` in `channels/last-chat.ts`, a regular file only, never fatal), and the last chat has its own file (above). **The runner sends the whole input as JSON** (`sdk-runner/src/approvals.ts`), so a preview is read with one `JSON.parse` (`previewInput` in `approvals/preview.ts`), and `previewMatches` (what `settlePromptsFor` uses) is a deep equal of the preview and the call's arguments. A prompt answered on the page or expired also posts `Approved on the page.`, `Denied on the page.` or `Expired, denied.` on its chat line.
- **metro keeps the pending prompts** (`approvals/pending.ts`, in memory, 500 max): Claude Code's (dropped with the session that raised them, since a session restart drops its prompts too), the daemon's own channel approvals (`origin: 'channel'`) and mcp.metro.box's (`origin: 'mcp-server'`). The page (`GET /api/approvals` lists `{id, tool, description, preview, line, requestedAt, requestedBy?}`, `requestedBy` only for an access key's approval, below, `POST /api/approvals/<id> {decision: allow|deny}`, member-level, 404 for an unknown or already answered id) or the expiry (24 hours, swept every minute, answers `deny`) settles one, and each prompt's `send` is told how (`page`, `expiry`, or `cancel` for a hang-up or a withdrawal). **An id belongs to whoever held it first**: `holdPrompt` refuses a second asker (the relay then answers Claude Code `deny`), so a `permission_request` sent with the id of a channel approval cannot replace what the page shows. Over 500, the oldest Claude Code prompt is dropped and the drop is logged; an approval the daemon holds is never dropped, since those are bounded on their own (50 channel requests, and what mcp.metro.box sends). **A call settles Claude Code's own prompt**: a prompt whose call then reaches the daemon with the same arguments is dropped before the policy check, whether the call then runs or is refused (`settlePromptsFor` in `runTool`), since the session has stopped waiting by then; before 2026-09-26 a call approved elsewhere and refused by the daemon left a dead prompt on the page. A denied one stays until expiry, and a late answer to a prompt Claude Code already closed is harmless. `test/permission-relay.test.ts` drives the relay, the chat answer, the page and the expiry over real HTTP; `test/approval-prompts.test.ts` the store.
- **Connector policies live only on mcp.metro.box** (2026-10-14): Block and Ask are enforced by the server for `tool_call` (see mcp.metro.box in `CLAUDE.md`), so the daemon has no connector gate. `tool_search` and `tool_call` are in `UNGATED`, so no station policy applies to them, and the guard keeps `mcp__metro__tool_call`, like any non-metro MCP tool, off the main thread. A Claude Code prompt for some other MCP tool is still relayed as `Claude wants to run <tool>: <description>`.
- **`MCP_INSTRUCTIONS` (`mcp/instructions.ts`) must stay under 2,048 characters**: Claude Code keeps only the first 2,048 of a server's instructions (2.1.281 logs `Server instructions truncated from 2140 to 2048 chars`), which cut the approval rule at its end. `test/permission-relay.test.ts` pins the length; tighten wording rather than drop a rule.
- **An agent without a server has no daemon, so its Ask approvals are answered on metro.box** (Less, 2026-10-23): the same `mcp_approvals` row, listed by `GET /api/agents/<id>/approvals` and answered by `POST /api/agents/<id>/approvals/<approval id> {decision}`, both member-level like a box's `POST /api/approvals/<id>`, with the store functions mcp.metro.box uses (`@metro-labs/connectors/db/mcp-approvals`: same 24 hour expiry, same single use within 10 minutes). The page shows them as approval cards on that agent's Connectors tab. Nobody tells the agent: the person repeats the call with `approval: "<id>"`, and the `needs_approval` wording says so. These routes refuse an agent with a server (409).
- **Approvals asked by mcp.metro.box are a third kind of pending prompt** (`origin: 'mcp-server'` in `approvals/pending.ts`, `mcp/server-approvals.ts`), held under the server's own 5-letter id: the link goes where a Claude Code prompt's would go (`ownerPromptLine`), written by `serverNotice` (`Approval needed: <agent> wants to run <tool> on <connector key>.` and the link; no preview), and the page lists it with tool `<connector key>.<tool>`. The page or the 24 hour expiry answers it; the answer goes to the server (`POST <url>/v1/approvals/answer`, retried until it is taken or answers 404), never to Claude Code (the server enforces its own approval). Once the server took it, the agent gets a metro notice through the same `tellAgent`: `Approved: <connector>.<tool> (<id>). Call tool_call again with the same arguments and approval: "<id>".` or `Denied: <connector>.<tool> (<id>).`; a 404 tells the agent nothing. **An approval the server marks `origin: 'key'` (an access key of this agent made the call, not its own session; 2026-10-23) is posted in no chat and gets no notice** (2026-11-15): it belongs to whoever holds the key, not to one of the agent's conversations, and the agent's last chat could be an unrelated group (seen on Emma, beta.333: the caller was told Metro posted the link in the agent's chat, and no chat was known). `holdServerApproval` picks no line for it, not even one an older version recorded in `mcp-approvals.json`, so the page lists it with no line and no `Approved on the page.` goes to a chat. **The page says who asked**: the pending prompt carries `requestedBy` (`access key "<label>"`, or `an access key` without a label; `requesterOf` in `mcp/server-approvals.ts`), `GET /api/approvals` answers it, and the approval page and Home's card show an Asked by row (the client's `approvalOf` keeps it only as plain text, at most 100 characters; a box without it shows no row); the page or the expiry answers it and the answer goes to the server exactly as for any other, but the session, which never made the call, is told nothing (`tellAgent` in `mcp/server-approvals.ts`). mcp.metro.box's `needs_approval` for any access key (places `page` and `owner`, `KEY_INSTRUCTIONS`) says it waits on metro.box at the link and tells the caller to give the person that link; it never promises a chat post. The person holding the key repeats the call. `origin: 'box'`, no `origin` (a server before `0020`) or an origin the daemon does not know keep the notice. The page and expiry confirmations in chat are the same as today. An id already held, or answered in the last 10 minutes, is not held again. **An id already posted in chat is never posted again** (`mcp-server/announced.ts`): the server sends a pending approval again every minute, so after a restart it used to be posted twice; the daemon keeps each posted id with its chat line in `<agents dir>/mcp-approvals.json` (0600, 200 at most, entries older than a day dropped, the file set from `boot.ts`), and an id found there is held again on that line (the page, the confirmation, the expiry) without a new post. `test/mcp-server-approvals.test.ts`, `test/mcp-server-announced.test.ts`.
- **Known limits, left as they are**: an approval covers what the call says, not the bytes behind it (a file named by `path`, `url` or `upload` can change between the answer and the repeat, within the 10 minutes); an approval is spent when its repeat is accepted, before the call is dispatched, so a call that then fails before anything is sent (a missing file, a station error) needs a new approval, as a vendor error does on mcp.metro.box; an agent can fill the 50 places with junk questions and refill them after each answer, nothing limits the rate; a denied call asked again without its id asks the owner again at once, as on mcp.metro.box; the answer to the agent says `Metro posted that link in the chat` before the chat post is known to have gone out (a failed post is logged and the request waits on the page); and Claude Code's own prompts keep their sizes as sent (500 prompts at most, each as large as the session sends it).
- **No stored calls.** metro's first own approval flow (stored calls, `approvals.json`, "Waiting for the owner's approval", the `approval_id` channel message) lived for an afternoon on 2026-09-24 and was replaced by the native prompt at Less's call. The channel approvals of 2026-11-10 keep the id, the digest and the state in memory only: no file, no stored arguments, no stored call that runs later by itself. Do not bring back the stored calls or `approvals.json`.
