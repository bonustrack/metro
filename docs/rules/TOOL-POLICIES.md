# Tool policies and approvals (`policy/`, `mcp/policy-gate.ts`, `mcp/channel-asks.ts`, `approvals/`)

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code.

- **Every metro MCP tool declares `group: 'read' | 'write'` next to its definition** (`ToolDef` in `mcp/tool-def.ts`, `StationTool.group` in core; `destructive: true` for delete, remove and close). Read is `read`, `list_members`, `get_profile`, `list_accounts`, `list_channels`, `tool_search`, xmtp `group_info`; everything else is write, and an undeclared tool counts as write. `mcp/tool-catalog.ts` is the one list: `toolList()` publishes `readOnlyHint`/`destructiveHint`, `channelToolsOf(station)` feeds the page. `test/tool-groups.test.ts` fails on a tool with no group. **Never mark a metro tool `requiresUserInteraction`**: Claude Code never relays such a tool's prompt.
- **A channel account may carry `policy: {read?, write?, tools?: {<tool>: …}}` in `agent.json`** (`allow`, `ask`, `deny`; absent means allow). The parser is tolerant (a bad value is logged and dropped), the API strict (`normalizePolicy`, 400 by name). The bundle and `.metro` exports carry it. `PUT /api/agents/<id>/accounts/<station>/<account>/policy` (member, like the allowlist) reloads the maps only. `list_accounts` shows each account's effective policy.
- **One rules engine** (Less, 2026-11-07, step 1 of `docs/CHANNELS-AS-CONNECTORS.md`): a channel rule has the connectors' shape and is decided by the connectors' function. `ToolPolicy` is `ConnectorPolicy`, and `decide` in `policy/policy.ts` is `decideTool` of `@metro-labs/http/connector-policy`, the function mcp.metro.box calls (a rule on the tool beats its group, nothing set allows). **The daemon is the only place a channel rule is applied.** The guard hook knows no rule (see Gone, below).
- **The rule that applies is the rule of the account that acts** (`channelTargets` in `mcp/policy-gate.ts`). A call with a `line` is always judged by the rule of the line's account, since `send`, `reply`, `react`, `unreact`, `edit`, `delete`, `typing` and the XMTP line tools act on it and never read an `account` argument. When such a call also names an `account`, that account's rule applies as well and the stricter wins (`read` and the group tools do forward it); `list_members` follows its line only. A call with no line is judged by the account it names, else by every account of its station, the strictest winning. **`account` must be text**: `runTool` refuses any other type before scope, rule or train (`givenCall`), and takes `null` and `""` out, so the scope check, the gate and the dispatch read the same call. Why: until 2026-11-10 an added account replaced the line's account in the gate, so `send {line, text, account: 7}` (or another account of the agent with no rule) ran straight through a Block or an Ask, on every box. `test/policy-matrix.test.ts` holds a row per verb.
- **The daemon blocks and asks by itself** (`policyGate` in `runTool`, right after the scope check). A name that is no metro tool is refused before all of it (`unknown tool: <name>`, the first line of `runTool`): until 2026-11-11 an unknown name on a line under Ask asked the owner and took one of the 50 places. A block answers `Blocked by the owner's policy for <station> (<tool>).` and no train call. **An Ask answers at once and nothing runs** (`askOwner` in `mcp/channel-asks.ts`): `Needs the owner's approval for <station> (<tool>). The owner was asked in chat` (or `on the agent's page on metro.box`) `, approval id "<id>". Keep working: metro tells you the answer. Once approved, call <tool> again with the same arguments and approval: "<id>".` This is the `needs_approval` contract mcp.metro.box uses for connectors: the owner answers in chat (`yes <id>`), on the page or not at all (24 hours, denied), the agent is told, and repeats the same call with `approval: "<id>"`, which runs once. Nothing waits, so the main thread may make an Ask call itself. Why the daemon and not the hook: an agent holds its own key and could call `/mcp` with `curl`, so the daemon has refused unapproved Ask calls since 2026-09-25; until 2026-11-10 only a Claude Code prompt raised by the hook could approve one.
- **What an approval is bound to** (`AskedCall` in `approvals/ledger.ts`): the tool, the SHA-256 of the canonical JSON of the arguments without `approval` (`@metro-labs/http/args-digest`, the digest mcp.metro.box uses), the channel account the rule was decided for (station and account), and the agent that made the call. A speech send is also bound to its live call (below). An approval runs once (`use` marks it before the call is dispatched, in the same synchronous step, so two repeats at the same moment run one call), within 10 minutes of the answer (`APPROVAL_USE_MS`), and the rule is decided again on every call: **a rule that now blocks wins over an approval, and a rule that stops asking withdraws the waiting question and the unused approval**, so a rule moved to Allow cannot leave an approval that would run the same call a second time. It happens at once when the rules are saved (the listener on `setPolicies` at the end of `mcp/channel-asks.ts`: every waiting request and unused approval whose tool and account are no longer on Ask). An agent that was waiting gets one notice, `Withdrawn: <tool> on <station> (<id>). The owner changed the rule. Call <tool> again, without the approval, to see what applies now.`, which promises no outcome: the call may now run, be blocked, be out of scope, or ask under another account's rule. The 24 hours, the 10 minutes, the 50 below and the id pattern are `@metro-labs/http/approval-rules`, shared with `@metro-labs/connectors/db/mcp-approvals`.
- **One waiting request per call.** The same call asked again while its request waits gets the same id and no second question (`…and has not answered yet`). The same call asked again after the owner approved, without the id, is pointed to that approval (`Already approved by the owner for <station> (<tool>), approval id "<id>". Nothing ran yet: call <tool> again…`), not asked twice; that is also how an agent finds an answer whose notice it never got. A denied id answers `Denied by the owner for <station> (<tool>), approval "<id>". Do not repeat it.`
- **An approval that cannot be used says why, then the owner is asked again** (`SPENT` in `mcp/channel-asks.ts`, between the first sentence and the new id): not known here (Metro restarted since), given for another call (another tool, channel or arguments), already used, answered more than 10 minutes ago, expired after 24 hours, or withdrawn before it was used. A value that is not a 5-letter id is said so and never repeated back.
- **Limits** (all in memory, `AskLedger`): 50 requests wait at once; the next call is refused with `50 approval requests are already waiting for the owner. Wait for answers before asking again.` and asks nobody. A call whose preview is over 100,000 characters (`PREVIEW_MAX` in `approvals/preview.ts`) is refused, not asked: the owner would approve what they cannot see. Answered requests are kept for the sentences above, 500 at most (`ASKS_KEPT_MAX`): the oldest answered one goes first, a waiting one never. **A daemon restart forgets every request**: the page no longer lists it, a `yes <id>` in chat is then an ordinary message, and a repeat with the old id answers "not known here" and asks again. A session restart keeps them (they belong to the module, not to a session).
- **The question** goes where a Claude Code prompt would go (`ownerPromptLine` in `mcp/owner-route.ts`, which is `relayLine`: the owner's direct chat, else the last inbound line, the call's chat for a speech send; never an `approvals: false` station, a line outside scope, an account that does not receive, or a chat without approvers; page only while messages are paused), formatted by `channelQuestion` in `mcp/permission-prompt.ts`: `Approval needed: <tool>`, `Channel: …`, one line per argument, then `Reply "yes <id>" or "no <id>"`, 1,000 characters at most. **The chat and the page read one list of arguments** (`approvalFields` in `@metro-labs/core/approval-fields`): what changes the call comes first (`FIRST`: text, attachments, wallet, frame, speech, subject, reply_to, account, members, …), then the rest in the call's own order; a list of plain values is written out, anything else is JSON, each file is its own line (`file 2 of 3: {"path":"…"}`, inline bytes as `inline data`), and an empty value is left out. **An argument cannot write or imitate a line of the question**: every run of white space, control characters and text direction overrides in a name, a value, a tool name or a description becomes one space (`oneLine`), and an argument name that is not a plain lower-case identifier shows in JSON quotes (`"Channel": …`, `"file 2 of 2": …`), so only the daemon's own lines start with `Approval needed`, `Channel`, `Text`, `file N of M` or `Reply`. **What matters is never pushed out by what does not** (`fitted`): each argument, in that order, gets at most 300 characters and at most half of the room that is left, a value too long for its share keeps both of its ends around `…`, and what does not fit is counted in a last line whose room is kept free: `Not shown here: N more. Read it all on metro.box before you answer.` **The page shows everything that will run**: `GET /api/approvals` lists the request as `mcp__metro__<tool>` with the arguments as JSON, whole and in their own order (`previewText` in `approvals/preview.ts`; only the bytes of an inline file are cut, to their first and last 64 characters around `\n⋯ N code points elided ⋯\n`, from which the page reads the size), and the approval card lists every argument, in full, under `Everything in this call` (`everything` in the client's `api/approval-card.ts`, the same `approvalFields`; `ApprovalCard.tsx`). Why: a call padded with long or unknown arguments used to push its files or its wallet card out of the chat message, seven junk arguments cut the text from 300 to 60 characters, a value with line breaks could draw a fake reply line, and the card showed neither a wallet card, a frame, a second file nor the members of a group call while the chat sent the owner there (review of 2026-11-10).
- **The answer**: a chat `yes <id>` or `no <id>` (same line, approver and `sender_verified` rules as every prompt, see Human in the loop in `CLAUDE.md`), the page (`POST /api/approvals/<id>`) or the 24 hour expiry. The agent then gets a metro notice (`tellAgent` in `mcp/owner-route.ts`): `Approved: <tool> on <station> (<id>). Call <tool> again with the same arguments and approval: "<id>".`, `Denied: <tool> on <station> (<id>).` or `Expired: <tool> on <station> (<id>). The owner did not answer within 24 hours, so it counts as denied.` It goes on the first of the prompt line, the session's last chat and the owner's chat whose account is still attached and receiving. **A notice is not guaranteed**: with messages paused, or with no such chat (a new session before its first message and no owner chat saved), nothing is delivered, and the waiting sentence then says `Metro cannot tell you the answer right now: to see it, call <tool> again…` in place of `Keep working: metro tells you the answer.` (`canTellAgent`, the test `tellAgent` itself uses). A request withdrawn by a hang-up sends no notice; one withdrawn by a rule change sends the `Withdrawn:` notice above. The chat confirmations (`Approved on the page.`, `Denied on the page.`, `Expired, denied.`) are the same as for every prompt.
- **A speech send** (`send` with `speech`) is asked only while its call is live and its source is real (`sharedCalls.source` with the caller's scope; otherwise `The call or its authorized source has ended or changed. Nothing was spoken.` and nobody is asked), its question goes to the call's chat, and **hang-up withdraws its request and its unused approval** (`revokeCallAsks`, called with `revokeCallPrompts` from `mcp/call-bridge.ts`). `callId`, `generation` and `sourceId` are in the digest, so an approved speech cannot pay for a chat post, another source or another call.
- **Every gated metro tool's published schema has an optional `approval`** (`withApproval` in `mcp/tool-catalog.ts`, the `APPROVAL_PROPERTY` mcp.metro.box publishes; never on `UNGATED`: `list_accounts`, `create_upload`, `tool_search`, `tool_call`), and `runTool` takes it out before the scope check, the rule and the dispatch, so it never reaches a train (a Claude Code prompt is settled against the call as it was sent, `approval` included). `test/policy-matrix.test.ts` is the daemon's case table; `test/channel-asks.test.ts` and `test/channel-asks-rules.test.ts` drive the contract over real HTTP (chat, page, expiry, single use, another call's id, six repeats at once, a rule change after approval, the 50, a restart, a new session, paused messages); `test/approval-ledger.test.ts` is the state machine; `test/approval-preview.test.ts` the preview written and read; the `the prompt text` tests of `test/permission-relay.test.ts` pin the question (order, forged lines, the 1,000 characters under hostile input) and `packages/client/test/approval-card.test.ts` what the card lists; `test/shared-call-security.test.ts` covers speech.
- **Gone** (2026-11-10): the hook's copy of the rules (`packages/cli/hooks/policy.mjs`, its use in `guard.mjs`), the snapshot `<agents dir>/policy.json` and `mcp/policy-snapshot.ts`, the grants (`takeGrant`, `GRANT_TTL_MS`, `NEEDS_APPROVAL` in `approvals/pending.ts`), the hook's `ask` and `deny` answers, and the rule that an Ask on the main thread moves to a worker. The agent view removes the agent's copy of `policy.json` at its first sync (`NEVER_COPIED` in `agent-user/view.ts`); the one an older version left in `<agents dir>` stays where it is, since nothing reads it and it holds rules, no secret. `packages/cli/test/hooks.test.ts` checks that a leftover snapshot changes nothing. The hooks ship in the same package as the daemon, so a new daemon never runs with an old hook; in the seconds of an update where the new hook is on disk and the old daemon still runs, an Ask call is refused (the old daemon wants a grant nothing gives any more).
- **A Claude Code prompt is still relayed** (the auto mode classifier, a tool that is not metro's) **and its answer never authorizes a metro call** (`test/connector-channel-grants.test.ts`): with a rule on Ask, a call the owner approved in a Claude Code prompt still answers `Needs the owner's approval` with the daemon's own id. The relay (`mcp/permission-relay.ts`): the SDK runner sends `notifications/claude/channel/permission_request` `{request_id, tool_name, description (the tool's own), input_preview (JSON of the input)}`, metro posts it to the owner's direct chat (below; never an `approvals: false` station, never a line outside scope), formatted by `mcp/permission-prompt.ts` (`Approval needed: <tool>`, the channel, the text, then `Reply "yes <id>" or "no <id>"`), and answers with `notifications/claude/channel/permission` `{request_id, behavior}`. **The prompt goes to the owner's direct chat** (`ownerLine` in `approvals/owner-line.ts`): the last private chat (`is_private`) where one of the account's approvers wrote, saved with that sender in `<state dir>/approval-line.json` so it survives restarts, and used only while that sender may still approve. A prompt bound to a call goes to the call's chat, and while a shared call is on so does any other prompt, as the last inbound line did then. Until an owner chat is known, or while it is out of scope or switched off, the prompt goes to the session's last inbound line (`knownLine`) as before. Why: a prompt names neither the chat nor the worker that raised it, so posting it in the last active chat put workers' prompts in front of whoever was there (an MCI chat, then a Trello chat; Less, 2026-10-09: "send other prompts to our DM"). XMTP marks a DM private by `'peerInboxId' in conv` (`emit.ts`): node-sdk 6 made `peerInboxId` a getter, and the old test for a function never matched, so no Stage DM was private before. **The runner sends the whole input as JSON** (`sdk-runner/src/approvals.ts`), so a preview is read with one `JSON.parse` (`previewInput` in `approvals/preview.ts`), a tool that is not metro's shows `Claude wants to run <tool>: <description>` and the same argument lines as above (a preview that is not JSON is one `arguments:` line), and `previewMatches` (what `settlePromptsFor` uses) is a deep equal of the preview and the call's arguments. The reader of the previews Claude Code's own relay elided (`⋯ N code points elided ⋯` inside a string, a trailing `⋯ … field(s) elided … ⋯` block) went on 2026-11-11, in the daemon and on the page: nothing has written that format since the runner became the only client (2026-10-15), and its regular expression could hold the whole daemon for hours on a crafted preview. **A chat prompt is at most 1,000 characters and never carries a metro tool's `description`** (a 4,470-character prompt was refused by Telegram, whose cap is 4,096, and a refused relay send is only logged). A prompt answered on the page or expired also posts `Approved on the page.`, `Denied on the page.` or `Expired, denied.` on its chat line.
- **metro keeps the pending prompts** (`approvals/pending.ts`, in memory, 500 max): Claude Code's (dropped with the session that raised them, since a session restart drops its prompts too), the daemon's own channel approvals (`origin: 'channel'`) and mcp.metro.box's (`origin: 'mcp-server'`). A chat answer (see Human in the loop), the page (`GET /api/approvals` lists `{id, tool, description, preview, line, requestedAt}`, `POST /api/approvals/<id> {decision: allow|deny}`, member-level, 404 for an unknown or already answered id) or the expiry (24 hours, swept every minute, answers `deny`) settles one, and each prompt's `send` is told how (`chat`, `page`, `expiry`, or `cancel` for a hang-up or a withdrawal). **An id belongs to whoever held it first**: `holdPrompt` refuses a second asker (the relay then answers Claude Code `deny`), so a `permission_request` sent with the id of a channel approval cannot replace what the page shows. Over 500, the oldest Claude Code prompt is dropped and the drop is logged; an approval the daemon holds is never dropped, since those are bounded on their own (50 channel requests, and what mcp.metro.box sends). **A call settles Claude Code's own prompt**: a prompt whose call then reaches the daemon with the same arguments is dropped before the policy check, whether the call then runs or is refused (`settlePromptsFor` in `runTool`), since the session has stopped waiting by then; before 2026-09-26 a call approved elsewhere and refused by the daemon left a dead prompt on the page. A denied one stays until expiry, and a late answer to a prompt Claude Code already closed is harmless. `test/permission-relay.test.ts` drives the relay, the chat answer, the page and the expiry over real HTTP; `test/approval-prompts.test.ts` the store.
- **Connector policies live only on mcp.metro.box** (2026-10-14): Block and Ask are enforced by the server for `tool_call` (see mcp.metro.box in `CLAUDE.md`), so the daemon has no connector gate. `tool_search` and `tool_call` are in `UNGATED`, so no station policy applies to them, and the guard keeps `mcp__metro__tool_call`, like any non-metro MCP tool, off the main thread. A Claude Code prompt for some other MCP tool is still relayed as `Claude wants to run <tool>: <description>`.
- **`MCP_INSTRUCTIONS` (`mcp/instructions.ts`) must stay under 2,048 characters**: Claude Code keeps only the first 2,048 of a server's instructions (2.1.281 logs `Server instructions truncated from 2140 to 2048 chars`), which cut the approval rule at its end. `test/permission-relay.test.ts` pins the length; tighten wording rather than drop a rule.
- **An agent without a server has no daemon, so its Ask approvals are answered on metro.box** (Less, 2026-10-23): the same `mcp_approvals` row, listed by `GET /api/agents/<id>/approvals` and answered by `POST /api/agents/<id>/approvals/<approval id> {decision}`, both member-level like a box's `POST /api/approvals/<id>`, with the store functions mcp.metro.box uses (`@metro-labs/connectors/db/mcp-approvals`: same 24 hour expiry, same single use within 10 minutes). The page shows them as approval cards on that agent's Connectors tab. Nobody tells the agent: the person repeats the call with `approval: "<id>"`, and the `needs_approval` wording says so. These routes refuse an agent with a server (409).
- **Approvals asked by mcp.metro.box are a third kind of pending prompt** (`origin: 'mcp-server'` in `approvals/pending.ts`, `mcp/server-approvals.ts`), held under the server's own 5-letter id: the chat prompt goes where a Claude Code prompt would go (`ownerPromptLine`: the owner's direct chat, else the last inbound line, never an `approvals: false` station, page only without approvers), formatted by `serverPromptBody` (`Approval needed: <connector key>.<tool>`, the preview's arguments as lines like every question, 1,000 characters at most), and the page lists it with tool `<connector key>.<tool>`. A chat `yes <id>` (same approver, line and `sender_verified` rules), the page or the 24 hour expiry answers it; the answer goes to the server (`POST <url>/v1/approvals/answer`, retried until it is taken or answers 404), never to Claude Code (the server enforces its own approval). Once the server took it, the agent gets a metro notice through the same `tellAgent`: `Approved: <connector>.<tool> (<id>). Call tool_call again with the same arguments and approval: "<id>".` or `Denied: <connector>.<tool> (<id>).`; a 404 tells the agent nothing. **An approval the server marks `origin: 'key'` (an access key of this agent made the call, not its own session; 2026-10-23) gets no such notice**: the prompt reads `Approval needed: <connector key>.<tool> (from an access key: <key label>)` (the label, never the key; `(from an access key)` without one), the page lists it, and the answer goes to the server exactly as for any other, but the session, which never made the call, is told nothing (`tellAgent` in `mcp/server-approvals.ts`); the person holding the key repeats the call. `origin: 'box'`, no `origin` (a server before `0020`) or an origin the daemon does not know keep the notice. The page and expiry confirmations in chat are the same as today. An id already held, or answered in the last 10 minutes, is not held again. **An id already posted in chat is never posted again** (`mcp-server/announced.ts`): the server sends a pending approval again every minute, so after a restart it used to be posted twice; the daemon keeps each posted id with its chat line in `<agents dir>/mcp-approvals.json` (0600, 200 at most, entries older than a day dropped, the file set from `boot.ts`), and an id found there is held again on that line (page, chat answer, expiry) without a new post. `test/mcp-server-approvals.test.ts`, `test/mcp-server-announced.test.ts`.
- **Known limits, left as they are**: an approval covers what the call says, not the bytes behind it (a file named by `path`, `url` or `upload` can change between the answer and the repeat, within the 10 minutes); an approval is spent when its repeat is accepted, before the call is dispatched, so a call that then fails before anything is sent (a missing file, a station error) needs a new approval, as a vendor error does on mcp.metro.box; a value longer than its share shows only its two ends in chat (in full on the page); an agent can fill the 50 places with junk questions and refill them after each answer, nothing limits the rate; a denied call asked again without its id asks the owner again at once, as on mcp.metro.box; a `yes <id>` counts from an approver of the chat the question was posted in, whichever channel the call is for; the answer to the agent says `asked in chat` before the chat post is known to have gone out (a failed post is logged and the request waits on the page); and Claude Code's own prompts keep their sizes as sent (500 prompts at most, each as large as the session sends it).
- **No stored calls.** metro's first own approval flow (stored calls, `approvals.json`, "Waiting for the owner's approval", the `approval_id` channel message) lived for an afternoon on 2026-09-24 and was replaced by the native prompt at Less's call. The channel approvals of 2026-11-10 keep the id, the digest and the state in memory only: no file, no stored arguments, no stored call that runs later by itself. Do not bring back the stored calls or `approvals.json`.
