# The Agent SDK runner (`packages/sdk-runner`, issue #119; the only runner since 2026-10-15)

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code.

- **The only runner** (2026-10-15, owner's call, see `docs/HISTORY.md`): the watcher runs `metro agent` in tmux session `metro` (same memory scope, same Terminal); there is no runner choice, no `metro claude` and no terms guard, so every Gateway page route runs it, a Claude subscription included. A box that ran the old `cli` runner moves to `metro agent` when it updates; the page still reads an older daemon's `runner: 'cli'` (`legacyRunner` in the client) and says to update Metro. `metro agent --prepare` installs and checks the runner store without starting a session. Start runs the session and enables autostart. Stop is explicit cancellation and disables autostart, not a drain. Restart the SDK to drain valid pending input; restore an unreadable ledger first, since startup refuses to overwrite it.
- **Why the runner, not Claude Code, holds `/mcp`**: a Claude Code session started through the Agent SDK does not deliver channel notifications (measured 2026-10-01, Claude Code 2.1.282 with SDK 0.3.287: dropped even with `--dangerously-load-development-channels server:metro`; `enableChannel` answers "requires a marketplace plugin"). So the runner is the MCP client of `/mcp`, and the daemon no longer advertises the experimental `claude/channel` capability: each `notifications/claude/channel` becomes the same `<channel source="metro" …>` text as a user message (origin `channel`), and the session gets the metro tools from an in-process SDK MCP server named `metro` that proxies `tools/list` and `tools/call` over that session. Tool names stay `mcp__metro__*`, so the guard and `noteSent` (`addressed="reply"`) work as before.
- **Approvals**: `canUseTool` sends `notifications/claude/channel/permission_request` with its own 5-letter id (the `PERMISSION_REPLY_RE` alphabet, so that contract now has three sides) and waits for `notifications/claude/channel/permission`; pending prompts, chat `yes <id>`, the page and the expiry are the existing daemon path. `canUseTool` fires for a hook's `ask` even in bypass mode, whatever the SDK's `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` warning says, and every ask is relayed. **Metro's own hook asks nothing since 2026-11-10**: a channel rule on Ask is answered by the daemon as a tool result with an approval id (see `docs/rules/TOOL-POLICIES.md`), so it never reaches `canUseTool`, never counts as a waiting approval in the activity snapshot and never stops chat intake; the answer of a Claude Code prompt never authorizes a metro call. **Only an approval the main thread itself waits on stops chat intake** (`mainAsks` in `runner.ts`, from `options.agentID`; `SessionWatch.admitting`): before 2026-10-31 any `requires_action` stopped it, so one worker waiting for the owner could hold every new message until the answer.
- **One model, the Gateway page's** (Less, 2026-10-02: "the same provider / model system", "allowed model only", "change model anytime"): `metro agent` passes the routed connection's model as `METRO_RUNNER_MODEL` (`currentModel` in `cli/src/route.ts`: the bare id for Anthropic, `<provider>:<model>` for the others, none when no model is picked, which leaves Claude Code's default), and the front and every worker think with it: no `CLAUDE_CODE_SUBAGENT_MODEL`, and `ANTHROPIC_MODEL` is dropped from the session's environment (`runnerEnv`), since a pinned id would keep workers on the old route after a switch. The gateway routes and sets effort per request (see The model gateway), and sends helpers to the route's helper models when it has them, so workers need no model of their own and the allowlist and live switch stay on the main primary. **Only that model is allowed**: right after start the runner writes `availableModels: [model]` and `enforceAvailableModels: true` into Claude Code's flag settings (`applyFlagSettings`, `allowedOnly` in `runner.ts`), so `/model`, the Config tool or an agent's `model` cannot pick another one (2.1.287 refuses with "restricted by your organization's settings"). Not through the `settings` query option: that layer stays beside the one `applyFlagSettings` writes, so the first model stayed allowed after a switch (measured). The metro skill and the guard (orchestrator-only main thread) apply unchanged; `FRONT_RULES` (`rules.ts`) is appended to the system prompt (Settings, Agent SDK setup). The runner runs from `$HOME`, since auto memory is keyed by the cwd.
- **A model change applies live, with no restart**: when the effective primary model of the delivered organization setup changes (the 60 s fetch, or `POST /api/model/sync` after a change on the page; see Organization models), the daemon sends `notifications/metro/model {model}` to the session holding `/mcp` (`switchModel` from `createMetroMcp`, wired through `boot.ts` and `local-mode.ts`; the method name is a contract between `mcp/index.ts` and `sdk-runner/src/link.ts`). The runner moves the allowlist first, then calls `setModel`, one switch at a time (`Runner.switchModel`). The conversation and the session id stay, and Claude Code tells the model its new name in the system prompt. A worker started after the switch uses the new model; one already running finishes on its own (on Anthropic the gateway pins its requests to the new model anyway). The change is made on api.metro.box, so the box cannot refuse it; a runner that is not up loads the new selection from the agent's view of `model.json` at its next start. **Fallback models need nothing from the runner**: the gateway walks the list per request whatever model id the session sends, so a fallback change neither switches nor restarts the session, and the allowlist keeps only the first model.
- **Restart and the ledger**: the session id lives in `~/.metro/agent-session.json` (agent home) and is resumed when its transcript exists. Chat messages pushed but not yet consumed (seen in `user_message_uuids` or in a `command_lifecycle` with `state: 'started'`) are kept in the same file and pushed again after a restart: a message in Claude Code's queue at a kill is lost on resume, and the daemon's ring will not replay it. A local process lock allows only one SDK runner per home and releases on process exit. An initial status-write failure refuses startup before MCP connects. The task ledger in the same file keeps each helper's short `description`, never its prompt, so a restart lists the helpers from before it with their description (not their agent, times or model), and never lists the ledger's own failed-turn and interrupted-input rows as helpers. **A full ledger (200 rows) never ends the session**: it drops the oldest finished row with no notice, then the oldest notice already delivered three times and not waiting on a delivery, and when nothing can go the new worker runs untracked, logged once (2026-11-02: a non-Claude model never echoes the acknowledgment marker, so Emma's ledger filled with exhausted notices and every new worker crashed the runner).
- **Live activity**: `~/.metro/agent-status.json` (0600, bounded, atomic) records real lifecycle events, main-thread status, active tools, worker state, approvals and safe error summaries. `/api/claude/session` returns the parsed snapshot. The Right now full view (`RunPage.tsx`) polls every 2 seconds while open; it shows stopped and stale snapshots explicitly. It retains at most 30 task rows, 20 active tools and 40 events, and of a helper only its one-line Agent `description` (160 characters): never prompts, progress descriptions, thoughts, summaries or tool I/O. An unclassified failure records only its error type name (`errorName`, a plain identifier ending in `Error`, never `Error` itself); the raw error is printed only with `METRO_RUNNER_DEBUG=1 metro agent`, to that terminal, never to a file or the page. It does not stop an individual worker. Terminal remains available for diagnostics; Conversations holds transcripts. `bun run sdk-runner-activity` proves live HTTP updates and chat during a background worker using the real SDK with a free scripted local upstream.
- **Calls** (see Voice calls): call words, typed chat and status notes go into bounded lanes that the runner schedules fairly at observed safe boundaries, with no priority interrupt, timeout restart or blind replay; the SDK gets at most one input it has not consumed yet, and only its exact consumption frees the slot. Hang-up removes call entries still in the host queue; input already handed to the SDK cannot be taken back, so its consumption is still tracked. Queueing input never interrupts a write or answers an approval.
- **Compaction**: Claude Code compacts by itself near the model's window, mid-turn if one message pushes it there. Startup compacts a saved conversation at 80,000 input and cache tokens (`COMPACT_AT`) before ordinary inputs, and the runner compacts at the same threshold after a quiet minute with no input pending, never during a live call, then waits for 40,000 tokens of growth before asking again. **Running workers never hold it back** (compaction is a turn of the main thread only), **and above 120,000 (`URGENT_FACTOR` 1.5) it compacts at the next safe boundary at once, ahead of queued chat** (2026-10-31): Lisa's main thread sat at 88k to 143k tokens on every call, half of them read without the cache, because the old rule (120,000, no running worker, no pending input) never held on an agent that always has workers and messages. Measured 8 to 23 s per compaction; it can take minutes.
- **The store and the Claude Code it runs**: `metro agent` copies `runtime/sdk-runner` into `~/.metro/sdk-runner` (`METRO_RUNNER_STORE`) and runs `bun install` there with `optional = false` and `peer = false` in `bunfig.toml`, plus exactly one of the SDK's platform packages, at the SDK's own version (`claudePackage`: `@anthropic-ai/claude-agent-sdk-<platform>-<arch>[-musl]`, the same pick as the SDK's, musl when Node reports no glibc), about 233 MB. **The runner runs the Claude Code bundled with the pinned SDK** (`METRO_RUNNER_CLAUDE` names the store's binary; without it the SDK finds its bundled one): the SDK and its Claude Code are released together (0.3.N carries 2.1.N), so there is no version gap to watch, and **one number moves both: `@anthropic-ai/claude-agent-sdk` in `packages/sdk-runner/package.json`**, with each Metro release that bumps it. The box has no other Claude Code: the memory routine runs this same binary (see Claude Code on the box). `DISABLE_AUTOUPDATER=1` keeps the bundled binary from updating anything. **One preparation at a time**: `prepareRunner` holds `<store>/.prepare.lock` (created with `wx`, holding the pid; `withLock` in `cli/src/lock.ts`, on the same `takeLock` as the memory routine's lock) for the whole copy and install, so the boot prepare, `metro agent` and the memory routine take turns instead of writing over each other; a waiter polls every 250 ms for up to 20 minutes, and a lock whose pid is dead or that is older than 20 minutes is taken over. **A lock is never left empty** (`takeLock` in `cli/src/lock.ts`): when the pid cannot be written (a full disk) the new file is removed before the error goes on, and an empty lock older than 5 s is taken over. Lisa's disk filled on 2026-10-28: her session failed, the empty lock it left held the next start for 20 minutes. Why the bundled one: the SDK's control protocol is pinned per Claude Code release, so a separately updated `claude` would drift from the SDK (review, 2026-10-02).
- `bun run sdk-runner-check` (`scripts/sdk-runner/run.ts`, on `harness.ts`) boots the daemon's MCP code in-process with a fake train and a temp policy, starts the real runner and Claude Code through this box's gateway, and prints timings for chat, delegation, approvals, calls (including a call cutting into a chat turn), a restart, a crash with a queued message and a compaction. **`SDK_RUNNER_CHECK_ROUTE=key` runs it on the gateway's Anthropic API-key path**: the daemon's gateway in-process with an Anthropic connection holding a stand-in key, and a stand-in upstream (`key-route.ts`) that counts what reaches "Anthropic" (`x-api-key`, no `authorization`, no OAuth beta, no `x-metro-key`) and relays it to api.anthropic.com with the box's Claude login, since a box has no real key to spend; only Anthropic accepting a real key is not covered. `bun run sdk-runner-long` (`long.ts`) is a long day in small: 200 chat messages (questions, acknowledgements, long notes, group chatter, recalls, bursts of three), 20 background workers and a call, and writes the front's context, cost per model, compactions and the react, reply and call timings to `SDK_RUNNER_LONG_OUT`. `bun run sdk-runner-model` (`model.ts`) checks the live switch through the real Model API and gateway: by default against a scripted upstream (`scripted-upstream.ts`, free) on an OpenRouter route, then a model change, a worker, a switch to another provider, a worker there, and a fallback model that takes over when the first one answers 429, printing the effort each request reached upstream with (`low` for the front, `max` for workers, per-turn ones included); with `SDK_RUNNER_CHECK_ROUTE=key` with real Claude on the API-key route (Sonnet 5.5, Haiku 4.5, back to Sonnet 5.5, then a recall of what was said before both switches). It prints the models each step reached upstream, the session ids (one) and the restarts (none). These are outside the gate and cost a few dollars (the long run about ten, the real model check about $0.55).
