# Stations

Moved out of `CLAUDE.md` on 2026-11-10 to keep that file short. These rules bind exactly like `CLAUDE.md`: read this file before changing anything in this area, and keep it up to date with the code.

- **XMTP single writer:** only one process may write an MLS inbox. A second burns the 10-installation budget. So `metro serve` refuses a second instance, and two boxes must never run the same agent. The db3 path is home-relative.
- XMTP accounts are ZeroDev Kernel smart accounts on Base (`smart: true`); older plain-key accounts cannot hold a name. A name claim is page-only and permanent.
- **WhatsApp:**
  - `connectionReplaced` is terminal, so a double run does not loop into a 463 time lock.
  - **Only `tctoken` and `lid-mapping` are persisted** (`token-store.ts`), because a 1:1 send without the contact's token gets `ack error 463`. Do not persist other Signal key types: `creds` is never written back, so half a Signal state is worse than none.
  - **A message key is never synthesized.** Keys come verbatim from a per-account LRU filled from every upsert and every send; a group key needs the original `participant`. An unknown message fails loud (`whatsapp_unknown_message`).
  - **The send verdict is read from `sock.ws` (`CB:ack,class:message`)**, which bypasses Baileys' buffered emitter. 463 throws `whatsapp_account_restricted`. No ack in the window counts as sent.
  - `sock.end()` must be awaited. Never run a second Baileys client on live credentials to test.
  - **The train reports each account's live state** (`reportsStatus`, `ConnectionWatch` in `connection.ts`), never a saved flag (the old `connected: true` came from `sock.user`, which stays set after a logout; Lisa, 2026-10-21): `connected` on Baileys' `open`; a 401 (`DisconnectReason.loggedOut`) and the `conflict type=device_removed` stream error (whatever its code: without one Baileys files a conflict under 440, `connectionReplaced`) are `logged_out` until paired again, and never reconnect; `connectionReplaced` and a failed (re)connect are `disconnected`; any other close is `connecting` with the reason, and `disconnected` once it has not come back for 3 minutes (`RECONNECT_GRACE_MS`, the first drop's time kept through repeated drops). Open is not trusted alone: a websocket that is not open (`sock.ws.isOpen`) or no frame for 90 s (`SILENT_MS`; Baileys pings every 30 s) reads `connecting`. It is checked every 30 s and on every read, and each change of state writes one stderr line (`whatsapp[<account>] state <from> -> <to>: <reason>`, the account id only), which the daemon logs as a warning.
  - **Pair again** (`pairAgain: {identity: 'phone'}`): the same QR or pairing code as attach (`WhatsappLogin` with `expect`), and only the same number: a pairing code for another number is refused before WhatsApp is asked, and a QR scanned by another phone is logged out again (`sock.logout()`) and stored nowhere. Only `phone` and `credentials` change; the token, names, history and channel files stay, since they belong to the WhatsApp account, not the linked device. A link replaced while it still worked stays in the phone's Linked Devices until removed there.
- Telegram user account (`telegram`): the session is a full-account secret, single writer, ToS risk.
- **Threema:** Gateway ID in end-to-end mode only; the private key never leaves the train. The callback checks the MAC first; a down train answers 503 (Threema retries), a refusing train 400 (it stops).
- **Outlook** (`packages/outlook`, Microsoft Graph): attach is interactive and **signs in through the browser by default**: the OAuth 2.0 authorization code flow with PKCE (S256), public client, on the `/common` authority (`browser.ts`, `OutlookBrowserLogin` in `login.ts`, driven by `stations/attach-browser.ts` step `browser`). `start` answers `authorizeUrl` (state and verifier held by the attach session, 15 min); **one Connect click does it all on the web** (Less, 2026-10-31: the form has no field left): the click opens an empty tab at once (`inNewTab`, so no popup blocker), starts the attach session and sends the tab to that link (`startInTab` in `lib/use-attach.ts`, for any form with a `provider`; the phone keeps the two steps), and the page remembers `{state, box, agent, attach session}` in `metro.outlook.pending` (the key name stayed when Gmail joined); Microsoft redirects to **`https://metro.box/?code=…&state=…`** (registered under the "Mobile and desktop applications" platform of the app, so the daemon may redeem the code without an Origin; `METRO_OUTLOOK_REDIRECT` overrides it, e.g. `http://localhost:5173/`), and any page load with that query is handled before routing (`api/sign-in-return.ts`, `SignInReturn.tsx`, shared with Gmail): it posts `step {code, state}` (or `{state, error, errorDescription}`) to that box's attach session, which checks the state, redeems the code, checks the mailbox with `GET /me` and stores it; the original tab keeps polling and flips on its own. **Why not the device code flow**: the first real sign-in (Anderra, 2026-09-24) failed with AADSTS530035, the tenant's security defaults block device code as a phishing risk. **The device code stays as the fallback** ("Use a code instead", `step {mode: 'device'}`): the page shows the code and a link to microsoft.com/devicelogin and the driver polls. A daemon on beta.175 answers `start` with step `device` directly, which the page still renders. Microsoft refusals become sentences (`failureOf`): consent (AADSTS65001, 90094, 90095) names the `/organizations/adminconsent` link, a policy block (530035, 53003) says the company blocks that sign-in. **The client id is Metro's own multi-tenant public app "Metro Mail"** (`OUTLOOK_CLIENT_ID`, in Stage Labs' tenant "Default Directory", publisher not verified yet, so a company tenant may need its admin to approve it once); `METRO_OUTLOOK_CLIENT_ID` overrides, and an empty id refuses with "Outlook is not set up on this Metro yet". A mailbox is attached once per box (409). The train keeps the rotating refresh token, the delta link and the ids it delivered in its own 0600 file (`~/.metro/outlook-state-<account>.json`, `OUTLOOK_STATE_DIR`), since trains never write `agent.json`; refresh is single-flight. It polls **the Inbox only** (Junk is never read) with Graph delta every 30 s (`METRO_OUTLOOK_POLL_MS`); the first sync records the delta link and emits nothing. Lines are `metro://outlook/<account>/<conversationId>` (`/`, `+`, `%` escaped), senders `…/user/<address>`. **Automated mail is skipped by default** (a no-reply style sender, `List-Unsubscribe`, `Auto-Submitted` other than `no`, `Precedence: bulk|list|junk`; `includeAutomated: true` in the account config keeps it). **Each delivered mail carries `sender_verified`**: true only when Microsoft's topmost `Authentication-Results` (or its own `ARC-Authentication-Results`) shows `dmarc=pass`, or `compauth=pass`, for the From domain, or the mail is internal (`X-MS-Exchange-Organization-AuthAs: Internal`); `trust.ts` decides. Verbs: **`send` on an address line (`metro://outlook/<account>/<email address>`, any resource holding `@`, which a conversation id never does) starts a new email**: a draft with `subject` (the `send` tool's optional argument, forwarded by the daemon; else the text's first line, 255 chars) and a Text body, files attached, then `/send`; the answer carries the new thread's `line`, which the daemon appends to the tool result, and a `reply` or `reply_to` on an address line is refused. `send` on a conversation line is reply-all to the conversation's latest mail, `reply` answers the named message, both through `/reply`/`/replyAll`, or a draft plus attachments plus `/send` when files go along; files are inline Graph attachments **up to 3 MB each**, refused above that before any draft exists. `read` implements every filter: `query` is Graph `$search` (with `from` folded in; the rest narrow what it found, since Graph refuses `$search` with `$filter`), otherwise one `$filter` newest first; `message_id` returns the full mail, saves its files and marks it read (nothing else marks mail read). **The daemon still takes an optional mailbox** (`mailbox`), though the page no longer shows the field (Less, 2026-10-31: an optional field the person must understand is not worth its place): it rides as `login_hint` (with `prompt=select_account` kept), and after the code (or device code) is redeemed, a `GET /me` whose `mail` and `userPrincipalName` both differ from it fails the attach with "You signed in as X, not Y. Nothing was connected." and stores nothing (`verifyMailbox` in `me.ts`). Why: the first live connect at Anderra (2026-09-24) picked the admin already signed in to Microsoft in that browser, so Andy's agent got Fabien's mail. A daemon before this change ignores the field.
- **Outlook sign-in setup trap (2026-09-24, first live connect of andy@anderra.ch):** the Metro Mail app's `https://metro.box/` redirect must exist ONLY under `publicClient.redirectUris` in the Entra manifest. The new Entra UI filed it under Web, and even after `web.redirectUris` was emptied, a leftover entry in `web.redirectUriSettings` kept Microsoft treating the code redemption as a confidential client (AADSTS7000218, `client_secret` required). Emptying `redirectUriSettings` fixed it. Admin consent for Anderra was granted by an admin account at the first sign-in.
- **Gmail** (`packages/gmail`, the Gmail API; Less, 2026-09-28, for admin@ and fabien@snapshot.org; setup in `docs/GMAIL.md`): modeled on Outlook, and the two share their mail code in core (`stations/mail` for the MailItem, lines, envelope, summaries, read query, outgoing files, `refusalOf` and the poll loop; `stations/mail-text` for HTML to text; `stations/mail-trust` for automated mail and `Authentication-Results`; `stations/oauth` for PKCE, `BrowserSignIn`, `TokenKeeper`, `postForm`, `tokensOf`, `parseMailbox`, `SignInError`), and one daemon driver (`stations/attach-browser.ts`). **Google has no Metro-owned app: each Workspace brings its own OAuth client** (an Internal app, Web application type, redirect `https://metro.box/`, `METRO_GMAIL_REDIRECT` overrides), so the connect form takes `clientId` and `clientSecret` (the daemon still takes an optional `mailbox`, which the page no longer shows); the secret is stored in the account config next to the refresh token, and a Web client needs it to redeem and to refresh. The authorize link asks `access_type=offline` and `prompt=select_account consent`, so a refresh token always comes back, with PKCE on top. Scopes are `gmail.readonly` and `gmail.send` only (no `gmail.modify`): the station never changes the mailbox, so `read` with `message_id` does NOT mark mail read, unlike Outlook. The mailbox is checked with `GET /gmail/v1/users/me/profile` (a 403 there usually means the Gmail API is not enabled). Inbound: `users.history.list` (`historyTypes=messageAdded`, `labelId=INBOX`) every 30 s (`METRO_GMAIL_POLL_MS`) from a `historyId` cursor kept in `gmail-state-<account>.json` (`GMAIL_STATE_DIR`) with the delivered ids; the first sync reads the cursor from the profile and emits nothing, and a 404 (cursor too old) starts over the same quiet way. No Pub/Sub. Lines are `metro://gmail/<account>/<threadId>`, senders `…/user/<address>`. **`sender_verified` is true only when the topmost `Authentication-Results` is Gmail's own (`mx.google.com`) and shows `dmarc=pass` for the From domain, or a `dkim=pass` whose `header.i`/`header.d` domain is exactly the From domain** (a domain without a DMARC record), never when its `header.from` names another domain. Automated mail is skipped like Outlook's. Verbs: `send` on a thread line is reply-all to its latest non-draft mail (own mail: back to its recipients), `reply` answers the named message's sender or `Reply-To`, `send` on an address line starts a new email (subject rules as Outlook, result carries the new `line`); every send is one MIME message (text/plain UTF-8 base64, `multipart/mixed` with files, `In-Reply-To` and `References` on answers) posted to `/upload/gmail/v1/users/me/messages/send?uploadType=multipart` with `{threadId}` metadata, files up to 25 MB in total, refused before any call. `read`: a `query` is Gmail search syntax with `from:`, `after:`/`before:` (epoch seconds) and `is:unread` added; a thread line without a query reads `users.threads.get` and filters locally; `message_id` returns the full mail with its files saved. `approvals: false`, like Outlook.
- **Webhook:** the url names `webhookId` (random digits), never `account_id`, which would leak the agent id. The whole url is the credential; anything else is a flat 404. The route must stay before the monitor router. **Attaching a webhook is refused on a local daemon today** (400, it needs a public url), so the code path is dormant. **The agent's `list_accounts` never carries a url with a secret in it**: `gatherAccounts` (the MCP path) drops the webhook `endpoint` and Threema's `callback`, while the page's `/api/agents` keeps them.
- **`read` is the one verb for history and lookups** (`mcp/read-tool.ts`): `line?`, `account?`, `limit?`, `before?`, `since?`, plus `until?`, `query?`, `from?`, `unread_only?` and `message_id?` (one message in full; its files come back with a `local_path` and a `/attach` grant url, like inbound media). The daemon forwards every argument unchanged (camelCase on the wire) and adds `ignored: [...]` for each filter the station does not declare in `readFilters`, so existing stations behave as before. A read with no line needs an `account`, is scoped like any account call (`scopeDenied`), and is refused unless the station declares `account` in `readFilters`.
- **Typing indicator** (`typing {line}`, a message verb, group `write` so it follows the channel's Allow/Ask/Block like any write; Less, 2026-09-26): one call sends one signal and the network clears it by itself (about 5 s on the Telegram bot `sendChatAction`, 10 s on Discord `POST /channels/<id>/typing`, 25 s on WhatsApp `composing`) or when a message arrives. Metro never repeats or stops it, and nothing calls it automatically: it is the agent's choice. The orchestrator rules (`packages/cli/skills/METRO.md`, Typing) recommend calling it whenever the agent is about to send on a line within the next 10 seconds. Only WhatsApp, the Telegram bot and Discord declare it; others refuse before any train call.
- **The daemon checks a call's verb against the station's `messageVerbs`**: `dispatchMessageTool` refuses an undeclared verb before any train call, naming the verbs the station supports (`test/message-verb-gate.test.ts`). Trains do not refuse verbs themselves. A train action that no declared verb, group op, tool, profile or account route names is dead code: delete it.
- Discord-bot verbs: all seven and group ops. Voice was removed. An inbound Discord edit reaches `metro tail` only; the channel relay routes `msg`, `react` and `system`.
- XMTP has no push: no FCM, no `METRO_CTRL:` control DMs. Every inbound DM goes through the allowlist. **An XMTP sender id is the inbox id (64 hex), not the wallet address**, so an address typed into the allowlist never matches (Less, 2026-09-26: Emma got nothing until the inbox id was listed). XMTP declares `resolvesSenders`: the allowlist's lookup (`resolve_sender`, `packages/xmtp/src/resolve.ts`) takes a `0x` address or a `.eth` name (read on Base through the basename registry) and answers the inbox id from `fetchInboxIdByIdentifier`. Its own tools are the Stage ones (`close_channel` with `removeInboxIds`/`removeSelf`, `set_channel_metadata`, labels); there is no `create_channel`, an agent uses `create_group` then `set_channel_metadata`.
- **A Stage frame goes with XMTP `send`, as `frame: {widget, title?, description?}`; there is no frame tool** (Less, 2026-10-01: no new tool just for this; beta.232's `send_frame` is gone). XMTP declares `sendsFrames`, and `handleSend` refuses a `frame` on any other station before a train call. The train's `send` builds the content with `buildFrameContent` (`frames.ts`) before it sends anything, sends the text first, then `stage.box/frame:1.0` (`FrameCodec` in `codecs.ts`), and answers with the frame's message id. `widget` is OpenAI ChatKit widget JSON (an object with a `type`, or a JSON string of one, 64K characters at most), and a missing title or description is taken from the first `Title` and text node. **An optional `source: {url}` names the node that serves the widget live** (beta.286, issue 251): `buildFrameContent` takes only an https URL of at most 2048 characters (Stage's own cap), trims it and sends it with the frame. **Stage then sends that frame's actions to the node, not to the chat** (Stage 8ca07e10, its `NODES.md`, Frames in chats): only a tap or Refresh in the frame's three-dot menu calls the node, once the chat is accepted, and the node's reply replaces the frame on that device only, so no message reaches the agent. **Only an action with ChatKit's `"handler": "client"` still comes to the chat** as a `frameAction`, as every action of a frame without `source` does (`frame.open`/`frame.back` stay in Stage). The train passes the widget as given, so `handler` reaches Stage; the `frameAction` Stage sends back has no `handler`. A node needs no Refresh button. Stage's Add to dashboard on that frame adds a live widget for that URL that remembers the frame, so its client actions still reach that chat. The send schema (`mcp/frame-schema.ts`) and `packages/cli/skills/STAGE.md` tell the agent this. **Or `frame: {screens, start, title?, description?}`** (#101): up to 50 screens by id (1 to 120 characters), each a widget or `{title, widget}`, 64K characters for all of them, never with `widget`; `start` is required (JSON lists number keys first, so "the first screen" is not reliable) and, like every `frame.open` action's `payload.screen`, must name a screen; the summary comes from the start screen. Stage moves between them with `frame.open`/`frame.back` actions, client side, and adds the current `screen` to every other action's payload. Stage shows the frame itself in the chat (the start screen), at image size, 400 x 400 at most, clipped with a fade when taller; a tap opens it full screen, and its buttons work only there (Stage 133efed9). A tap there comes back as `stage.box/frameAction:1.0` `{frameId, action: {type, payload?}, label?}`, emitted as a reply to the frame (`event.replyTo` = the frame id, `reply_to_self` when this train sent it) with the text `Frame action: <type> <payload JSON> (tapped "<label>")`. Both codecs are registered; `read` shows them as `[frame]` and `[frameAction]`, like `[poll]`.
- **A Stage wallet card goes with XMTP `send` too, as `wallet: {type, content}`** (issue #130): `walletSendCalls` and `transactionReference` (`xmtp.org`, `WalletSendCallsCodec` and `TransactionReferenceCodec` in `codecs.ts`), `signatureRequest` and `signatureReference` (`metro.box`), JSON encoded exactly as Stage sends them, with Stage's fallback text. `buildWalletContent` (`wallet.ts`) checks the type and the keys Stage requires before anything is sent; `content` is passed as given (Stage checks the rest). It is sent after the text and the frame and answers with the card's id; `handleSend` refuses it on a station without `sendsFrames`, and an approval prompt shows its JSON. Sending one moves nothing: the person pays or signs in Stage. The node-sdk's own `sendWalletSendCalls` is not used, since its call metadata is a string map and Stage reads `amount` as a number. The two `xmtp.org` codecs are not registered, and both types stay in `SILENT_TYPES`, so a receipt Stage posts after a payment does not reach the agent.
- **XMTP `delete` sends the XIP-76 request Stage sends** (`xmtp.org/deleteMessage:1.0`, protobuf `message_id = 1`, no fallback, `shouldPush: false`, `encodeDeleteMessage` in `codecs.ts`), so Stage and other XMTP apps show "Message deleted". node-sdk 6 has no delete call, so the train hand-encodes it like Stage web. It deletes only this account's own messages in the line's conversation: another sender's message, a group update or a delete request is refused before any send. This installation keeps the original in its own db3, so `read` on this box still shows it. **Stage deletes its own types (frames, frame actions, polls) with `stage.box/deleteRequest:1.0` `{messageId}`** instead (Stage 61b8481d, issue #106), since XMTP only deletes the types it knows. The train registers its codec, never emits it inbound (`SILENT_TYPES`), and `read` drops the request rows and shows the target as `[deletedMessage]` when the request comes from the target's sender or a current super admin (`delete-requests.ts`), as libxmtp does for XIP-76. There is no `edit`: Stage has no edit content type and XMTP's edit (XIP-77) has not shipped (Less, 2026-09-30, issue #85).
- **A train builds its events with `@metro-labs/core/stations/train-events`** (`emitInbound`, `reportAttachment`, `attachmentSavedEvent`, `attachmentFailedEvent`, `selfUri`). Never hand-build an `attachmentSaved` envelope; it carries `attachmentPath` (the only path field the daemon reads) and `size` when the saved file reports its bytes. Train events carry no `kind` and no top-level `account`; the account rides in `payload.account`. `selfUri()` is `METRO_SELF_URI`, which the supervisor always sets. The boot banner and empty-accounts exit are `announceAccounts` (`core/stations/train-boot`); a client-per-account train (telegram, whatsapp) is one `runClientTrain` call. Account configs carry no `owner`.
- **A train maps verbs through `makeStation`'s optional `normalize`**, applied only to an action it has no handler for; the one shared normalizer is `messagingAliases` in `core/stations/messaging-normalize` (reply to send, unreact to react, with a per-station removal marker). A station's read handler is named `read`. Trains always ship with the daemon from the same install, so the wire between them may change freely.
- **Account stores come from `makeAccountStore({ prefix })`** (`core/stations/account-store`): the file is `<PREFIX>_ACCOUNTS_FILE` or `~/.metro/<prefix>-accounts.json`, the same rule as `materialize.ts`, and it checks missing and duplicate ids. **Every line carries its account segment** (`metro://<station>/<account>/…`); there is no implied `default` account.
- **Receiving is never held for a profile lookup**; anything costing a network call is behind the `get_profile` tool.
