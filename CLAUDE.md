# CLAUDE.md

The story behind these rules, with dates and incidents, is in `docs/HISTORY.md`. Search it before changing a load-bearing behaviour. Design notes: `docs/SETUP.md`, `docs/ISSUING-SERVERS.md`, `docs/MICROSOFT-365.md`.

## What Metro is

A relay between chat networks (XMTP, Telegram, Discord, WhatsApp, Threema, an Outlook or Gmail mailbox) and Claude Code, run on the user's own machine ("box") by `metro serve`. One daemon serves MCP over HTTP, a model gateway and an admin API, and supervises one subprocess ("train") per station.

Inbound: network message, station, in-process bus, MCP channel notification. Outbound: agent tool call, station verb, network. `api.metro.box` (`apps/api`, Fly) runs no station: sign-in, the agent list, the organization's model setup (see Organization models), AWS launches, resizes and deletions, the CloudWatch usage charts, `/health`. `mcp.metro.box` (`apps/mcp`, Fly) is the one MCP endpoint every agent uses for its organization connectors (see mcp.metro.box below). The app (`apps/app`: `https://metro.box` on Netlify, and the same code on phones) manages one box at a time. **Every daemon is local. There is no hosted mode.**

**One box is one agent.** The daemon creates `~/.metro/agents/agent.json` (`{version: 1, id, name?, key, stations[]}`; an old file's `owner` and `connectors` keys are ignored and dropped at the next save) at first boot. A second agent, or an import of another agent id, is 409. The name a person sees is the box's row on metro.box.

**An agent may have no server** (2026-10-23, see Access keys and agents without a server): an agent row of kind `remote` has no box, no daemon and no host. It exists only to give a person's own Claude Code, or any MCP client, the organization's connectors through mcp.metro.box with an access key; any agent, with a server or not, can have access keys. Everything said here about a box, a daemon or a station is about agents of kind `box`.

**Vocabulary:** the page says "channel"; code, files, wire and this document say `station`. Do not rename `station` identifiers, JSON keys or `metro://<station>/…` lines without a migration: they are on-disk and wire contracts.

## Monorepo layout

Bun workspaces, `bun@1.4.0` minimum (Bun 1.3.9 leaks the upstream socket of an aborted relayed stream). `ci.yml` and the Dockerfile pin the same version.

- `packages/core` (`@metro-labs/core`): the kernel every process shares (`log`, `events`, `ids`, `protocol`, `lines`, `stations/*`, …). **It imports nothing from the workspace, has no HTTP and no policy, and is the only workspace package a station may import.** Import it through its exports map (`@metro-labs/core/log`, `/events`, `/stations/types`, …).
- `packages/http` (`@metro-labs/http`): request auth and answers (`cors`, `api-http`, `api-error`, `workos-token`, `return-to`, `mode-api`), `sigv4`, the one AWS request signer (the api's EC2 and CloudWatch calls, the daemon's CloudWatch readings), and `agent-signature`, the one signer and checker of an agent's requests to api.metro.box and mcp.metro.box (see Organization connectors), plus the connector helpers `apps/api` and `apps/mcp` share (`connector-policy`, `connector-url`, `connector-mcp`, `connector-oauth`, …). Imports only `core`. It exists so heavy crypto and HTTP deps never reach a station process. `stringOf` (next to `bodyField` in `api-http`) is the one string-or-empty reader for the daemon; do not add a local copy.
- `packages/connectors` (`@metro-labs/connectors`): the organization connector runtime that `apps/api` and `apps/mcp` share: sealed secrets (`secrets`, `model`), OAuth refresh with imported grants and their uncertainty records (`refresh`, `imported-refresh`), the credential revision and policy layers (`revision`), the safe egress (`egress`), tool listing and its redaction (`catalogue`, `catalogue-auth`), the connector, assignment, agent key, access key (`db/agent-tokens`), nonce, approval (`db/mcp-approvals`) and call tables with their store functions (`db/*`), the connector keys (`connector-keys`), and agent request authentication (`agent-auth`). It imports only `core` and `http`, has no HTTP routing, and never reaches the daemon or a station.
- `packages/inference` (`@metro-labs/inference`): the model router (providers, backups and holds, effort, tool search fitting, usage), moved out of the daemon on 2026-10-26 so gateway.metro.box can run it too (`docs/GATEWAY-SERVER.md`). It imports only `core` and `http`. Since beta.324 only gateway.metro.box (`apps/gateway`) runs the router; the box relays (`gateway/relay.ts`) and uses only `forward` for that. The router's tests live in `packages/inference/test` (with `model-fixture.ts`, which a few daemon tests import by path). It is staged into the box runtime with `core` and `http` (`stage-runtime.mjs`). Below, `gateway/<file>` means `packages/inference/src/<file>` for the router files; the box's own model files (`org-models`, `effective`, `model-api`, `model-leftovers`, `relay`) stay in `apps/daemon/src/gateway/`.
- `apps/api` (`@metro-labs/api`, api.metro.box): WorkOS sign-in, organizations and members, the agent list, the AWS launcher, the operator pages, `/health`. The Postgres schema file and every migration live here (`apps/mcp` uses the same database). No station, no MCP, no gateway.
- `apps/gateway` (`@metro-labs/gateway`, gateway.metro.box): the model router every agent and access key will go through (`docs/GATEWAY-SERVER.md`); see gateway.metro.box below.
- `apps/mcp` (`@metro-labs/mcp`, mcp.metro.box): the one MCP endpoint for organization connectors (`tool_search`, `tool_call`), which every agent reaches through its daemon's `metro` server, and the approvals its daemon relays. Design: `docs/MCP-SERVER.md`; see mcp.metro.box below.
- `apps/daemon` (`@metro-labs/daemon`, what `metro serve` runs), one folder per domain:
  - `boot/` (boot, crash guard, paths, local owner), `routes/` (the HTTP server and mount order, `local-mode` which wires every API's deps, `bearer`, `threema-callback`).
  - `agents/` (agent file, key map, scope, accounts API, bundle), `stations/` (registry, attach, materialize, supervisor, train calls, runtime deps), `connectors/` (enrollment, the agent key, the signed api.metro.box client), `mcp-server/` (the client of mcp.metro.box: the MCP token, the approval relay, the approvals already posted in chat, and the `tool_search`/`tool_call` forwarding).
  - `mcp/` (MCP server at `/` and `/mcp`), `channels/` (bus events to `notifications/claude/channel`), `gateway/` (the box's model setup, the Model API and the wiring of `packages/inference` at `/gateway`), `monitor/` (`/api/tail`).
  - `claude/` (transcripts, memory, settings, skills, setup and hooks, session watcher, login), `terminal/`, `files/` (attachments, uploads), `net/` (tunnel), `server/` (control, machine, update, owner, cloudwatch), `voice/` (live Stage calls, see Voice calls).
- `apps/app` (`@metro-labs/app`): metro.box and the phone app, one Expo app (Expo Router, React Native, react-native-web, `@stage-labs/kit`), like Stage's `apps/stage`. Web is the Expo web export on Netlify; Android and iOS run the same code in a dev client. Platform files (`*.web.tsx`) only where the web and the phone must differ.
- `apps/bundler` (`@metro-labs/bundler`, bundler.metro.box): a Cloudflare Worker, copied from Stage's `bundler.stage.box` (`apps/proxy/src/bundler.ts`, `branchChannel.ts`). `/<branch>` hands the dev client that branch's latest EAS Update (channel = `channelKey(branch)`, the one `scripts/app/channel-key.mjs` uses, with the client's `expo-runtime-version` and `expo-platform`); a browser is sent to `/preview-launcher.html`, which the Worker serves from `apps/app/public`. `/` is `main`. Deployed by Cloudflare Workers Builds (Worker `metro-bundler`, root `/`, deploy command `bun --filter @metro-labs/bundler deploy`); `bundler.metro.box` is its Custom Domain (`wrangler.toml`), so the deploy makes the DNS record and the certificate.
- `packages/client` (`@metro-labs/client`): the app's logic without React: the api.metro.box and box API clients, sign-in, the route grammar, the `.metro` export format. Storage, the address and the api base are seams set by the app (`platform.ts`, `configurePlatform`).
- Stations: `packages/{xmtp,telegram-bot,telegram,discord-bot,whatsapp,threema,outlook,gmail,webhook}`. Each exports `.` (`src/station.ts`) and `./train` (`src/index.ts`).
- `packages/cli`: `@stage-labs/metro`, the CLI. It also ships, as plain files, the Claude Code hooks (`hooks/`) and the `metro`, `stage` and `memory` skills (`skills/`); see Claude Code hooks and the connector tools.
- `packages/sdk-runner` (`@metro-labs/sdk-runner`): the Agent SDK runner that `metro agent` starts, the only way the agent runs (see The Agent SDK runner). It imports only `core`, and it is staged into the CLI's `runtime/sdk-runner`, never into Metro's store, because it runs as the agent.

**Import law** (convention, reviewed by hand; `bun run madge` only fails on circular imports, it does not check domains):
- A domain imports `core`, `http` and other domains only at named seams: `agents/scope`, `stations/registry`, `stations/train-call`, `files/attach-serve`.
- `agents/` and `stations/` never import `mcp/`. Their deps are injected from `boot.ts`.
- Nothing imports `routes/` except `boot/`. Known exceptions today: `stations/materialize.ts` and `stations/supervisor.ts` import `trainsDir` from `boot/paths`, and `mcp/index.ts` imports from `routes/http`.
- `mcp/` imports `channels/`, never the reverse.

**Station naming:** `telegram` is the user-account station (MTProto), `telegram-bot` is the Bot API one. `outlook` is a Microsoft 365 or Outlook.com mailbox, `gmail` a Gmail or Google Workspace one. Lines, account files (`telegram-bot-accounts.json`, `outlook-accounts.json`, `gmail-accounts.json`) and env vars (`TELEGRAM_BOT_*`, `TELEGRAM_*`, `DISCORD_BOT_*`, `OUTLOOK_*`, `GMAIL_*`) follow these names. There is no LINE station; a leftover `line` account crashes `materialize.ts`.

## The CLI and publishing

- **`@stage-labs/metro` (`packages/cli`) is the only published package.** Everything else is `private: true`.
- It ships `dist`, the staged `runtime`, `hooks` and `skills` (its `files`), `bin.metro` is `dist/cli.js`, `engines.node >= 22`. **It uses no Bun API and its shebang is `node`.** Do not import `Bun.*` there. It has no `dependencies`.
- **Publish only as a prerelease on the `beta` dist-tag.** A `latest` publish would roll out to every box. `publishConfig.tag` is `beta`, and the workflow still passes `--tag beta` explicitly.
- Publishing is the manual `Publish @stage-labs/metro` workflow (`.github/workflows/publish-cli.yml`, `dry_run` input). It builds first, since `dist` is gitignored and a bare `npm publish` ships an empty package. `NPM_TOKEN` must be an npm automation token (a personal one gets 403 for 2FA).
- **`metro update` picks the highest version across all dist-tags, never `latest`** (`latest` is stuck at `beta.0`, so trusting it would downgrade). `newestOf` and `isNewer` are pinned in `test/version.test.ts`.
- Commands: `serve`, `service install|uninstall|status|root-upgrade`, `stop`, `tail [agent-id]`, `whoami`, `agent [--prepare]`, `task submit|status|finish`, `memory [skill file]`, `update [--check]`, `version`. The CLI talks only to the daemon on this machine. There is no `metro claude` and no `metro voice` (2026-10-15).
- **`metro serve`** runs the daemon from a per-user runtime store (`~/.metro/runtime`, `METRO_RUNTIME_STORE` overrides) through a one-line shim `<store>/server.ts`, so a moved daemon package never strands a box. It always uses Tailscale Funnel and refuses to start without a running Tailscale. `--owner` (an organization id) is needed until `<agents dir>/.owner` exists. **A wallet `--owner` is accepted and ignored, never refused**: every installed systemd unit and launchd plist still carries the wallet it was installed with, and a refusal would crash-loop those services. It runs only from the staged runtime (a `stations.json` manifest is required; the bare-checkout path is gone). `metro service install --user metro` is how a box is installed (see Three users on every box).
- Daemon exit 75 means respawn (Update, Restart). Exit 76 means park (Stop): the parent holds the port with a stub answering `/api/mode` with `stopped: true` and `POST /api/start`.
- **The runtime store installs only the vendor SDKs of the stations in use.** `prepareRuntime` copies the staged sources and runs `bun install` only when the generated `package.json` changed. A station attached later installs its SDK from the daemon side (`stations/runtime-deps.ts`). Both writers produce byte-identical `package.json` files; keep them so.
- **The sync code that runs is the long-lived PARENT's, not the new package's.** A box whose `metro serve` started on an old CLI keeps old sync logic through every update until `systemctl restart metro`. The page's Restart only restarts the child.
- **`headlessEnv` in the CLI is the launch environment of `metro agent` and `metro memory`**, and its lines print as `metro agent:` or `metro memory:`. When the daemon is serving, it sets `ANTHROPIC_BASE_URL` to the gateway and `ANTHROPIC_CUSTOM_HEADERS=x-metro-key: <key>`. **It never sets `ANTHROPIC_AUTH_TOKEN` while Claude Code has its own login**, because a credential variable replaces the claude.ai login. With no login at all it uses the agent key as a stand-in credential.
- **`headlessEnv` turns MCP tool search on (`ENABLE_TOOL_SEARCH=true`) for every route** (`toolSearchEnv`; a value already set wins). Claude Code turns it off by itself for a custom `ANTHROPIC_BASE_URL`, since most proxies do not forward `tool_reference` blocks, and then loads every connector schema at start (Tony, 2026-09-27: MCP tools took 133.7k of a 200k window). `ToolSearch` is Claude Code's own tool, run on the box, so every model gets the same tool, name and syntax, and the gateway does the API's part for every route (see The model gateway). Measured 2026-09-27 on 2.1.282 with a real `claude -p`: tools deferred with `true` even for a model id Claude Code does not know (`openrouter:openai/gpt-5.2`). `react`, `typing`, `send` and `reply` carry `_meta: {"anthropic/alwaysLoad": true}` (`ALWAYS_LOADED` in `mcp/tool-catalog.ts`), so the orchestrator never needs a ToolSearch before answering a message.
- **`headlessEnv` gives the prompt cache one hour when it goes through the gateway** (`cacheTtlEnv`: `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h`; a value already set wins). Claude Code picks the TTL by itself ("1 hour on a Claude subscription, 5 minutes on an API key"), and the agent key standing in as its credential reads as an API key, so every chat message after five quiet minutes wrote the whole conversation to the cache again (measured 2026-10-23 on 2.1.287: `cache_control: {"type":"ephemeral"}` without `ttl`; with the variables, `"ttl":"1h"` and the `extended-cache-ttl-2025-04-11` beta). Anthropic gets both as sent; Routeway gets neither (`routewayBody`, `routewayHeaders`), as before; Bedrock drops the `ttl` for the daemon's life if it refuses it; Codex never had them.
- **`headlessEnv` turns on Claude Code's gateway hint headers when it goes through the gateway** (`CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` in `gatewayEnv`; a value already set wins). Claude Code then sends `x-claude-code-request-class` (`main`, `subagent`, `compaction`), `x-claude-code-compaction` (`auto`, `manual`), `x-claude-code-prompt-id` and `x-claude-code-agent-type` (measured 2026-10-23 on 2.1.287; without the variable a custom `ANTHROPIC_BASE_URL` gets none of them), and the gateway reads the request class to send a compaction at low effort (see Effort policy). They reach Anthropic and Routeway with the other forwarded headers.
- **`headlessEnv` switches off Claude Code's prompt for a shell `-c` script that runs `rm`** (`CLAUDE_CODE_DISABLE_INLINE_SHELL_RM_PROMPT=1`, `rmPromptEnv`, unless already set; `0` keeps the prompt). Claude Code asks before a `bash -c` script it cannot check for `rm` (one built from variables, for example) even in bypass mode, and those prompts from workers reached the owner's chats (measured 2026-10-09 on 2.1.289; Less: "make it the default for any agent"). **Only the launch environment can set it**: Claude Code ignores this key in every settings file ("this key can only come from the environment Claude Code is started with, not from any settings file").
- `metro tail` prints only event JSON on stdout (status lines go to stderr) because Monitor treats each stdout line as an event.

## Claude Code hooks and the connector tools (no plugin since 2026-10-14)

- **There is no Claude Code plugin.** The hooks and skills are committed plain-Node `.mjs` and Markdown in the CLI package (`packages/cli/hooks`, `packages/cli/skills`, both in `files` of its `package.json`), no build, no deps. `hooks/guard.mjs` is a PreToolUse guard (orchestrator-only main thread; unparsable payload is denied) and applies the owner's tool policy to `mcp__metro__*` calls (`hooks/policy.mjs`, see Tool policies). `hooks/session-start.mjs` injects the orchestrator rules from the `metro` skill, else from the CLI's `skills/METRO.md`. `skills/METRO.md` (skill `metro`) is the one source of those rules; `skills/STAGE.md` (skill `stage`) tells an agent how to use Stage channels over the XMTP station and is installed on every box, XMTP or not; `skills/MEMORY.md` (skill `memory`) is the memory layout, its rules and the daily routine that `metro memory` runs.
- **The daemon writes the hooks into the agent's `~/.claude/settings.json`** (`claude/hooks.ts`, merged by `ensureClaudeSetup` with the privacy env, written as the agent through `home-fs`, only when the text changes; a box without an agent user gets the daemon user's settings): `PreToolUse` `node "<cli>/hooks/guard.mjs"` (`statusMessage: Checking the orchestrator boundary`) and `SessionStart` `node "<cli>/hooks/session-start.mjs"`, each in its own group with no matcher. **Metro's entries are the ones whose command is `node "<anything>/hooks/guard.mjs"` or `…/hooks/session-start.mjs"`**: they are replaced in place (a duplicate is dropped), the owner's other hooks are never touched, and a `hooks` value Claude Code cannot read (not an object, or an event that is not a list) is left alone with a warning. `<cli>` is the installed CLI package (`claude/cli-files.ts`: the real path of `METRO_CLI_BIN`, two folders up, so `/var/lib/metro/.npm-global/lib/node_modules/@stage-labs/metro` on a box, which `metro update` reinstalls in place; else the checkout's `packages/cli`), resolved at every boot and rewritten when it moves; a path that would need shell quoting, or no hooks there, writes nothing. The agent can read it because `.npm-global` stays open (see Three users on every box). The daemon reads the skills from the same package. Checked 2026-10-14 on Claude Code 2.1.282: a `SessionStart` group with no matcher in `settings.json` runs, with the session's environment.
- **One MCP server, `metro`: connectors are two of its tools, `tool_search` and `tool_call`** (Claude Code names them `mcp__metro__tool_search` and `mcp__metro__tool_call`; owner's call, 2026-10-14). There is no separate `mcp` server: the SDK runner's `mcpServers` hold only `metro`, which proxies the daemon's tool list, so the session gets the two tools. Their definitions (schemas, descriptions, annotations: `tool_search` read-only, `tool_call` destructive and open-world) are the ones mcp.metro.box serves (`@metro-labs/http/mcp-server-tools`, one source for both). In `mcp/tool-catalog.ts` they are `TOOL_DEFS` with groups `read` and `write`, published from `connectorTools()`.
- **The daemon forwards each call** (`mcp-server/connector-tools.ts`, `mcp-server/rpc.ts`): a JSON-RPC `tools/call` to `<mcpServerUrl()>/` with `Authorization: Bearer <MCP token>` read from Metro's own `<agents dir>/mcp-token`, 120 s timeout, and the server's `result` (content, structuredContent, isError) goes back to the agent as it is. No token or no server url answers a tool error saying connectors are not set up (the agent links to its organization once an admin of the organization opens its page); a network error, a timeout, a 5xx or an unreadable answer answers "mcp.metro.box is unavailable, try again."; a 401 also asks the link to register the token again (`reregisterMcpToken`); a JSON-RPC error is passed on as "mcp.metro.box refused the call: …". The two tools are dispatched before the scope check and `policyGate` and are in `UNGATED`, since mcp.metro.box enforces connector permissions itself. Nothing logs arguments, results or the token.
- **`tool_search`'s description names the agent's connectors**: the daemon reads the server's `tools/list` at start, every 5 minutes (`watchConnectorTools`) and right after the link registers the token, keeps the last good definitions (a static fallback before the first one, `mcpServerTools(null)`), and when they change it bumps the tool schema signature and tells the live session with `notifications/tools/list_changed` (`McpSession.toolsChanged`, the existing schema notice).
- **The memory routine runs with `METRO_SESSION=memory`**: `guard.mjs` exits at once and `session-start.mjs` injects nothing there, as when it ran with the plugin off.
- **The old plugin is gone from every box**: beta.306 removed it once at boot (`claude plugin uninstall metro@metro`, `claude plugin marketplace remove metro`, `<agent home>/.metro/marketplace`, then `pluginRemoved: true` in `claude-setup.json`), every box ran it, and that code (`claude/plugin-cleanup.ts`) was deleted on 2026-10-15. A runtime store's leftover `marketplace/` is still removed when the next version is synced (`runtime-install.ts`).
- **A box that updates to a version with this change restarts its session once** (the watcher's stale-version restart), so the new flags and settings hooks load. A connector change on the page needs no reload: mcp.metro.box reads assignments and policies on every call, and the tool description follows within 5 minutes.

## The gate and tests

- `bun install`. CI and Docker use `--frozen-lockfile`: **commit `bun.lock` after any dependency change.**
- **Before any PR: `bun run build && bun run typecheck && bun run lint && bun run knip && bun run madge && bun run test`, all green.** Test the gate's exit code before committing or pushing.
- Local run: `bun apps/daemon/src/server.ts`. Prod runs TS from source; `dist/` is built only by the gate.
- Tests set `DYLD_FALLBACK_LIBRARY_PATH=/usr/lib` (xmtp bindings on darwin) and `METRO_STATE_DIR="$(mktemp -d …)"`. Run the whole suite; never assert an exact test count.
- **Tests that boot an HTTP server pick a port in 10000 to 29999**, below Linux's ephemeral range. Port 0 cannot be requested (`webhookPort()` treats 0 as unset).
- **Every test that materializes trains must point `METRO_TRAINS_DIR` at a temp dir in `beforeEach`**, or it writes stubs into the checkout. The default `trainsDir()` is `apps/daemon/trains` (gitignored), never `~/.metro/trains`.
- turbo `test` depends on `^build`, so a core edit reruns station tests.
- **`bun run compat` (`scripts/compat.sh`) runs the current page's API calls (`scripts/compat/probe.ts`) against the daemon on the `beta` dist-tag** (`COMPAT_REF` picks another commit): it checks out the commit that set that version into a temp worktree and boots it isolated (`env -i`, temp HOME and dirs, a fake WorkOS issuer, a fake MCP server), and fails on any call the old daemon rejects. The `Compat` workflow runs it on every push and PR, outside the gate. Add a new page call to the probe.
- **Remove agent worktrees under `.claude/worktrees/` once merged** (`git worktree remove`).
- **`bun run lint` is `stage lint`: `oxlint --type-aware` with the root `.oxlintrc.json`** (since `@stage-labs/config` 0.1.0-beta.3, which dropped the ESLint presets). The file carries the old ESLint rules, as Stage does, plus the two Metro rules below (`void p`, inline styles). `eslint` stays installed only for the config's `core` oxlint plugin.

## Coding conventions (hard, enforced by `@stage-labs/config`)

- **No comments in source. None.**
- **No escape hatches:** no `oxlint-disable` or `eslint-disable`, `@ts-ignore`, `@ts-expect-error`, or `any` casts to dodge types.
- **No floating promises, and `void p` is a lint error** (`ignoreVoid: false`). Every promise is awaited or ends in a `.catch()` that logs.
- `max-lines` (400) and function-length caps: split files instead of suppressing.
- Strict TS, ESM, import specifiers carry explicit `.js`.
- Throw real errors; surface with `errMsg` and `TrainError`. Never swallow.
- Log through the shared `log`, never `console`.
- **Inline style object literals in JSX are a lint error.** Use kit `Row`/`Column` props, or a named constant (`SHRINK`, `GROW` in `theme.ts`).
- Style for prose and commit messages: conventional commits (`type(scope): subject`), no em dashes, plain English.

## Architecture invariants

### Bus, stations, trains

- **The bus is an in-memory ring (`BUS_BUFFER_MAX` 500), not a journal. Do not add an on-disk journal or history.** `channels/relay.ts` replays missed events on rebind, best effort.
- Stations are wired through `stations/registry.ts`; core dispatches over station defs. No per-network branching in core. Capabilities are declared on the `Station` (`hasAccounts`, `hasTrain`, `profileFields`, `readsProfiles`, `resolvesSenders`, `claimsName`, `attachmentMode`, `readFilters`, `approvals`, `sendsFrames`, `reportsStatus`, `pairAgain`) and read, never branched on by name.
- **A station that `reportsStatus` answers each account's live state on its `accounts` row** (`status: {state, reason?, since}`, `@metro-labs/core/stations/account-status`: `connected`, `connecting`, `logged_out`, `disconnected`; `since` is when it entered that state). The daemon passes it on only for such a station, checked by `accountStatusOf` (anything else is dropped), and waits 5 s at most for that train's `accounts` (`STATUS_WAIT_MS` in `mcp/accounts.ts`): a train that does not answer in time is unavailable, so the page shows Unknown, never an old value. Nothing caches it. `GET /api/agents` lists these stations as `reportsStatus`, and the agent's `list_accounts` carries the state too.
- **A station that declares `pairAgain: {identity}` can link the same account again** (`identity` is the config key naming who the account is: `phone` for WhatsApp). `POST /api/agents/<id>/accounts/<station>/<account>/repair` (member, like attach; the body is the attach fields) starts the station's interactive attach as an attach session with the account id (`AttachSessions.start(…, repair)`), which the poll, step and cancel routes then drive as usual; the start gets `expect` (the stored identity, never from the body, `pairAgainInput` in `routes/pair-again.ts`), and the completion replaces only that account's config in `agent.json` (`localPairAgain`: the id, allowlist, approvers, policy and `enabled` stay; another identity is a 400 and nothing is written), then reloads the station, which restarts its train. A station without it is a 400, an unknown account a 404. `GET /api/agents` lists these stations as `pairAgain`.
- **A station that keeps secrets of its own on disk declares `forget` and `forgetExcept`** (`core/stations/account-files.ts` `accountFiles(<dir env>, <prefix>)`: `<prefix><account>.json` under the env dir or `~/.metro`). The detach route calls `forget(accountId)` after the account left `agent.json` (a throw is logged, the detach still answers 200), and boot calls `forgetExcept` with every account the agent map still knows, disabled ones included (`forgetOrphans` in `stations/registry.ts`), which cleans files left by a detach before this existed or rewritten by a train that had not stopped yet. Outlook removes `outlook-state-<account>.json` (the refresh token), Gmail `gmail-state-<account>.json`, WhatsApp `whatsapp-tokens-<account>.json`, Threema `threema-groups-<account>.json`. **XMTP's db3 is deliberately left alone**: it holds the inbox installation, and deleting it would spend one of the ten installations if the same key were attached again.
- `hasAccounts` and `hasTrain` are independent. `webhook` is `true`/`false`: no train, accounts read in-core, and `list_members` refuses it.
- A train call line longer than `STDOUT_LINE_MAX` (4 MiB) is dropped by `drainLines`. That is why no base64 ever crosses the train pipe: inline data lands in a temp file first.
- `materializeFrom` prunes stale stubs at first boot too, since the supervisor spawns every `*.ts` in the trains dir. A stub is rewritten only when its content changes.
- **A disabled account (`stations[].enabled: false`, the page's Receive messages Off) only stops inbound.** It stays in the agent map and in the account file, so its train keeps running and every tool still works; `makeEmit` drops its events before the bus (`lineReceives` in `agents/map.ts`), so the channel, `/api/tail` and the People list never see them, nothing is replayed after switching back on, and a permission prompt is never posted to it (`relayLine` keeps it for the page, since no answer from there could arrive). Toggling, like an allowlist change, only reloads the maps (no train restart). Before beta.217 Off took the account out of the account file, so a station with every account off had no train, `/api/agents` called it unavailable, and the page dropped it from the list after a reload (Less, 2026-09-26). The page lists an unavailable station's known accounts (`carryForward`), so an old daemon's switched-off channel can still be turned back on.
- **Allowlist entries** (`agents/allowlist.ts`, `senderMatchesAllowlist` and `senderPermitted` in `agents/map.ts`) match the last segment of the sender line, case-insensitive. **An entry starting with `@` is a domain** (`@anderra.ch`): it matches a sender id that is an email address at exactly that domain, never a subdomain (`x@mail.anderra.ch` needs `@mail.anderra.ch`), and never a sender id that is not an address. A bare `@` or a non-domain is refused at save. `*` or an empty list means anyone.
- **A station may report `sender_verified` on an inbound event** (`senderVerified` on the `MetroEvent`, `sender_verified` in the channel meta). When the allowlist is not `*`, a sender whose event says `false` is dropped even if listed; a station that does not report the fact is unchanged. With `*` the event is delivered and the meta says `sender_verified="false"`, which `MCP_INSTRUCTIONS` tells the agent to distrust.

### Never fatal

- **Nothing in the relay path may kill the daemon.** A notification failing because a client left is normal.
- Three layers, keep all: the fallback timer `.catch()`es and logs; `ChannelRelay.enqueue` ends its chain with a `.catch()`; `boot/crash-guard.ts` installs `unhandledRejection` and `uncaughtException` as the first statement of `boot.ts`.
- Before `markDaemonReady()` a crash exits 1 (visible crash loop); after it, errors are logged and counted.
- The fatal path writes with `writeSync(2, …)` (`logFatalSync`), because pino's async destination is truncated by `process.exit`.
- Keepalive `res.write`s are guarded and close the stream on failure.
- Pinned by `test/never-fatal-notify.test.ts` and `test/crash-guard.test.ts`.

### Identity, sessions, scope

- **The agent key is the only credential for `/mcp`, the gateway, uploads and `/api/tail`.** `authenticate()` checks the key map only (`agents/keys.ts`, SHA-256 of the key to agent id, no plaintext). A daemon with no key is closed, not open.
- **The agent key never leaves the box and no API returns it to the page.** `GET /api/agents` and the bundle carry no key; a restore keeps the key on disk. The key is needed because Funnel delivers internet requests from loopback.
- **The agent key works only on the box itself** (2026-10-01, #112 audit): a request that came through Tailscale serve or Funnel carries `x-forwarded-host` and `x-forwarded-for` (tailscaled sets both on every proxied request, plus `tailscale-funnel-request` for Funnel), and `cameThroughProxy` in `@metro-labs/http/api-http` makes `authenticate()` (MCP, `/api/tail`, uploads, `/attach`) and the gateway refuse the key then. So a key the agent copies off the box opens nothing; upload tickets and attachment grants still work through the public address.
- There is no key reset. Recovery: a new `key` in `agent.json`, then a restart.
- `allowedAgents()` is the one place turning an identity into a `Set`; it never returns `undefined`. The only identity is `{kind: 'agent', agentId}`.
- **Scope by agent id, never by name.** Names are not unique; a name comparison in an auth path is a cross-owner leak that is not a type error.
- **One MCP session per box** (`mcp/session-slot.ts`): a box runs one agent, whose SDK runner is the one MCP client, so the daemon holds one `McpSession` (its server, transport, stream, event store, relays and bus subscription). An `initialize` closes the current one and opens a new one. A request with no session id uses the current one. An unknown session id is adopted (a client that outlived a daemon restart), never refused. `test/one-session.test.ts`.
- **The replay ledger belongs to the slot, not the session**, so a message that arrived while the agent was away is delivered after a reconnect and after a full re-initialize.
- An adopted session is told the tool schema moved (on the GET stream or inside a `tools/call`); `tools/list` settles it silently, since notifying there loops.
- **A client that is neither streaming nor calling cannot be reached.** The runner reconnects its stream by itself (`RECONNECT` in `sdk-runner/src/link.ts`), and a daemon update restarts the session (see Claude Code on the box). **The GET stream advertises `retry: 1000`** (`raw-get-stream.ts`), and the MCP client waits exactly that between tries, so a dropped stream is back in about a second; the runner's 900 tries keep the old 15 minutes for a daemon restart. It was 15 s from #100, when Claude Code's own client held the stream and gave up after 2 tries; it held every message for 15 s after any drop.

### One scope predicate for every egress (`agents/scope.ts`)

- `lineTargetDenied` resolves `args.line` and also any `args.account` override (stations resolve `account ?? line`). `stationFullyScoped` covers calls with no line.
- **`eventInScope` fails closed.** An account-station line whose account maps to no agent goes nowhere; an unparsable line reaches nobody. The one carve-out is by station: a station with no accounts (`metro://claude/…`) reaches every authenticated tail. Do not remove that carve-out.
- **Four egresses share one case table** (`test/egress-scope-matrix.test.ts`): channel live, channel bus replay, SSE resumption, monitor tail. **Add any new egress to that table.**
- **SSE resumption re-checks every frame that names a line** (`replayEventsAfter` takes the reconnecting scope as a required option); a frame with no line (a response, a tool list notice) replays. Keep both this gate and the relay gate.
- The channel delivers only while a GET stream is attached. Otherwise the event is withheld, not dropped, and the bus ring replays it when a stream comes back.
- **Live messages can be switched off** (`liveEvents: false` in `<agents dir>/claude-setup.json`, default on; Settings' Pause messages switch, `POST /api/claude/setup {liveEvents}`, admin; Less, 2026-09-26). Off, the slot drops the session's bus subscription at once (`SessionSlot.setLive`, wired from `boot.ts`), holds back what is still queued, drops messages waiting for their attachments (`dropPending`, so the 15 s fallback cannot fire) and skips the bus replay when a GET stream attaches; switching back on starts from the current bus position, so nothing held back or published while Off is ever replayed. Nothing restarts and nothing else stops: the trains run, so every tool and `/api/tail` still work, and the runner still relays permission requests, so a permission prompt still reaches the page, the only place to answer it then (`relayLine` picks no chat, and a chat `yes <id>` is not read while Off). After switching back on, the known line is still the last chat seen before Off. A daemon without it answers the setup with no `liveEvents`, and the page then hides the switch.
- `permission-relay.ts` re-checks the line with the session's scope before pushing an approval prompt (it contains tool input).

### Human in the loop

- **`PERMISSION_REPLY_RE = /^\s*(y|yes|n|no)\s+([a-km-z]{5})\s*$/i` is a contract with the relayed prompt's id format. Change both sides or neither.**
- **A station with `approvals: false` (Outlook, Gmail) never becomes the line a prompt is sent to, and a `yes <id>` from it is an ordinary message**: email is too weak a channel for approvals.
- **A reply counts only on the line the prompt was sent to** (`promptLine` in `approvals/pending.ts`), from a sender the account's allowlist passes (the relay drops everyone else before), **who is also one of the account's approvers**, and never when the station reports `sender_verified: false`. Only `msg` events are checked, so a webhook body can never answer a prompt. A reply from anyone else is an ordinary message.
- **Approvers** (`approvers?: string[]` on a station account in `agent.json`, `setApproversMap`/`mayApprove` in `agents/map.ts`) are a subset of the allowlist, matched like it. They ride on the allowlist save (`PUT …/allowlist {allowlist, approvers?}`; without `approvers` the current ones are kept, filtered to the new list; `*` means none) and in the bundle and `.metro` exports. **An account with no approvers never gets a prompt in chat**: `relayLine` keeps it for the page only. So allowlist `*` means page-only approvals. The page shows a Can approve switch per sender (hidden for Outlook and Gmail).
- **The allowlist shows who each id is**: `GET …/accounts/<station>/<account>/profiles` (`agents/sender-cards.ts`) answers `{senders: [{id, name?, handle?}]}` for every listed id (not `*`, not an `@domain`), from the train's `profile` action when the station `readsProfiles` (8 s per lookup, 50 at most, a failure keeps the bare id), else the name seen on a recent message. The page asks for them and draws a chat link per row with `chatLink` in `api/senders.ts` (t.me or tg://, discord.com/users, wa.me, threema.id, mailto). **WhatsApp ids are mostly `@lid`**, which name nobody: the WhatsApp profile answers the phone number from Baileys' persisted lid mapping (`getPNForLID`, as `name` and `address`) and the name the person last used (`names.ts`, in memory, filled from inbound `pushName` and `contacts.upsert`, 2,000 max), and the chat link falls back to wa.me of that number. Names also come from WhatsApp's own syncs (`contacts.upsert` and `contacts.update`, which carry the phone's address book names from app state, Baileys' per-message `notify` and business `verifiedName`; `messaging-history.set` contacts, its pushnames and past messages' `pushName` or `verifiedBizName`), recorded under every id a contact or message carries (`noteContact`: `id`, `lid`, `phoneNumber`; a message's `participant`/`remoteJid` and its `participantAlt`/`remoteJidAlt`), and a name known under one id is copied to the other when a lid mapping is learned (`alias`: `lidPnMappings`, `lid-mapping.update`, a contact with both ids; a name already there is never overwritten). **The profile looks under both ids** (`profile.ts`: `readPeer` resolves the other id with Baileys' lid mapping, `getPNForLID` or `getLIDForPN`, which asks WhatsApp when it does not know it), and reads the name at answer time (`withName`), so a name learned after the 10-minute profile cache shows at once. The picture tries the full picture, then the preview, for the id and then the other id (a lid can be refused where the number works), 1.5 s per try and 6 s per lookup at most (`LOOKUP_BUDGET_MS`, under the daemon's 8 s); an id WhatsApp refuses (401, 403, 404) or has no picture for is not asked again for 6 hours (`PictureMemory`, 2,000 ids), any other error stops that lookup (a timeout is asked again next time), and a rate limit (429 or `rate-overlimit`) stops every picture lookup of the account for 30 minutes. **Profile reads go to WhatsApp 4 at a time** (`limiter`, `PROFILE_READS`): the People list sends its 50 lookups at once, so the last ones may answer bare and are filled in at the next load from the 10-minute profile cache. Ids are normalized (`jidNormalizedUser`) wherever a name is noted, read or copied. `getBusinessProfile` has no name in Baileys 7, so a business is named only by its verified name. **The names are kept on disk** (`whatsapp-names-<account>.json` under `WHATSAPP_TOKEN_DIR` or `~/.metro`, 0600, saved 2 s after a change, 2,000 max; `nameFiles`, removed with the account by the station's `forget`/`forgetExcept`), so the People list keeps them across restarts. The People list shows each sender's picture when the network gives an https one (`avatar` on the sender card: an https link, or `data:image/…` up to 100,000 characters; WhatsApp profile picture, Discord avatar, XMTP avatar, and the Telegram bot's small profile photo, which the train downloads itself (`getFile` then the file API, 64 KB max) because the file link carries the bot token; Threema gives none), else the generated pattern (`AgentAvatar`).
- **A new approver must be a real person** (`unconfirmedSenders` in `agents/sender-cards.ts`): on a station that `readsProfiles`, each id newly marked Can approve must have written recently or have a profile with any field beyond its id, else the save is a 400 naming it. A station without profiles (Threema) is not checked.
- **An approval asked by mcp.metro.box follows the same rules** (prompt line, approvers, `sender_verified`, `approvals: false`, the page, the expiry); only where the answer goes differs (see Tool policies and approvals, and mcp.metro.box).
- A `msg` with blank text and no attachment is dropped by the relay.
- `addressed` (`direct`, `mention`, `reply`) is decided in core (`channels/addressed.ts`) from facts stations report (`is_private`, `mentions_self`, `reply_to_self`) plus the relay's memory of ids it sent (`SENT_IDS_MAX` 2000).

### Tool policies and approvals (`policy/`, `mcp/policy-gate.ts`, `packages/cli/hooks/policy.mjs`, `approvals/`)

- **Every metro MCP tool declares `group: 'read' | 'write'` next to its definition** (`ToolDef` in `mcp/tool-def.ts`, `StationTool.group` in core; `destructive: true` for delete, remove and close). Read is `read`, `list_members`, `get_profile`, `list_accounts`, `list_channels`, `tool_search`, xmtp `group_info`; everything else is write, and an undeclared tool counts as write. `mcp/tool-catalog.ts` is the one list: `toolList()` publishes `readOnlyHint`/`destructiveHint`, `channelToolsOf(station)` feeds the page. `test/tool-groups.test.ts` fails on a tool with no group. **Never mark a metro tool `requiresUserInteraction`**: Claude Code never relays such a tool's prompt.
- **A channel account may carry `policy: {read?, write?, tools?: {<tool>: …}}` in `agent.json`** (`allow`, `ask`, `deny`; absent means allow). The parser is tolerant (a bad value is logged and dropped), the API strict (`normalizePolicy`, 400 by name). The bundle and `.metro` exports carry it. `PUT /api/agents/<id>/accounts/<station>/<account>/policy` (member, like the allowlist) reloads the maps only. `list_accounts` shows each account's effective policy.
- **Both `deny` and `ask` are enforced by the daemon; the guard hook only raises the prompt.** The daemon (`policyGate` in `runTool`, right after the scope check) refuses a denied call with `Blocked by the owner's policy for <station> (<tool>).` and no train call. **An `ask` call runs only by consuming a grant** (`takeGrant` in `approvals/pending.ts`): answering a prompt `allow` in chat or on the page records `{tool, preview}` for 10 minutes (`GRANT_TTL_MS`, 200 max), and the call whose tool and arguments match it (`previewMatches`) uses it up; anything else gets `NEEDS_APPROVAL` (`approvals/pending.ts`) and no train call. Why: the agent holds its own key, so it could call `/mcp` with `curl` or switch its hook off, and before this the daemon took any `ask` call as approved (2026-09-25, after an agent sent mail with the Outlook token it found on disk). Consequence: a session without the guard hook has no way to raise a prompt, so its `ask` calls are refused. `test/policy-matrix.test.ts` is the daemon's case table.
- **The hook reads a snapshot the daemon writes: `<agents dir>/policy.json`** (`mcp/policy-snapshot.ts`, 0600, rewritten at boot and on every `setPolicies`, only when the text changed): `{version: 1, tools: {<tool>: read|write}, owners: {<station tool>: station}, ungated: [...], accounts: {"<station>/<account>": policy}, stations: {<station>: [account ids]}}`, and no connector (2026-10-14). It lives beside `agent.json` because the hook already knows that folder (`METRO_AGENTS_DIR`, else `~/.metro/agents`, the same rule as `hooks/mcp-headers.mjs`), and the agent view copies it for Claude Code, which runs as the agent. **The hook mirrors `channelTargets`/`decide` exactly** (a `line` with an `account` override, `get_profile`'s `from`, `station` for `create_group`/`set_profile`, a station tool's owner, an account alone, else every account of the station with the strictest winning; per-tool beats group; unknown tool is write; nothing set is allow); `test/policy-snapshot.test.ts` runs the real `guard.mjs` on the daemon's own snapshot and compares it with `channelDecision`. **A missing or unreadable snapshot allows**: the daemon still refuses blocked calls.
- **What the hook answers**: `deny` on either thread is a deny with the same sentence as the daemon. `ask` inside a subagent (the payload carries `agent_id`) is `permissionDecision: 'ask'`, which makes the runner's `canUseTool` fire even in bypass mode (see The Agent SDK runner); only that subagent waits, the main thread keeps answering, and several prompts relay in parallel. **`ask` on the main thread is a deny telling the orchestrator to run that exact call from a background worker**, because a prompt there blocks the whole session (no timeout: an unanswered prompt waits forever). Never answer `defer`: Claude Code ignored it in interactive mode and the tool just ran. `packages/cli/test/hooks.test.ts` pins every case.
- **The prompt reaches the owner through the channel permission relay** (`mcp/permission-relay.ts`): the SDK runner sends `notifications/claude/channel/permission_request` `{request_id, tool_name, description (the tool's own), input_preview (JSON of the input)}`, metro posts it to the owner's direct chat (below; never an `approvals: false` station, never a line outside scope), formatted by `mcp/permission-prompt.ts` (`Approval needed: <tool>`, the channel, the text, then `Reply "yes <id>" or "no <id>"`), and answers with `notifications/claude/channel/permission` `{request_id, behavior}`. **The prompt goes to the owner's direct chat** (`ownerLine` in `approvals/owner-line.ts`): the last private chat (`is_private`) where one of the account's approvers wrote, saved with that sender in `<state dir>/approval-line.json` so it survives restarts, and used only while that sender may still approve. A prompt bound to a call goes to the call's chat, and while a shared call is on so does any other prompt, as the last inbound line did then. Until an owner chat is known, or while it is out of scope or switched off, the prompt goes to the session's last inbound line (`knownLine`) as before. Why: a prompt names neither the chat nor the worker that raised it, so posting it in the last active chat put workers' prompts in front of whoever was there (an MCI chat, then a Trello chat; Less, 2026-10-09: "send other prompts to our DM"). XMTP marks a DM private by `'peerInboxId' in conv` (`emit.ts`): node-sdk 6 made `peerInboxId` a getter, and the old test for a function never matched, so no Stage DM was private before. **The runner sends the whole input as JSON** (`sdk-runner/src/approvals.ts`), but Claude Code's own relay elided a long string in `input_preview` (2.1.281: the first 1999 characters, `\n⋯ <N> code points elided ⋯\n`, the last 1499, and possibly a trailing `⋯ … field(s) elided … ⋯` block), so the preview is not JSON: `approvals/preview.ts` `readPreview` turns each marker into a placeholder before parsing and cuts a field-elision block, the chat shows `…` there, and `previewMatches` (what `settlePromptsFor` uses) takes an elided string as a head and a tail of the real value. **A chat prompt is at most 1,000 characters and never carries a metro tool's `description`** (a 4,470-character prompt was refused by Telegram, whose cap is 4,096, and a refused relay send is only logged). A prompt answered on the page or expired also posts `Approved on the page.`, `Denied on the page.` or `Expired, denied.` on its chat line.
- **metro keeps the pending prompts** (`approvals/pending.ts`, in memory, 500 max, dropped with the session that raised them, since a session restart drops its prompts too): a chat answer (see Human in the loop), the page (`GET /api/approvals` lists `{id, tool, description, preview, line, requestedAt}`, `POST /api/approvals/<id> {decision: allow|deny}`, member-level, 404 for an unknown or already answered id) or the expiry (24 hours, swept every minute, answers `deny`) settles one. **A call settles its own prompt**: a prompt whose call then reaches the daemon with the same arguments is dropped before the policy check, whether the call then runs or is refused (`settlePromptsFor` in `runTool`), since the session has stopped waiting by then; before 2026-09-26 a call approved elsewhere and refused by the daemon left a dead prompt on the page. A denied one stays until expiry, and a late answer to a prompt Claude Code already closed is harmless. `test/permission-relay.test.ts` drives the relay, the chat answer, the page and the expiry over real HTTP.
- **Connector policies live only on mcp.metro.box** (2026-10-14): Block and Ask are enforced by the server for `tool_call` (see mcp.metro.box below), so the daemon has no connector gate, no connector grant and no connector in `policy.json`, and the hook has no connector verdict (`hooks/policy.mjs` only judges `mcp__metro__*`). `tool_search` and `tool_call` are in `UNGATED` (the snapshot's `ungated`), so no station policy applies to them, and the guard keeps `mcp__metro__tool_call`, like any non-metro MCP tool, off the main thread. A Claude Code prompt for some other MCP tool is still relayed as `Claude wants to run <tool>: <description>`, and its grant never authorizes a metro tool (`test/connector-channel-grants.test.ts`).
- **`MCP_INSTRUCTIONS` (`mcp/instructions.ts`) must stay under 2,048 characters**: Claude Code keeps only the first 2,048 of a server's instructions (2.1.281 logs `Server instructions truncated from 2140 to 2048 chars`), which cut the approval rule at its end. `test/permission-relay.test.ts` pins the length; tighten wording rather than drop a rule.
- **An agent without a server has no daemon, so its Ask approvals are answered on metro.box** (Less, 2026-10-23): the same `mcp_approvals` row, listed by `GET /api/agents/<id>/approvals` and answered by `POST /api/agents/<id>/approvals/<approval id> {decision}`, both member-level like a box's `POST /api/approvals/<id>`, with the store functions mcp.metro.box uses (`@metro-labs/connectors/db/mcp-approvals`: same 24 hour expiry, same single use within 10 minutes). The page shows them as approval cards on that agent's Connectors tab. Nobody tells the agent: the person repeats the call with `approval: "<id>"`, and the `needs_approval` wording says so. These routes refuse an agent with a server (409).
- **Approvals asked by mcp.metro.box are a second kind of pending prompt** (`origin: 'mcp-server'` in `approvals/pending.ts`, `mcp/server-approvals.ts`), held under the server's own 5-letter id: the chat prompt goes where a Claude Code prompt would go (`relayLine`: the owner's direct chat, else the last inbound line, never an `approvals: false` station, page only without approvers), formatted by `serverPromptBody` (`Approval needed: <connector key>.<tool>`, the preview's arguments, 1,000 characters at most), and the page lists it with tool `<connector key>.<tool>`. A chat `yes <id>` (same approver, line and `sender_verified` rules), the page or the 24 hour expiry answers it; the answer goes to the server (`POST <url>/v1/approvals/answer`, retried until it is taken or answers 404), never to Claude Code, and records no daemon grant (the server enforces its own approval). Once the server took it, the agent gets a metro notice on the prompt line (else its last chat): `Approved: <connector>.<tool> (<id>). Call tool_call again with the same arguments and approval: "<id>".` or `Denied: <connector>.<tool> (<id>).`; a 404 tells the agent nothing. **An approval the server marks `origin: 'key'` (an access key of this agent made the call, not its own session; 2026-10-23) gets no such notice**: the prompt reads `Approval needed: <connector key>.<tool> (from an access key: <key label>)` (the label, never the key; `(from an access key)` without one), the page lists it, and the answer goes to the server exactly as for any other, but the session, which never made the call, is told nothing (`tellAgent` in `mcp/server-approvals.ts`); the person holding the key repeats the call. `origin: 'box'`, no `origin` (a server before `0020`) or an origin the daemon does not know keep the notice. The page and expiry confirmations in chat are the same as today. An id already held, or answered in the last 10 minutes, is not held again. **An id already posted in chat is never posted again** (`mcp-server/announced.ts`): the server sends a pending approval again every minute, so after a restart it used to be posted twice; the daemon keeps each posted id with its chat line in `<agents dir>/mcp-approvals.json` (0600, 200 at most, entries older than a day dropped, the file set from `boot.ts`), and an id found there is held again on that line (page, chat answer, expiry) without a new post. `test/mcp-server-approvals.test.ts`, `test/mcp-server-announced.test.ts`.
- metro's own approval flow (stored calls, `approvals.json`, "Waiting for the owner's approval", the `approval_id` channel message) lived for an afternoon on 2026-09-24 and was replaced by the native prompt at Less's call; do not bring it back.

### Attachments and uploads

- **Inbound:** a station emits `attachmentSaved` or `attachmentFailed` (with `reason`), both through one correlator (`InboundRelay.mediaCtxFor`). A failure note has no url and no path.
- `saveStreamToCache` streams to `.part` with a running size check and renames on success.
- **The inbound cache (`attachDir()`) cleans itself** (`files/attach-reaper.ts`, started from boot beside the upload reaper: one sweep at start, then every 10 min, never fatal, logs counts at info). A file older than `METRO_ATTACH_TTL_DAYS` (default 7, by mtime) goes with its `.owner`/`.grant`; an orphan sidecar goes; a `.part` older than an hour goes (its sidecars are kept while a fresh `.part` exists); then the dir is capped at `METRO_ATTACH_MAX_MB` (default 2048), oldest first. A zero or bad value means the default, never "delete everything". **Only cache-shaped names are touched** (`resolveCachedAttachment`, the rule `/attach` serves by), so anything else in that dir is safe. The TTL is generous because a url handed to an agent may be fetched days later.
- **`/attach` is scoped by the owning agent.** The `?token=` is a per-attachment grant (`.grant` sidecar), never the agent key; access is that grant or a caller whose scope holds the owner. **Everything else is 401, including a cache-shaped name that does not exist; do not turn it into 404** (that would be an existence oracle). The only 404 is a name that is not cache-shaped.
- **Outbound sources: exactly one of `upload`, `data`, `url`, `path` per attachment.** Zero or two is an error. `path` is on the daemon host, `url` must be public, `data` is for tiny files.
- `MAX_INLINE_BYTES` (8 MiB) is set so it errors before `MCP_BODY_MAX` (32 MiB) answers a bare 413; raise both together. base64 is validated strictly. Inline and url bytes go into a per-attachment `mkdtemp`, never `attachDir()`, cleaned in a `finally`.
- **Uploads** (`files/upload-*`, `mcp/upload-tool.ts`): `create_upload` mints a slot and a command; bytes go over HTTP (a shell step is unavoidable). Slots live in `uploadDir()` (`~/.metro/uploads`, Metro's own folder; it was `/tmp/metro-uploads` until 2026-09-26, which the old root daemon had created 700, so the `metro` user got EACCES on every `create_upload`), 30 min TTL read on every lookup, reaper every 60 s. 64 MiB per file, 512 MiB live total. Anything not authorized is a flat 404 (an upload id is a capability). The PUT url names the daemon that minted it.
- **An over-size chunked upload DRAINS (capped at 2x), it does not throw**: throwing destroys the socket in Bun and the client hangs. `streamToSlot` removes its own `.part` on failure.
- A send does not consume an upload, so a retry after a timeout works.
- **Outbound reporting is derived, never asserted.** `assertDelivered` compares labels to `atts.length` on every path; fewer labels is an error. **Each station builds its label list inside the send loop, after each push resolves, never by mapping the input.** Add every new station to `test/send-attachment-honesty.test.ts`.

### Organization connectors (issue 254, Less 2026-10-09: option A; reached only through mcp.metro.box since 2026-10-14)

- **Where this is:** connectors belong to the organization and live in api.metro.box's Postgres, each assigned to zero, one or many agents. An agent reaches its assigned connectors only through mcp.metro.box (`tool_search`, `tool_call`, which its daemon's `metro` server forwards, see mcp.metro.box below; an access key of any agent calls it directly, see Access keys and agents without a server), which calls the vendor itself, so **no connector credential, url or revision ever reaches a box**. The daemon keeps no connector of its own: the local connectors and the move went on 2026-10-14, and the same day the credential delivery to boxes, the daemon's sync, runtime, relay (`/relay/org-<id>`), discovery, publication and server keys, and the per-connector plugin servers went too (see `docs/HISTORY.md`). **The files the old path left in `<agents dir>` are deleted at every boot** (`removeConnectorLeftovers` in `connectors/leftovers.ts`, the first step of `main()` in `boot.ts`; never fatal, every error a warning, one info line with the count): exactly `connectors.json`, `connector-migrations.json`, `connector-migrations.initialized`, `connector-server-keys.json`, `connector-server-keys.initialized`, `org-connector-sync.json`, `connector-migration-operations-<id>.json` and its `.initialized` marker, plus the temp files a crash could leave beside them (`<name>.tmp-<pid>` from `writeSecure`, `connector-migrations.json.<24 hex>.tmp`). Each name is checked with `lstat` and only a regular file is removed: a symlink or a folder with such a name is left alone with a warning. Nothing else in the folder is touched, and the agent view had no connector file but `mcp-token`, which `view.ts` already removes.
- **No switch, one key** (2026-10-14): `connectors/setup.ts` reads only `METRO_CONNECTORS_KEY` and logs it once at boot as `connectors: …` (a warning when it is missing or malformed). Without a usable key, every route that seals or opens a secret answers 503 with a sentence naming the key: adding a connector, a new key, sign-in and the tool list. Listing, renames, policies, assignments, deletes and enrollment hold no secret and still work. `METRO_CONNECTORS_ENABLED` and `METRO_CONNECTORS_DELIVERY_ENABLED` are gone; api.metro.box no longer reads them.
- **No plaintext secret in the database, ever.** A connector's secret is one sealed string (`packages/connectors/src/secrets.ts`: AES-256-GCM, `v1.<iv|tag|data>`), whose additional data is `metro-connector/v1`, the owner and the connector id, so a value copied to another connector or organization does not open. **One key seals every secret: `METRO_CONNECTORS_KEY`**, a Fly secret on api.metro.box, 32 random bytes in base64 (`openssl rand -base64 32`), read once at boot; without it, or with a malformed one, no connector secret can be kept. It is never in the database, the repo or a log. Changing it makes every stored secret unreadable, so rotating it (open each secret with the old key, seal it with the new one) is for a later phase. No AWS KMS and no per-organization data key (Less, 2026-10-10: "Simplify the design").
- **Agent identity:** each enrollment makes the agent a new key pair in memory (`connectors/agent-key.ts`: one Ed25519 key that signs its requests; the X25519 sealing key went on 2026-10-15, since nothing was sealed to it once the delivery went on 2026-10-14: a new key has none, enrollment no longer sends one, and an `agent-key.json` or `agent-key.pending.json` an older daemon wrote with a `sealing` field still loads, the field ignored and dropped at the next save) and writes it to `<agents dir>/agent-key.json` (0600, Metro's folder, never in the agent view, a bundle or an export) only after api.metro.box confirmed it, so enrolling again is how a key is rotated, and a failed enrollment leaves nothing behind. Enrolling: an organization admin's page gets a single-use ticket for one agent row (`POST /api/servers/<id>/enrollment`, 10 minutes, in memory, one open ticket per agent, at most 20 waiting per organization and 1,000 in all), hands it to the agent (`POST /api/enrollment`, admin), and the agent sends it to `POST /api/agents/enroll` signed with the new key, then checks `GET /api/agents/session`. The api binds the key to that agent row and organization (`agent_keys`: one key per agent; a key already bound to another agent is refused with 409). `POST /api/agents/enroll` still accepts a `sealingKey` field from an older daemon and ignores it, whatever its value; no code reads or writes `agent_keys.sealing_key` any more. Moving an agent to another organization removes its agent key and its assignments in the same transaction. **The page enrolls by itself, and there is no enrollment section on the Server page** (Less, 2026-10-17: models and connectors live at the organization, so nobody should have to think about enrollment): while an organization admin has one of the agent's pages open and the box answers `sync.enrolled: false` on `GET /api/model`, the page runs the enrollment once (see The app), so a key is rotated only when the box says it is not enrolled. Phase 4 must also refuse an agent whose `.owner` is no longer the organization it enrolled with (`POST /api/owner` keeps the file).
- **An agent request carries `Authorization: MetroAgent <key id>.<ms>.<nonce>.<signature>`** (`@metro-labs/http/agent-signature`): Ed25519 over the method, host, path with query, key id, time, nonce and the body's SHA-256. The api checks it against its own host (`api.metro.box`, never the request's `Host` header; mcp.metro.box checks `mcp.metro.box`, or `METRO_MCP_HOST`), and refuses a browser (`Origin`, `Sec-Fetch-Site`, `Sec-Fetch-Dest` or `Sec-Fetch-User`; a server-side fetch may send `Sec-Fetch-Mode`), a clock more than 5 minutes off (named, so the owner can fix it), a small-order or non-canonical Ed25519 key (which would let anyone forge its signatures), and a key whose agent row was deleted or moved (`agent_keys.owner` must equal the agent's owner). Every agent route goes through `AgentAuth.accept` (`@metro-labs/connectors/agent-auth`), which also refuses a nonce it saw: nonces are kept in memory until their time window closes, with budgets per key (600), per organization (20,000) and in all (200,000), so one agent or one organization cannot block the others. A restart forgets them, which is fine while every agent route only reads or is guarded by a single-use ticket; **an agent route that changes state must keep its nonces in Postgres first**. A key id is the SHA-256 of the raw signing key.
- **Rename compatibility (2026-10-11):** migration `0006_agent_keys` renames the deployed `box_keys` table, its primary/foreign-key constraints and unique index in place. No key, assignment, secret or audit row is rewritten. A simple `box_keys` view kept the previous API's organization-move delete working during Fly's release-command overlap; `0013` dropped it with `sealing_key`. The daemon writes `agent-key.json` and can still read a legacy `box-key.json` when the new file is absent, without changing the key. Both files stay outside the agent view. Historical `box.enrolled` and `box.unenrolled` events stay intact and display with agent wording.
- **Wire cutover:** both sides now use `/api/agents/enroll`, `/api/agents/session`, `MetroAgent` and signing domain `metro-agent-request/v1`. The old connector routes/signature are not aliases. Update the daemon before using enrollment with the new API; mixed versions cannot enroll or use the signed session. The existing `/api/servers/<id>/enrollment`, daemon `/api/enrollment` and response `server` field stay unchanged, as does the unrelated local agent bearer key.

### Access keys and agents without a server (`agent_tokens`, `agents.kind = 'remote'`, Less 2026-10-23, `docs/MCP-SERVER.md`)

- **What it is**: an agent row with no box (`host` null), created by an organization admin (`POST /api/servers {kind: 'remote', name}`; only an admin adds any agent; the page's New agent asks With a server or Without a server first). Connectors are assigned to it like to any agent, and rename, slug, picture, move and delete are the agent list's routes; deleting one needs the admin role (a member may still remove a box's row, as before). Enrollment refuses it (409), so no daemon can take its row.
- **Access keys** (`agent_tokens`, `@metro-labs/connectors/db/agent-tokens`): `GET /api/agents/<id>/tokens` (members, no secret), `POST …/tokens {label}` (admins, 1 to 64 characters) answers the key once, `mcp_` plus 32 random bytes in base64url (the `MCP_TOKEN_RE` shape), and stores only its SHA-256; `DELETE …/tokens/<id>` revokes (the row stays, with `revoked_at`). 20 live keys per agent at most. **Any agent has them** (Less, the same day: "access keys should also work for agent with a server"): an agent with a server shows them in its Connectors tab (`components/tools/AccessKeys.tsx`, next to its connectors), one without a server in its Access keys tab. Deleting the agent deletes its keys, and `leaveOrganization` (a move) drops them. **Scopes** (`agent_tokens.scopes`, migration `0021`, 2026-10-26): `connectors` and `gateway` (the page will say Gateway, `docs/GATEWAY-SERVER.md`); every key made before has `{connectors}`, so none gains power silently. mcp.metro.box refuses a key without `connectors` with the same 401 as an unknown key. `POST …/tokens {label, scopes?}` takes the scopes (absent means `{connectors}`, so an older page keeps working; an empty list or an unknown scope is a 400), `PATCH …/tokens/<id> {scopes}` (admin) changes them on a live key (409 on a revoked one), and every key in a list carries `scopes`. The page's Access keys asks which ones when a key is created (Connectors, Gateway: switches, Connectors on by default), shows them on each row, offers Change access in the row's menu, and shows the Claude Code command for Connectors and an Anthropic SDK snippet for Gateway (`gatewaySnippet`, `model: 'metro'`); a key from an api without `scopes` reads as connectors only.
- **mcp.metro.box takes either credential** (`apps/mcp/src/token.ts`): a bearer is a box's MCP token (`agent_keys.mcp_token_hash`, accepted only on a row with a host, as is a daemon's signed key in `agentKeyStore.find`) or a live access key of an agent still in the key's organization. The identity is then `{agent, owner, tokenId, remote}` (`isTokenIdentity`), and the assigned connectors are read only while that key is still live. Everything else is the same code (policies, `tool_search`, `tool_call`, `mcp_approvals`, `mcp_calls`), so a key of a box works as that box's agent. Only the words follow where the owner answers (`approvalPlace` in `apps/mcp/src/tools.ts`, `ApprovalPlace` in `@metro-labs/http/mcp-server-tools`): the box's own token keeps `MCP_INSTRUCTIONS` (`session`); a key of an agent without a server gets `REMOTE_INSTRUCTIONS` and "approve it on this agent's page on metro.box" (`page`); a key of a box gets `KEY_INSTRUCTIONS` and "the agent's owner was asked in chat and on its page on metro.box" (`owner`), since its Ask row goes through the box's daemon relay as today (chat, the box page, the daemon's answer). The row records who made the call (`origin` and `token`, migration `0020`, 2026-10-23), the daemon gets `origin: 'key'` and the key's label, and a daemon from that release posts no `Approved: …` notice in its own session for such a call (an older daemon still does). `last_used_at` is written at most once a minute per key, never awaited.
- **On the page**: a remote agent is `RemoteServer` (`kind: 'remote'`, `host: null`) in `@metro-labs/client/api/servers`; an api that sends no `kind` means a box. `RemoteAgentScreen` (`components/remote/`) replaces the box's five tabs with Connectors (`#/<agent>`, with the approval cards), Access keys (`#/<agent>/keys`) and Activity (`#/<agent>/activity`); its connector page and profile page are the box's deep pages under its Connectors crumb. **Nothing on its page calls a box**: `useAgentRows` probes boxes only, and while the current agent has no host `daemonBase()` is `NO_SERVER_BASE`, which every box request refuses with `NoServerError` before any request is made (`refuseNoServer` in `auth/daemon.ts`, called by `call`, `fetchMode`, `startDaemon`, the health and Run events checks); no enrollment, setup checklist, model or server page renders for it. **`GET /api/servers` lists every kind** (2026-10-26; from 2026-10-23 it listed agents without a server only on `?kinds=all`, so a tab loaded before them could still read the list). The page stopped sending it the same day. In the list it has a plug mark on its avatar and the line "No server · N connectors", or "Waiting for you: approve <tool> on <connector>".

### mcp.metro.box (`mcp-server/`, `docs/MCP-SERVER.md`)

- **On by default** (2026-10-14): the daemon talks to `https://mcp.metro.box` unless `METRO_MCP_SERVER_URL` names another url (`mcp-server/config.ts`: https, or http on this machine only, no credentials, query or fragment; anything else is ignored with one warning, and the client stays off). **An empty `METRO_MCP_SERVER_URL` turns it off** (dev and tests): no token, no approval relay, and `tool_search`/`tool_call` answer that connectors are not set up. It is the only way connectors reach an agent; the per-connector servers are gone.
- **The MCP token** (`mcp-server/token.ts`): once the agent is enrolled with the box's owner, the daemon makes `mcp_` plus 32 random bytes in base64url (`MCP_TOKEN_RE`), keeps it in `<agents dir>/mcp-token` (0600) with the enrollment key id it belongs to in `mcp-token.json`, and registers only its SHA-256 (base64url) with a signed `POST <url>/v1/token` (`agentCall`, the `MetroAgent` signature). A new enrollment (another key id) makes a new token; every start registers the kept one again, and so does a 401 from the server. Failures retry with a doubling pause (2 s to 60 s) and are only logged. **The token never leaves Metro's folder**: the daemon itself sends it to mcp.metro.box (see the connector tools), the agent view never carries `mcp-token` and removes a copy an older daemon left there (as the agent, at its first sync), and `mcp-token.json` and the enrollment key are never copied.
- **The approval relay** (`McpServerLink` in `mcp-server/link.ts`, started from `boot.ts`, stopped at shutdown): while the token is registered, one signed `POST <url>/v1/approvals` is kept open (the server holds it up to 25 s), errors back off the same way, and every approval received goes to `holdServerApproval` (see Tool policies and approvals).
- **A metro notice** (`channels/notice.ts`: `from: metro://metro`, `event: {type: 'system', source: 'metro'}`) goes through `emit`, the bus and the channel relay like any event, so scope, live events, the GET stream rule and replay apply, but the inbound relay skips the sender allowlist for it (it comes from the daemon, not a person) and shows its text as it is, not as a webhook note. `/api/tail` does not show it.
- `hooks/guard.mjs`: `mcp__metro__tool_search` is allowed on every thread; `mcp__metro__tool_call` is a connector call, so the main thread gets the connector wording (run it from a background worker) and a subagent runs it (the server applies Block and Ask itself). `packages/cli/test/hooks.test.ts`, `test/mcp-server-token.test.ts`, `test/mcp-server-tools.test.ts`.

### Sign-in and ownership (WorkOS)

- The page signs in through api.metro.box with WorkOS (Google, Microsoft, GitHub, or a code by email).
- **Email code sign-in (WorkOS Magic Auth)** exists because WorkOS's Microsoft OAuth only takes personal Microsoft accounts (it always uses the `/consumers` authority), so a Microsoft 365 work account (anderra.ch, mcigroup.ch) could not sign in (2026-09-26). `POST /api/auth/email/start {email, intent?, invitation?}` has WorkOS email a six-digit code (valid 10 minutes; 5 sends per address per 10 minutes); `POST /api/auth/email/verify {email, code, intent?, invitation?}` redeems it and answers `{hash}`, the same hash the OAuth callback redirects to (`#/auth/<handoff>`, `#/waitlist?joined=1`, `#/login?refused=…`), after the same `admit` (`auth/email.ts`). A wrong or expired code is 400 with a sentence. The invitation token rides on both steps so the invite is accepted in the same sign-in. **Every sign-in that lands with no organization also accepts the pending WorkOS invitations for the user's email** (`acceptInvitationsFor` in `workos.ts`, `withInvitations` in `routes.ts`, then a refresh into the first organization), because the page keeps the invitation token only in the tab that opened the link, and an invitee who logged in from another tab was told "No Metro account" (2026-09-26). A failure there is logged and the sign-in goes on as before. Magic Auth must be on in the WorkOS dashboard (Authentication, Magic Auth). Zero cookies: the page keeps the tokens and sends `Authorization: Bearer` to metro.box and to every box.
- **The owner check lives in one place:** `routes/bearer.ts` `installBearerSessions` refuses a token for another organization with 403 (`test/bearer-session.test.ts`). The agent, account, connector, Claude, model, server and terminal APIs only check that a session exists, plus `requireAdmin` where listed. There is no per-API `authorize` hook and no `?project=`: the daemon ignores a `project` query; `/api/mode` has no `project` field (api.metro.box answers `{mode: 'hosted', owner: null, version}`).
- **A box verifies the token offline** (`packages/http/src/workos-token.ts`, RS256 against the WorkOS JWKS cached at `<agents dir>/.jwks`). **The owner is the organization: the token's `org_id` must equal `.owner`**, else 403.
- **The page's organization belongs to the tab, the session to the browser** (2026-10-16, see `docs/HISTORY.md`; `auth/account.ts`). `metro.account` (localStorage) holds the one WorkOS session: the newest refresh token, the user, the `sessionScope` marker and the token of the organization last used. Each tab keeps its own organization and token in memory and in `metro.account.tab` (sessionStorage, bound to the marker), so a switch in one tab never moves another tab, bumps its scope or fails its requests. Other organizations' access tokens stay in the tab's memory until they expire (`organizationAccount`), never in storage: switching back is free, and the operator dashboard rotates once per organization with `/api/auth/switch` and keeps the current organization's token (`keepOrganizationAccount`, no switch back). **A switch is bound to the session, not the scope** (`selectOrganization`, `fetchOrganizations`): queued behind another switch it runs from wherever the tab is; every rotation runs in `serialize` under the Web Lock and reads storage first, so a refresh token is never sent twice. `OrganizationGate` opens the routed organization through `openOrganization` (`auth/org-route.ts`): a stale open is dropped, an `AccountChangedError` is retried, and only a refusal (not a member, a dead session) offers another account; a sign-out goes to the login, any other failure offers Try again. **Only a refused refresh of the tab's own organization clears the session**; a failed cross-organization switch never does. On a tab's scope change the app cancels its in-flight queries (`dropStaleQueries`, except the user's organization list), `AccountChangedError` is never retried, and `forOrganization` binds a read to the organization in its key. `test/org-switch.test.ts`, `test/dashboard-auth*.test.ts`, `apps/app/test/org-switch-queries.test.ts`.
- `METRO_OWNER` (`--owner`) is written to `.owner` only when no organization owns the box yet, so a unit's old value never undoes a move (`boot/local-owner.ts`). A `.owner` still holding a wallet address reads as no owner.
- **Who gets in, who may create an organization** (`auth/operator.ts`; Less, 2026-09-26): a login is let in when the user is approved on the waitlist, is the operator, or is a member of an organization (an invited person, no approval needed). **Only an approved user or the operator may create an organization** (`mayCreateOrganization`, `POST /api/auth/organization` answers 403 otherwise). A member's login no longer marks them approved (only the operator's does), so being invited never grants the right to create one; a member removed from every organization and never approved is turned away again.
- **An invitation can open metro.box's own login** (2026-09-26): with the WorkOS dashboard's invitation link pointed at `https://metro.box/`, WorkOS adds `?invitation_token=`; the page keeps it for the tab (`auth/invitation.ts`, `sessionStorage` `metro.invitation`), shows the login with a note (any of Google, Microsoft, GitHub, the account the invitation was sent to), sends it as `invitation_token` on `/api/auth/login`, which keeps it with the sign-in state and passes it to WorkOS's `authenticate` with the code, so the person joins the organization in the same sign-in. A malformed token is a 400. Why: WorkOS's hosted invitation page offered only Google to a Microsoft account (Less, 2026-09-26).
- **Invitations** are WorkOS's (`sendInvitation`): the email link goes to WorkOS's own AuthKit page (`real-quill-71.authkit.app/invite`), which signs the person up, accepts the invitation and then sends them to `/api/auth/callback` with a code but without metro's `state`. **metro never exchanges a code it did not ask for** (that would let anyone sign a visitor into another account): a stateless callback with a code redirects to `https://metro.box/#/login?invited=1`, where the page says the invitation is accepted and asks to log in with the same account; the membership already exists, so that login lands in the organization. A callback with neither state nor code is still a 400. (Before 2026-09-26 the invited person saw "this sign-in link is stale".)
- Single-path owner routes (`server/*`, `terminal/api`) go through `sessionRoute` in `http/api-http` (path and method match, OPTIONS, 405, session, admin by method, `apiFailure`). One-time single-use tokens with a TTL (OAuth `state`, terminal tickets) are `ticketStore` from `core/tickets`.
- **`requireAdmin` gates:** stop and restart, the update POST, the Terminal, agent delete, the bundle and restore, `POST /api/owner`, and non-GET Claude `login`, `session`, `setup` routes. Keep the `ADMIN_ONLY` pattern in `claude/api.ts` matching the full path.
- metro.box: the launch, server list and admin APIs take the bearer only; the owner is always the signing organization, never a value from the body. Operator pages check the stored email against `OPERATOR_EMAIL`. Waitlist status is checked at the callback and on every refresh.

### Export and import

- A `.metro` file is gzipped JSON sealed with a **passphrase** (`packages/client/src/export/passphrase.ts`: PBKDF2-SHA256 600k, AES-256-GCM, envelope `v: 2`; WebCrypto when the platform has it, else the same maths in pure JS, `export/primitives.ts`, for the phone). A `v: 1` wallet-sealed file fails as not a metro export file.
- The agent id and key are never in the file; import fills in the local agent's. Import modes `append` and `overwrite` never delete what the file does not mention.
- `GET /api/agents/<id>/bundle` and `POST /api/agents/restore` move the plaintext bundle between the page and its own box only, never to metro.box. The bundle carries no connector (`connectors: []`); a restore still accepts an old bundle and ignores its `connectors` (answers `connectors: 0`).
- **No model setup in a bundle or a `.metro` file** (2026-10-15): the model setup belongs to the organization (see Organization models). A new file has the sections channels, skills, memory and sessions; an older file's `model` section is read past and dropped, and a restore ignores a model setup.

### Stations

- **XMTP single writer:** only one process may write an MLS inbox. A second burns the 10-installation budget. So `metro serve` refuses a second instance, and two boxes must never run the same agent. The db3 path is home-relative.
- XMTP accounts are ZeroDev Kernel smart accounts on Base (`smart: true`); older plain-key accounts cannot hold a name. A name claim is page-only and permanent.
- **WhatsApp:**
  - `connectionReplaced` is terminal, so a double run does not loop into a 463 time lock.
  - **Only `tctoken` and `lid-mapping` are persisted** (`token-store.ts`), because a 1:1 send without the contact's token gets `ack error 463`. Do not persist other Signal key types: `creds` is never written back, so half a Signal state is worse than none.
  - **A message key is never synthesized.** Keys come verbatim from a per-account LRU filled from every upsert and every send; a group key needs the original `participant`. An unknown message fails loud (`whatsapp_unknown_message`).
  - **The send verdict is read from `sock.ws` (`CB:ack,class:message`)**, which bypasses Baileys' buffered emitter. 463 throws `whatsapp_account_restricted`. No ack in the window counts as sent.
  - `sock.end()` must be awaited. Never run a second Baileys client on live credentials to test.
  - **The train reports each account's live state** (`reportsStatus`, `ConnectionWatch` in `connection.ts`), never a saved flag (the old `connected: true` came from `sock.user`, which stays set after a logout; Lisa, 2026-10-21): `connected` on Baileys' `open`; a 401 (`DisconnectReason.loggedOut`) and the `conflict type=device_removed` stream error (whatever its code: without one Baileys files a conflict under 440, `connectionReplaced`) are `logged_out` until paired again, and never reconnect; `connectionReplaced` and a failed (re)connect are `disconnected`; any other close is `connecting` with the reason, and `disconnected` once it has not come back for 3 minutes (`RECONNECT_GRACE_MS`, the first drop's time kept through repeated drops). Open is not trusted alone: a websocket that is not open (`sock.ws.isOpen`) or no frame for 90 s (`SILENT_MS`; Baileys pings every 30 s) reads `connecting`. It is checked every 30 s and on every read, and each change of state writes one stderr line (`whatsapp[<account>] state <from> -> <to>: <reason>`, the account id only), which the daemon logs as a warning.
  - **Pair again** (`pairAgain: {identity: 'phone'}`): the same QR or pairing code as attach (`WhatsappLogin` with `expect`), and only the same number: a pairing code for another number is refused before WhatsApp is asked, and a QR scanned by another phone is logged out again (`sock.logout()`) and stored nowhere. Only `phone` and `credentials` change; the token, names, history and channel files stay, since they belong to the WhatsApp account, not the linked device. A link replaced while it still worked stays in the phone's Linked Devices until removed there.
- Telegram user account (`telegram`): the session is a full-account secret, single writer, ToS risk.
- **Threema:** Gateway ID in end-to-end mode only; the private key never leaves the train. The callback checks the MAC first; a down train answers 503 (Threema retries), a refusing train 400 (it stops).

- **A route is `{primary: {connection, model}, fallbacks: [{connection, model}], helpers?: {primary, fallbacks}, effort?: {main?, helpers?}}`**, 8 fallbacks at most (helpers too). `connection` is a `model_connections.id` of the same owner; a `local:` step (a box Claude login before 2026-10-16) is refused with a sentence that points to the Claude subscription, and a stored one is dropped on read. ### Voice calls (`apps/daemon/src/voice/`, issue #112)

- **The box answers a Stage call itself** (Less, 2026-10-01, option B): Stage's `stage.box/callInvite:1.0` and `stage.box/callSignal:1.0` (JSON, Stage's `packages/client/src/xmtp/call.ts`) are registered in the XMTP train, which emits them with `payload: {contentType, call}`; `boot.ts` hands every such event to `voice/calls.ts` (`isCallEvent`, `onCallEvent`) **before the bus**, so a call never reaches the agent as text, `/api/tail` or the replay ring. `read` drops call signal rows and shows an invite as `[callInvite]`. Signals go out through the train's `callSignal` action (`shouldPush: false`, no fallback, like Stage).
- **Who is answered:** an invite under 40 s old (the caller's Stage stops ringing at 45 s, so an older one is only logged), one call at a time, voice on with a key (`voice.json`), and a caller the channel's **approvers** pass (`mayApprove`), since the call drives the agent with its full tools. A ringing invite the box will not take is answered with `decline {callId}`, which ends a one-to-one call on the caller's side at once ("Call declined"; Stage ignores a decline in a group). A new invite from the caller of the current call on the same line ends that call first (the caller's Stage has given it up) and is answered. A call started in a group is answered too, but the box connects only to the caller's peer (offers from other members are ignored), so it is a one-to-one call inside the group.
- **The box always leaves a call it joined**, whoever hangs up, because Stage keeps a call alive while anyone is in its roster (`activeCall` in Stage's `callMachine.ts`: a non-empty roster and a signal in the last 2 hours; a one-to-one call stops being joinable 45 s after the last signal, a group call does not). Before beta.239 the box sent no `leave` when the caller hung up, so in a group (the #112 issue chat, Less, 2026-10-01) Stage kept showing Join instead of Call for 2 hours, and each Join then hang up started those 2 hours again. A failed `leave` is tried once more after 3 s. **On shutdown** (Update, Restart, Stop, SIGTERM) `leaveCallsForShutdown` sends the current call's `leave` before the trains stop (2 s cap); a `systemctl stop` signals the trains too (default `KillMode`), so there the start sweep is what sends it. **At start** (`sweepLeftoverCalls`, 5 s after the trains spawn, retried every 10 s up to 12 times until the XMTP train answers) the train's `callLeftovers` action reads each conversation's last 100 messages of the last 24 hours (Stage rebuilds a call from the last 100 messages, and anyone's signal keeps it alive, so the box's own `join` can be older than 2 hours), lists every `join` this inbox sent with no `leave` of its own after it (its own messages are in its db3), and the daemon sends the missing `leave`s; this also covers a hard kill and calls from before this change.
- **The flow is Stage's callee side**: `join {callId, from: <our peer uuid>}`, wait up to 45 s for the caller's `offer` addressed `to` our peer, answer with the full SDP after ICE gathering (2.5 s cap, no trickle), `leave` on hang-up. `voice/peer.ts` is werift: Stage's STUN servers, `max-bundle`, the negotiated `media` data channel id 0 (sends `{"audio":true,"video":false,"screen":false}` when it opens), audio `sendrecv`, video `inactive`, **UDP ports 40000 to 40100** (the server's firewall or security group must let them in).
- **Audio:** caller Opus 48 kHz decoded with opusscript, averaged down to 16 kHz, sent to ElevenLabs Scribe v2 Realtime (`voice/scribe.ts`, VAD commit after 0.5 s of silence). Replies go to ElevenLabs Flash v2.5 over the stream-input WebSocket (`voice/speech.ts`, `auto_mode`, `pcm_24000` doubled to 48 kHz, one socket per reply plus a warm spare), cut into sentences (the first may end at a comma, `speakable.ts`), Opus-encoded and paced every 20 ms (`audio.ts`; silence frames between replies).
- **A call goes into the agent's own Agent SDK conversation** (`voice/shared.ts`, `voice/shared-talk.ts`; Less approved one conversation for chat, calls and workers, 2026-10-05): no second Claude Code session, no copied chat history. The daemon sends ephemeral, scoped call notices (`started`, `heard`, `speech`, `ended`) over the runner's `/mcp` session; they never enter the bus or the SSE replay, and each GET reattach sends only the current call route, so a missed hang-up clears stale call state. The runner turns them into `<call line from callId generation sourceId>` blocks (`callWords` in `sdk-runner/src/rules.ts`). A message the caller types on the call's line during the call carries `call_id`, `call_generation` and `call_source_id` in its channel meta, so it can be answered by voice too.
- **Speech is an explicit action on `send`**: `speech: {callId, generation, sourceId}` speaks the text on the call, audio only, never a chat post. The source must be a real input from the caller on that exact live call (1,024 sources at most, then the call ends), each source speaks once (the same text again is a duplicate, another text is refused), and the channel's write policy applies at acceptance and again before the audio. The agent gets status notices (accepted, queued, started, completed, interrupted, failed); transport completion is not proof the caller heard it. **Plain assistant text is never spoken**, and ordinary chat and worker output stay silent (`FRONT_RULES`).
- **Barge-in only cuts audio the caller can hear:** a partial or committed transcript of 2 or more words while speech is playing cancels the speech queue (`SharedTalk.barge`). Words said while the agent is only thinking, or a single word over its audio ("Hello?", "ok"), cut nothing. Why: beta.237 also cut while the agent was thinking, so a caller repeating "Hello?" on the first real call (Less, 2026-10-01) restarted every reply before any audio played.
- **Hang-up** revokes the call route, its pending speech and its call-bound approvals, stops the audio and the transcription and frees the slot, then sends the `leave` in the background; it never closes the SDK conversation or unrelated workers, and closing the runner's MCP session ends the call. Unusable speech synthesis (an ElevenLabs refusal such as `Invalid API key`) ends the call and leaves a safe failure fact in the conversation; nothing is posted in chat about a call unless the owner asks.
- **Approvals during a call are bound to the call** (its route and source) and go to the call's chat (see Tool policies and approvals). A spoken yes never approves.
- **Speech to text listens in one language** (`language` in `voice.json`, `language_code` on the Scribe socket): default `en`, the page offers English, French and Detect (`auto`, no `language_code`). Why: on Less's call of 2026-10-01 Scribe's own detection turned English speech into Russian or Portuguese fragments.
- **`voice.json`** (`voice/store.ts`, Metro's agents dir, 0600): `{provider: 'elevenlabs', apiKey, voiceId, language, enabled}`. There is no call model (2026-10-15): a call thinks with the Gateway page's model, and the page neither shows nor sends `model`. `GET /api/voice` answers `hasKey`, never the key; `PUT` (admin) patches it, an absent or empty `apiKey` keeps the stored one and `null` removes it. The page's Voice section (`VoicePage.tsx`) needs `VOICE_SINCE`; it shows Language only when the daemon answers a `language` field. `METRO_ELEVENLABS_URL` points both sockets elsewhere (local tests).

The metro skill and the guard (orchestrator-only main thread) apply unchanged; `FRONT_RULES` (`rules.ts`) is appended to the system prompt (Settings, Agent SDK setup). The runner runs from `$HOME`, since auto memory is keyed by the cwd.
- **A model change applies live, with no restart**: when the effective primary model of the delivered organization setup changes (the 60 s fetch, or `POST /api/model/sync` after a change on the page; see Organization models), the daemon sends `notifications/metro/model {model}` to the session holding `/mcp` (`switchModel` from `createMetroMcp`, wired through `boot.ts` and `local-mode.ts`; the method name is a contract between `mcp/index.ts` and `sdk-runner/src/link.ts`). The conversation and the session id stay, and Claude Code tells the model its new name in the system prompt. A worker started after the switch uses the new model; one already running finishes on its own (on Anthropic the gateway pins its requests to the new model anyway). The change is made on api.metro.box, so the box cannot refuse it; a runner that is not up loads the new selection from the agent's view of `model.json` at its next start. **Fallback models need nothing from the runner**: the gateway walks the list per request whatever model id the session sends, so a fallback change neither switches nor restarts the session, and the allowlist keeps only the first model.
- **Restart and the ledger**: the session id lives in `~/.metro/agent-session.json` (agent home) and is resumed when its transcript exists. Chat messages pushed but not yet consumed (seen in `user_message_uuids` or in a `command_lifecycle` with `state: 'started'`) are kept in the same file and pushed again after a restart: a message in Claude Code's queue at a kill is lost on resume, and the daemon's ring will not replay it. A local process lock allows only one SDK runner per home and releases on process exit. An initial status-write failure refuses startup before MCP connects. The task ledger in the same file keeps each helper's short `description`, never its prompt, so a restart lists the helpers from before it with their description (not their agent, times or model), and never lists the ledger's own failed-turn and interrupted-input rows as helpers.
- **Live activity**: `~/.metro/agent-status.json` (0600, bounded, atomic) records real lifecycle events, main-thread status, active tools, worker state, approvals and safe error summaries. `/api/claude/session` returns the parsed snapshot. The Right now full view (`RunPage.tsx`) polls every 2 seconds while open; it shows stopped and stale snapshots explicitly. It retains at most 30 task rows, 20 active tools and 40 events, and of a helper only its one-line Agent `description` (160 characters): never prompts, progress descriptions, thoughts, summaries or tool I/O. An unclassified failure records only its error type name (`errorName`, a plain identifier ending in `Error`, never `Error` itself); the raw error is printed only with `METRO_RUNNER_DEBUG=1 metro agent`, to that terminal, never to a file or the page. It does not stop an individual worker. Terminal remains available for diagnostics; Conversations holds transcripts. `bun run sdk-runner-activity` proves live HTTP updates and chat during a background worker using the real SDK with a free scripted local upstream.
- **Calls** (see Voice calls): call words, typed chat and status notes go into bounded lanes that the runner schedules fairly at observed safe boundaries, with no priority interrupt, timeout restart or blind replay; the SDK gets at most one input it has not consumed yet, and only its exact consumption frees the slot. Hang-up removes call entries still in the host queue; input already handed to the SDK cannot be taken back, so its consumption is still tracked. Queueing input never interrupts a write or answers an approval.
- **Compaction**: Claude Code compacts by itself near the model's window, mid-turn if one message pushes it there. Startup compacts a saved conversation at 120,000 input and cache tokens (`COMPACT_AT`) before ordinary inputs, and the runner compacts when idle at the same threshold, never during a live call or with input pending, then waits for 60,000 tokens of growth before asking again. Measured 8 to 23 s per compaction; it can take minutes.
- **The store and the Claude Code it runs**: `metro agent` copies `runtime/sdk-runner` into `~/.metro/sdk-runner` (`METRO_RUNNER_STORE`) and runs `bun install` there with `optional = false` and `peer = false` in `bunfig.toml`, plus exactly one of the SDK's platform packages, at the SDK's own version (`claudePackage`: `@anthropic-ai/claude-agent-sdk-<platform>-<arch>[-musl]`, the same pick as the SDK's, musl when Node reports no glibc), about 233 MB. **The runner runs the Claude Code bundled with the pinned SDK** (`METRO_RUNNER_CLAUDE` names the store's binary; without it the SDK finds its bundled one): the SDK and its Claude Code are released together (0.3.N carries 2.1.N), so there is no version gap to watch, and **one number moves both: `@anthropic-ai/claude-agent-sdk` in `packages/sdk-runner/package.json`**, with each Metro release that bumps it. Why the bundled one: the SDK's control protocol is pinned per Claude Code release, so a separately updated `claude` would drift from the SDK (review, 2026-10-02).
- `bun run sdk-runner-check` (`scripts/sdk-runner/run.ts`, on `harness.ts`) boots the daemon's MCP code in-process with a fake train and a temp policy, starts the real runner and Claude Code through this box's gateway, and prints timings for chat, delegation, approvals, calls (including a call cutting into a chat turn), a restart, a crash with a queued message and a compaction. **`SDK_RUNNER_CHECK_ROUTE=key` runs it on the gateway's Anthropic API-key path**: the daemon's gateway in-process with an Anthropic connection holding a stand-in key, and a stand-in upstream (`key-route.ts`) that counts what reaches "Anthropic" (`x-api-key`, no `authorization`, no OAuth beta, no `x-metro-key`) and relays it to api.anthropic.com with the box's Claude login, since a box has no real key to spend; only Anthropic accepting a real key is not covered. `bun run sdk-runner-long` (`long.ts`) is a long day in small: 200 chat messages (questions, acknowledgements, long notes, group chatter, recalls, bursts of three), 20 background workers and a call, and writes the front's context, cost per model, compactions and the react, reply and call timings to `SDK_RUNNER_LONG_OUT`. `bun run sdk-runner-model` (`model.ts`) checks the live switch through the real Model API and gateway: by default against a scripted upstream (`scripted-upstream.ts`, free) on an OpenRouter route, then a model change, a worker, a switch to another provider, a worker there, and a fallback model that takes over when the first one answers 429, printing the effort each request reached upstream with (`low` for the front, `max` for workers, per-turn ones included); with `SDK_RUNNER_CHECK_ROUTE=key` with real Claude on the API-key route (Sonnet 5.5, Haiku 4.5, back to Sonnet 5.5, then a recall of what was said before both switches). It prints the models each step reached upstream, the session ids (one) and the restarts (none). ### mcp.metro.box (`apps/mcp`)

The one MCP endpoint every agent uses for its organization connectors (`docs/MCP-SERVER.md`): two tools, `tool_search` (Claude Code's `ToolSearch` design over every assigned connector's tools) and `tool_call` (1 to 10 calls in parallel, run from here through the safe egress, so connector credentials never reach a box). A tool is `<connector key>.<tool>`; the key is the slug of the connector's name, with `-2`, `-3` in connector id order when two assigned connectors share one. The policy is the organization and agent layers (the stricter wins, a per-tool rule beats its group, the group comes from the vendor's `readOnlyHint`, an unknown tool is write), read from Postgres on every call. Block hides a tool from `tool_search` and refuses it; Ask records an `mcp_approvals` row and answers `needs_approval` with its id, the daemon relays it to the owner and posts the answer back, and the agent repeats the same call with `approval: "<id>"`, which works once, for exactly that tool and those arguments (SHA-256 of their canonical JSON), within 10 minutes of the answer. **The row records who made the call** (2026-10-23, `0020`): `origin` `box` for a box's MCP token, `key` with the access key's id in `token`; each caller has its own pending row for the same call (the pending index takes `coalesce(token, '')`, so a box's own request and an old row without origin share a slot), and `POST /v1/approvals` sends `origin` and, for a key, its `keyLabel` (`agentTokenLabels`), never the key or its id. Redeeming is not bound to the caller. Rows from before `0020` have no origin; the store's fallback for a database without those columns went on 2026-10-26. Unanswered requests expire after 24 hours. **Answered rows are kept 7 days**: each machine deletes `mcp_approvals` rows in state `allow`, `deny`, `used` or `expired` whose last change (`answered_at`, else `requested_at`) is more than 7 days old, at start and every hour (`startApprovalPruning` in `prune.ts`, `pruneApprovals` in `approvals.ts`; an unref'd timer, never fatal, one info line with the count). A pending row is never pruned: it expires after 24 hours as before (when its agent next asks or polls), and goes 7 days after that. Two machines pruning at once is fine, since it is one plain `DELETE … WHERE`. `tool_search` ends with a `Call these with tool_call: {...}` line naming the first result, and also answers `structuredContent` `{connectors: [{key, name}], tools: [{name, title, connector}]}` (every usable connector with its metro.box name; a tool's `title` is the vendor's, else `annotations.title`, else its id in words, `toolTitleOf`), and text names a connector `key (Name)` unless the name is only the key in other letters (`connectorLabel`), and a miss names the connectors and suggests a broader query or `select:`; an unknown tool or connector in `tool_call` answers `not_found` with up to 3 closest names (bigram similarity, `closestNames`) and "Run tool_search first"; a malformed `calls` answers with the expected shape. The two tool definitions and descriptions live in `@metro-labs/http/mcp-server-tools`, shared with the daemon's fallback. **Tool lists are answered from a cache, never by waiting on a vendor that has a list** (2026-10-29, after a dashboard waited 52 to 75 s and one unreachable vendor, Slash, held every `tool_search`; Claude Code's ToolSearch also searches only what it already holds): `ToolLists` (`tool-lists.ts`) keeps each connector's redacted list in memory (the 500 most recently read connectors) and in Postgres (`connector_tools`, so both machines and a restart share it); a list younger than 5 minutes (`TOOL_LIST_TTL_MS`) is used as it is, an older one is answered at once and read again in the background (one flight per connector, which first adopts a fresher row the other machine wrote), and a connector never listed waits 8 s at most (`FIRST_LIST_WAIT_MS`) and then reads `listing` while the read goes on (30 s at most in all). A failed read is kept with its message and not tried again for a minute (`FAILURE_PAUSE_MS`); an older list stays in use meanwhile. `tool_call` checks a tool against the held list and reads it again (8 s at most) when the tool is missing from an old one, and always before a call whose rule depends on the tool's kind (read or write), so an old list never decides a policy. A failure that only concerns the calling agent (`not_found`: unassigned meanwhile) is kept as `unavailable`, since every agent of that connector reads it. `tool_search`'s `structuredContent.connectors` carries each connector it consulted with `status` (`ok`, `listing`, `signin`, `unavailable`) and `error`. **A third tool, `list_connectors`, is served only by mcp.metro.box** (`list.ts`, never in `mcpServerTools`, so a box's daemon, which picks `tool_search` and `tool_call` by name, never shows it to its session; everything stays MCP, no HTTP route, Less 2026-10-29): it answers from the cache without waiting on any vendor (a never-read connector reads `listing` and its read starts), light by default: `structuredContent.connectors: [{key, name, status, error?, listedAt?, toolCount, icons}]`, where `icons` is MCP's Icon shape with a URL, never the image: **first the icons the connector's own server declares** in its initialize answer (`serverInfo.icons`, MCP 2025-11-25; ## Deploy and operations

- **Merging to `main` auto-deploys `apps/api` to Fly** (app `metro`, region `iad`, no volume). Do not merge unfinished work. Land via PR (squash merge). `DATABASE_URL` is the one required secret, plus WorkOS and the launcher's AWS and Tailscale secrets.
- **Merging to `main` deploys mcp.metro.box** when it touches `apps/mcp`, `packages/connectors`, `packages/http`, `packages/core`, `bun.lock` or the workflow (`.github/workflows/mcp.yml`: the connectors and mcp tests, then `flyctl deploy . --config apps/mcp/fly.toml --dockerfile apps/mcp/Dockerfile` with `FLY_API_TOKEN`; also `workflow_dispatch`). It runs no migration, so a change that needs a new column ships its migration in an api deploy first.
- The app deploys to Netlify as the Expo web export (the root `netlify.toml`); merging to `main` switches metro.box.
- Boxes run `metro serve` under systemd (`metro service install`). `systemctl stop metro` keeps it stopped; `metro stop` alone is restarted by the service. The unit runs as `User=metro` (see Three users on every box); SSH in as root and look in `/var/lib/metro/.metro`.
- **One public address per box: Tailscale Funnel** (`net/tunnel.ts`). The node name `metro-<6 chars>` lives in `<agents dir>/.node`; a pre-written valid name is kept. An existing Funnel that answers with this owner is adopted and watched.
- After a daemon update the watcher restarts the session on the new version, and the runner reconnects to `/mcp` by itself. A connector change needs nothing on the box: mcp.metro.box serves it at the agent's next call.
- **Deleting a box never lists, filters or guesses** (`apps/api/src/aws/deletion.ts`). It reads the stored instance id of the row the organization owns, asks EC2 for that one id, refuses unless the instance's `metro` tag is the node of the row's address and its `metro:agent` tag, when present, is the row's id (boxes launched before 2026-09-29 carry only `metro` and `Name`; no organization tag, since a move changes the owner), asks for exactly the volume ids attached to it and refuses a disk attached elsewhere or tagged for another box, then compares both, and the state, with what the dialog showed. Disks go through `DeleteOnTermination` (set on the exact device first when off, then checked again), so there is no `DeleteVolume` call at all. Only then `TerminateInstances` with that one id, and the row is removed last. **A box no longer on AWS only leaves the list** (Less, 2026-09-29): `InvalidInstanceID.NotFound` (state `not-found` in the view) or `terminated` means no AWS write at all, only the row goes, and the dialog says "Server not found on AWS, only the agent entry will be removed". NotFound on a row under 10 minutes old (`addedAt`) is still refused as just launched, since EC2 answers NotFound for a few seconds after a launch. `shutting-down` is refused (try again). Only the `InvalidInstanceID.NotFound` code is classified (`described()`): any other describe error (auth, throttling, unreachable) refuses and keeps the row. A row with no instance id (added by hand) is removed without asking AWS (state `not-launched`). The core logs `deletion: entry only, nothing is deleted in AWS` with `by`, owner and agent. The Tailscale machine stays: the api holds an auth key, not an API token, and the page says so. **The operator may delete a box for another organization** (Admin, Agents, Delete; Less, 2026-09-29): `/api/admin/servers/<id>/deletion` finds the row by id across organizations, only behind the operator email check (an organization's `admin` role does not open it), and runs the same `deletionView`/`confirmDeletion` in `deletion.ts`, so every check above holds; it logs `admin: deleting a server for its organization` before AWS is called and `admin: server deleted for its organization` after (`admin: agent entry removed for its organization, entry only` when nothing was on AWS), both with the operator's user id (`by`) and the owner.
- **The Server page's charts come from CloudWatch only** (Less, 2026-09-29: "rely just on this"), so they show while a box is down. **Memory and disk are sent by the daemon itself** (`server/cloudwatch.ts`: once a minute, `CWAgent` `mem_used_percent` and `disk_used_percent` of `/`, the CloudWatch agent's names, signed with the instance role read from IMDSv2; the first send after a start also carries `server_booted` when the server is up under 5 minutes, else `metro_started`, valued at the start in epoch seconds, for the restart lines), not by the CloudWatch agent: the daemon runs as `metro` and the helper cannot install a package. Off EC2 or without a role it sends nothing and logs once; a failure only logs. A launch asks for the `metro-box` instance profile and starts without it when AWS refuses it. The role and the policy are in `docs/ISSUING-SERVERS.md`. **A box has charts when Metro launched it, or when it is linked to its instance in a connected AWS account** (Less, 2026-10-03, issue: connect AWS with one link; the 2026-09-29 per-box role link and Admin Charts button stay gone): the other account's `metro-access` role does the reads and gives the box that account's `metro-box` role. The beta.223 sampler (`server/resources.ts`, `~/.metro/resources.jsonl`, `/api/server?range=`) is gone.
- **Moving a box to another AWS region:** stop the instance, image the stopped disk, `copy-image`, `run-instances` with the same type and tags and no user data, then wait for `/api/mode` on the same Funnel address. **Keep the old instance stopped until terminated** (single writer). Then fix the `agents` row's `instance_id` and `launch_region` from inside the Fly machine.
