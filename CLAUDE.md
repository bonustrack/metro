# CLAUDE.md

## What Metro is

A relay bridging chat networks (XMTP, Telegram, Discord, WhatsApp, inbound webhooks) to an MCP server. One always-on Fly process serves MCP over HTTP and supervises one subprocess ("train") per station with a train. Inbound network message → station → in-process bus → MCP event. Outbound: agent tool call → station verb → network.

## Monorepo layout

Bun workspaces (`bun@1.4.0` — the relay REQUIRES ≥1.4: Bun 1.3.9's HTTP clients, fetch and `node:http` alike, never tear down an aborted upstream connection, so every relayed stream whose client vanished would leak a live vendor socket; `ci.yml` passes `bun-version: '1.4.0'` to the shared workflow and the Dockerfile pins the same): `apps/*`, `packages/*`.

- `apps/mcp` — the core, `@metro-labs/mcp`.
  - `src/mcp/` — MCP server, sessions, tool dispatch, `str()`. No per-channel transport logic.
  - `src/channels/` — `InboundRelay` (`inbound.ts`) turning bus events into `notifications/claude/channel`. Depends on `mcp/`, not vice-versa.
  - `src/monitor/` — the lightweight Monitor transport (`api.ts`).
  - `src/daemon/` — boot, HTTP, supervisor, logging, secure-fs, protocol, event bus. **Never imports `mcp/`** — deps are injected from `boot.ts`, or madge breaks.
  - `src/stations/` — registry, types, account-store, attachments, lines, attach.
  - `src/db/` — drizzle schema, materialize, agent/key/allowlist maps, scope predicate.
- `apps/ui` — the control panel (Vite + react-native-web + `@stage-labs/kit`).
- `packages/*` — six stations: `xmtp`, `telegram-bot`, `telegram`, `discord-bot`, `whatsapp`, `webhook` — plus `packages/cli`.
  - **`telegram` is the USER-ACCOUNT station and `telegram-bot` is the Bot API one.** Until `0018` the names were `telegram-user` and `telegram`: the plain name swapped meaning from bot to user account. `0018` rewrote `stations.station` in that order (bot out of the way first, or the two would collide on `unique(station, account_id)`), and everything derived follows the new names: `metro://telegram-bot/…` lines, `telegram-bot-accounts.json`, the `TELEGRAM_BOT_*`/`TELEGRAM_*`/`DISCORD_BOT_*` env vars, and the train stubs. A pre-`0018` line or file name refers to a station that no longer exists and fails loud, not sideways. The migration is plain UPDATEs, so it IS hand-reversible, unlike `0015`.
- **`packages/cli` is `@stage-labs/metro`, the ONLY published package in the repo.** Everything else is `private: true`. That name is not new: it is what this repo published up to `0.1.0-beta.15` back when it was a stdio MCP, before the rename to `@metro-labs/mcp`. The CLI continues the version line rather than starting a new one, so an existing `npm i -g @stage-labs/metro` upgrades into it.
  - It ships `dist` only (`files`), `bin.metro` → `dist/cli.js`, `engines.node >= 22`, and `publishConfig.tag` is **`beta`** — publishing without that tag would move `latest` and hand the beta to everyone.
  - **Publishing is the `Publish @stage-labs/metro` workflow, run by hand from the Actions tab** (`.github/workflows/publish-cli.yml`, `workflow_dispatch`, with a `dry_run` input that builds and packs without publishing). It must `bun install` and BUILD before packing: `dist` is gitignored, so a bare `npm publish` on a fresh checkout ships a tarball holding nothing but `package.json`. It publishes `--tag beta --access public --provenance`. **The tag is passed explicitly even though `publishConfig` already carries it**, because `npm publish` announces `with tag latest` either way — npm reads that notice from the raw config (`publish.js` line 76) while the upload uses the flattened `opts.defaultTag` (`libnpmpublish` line 99), so the message is wrong and only the message. Auth is the repo's `NPM_TOKEN`, which has to be an npm AUTOMATION token: a personal login is refused with a 403 demanding 2FA.
  - It uses NO Bun API and its shebang is `node`, so the published artifact runs anywhere Node 22 does. The rest of the repo runs under Bun; do not import `Bun.*` here.
  - **`metro update` resolves the highest dist-tag, never `latest`.** This package's `latest` is stuck at `0.1.0-beta.0` while `beta` is the real head, so an update that trusted `latest` would DOWNGRADE. `newestOf` picks the greatest parseable version across all tags and `isNewer` refuses to move sideways or backwards; `test/version.test.ts` pins both, including that a release outranks its own prereleases and that `beta.10` beats `beta.9`.
  - **`metro login` authorizes ONE AGENT, not an account.** The agent page mints an `ma_` code (`POST /api/agents/<id>/code`), you paste it back, and the CLI holds a `typ: 'agent'` token for that one agent. **The same code is what `metro start <id>` claims**: one store (`daemon/agent-pair.ts`, `makeCodeStore('ma')`), two consumers (`/api/cli/claim`, `/api/run/claim`). There is no browser flow in the CLI at all — the ephemeral `127.0.0.1` listener it replaced cannot work over SSH, because the listener is on the server's loopback while the browser is on your laptop. Deleting it also deleted its whole attack surface: the nonce, the 16 KiB body cap, and the cross-origin POST that made both necessary. Do NOT reintroduce a browser flow to "help" desktop users.
    - **An agent token is a DIFFERENT TOKEN TYPE from a session, and that is the security boundary.** `signAgentToken` mints `typ: 'agent'` carrying `{sub: subject, agent: id}` (the subject is the wallet address, or an email on a token minted before SIWE); `verifySession` refuses it because the `typ` does not match, so `apiSession()` rejects it everywhere. A token sitting on a Linux box therefore cannot read `/api/agents`, cannot create or delete a connector, and cannot see any other agent. It can do exactly three things: `GET /api/cli/mcp` (its agent's relay block, no vendor credential), `GET /api/cli/session` (who it is) and `/relay/<connector-id>` for a connector its agent holds. **`agentIdentity()` (`daemon/api-http.ts`) accepts a `typ: 'run'` token on the same routes**, so a `metro start` machine reads its agent's connectors with no second sign-in. `test/cli-pair-api.test.ts` pins every direction: a session token is refused on the CLI routes, an agent token is refused on the agent admin routes, a run token is accepted, and an agent the token does not name is a 404.
    - **`POST /api/cli/claim` and `POST /api/run/claim` are the unguarded routes on this surface**, alongside the OAuth callback, and for the same reason: the caller has no credential yet — acquiring one is the point. They authenticate by holding an unguessable single-use code (`ma_` + 16 base64url, 96 bits) in an IN-MEMORY map (`daemon/agent-pair.ts`, 10-min TTL, 100 max, unref'd sweeper), mirroring `oauth-pending.ts`. The code carries `{email, agentId}`, `takeAgentCode` consumes it on EVERY path including the expired one and the webhook-refused one, and the code never reaches a log.
    - **`metro login [code]` takes the code as an argument or prompts for it hidden**, and **`metro mcp`/`metro whoami` fall back to the machine's run token** (`readRunTokens` in `store.ts`: `METRO_RUN_TOKEN`, else exactly one `runtime-<id>.json` for this `METRO_URL`) when no CLI sign-in is stored — the CLI half of "a `metro start` machine needs no second sign-in". Two run tokens on one machine are ambiguous and fall through to `NotSignedIn`.

  - **The session never leaves over plaintext.** `carriesSecretsSafely` allows https anywhere and http only to loopback, and `get()` resolves the token BEFORE the try — the first version called `tokenOrThrow()` inside the fetch argument, where its throw was caught and reported as "could not reach", silently disarming the guard.
  - **`metro claude [args...]` is a verbatim passthrough** (`src/claude.ts`): it runs `claude --dangerously-load-development-channels server:metro` followed by every argument exactly as given, parsing NOTHING — a new Claude Code flag needs no metro change. The channel flag comes first so a user-supplied flag wins on conflict. The wrapper ignores SIGINT/SIGTERM while claude runs (the TTY delivers them to claude directly) and exits with claude's own status.
  - **`metro bedrock [args...]` is `metro claude` with inference on Amazon Bedrock through a loopback proxy** (`src/bedrock.ts`, `src/bedrock-proxy.ts`, `src/bedrock-eventstream.ts`), and it exists for ONE reason: Claude Code gates Channels on a provider enum (`firstParty` vs `bedrock`/`mantle`/`vertex`/`foundry`/`anthropicAws`/`gateway`), and `firstParty` is simply "no `CLAUDE_CODE_USE_*` flag set". `ANTHROPIC_BASE_URL` never enters that check. So the proxy presents the Anthropic Messages API on `127.0.0.1`, the command launches `claude` with the provider flags scrubbed, `ANTHROPIC_BASE_URL` pointed at the proxy and a random per-run `ANTHROPIC_AUTH_TOKEN` the proxy requires, and Channels come up while every token is billed to Bedrock. `metro claude` itself stays a verbatim passthrough and is NOT touched.
    - Translation is thin because both sides are Anthropic: `model` moves from the body into the url (`claude-sonnet-4-6` → `<region prefix>.anthropic.claude-sonnet-4-6`, or whatever `METRO_BEDROCK_MODEL` pins), `stream` is dropped, `anthropic_version: bedrock-2023-05-31` is added, the `anthropic-beta` header becomes the `anthropic_beta` array, and the streamed reply is AWS eventstream frames each carrying an unchanged Messages-API SSE event. **A 400 is repaired and retried, and the repair is REMEMBERED for the proxy's lifetime** (`bedrock-upstream.ts`, `Adaptations`): when Bedrock's message names an extra input (`context_management: Extra inputs are not permitted` was the first, seen 2026-09-02) that field is dropped from this and every later request; otherwise, if betas were sent, they are dropped the same way. First-party mode makes Claude Code send fields and betas Bedrock may not know, and this is what keeps each new one from being a hard outage while costing one extra round trip once, not per request. With `METRO_BEDROCK_MODEL` pinned, `ANTHROPIC_MODEL` is set to the pin's first-party id (`eu.anthropic.claude-sonnet-4-6` → `claude-sonnet-4-6`) unless the user set one, so Claude Code's context-window and model display match what Bedrock actually serves instead of defaulting to Opus 5 (1M). `count_tokens` goes to Bedrock's count-tokens API and falls back to a chars/4 estimate.
    - **Auth is `AWS_BEARER_TOKEN_BEDROCK` only** (a Bedrock API key, region-bound), region from `AWS_REGION`/`METRO_BEDROCK_REGION`. No SigV4 and no IMDS in this version; the tested signer in `apps/mcp` is the obvious donor if instance-role auth is ever wanted. The key is scrubbed from the env `claude` sees.
    - **It refuses to start when a settings `env` block carries a provider flag or `ANTHROPIC_BASE_URL`** (`settingsConflicts`, user + project + local files), naming the file and key: the Bedrock login wizard writes `CLAUDE_CODE_USE_BEDROCK` there, and that would silently put Claude Code back on the gated provider. `CLAUDE_CONFIG_DIR` is the sanctioned way to keep a Bedrock-mode profile and a proxy profile side by side.
    - **This is an unsupported configuration by construction.** Anthropic's feature matrix lists Channels as ✗ on Bedrock on purpose, and a release could close the gap. Everything that needs Anthropic's own servers stays off regardless (web search, fetched feature flags, Remote Control). Mantle (`bedrock-mantle.<region>.api.aws/anthropic`, Anthropic-shaped, bearer-authenticated) would make the proxy unnecessary once AWS grants it to the account; as of 2026-09-02 it answers `not_found_error` for every model on this account.
    - `test/bedrock-proxy.test.ts` runs the proxy against a fake Bedrock over real HTTP and pins the url, auth header, body rewrite, SSE output, error mapping, the beta retry and the 401 on a wrong local token; `test/bedrock-eventstream.test.ts` pins the framing across split chunks.
  - **`metro tail <agent-id>` follows the LOCAL daemon's `/api/tail` and prints one JSON event per line** (`src/tail.ts`). It exists as the Monitor-tool ingress for Claude Code — `Monitor({command: 'metro tail <id>', persistent: true})` delivers events into a session that is ALREADY running, which the experimental Channels flag cannot — and it is loopback-only by construction (`localUrl()`), so message content never transits hosted metro. The key comes from `METRO_AGENT_KEY`, else one `GET /api/run/config` with the stored run token (a credential read, the same call the daemon's poller makes; 401/403/409 there is `RuntimeRevoked` and terminal, matching the poller's semantics — a refused `METRO_AGENT_KEY` is terminal too, never retried). Reconnects with 1s/2s/5s backoff (reset after a healthy stream), treats 90s of silence as a dead socket (the tail keepalive comes every 25s), and stdout carries ONLY event JSON — every status line goes to stderr, because Monitor treats each stdout line as an event.

## The Claude Code plugin (`plugin/`, repo-as-marketplace)

The repo doubles as a plugin marketplace: root `.claude-plugin/marketplace.json` lists `./plugin`, so `claude plugin marketplace add bonustrack/metro` (or a local path) then `claude plugin install metro@metro` installs it. **`plugin/` is NOT a workspace package** — it ships committed plain-Node `.mjs` (no build, no deps) because a marketplace install is a git snapshot.

- `/metro:login <code>` claims a pairing code and writes `~/.config/metro/credentials.json` — the SAME file the CLI's `metro login` writes, so the two sign-ins are interchangeable. `/metro:refresh` re-fetches `/api/cli/mcp` and rewrites the plugin's `.mcp.json`.
- **Plugin MCP registration is a SNAPSHOT, not a live read.** A rewritten `.mcp.json` is invisible until `/reload-plugins` (in-session; keeps unchanged servers connected, adds new, drops removed) or `claude plugin update metro@metro` (CLI) re-registers it — verified empirically; a fresh session alone does NOT pick up a hand-edited file. This is why every skill ends by telling the user to run `/reload-plugins`, and why the committed `.mcp.json` placeholder is `{}`.
- **The generated `.mcp.json` carries NO credential**: entries are `{type, url: <relay>, headersHelper: node "${CLAUDE_PLUGIN_ROOT}/bin/metro-plugin.mjs" headers}` — the helper prints the agent token fresh from the credentials file on every connect and 401, so a re-login propagates with zero regeneration. Signed out it prints `{}` and the relay answers 401.
- **The `metro.box ` name prefix is STRIPPED inside the plugin** (`serverEntries`): plugin servers are already namespaced (`plugin:metro:<name>`, tools `mcp__plugin_metro_<name>__*`, non-alphanumerics → `_`), so the prefix would only mangle tool names. The raw `metro mcp` export keeps it.
- A plugin UPDATE overwrites the install dir, resetting `.mcp.json` to `{}` — `/metro:refresh` regenerates it; the sign-in survives (it lives in `~/.config/metro`).
- `packages/cli` remains the npm package and is NOT replaced by the plugin: it carries the daemon runtime (`metro start`), `tail`, `update`, and `metro mcp` for non-plugin clients.

## Architecture

### Bus and stations

- **In-process bus** (`daemon/events.ts`): a bus, not a journal. Bounded in-memory ring (`BUS_BUFFER_MAX = 500`) keyed by monotonic `busSeq`; `channels/relay.ts` tracks the highest contiguously-delivered seq and replays missed events on rebind. **Do NOT add an on-disk journal or history.**
- **Static seam:** stations are wired through `stations/registry.ts`; core dispatches generically over station defs. No per-network branching in core.
- **Tolerated package cycle** between core and station packages. Intentional — do NOT "fix" it; madge is configured around it.
- **`Station` carries TWO independent booleans: `hasAccounts` and `hasTrain`.** They were once conflated (`hasAccounts: false` meant "no subprocess"); webhook is the one station where they differ (`true`/`false`). `hasTrain` decides the subprocess:
  - `materialize.ts`'s `STATION_TARGETS.webhook.trainImport` is `null`, so `writeStations` writes the account file but no stub, and `pruneStations` blanks the file without `rmSync`ing a stub that never existed.
  - `boot.ts`'s `syncStations` returns before touching the supervisor.
  - `mcp/accounts.ts` reads webhook's accounts in-core (`inCoreAccounts`) instead of calling an absent train — which is also why webhook can never appear in `unavailable`.
  - The Monitor's `/api/call/:train/:action` is a flat 400 for it; `list_members` refuses on `!hasAccounts || !hasTrain`.
- telegram and whatsapp trains spawn only when an account of that station exists.
- **The LINE station was removed.** No `line` package, no `line` in `STATIONS` — a leftover `line` row in `accounts` crashes `materialize.ts` at boot. Drop those rows before deploying.

### Sessions, identity and scope

- **`agents.key` is the ONLY credential.** No env bearer, no unscoped principal anywhere. Since `0009` an agent has at most one key and a key belongs to at most one agent (`agents.key` nullable text UNIQUE), which is what makes a bare `?token=<key>` unambiguous with no agent selector.
- `db/key-map.ts` keeps ONE index: SHA-256(key) → agent id, no plaintext. `authenticate()` order: key map → session JWT. Neither is a 401 — **a daemon with nothing configured is CLOSED, not open.**
- `allowedAgents()` is the single place turning an identity into a `Set<number>`; it never returns `undefined`. Use it, don't re-derive.
- **Scoping is by `agents.id` (an opaque 11-char string), never by name.** `agents.name` has no uniqueness since `0007`, so a name comparison in an auth path is a cross-owner leak and will NOT be a type error. Do not reintroduce a name-keyed grant.
- **Key reset** (`POST /api/agents/<id>/key` → `resetAgentKeyForUser`) is a hard cutover with no overlap window: `UPDATE … WHERE id = … AND owner_id = …` (0 rows → 404, retried on `23505`), then `rotateAgentKey` = unregister + register in ONE synchronous call, so the map never holds two live keys or none. Order is load-bearing: row commits → map swaps → new key goes out. `registerKey` alone is NOT a rotation — it adds a hash without evicting the old one, which `test/key-map.test.ts` pins. Registration is skipped on a `METRO_AGENT`-pinned daemon that doesn't serve the agent; **eviction is unconditional.** `boot.ts` composes the reset with `closeAgentSession(id)`, since an attached SSE stream never re-authenticates.
- **Per-identity MCP sessions** (`mcp/session.ts`). `McpSession` owns everything that was once a module-level singleton: its own `mcp.Server`, transport, `_GET_stream` sink, `ChannelOwner`, `BoundedEventStore`, `InboundRelay`, `ChannelRelay` and bus subscription.
  - `mcp/session-registry.ts` holds two indexes filled together (session id → session, scope key → session) so a lookup by either cannot drift.
  - The scope key (`sessionScopeKey`) is the SORTED agent id set, not the identity: an `agents.key` and a browser session over the same agent are the SAME session.
  - At most one live session per scope key. A second `initialize` from the same identity supersedes; a second identity does not touch it.
  - `rebindDecision` is GONE. `routeSession` returns `use` for an id the caller owns, a flat 404 for one somebody else owns, `create` with `adoptId` only for an id nobody owns. `initialize` never adopts.
  - Lifetime: idle streamless sessions reaped after `SESSION_IDLE_MS` (10min) by a 60s unref'd sweeper; `MAX_SESSIONS` 64, evicting the LRU **streamless** session and refusing with 503 rather than dropping a live one.
  - `ReplayLedger`s live in a registry LRU keyed by scope key, so a message that arrived while an agent was disconnected survives reconnect AND full re-initialize.
  - `InboundRelay` state (`knownLine`, `allowedLines`, `seenEvents`, `pendingPermissions`) is per session, so one agent's chat reply cannot answer another's approval prompt. The dedupe key still strips the account segment (that is what collapses one agent's two accounts in one conversation) but is prefixed by the owning agent id.
  - Do NOT re-collapse any of this into a singleton. `test/session-concurrency.test.ts` drives two agents over real HTTP and fails first if you do.
- **Adoption is silent, so an adopted session must be told the tool schema may have moved.** Armed by a schema SIGNATURE, not the adoption flag: `toolSchemaSignature()` is a memoized hash of `toolList()`, `issuedSchema` is the signature the session was issued (`undefined` when adopted), and `schemaNoticeDue` is `issuedSchema !== toolSchemaSignature()`.
  - **Arming is not delivering.** The notice rides whichever egress the client is actually reading: `announceToolSchema` on a GET bind (guarded by `streamAttached`), or `extra.sendNotification` from inside the `tools/call` handler, which the SDK routes onto that request's own response stream. `tools/list` settles it silently (`markCurrent`) — notifying there is a refetch loop. `issuedSchema` updates only once the send RESOLVES; an `announcing` latch stops two concurrent calls both sending. Pinned in `test/schema-notice-without-stream.test.ts` and `test/mcp-session-restart.test.ts`.
  - **The ceiling: the daemon cannot reach a client that is neither streaming nor calling.** The SDK client opens its GET stream once, retrying twice at 1s and 1.5s; any deploy outage exceeds that and the stream is gone for the life of that client process. Such a client keeps making tool calls and receives no inbound chat at all. Only a `/mcp` reconnect or client restart fixes it. **Tell the user to reconnect after every deploy.**

### One scope predicate, every egress (`db/agent-scope.ts`)

- `lineTargetDenied` resolves `args.line` → agent id and denies anything outside the scope set, including an `args.account` override that would re-route to another agent's account (stations resolve `account ?? line`, which is the hole a line-only check leaves). `mcp/index.ts`'s `scopeDenied` and the Monitor's call gate are that one function.
- `stationFullyScoped` covers a call naming no line (`accounts`): allowed only when every account of that station is in scope.
- **`eventInScope` is the delivery filter for EVERY inbound egress and FAILS CLOSED.** An account-station line (the `STATIONS` list in `db/schema.ts`) whose account maps to no agent goes NOWHERE. An unparsable line reaches nobody.
  - The remaining carve-out is by STATION, not by lookup failure: a line on a station with no accounts at all (local `metro://claude/…`) still reaches every authenticated tail. **Do NOT remove it wholesale** — `metro://claude/…` depends on it.
  - `webhook` is IN `STATIONS`, so an endpoint reaches its owning agent and nobody else.
- **Four egresses, one case table** (`test/egress-scope-matrix.test.ts`): channel live, channel bus replay, SSE resumption, monitor tail. **Add a new egress to that table or it will leak.**
- **SSE resumption is a separate egress.** `serveStandaloneGet` replays `BoundedEventStore` before the sink is bound and without consulting `ChannelRelay`, so gating the relay alone left a real leak with no log line at all. `storeEvent` records the frame's `meta.line` and the `ChannelOwner` scope in force; `replayEventsAfter` takes the reconnecting scope as a REQUIRED option and re-checks every frame through `mcp/frame-scope.ts` → the same `eventInScope`. `scope: undefined` replays NOTHING. Withholding does not consume the frame — the store is a buffer, not a queue. Both gates are kept and are redundant by construction; **do not remove either** on the grounds that isolation makes it unreachable.
- The Channel applies scope through `ChannelOwner` (`mcp/channel-owner.ts`), which records the identity that authenticated the currently-attached GET stream — that stream is the wire, so it decides scope. An out-of-scope event is WITHHELD, not dropped, so the ring buffer replays it to its real owner. With no stream attached nothing is deliverable, which keeps events alive rather than writing them into a transport with no reader.
- `streamBelongsTo` is the last-line guard on a stream takeover (409); unreachable while routing is correct, which is why it stays.
- `permission-relay.ts` re-checks `owner.inScope(relay.knownLine)` before pushing an approval prompt, because a prompt is Claude's tool name and input preview.

### Never fatal

- **Nothing in the relay path may kill the daemon** (the v157 outage: one unwritable `mcp.notification()` took every station down). A notification failing because a client vanished is normal.
- Pinned by `test/never-fatal-notify.test.ts` (against a real closed SDK `Server`) and `test/crash-guard.test.ts` (through real subprocesses, the only honest way). Three layers, all kept: the `flushPendingFallback` timer `.catch()`es and logs; `ChannelRelay.enqueue` terminates its chain with a `.catch()` so one failure cannot poison the chain; `daemon/crash-guard.ts` installs `unhandledRejection` + `uncaughtException` as the FIRST statement in `boot.ts`.
- The guard is asymmetric on one flag: before `markDaemonReady()` a crash exits 1 (a daemon with no HTTP server should crash-loop visibly); after ready it logs at `error` with a per-kind counter and keeps relaying. `/health` is the independent backstop for a genuinely wedged process.
- The fatal path does NOT go through pino — `logFatalSync()` writes one pino-shaped line with `writeSync(2, …)`, because `pino.destination(2)` is async and `process.exit` truncates it (`flushSync()` does not fix it).
- Keepalive `res.write`s in `raw-get-stream.ts` and `monitor/api.ts` are the same class in sync form: guarded, and they close the stream.

### Attachments

- **Inbound:** a station emits `attachmentSaved` when bytes land and `attachmentFailed` (same correlation fields plus `reason`) when they cannot. Both go through ONE correlator (`InboundRelay.mediaCtxFor`), so a failure consumes the pending slot exactly like a success and clears the 15s fallback timer. That timer is right for a download that never returned and wrong for one refused outright. Failure notes advertise no `url` and no `local_path` — there is no file. Only whatsapp emits `attachmentFailed` today; the rest still fall through to the timeout.
- `saveStreamToCache` streams to a `.part` with a running `assertAttachmentSize` counter and `rename`s on completion, so RSS stays flat and a refused save leaves neither a half file nor an orphan.
- **Serving** (`daemon/attach-serve.ts` + `attach-owner.ts` + `attach-grant.ts`) is scoped by the OWNING agent, not a shared secret. Minting a url writes two 0600 sidecars beside the cached file: `.owner` (agent id) and `.grant` (`{token, agentId, mintedAt}`, `at_<43 base64url>`, 32 CSPRNG bytes). The `?token=` is that per-attachment token, never the agent's key. Minting is idempotent for the same owner, so re-emitting an event does not break a delivered link.
  - `/attach` takes two paths, both re-checking `.owner` first: the presented token matches that attachment's own grant (`timingSafeEqual`, and the grant's `agentId` must equal the recorded owner), OR the caller authenticates as an identity whose scope contains the owner. Everything else is a flat 401.
  - The ONE 404 is a name that is not cache-shaped (`CACHE_NAME_RE`), decided before `authorized()` — it depends only on the request string. A cache-shaped name stays 401 whether or not it exists: cache names derive from public ids (a discord-bot snowflake), so a distinguishable "gone" would be an existence oracle. **Do not "improve" that 401 into a 404.**
  - Fails closed: no `.grant` means no token can match. Sidecars are unservable by construction (`CACHE_NAME_RE` cannot match two dots).
- **Outbound sources** (`stations/attach-resolve.ts`, `attach-inline.ts`): exactly ONE of `upload`, `data`, `url`, `path`. Two is an error and so is none — the old filter that swallowed a source-less entry is gone, because dropping it and answering `sent: text` is the #134 dishonesty.
  - `path` resolves on the DAEMON host; `url` must be publicly reachable; `data` transits the model's output. `upload` is the only one fit for a real file.
  - **`data` is for TINY files.** `MAX_INLINE_BYTES` is 8 MiB decoded, per attachment and per send — derived so the limit-naming error fires before `MCP_BODY_MAX` (32 MiB) answers a bare 413. Don't raise one without the other. But the binding limit is the model, not the daemon: the practical ceiling is roughly **10 KB**, three orders of magnitude below the cap.
  - base64 is validated strictly (alphabet, whole quanta, decoded-length equality) because `Buffer.from(x, 'base64')` silently drops junk. `splitInlineData` strips a `data:<mime>;base64,` prefix and adopts that mime when `mime` is omitted; a `data:` url without `;base64` is refused.
  - Inline bytes land in a per-attachment `mkdtemp` (0700) under `os.tmpdir()`, **never `attachDir()`** — that cache is durable and is the only thing `/attach` serves. `cleanupAttachments` runs in a `finally` on success, station error and under-report alike. Stations only ever see a local file, so no base64 crosses the train stdin pipe — `drainLines` would drop a call line over `STDOUT_LINE_MAX` (4 MiB) in silence.
- **The upload endpoint** (`daemon/upload-store.ts` + `upload-api.ts` + `mcp/upload-tool.ts`). Bytes go over HTTP from the caller's disk to the daemon, never through an MCP message. **One step needs a SHELL and there is no way around it** — an MCP tool call is model output by construction. `create_upload` mints the slot and returns a ready-to-run command; pushing bytes is `curl`. An orchestrator-only main loop should delegate the one command and keep the `upload_id`; the slot belongs to the metro AGENT, not whoever ran it.
  - Two ways in: `POST /api/uploads?name=&mime=` with the raw body, authenticated by the agent's key (owner is the single agent in scope, or `?agent=<id>`); or `create_upload` → `PUT /api/uploads/<id>?token=<ut_…>`, where the ticket is the only credential on the wire. `DELETE` drops a confidential file early.
  - **The advertised PUT url must name the daemon that minted the slot.** Slots live in the minting daemon's `uploadDir()` (per-machine tmp, never `/data`), so `publicBaseOrDefault()` resolves `METRO_PUBLIC_URL`/tunnel first, then — on a `METRO_RUN_TOKEN` daemon — its own `http://127.0.0.1:<webhookPort()>`, and only then the hosted `https://mcp.metro.box`. The local branch is load-bearing: the old unconditional hosted fallback pointed every local `create_upload` curl at a daemon holding no slot, a flat 404 `no such upload` on every fresh ticket, which silently broke attachment sends for every locally-run agent. The other `publicBaseOrDefault` consumers (`mcpEndpoint`, OAuth `callbackUri`, webhook `hookUrl`) sit on session-gated surfaces a local daemon cannot serve, so the local branch never reaches them. **Inbound takes the same branch:** `attachmentUrl` falls back to the loopback base too, so a local daemon's inbound media notes advertise a working `/attach` url instead of none — while a hosted daemon with no `METRO_PUBLIC_URL` and no tunnel still advertises nothing, unchanged.
  - Ownership reuses #130's primitives, not a copy. Same two paths as `/attach`, failing closed the same way, but everything else is a flat **404** — an upload id is an unguessable capability, so "exists but not yours" would be an oracle. At `send` time `fromUpload` re-checks the owner against `allowed`, passed IN as a parameter (`stations/` must not import `mcp/`); `allowed === undefined` resolves NOTHING.
  - **Transient by construction:** `uploadDir()` (0700), never `attachDir()`. `UPLOAD_TTL_MS` 30 min, expiry read from `.meta` on EVERY lookup, `startUploadReaper()` sweeping every 60s with one sweep at start. `UPLOAD_ID_RE` (`up_` + 22 base64url) is the traversal guard and makes sidecars unaddressable. A send does NOT consume the upload — a timed-out `send` has usually succeeded, so a retry must work.
  - **64 MiB per file, 512 MiB daemon-wide live budget.** Under `MAX_ATTACHMENT_BYTES` (100 MiB) so the naming error fires first, and above the largest station ceiling (Telegram's 50 MB) so metro never refuses a file a station would carry. Over-size is refused from `content-length` before a byte is written; a chunked body is caught by the running counter, which **DRAINS rather than throws** — throwing there destroys the socket in Bun's `node:http` and the client hangs forever. Drain capped at `DRAIN_MAX` = 2x. Do not "simplify" it back into a throw.
  - `streamToSlot` owns removing the `.part` on failure, not its callers: the `wx` open makes an orphan permanent, wedging that slot at 409 for the full TTL.
- **Outbound reporting is derived, never asserted** (#134). `handleSend` compares what came back against `atts.length` through ONE predicate, `assertDelivered`, applied to both the forwarded and native paths. **Fewer labels than attachments is an error, never a success.** Each station's label list must be built INSIDE the loop that pushes, appended only after the push resolves, and derived from the branch that chose the verb — never `map`ped over the input array, which is what let telegram report full success for a partial send. `test/send-attachment-honesty.test.ts` crosses drop/partial/complete against every station's line; add a station to it and to the package's own send-loop test.

### Human-in-the-loop

A pending MCP `permission_request` is relayed to chat as `yes <request_id>` / `no <request_id>`; `inbound.ts` matches with `PERMISSION_REPLY_RE = /^\s*(y|yes|n|no)\s+([a-km-z]{5})\s*$/i`. The 5-char format is a contract with the relayed prompt — never change one side only.

### Connectors (`db/connectors.ts`, `daemon/connector-*.ts`)

A connector is a **user-level verified bookmark for a remote MCP server**, plus a paste-ready `mcpServers` block. Metro stores it, proves it answers, and **RELAYS its MCP traffic through `/relay/<connector-id>`** — the claude.ai `mcp-proxy` architecture: the vendor credential is injected server-side per request and never reaches any machine. This deliberately REVERSED the original "metro does not proxy connectors" rule; connector tool traffic transits metro by design now, while chat/station traffic never does. The relay still holds no MCP session of its own (pure passthrough), gives connectors no MCP tool and puts nothing on the bus.

- **The relay** (`daemon/relay.ts` + `db/connector-relay.ts`, wired as `SessionApis.relayApi`): `POST`/`GET`/`DELETE /relay/<id>`, mounted in `handlePreMcpRoutes` (path is outside `/api/*`, so the monitor router never sees it).
  - **Inbound auth is an agent token or a run token** (`agentIdentity`), and the connector must be held by that token's agent (one `agent_connectors` join, `db/connector-relay.ts`). Everything else — no token, session JWT, agent key — is 401; a connector the agent does not hold is a flat 404 identical to nonexistent. Tokens ride the `Authorization` header; browsers get no CORS here on purpose.
  - **The caller's token is stripped before anything goes upstream.** Only `accept`, `content-type`, `mcp-session-id`, `mcp-protocol-version`, `last-event-id` pass through, plus the injected vendor credential (stored header, or `Bearer <accessToken>` refreshed via single-flight — one in-flight refresh per connector id, which also closed the old rotation race on concurrent reads).
  - **Sessions pass through verbatim; metro owns none.** One machine and per-connector URLs make client↔upstream sessions 1:1, so there is no session table and no event store; an upstream 404-expired reaches the client, which re-initializes per spec. A second hosted machine would force session re-mapping — documented constraint, not supported.
  - **Status discipline: metro's 401 means only metro's credential.** An upstream 401/403 triggers ONE forced refresh and ONE retry; still refused → **424** with `{error, reconnect}` naming the connector page. **A row with no stored credential forwards BARE — never a pre-emptive 424.** Lazy auth is real: Snapshot's MCP (like Gmail's) advertises OAuth metadata yet serves unauthenticated calls, so the `config.oauth` flag must not gate the relay — the first ship did and broke every such connector on day one. Sign-in refusal is evidence-based only: the upstream 401s, the forced re-resolve has nothing better (no refresh token, or nothing stored at all), then 424. **The OAuth degradation ladder ends BARE, not refused**: fresh token → refreshed token → stale-but-unexpired token → no headers at all — a row whose refresh is dead must not be worse off than a row that never signed in (Snapshot's was exactly that: an old sign-in with dead tokens on a lazy-auth server). Upstream 3xx is refused (502) — a followed redirect with an injected credential is token exfiltration. Upstream auth bodies/headers are never echoed.
  - **Streaming:** POST bodies buffered (8 MiB cap, checked from `content-length` first, socket dropped after answering if the body is unread — the upload-api Bun lesson), responses piped unbuffered with drain backpressure; SSE responses get `: keepalive` comments injected after quiet stretches (`METRO_RELAY_KEEPALIVE_MS`, 25s) — comments are invisible to SSE event ids, so upstream `Last-Event-ID` resumability survives. Client disconnect aborts the upstream fetch via **`res` 'close' AND `res.socket` 'close', both guarded by `!res.writableEnded`** — never `req` 'close', which Bun fires at request-body end. BOTH hooks are load-bearing: Bun 1.3.9 (the prod runtime) never fires `res` 'close' on a mid-stream client disconnect — only the socket event — while 1.4.0 fires `res` 'close'; with only the res hook, 1.3.9 leaks the upstream connection and pumps into a dead response forever. The socket listener is removed on 'finish' so keep-alive sockets don't accumulate one per request.

- **A connector is NOT a station and carries no egress.** Nothing on this path touches `STATIONS`, `stations/registry.ts`, `materialize.ts`, `db/agent-scope.ts` or `eventInScope` — there is no fifth egress to add to the case table. Don't "unify" it with stations.
- **Owned by `users.id`, never `agents.id`.** It belongs to the signed-in person, not to an agent, which is why the sidebar page is user-level and takes no agent. `ownedConnectorOrThrow` re-asserts `user_id` in the WHERE, so not-yours and unknown are the SAME 404.
- **A row normally requires a real MCP `initialize` — with ONE deliberate exception.** `createConnectorForUser` still verifies BEFORE the insert, so a header-auth or no-auth row has `config.verified` by construction. The exception is a server that demands OAuth: `createPendingConnectorForUser` stores it UNVERIFIED (`auth: none`, `oauth: true`, an empty `verified`) so it exists whether or not you finish signing in. **The cost is real and accepted:** a mistyped url that happens to advertise OAuth metadata persists as a connector until deleted. Without it a connector you never connected was invisible, which is the bug this fixes.
- **`parseConnectorUrl` is a security boundary, not validation polish.** https only; no IPv4/IPv6 literal, no `localhost`, `*.local`, `*.internal`, `*.flycast` or bare single-label host; no userinfo, no `#fragment`; every frame is `redirect: 'manual'` and a 3xx is refused rather than followed. The fetch is made by the Fly machine that holds `DATABASE_URL`, the pg pool and `/data` with the MLS db3s, at a url named by ANY signed-in wallet — sign-up is open by design. DNS rebinding is accepted for v1, and the channel stays blind: never echo a remote body or header back to the caller.
- Raw `fetch`, never the SDK `Client` — its `requestInit.signal` is overwritten by the transport, its default timeout is 60s, and after `initialize` it starts an unawaited background GET SSE with reconnect backoff. Streamable HTTP only: `transport` is always `'http'` on a written row, and the column exists so `sse` needs no migration. **No stdio, ever** — the only way to "verify" it is to execute a user-supplied command line on the Fly box.
- **A remote 401 is metro's 400, never metro's 401** (`ConnectorVerifyError` is always 400, like every `stations/attach.ts` provider refusal). 401 is reserved absolutely for a missing or invalid metro session: `apps/ui/src/api/client.ts` throws `AuthError` on ANY 401 and `App.failed` answers with `clearSession()`, so proxying a remote refusal would log the user out mid-form. On re-verify it is not even an error — `verifyConnectorForUser` catches `ConnectorVerifyError` into `200 {ok:false, reason}` and leaves the row alone; anything else rethrows.
- **A connector name is unique PER AGENT, not within a project.** The name is the `mcpServers` object key, so two connectors named `linear` on one agent would silently overwrite each other in the exported JSON — but two rows sharing a name in one project export nothing together and are fine, which is why `0016` DROPPED `unique(project_id, name)`. The rule cannot be a unique index: the name lives on `connectors` and the membership on `agent_connectors`, so no single table holds both. It is ONE predicate instead, `collidingAgent` in `db/agent-connectors.ts`, applied on the two paths that can create a clash — `addConnectorToAgentForUser`, and `renameConnectorForUser` via `assertRenameFreeOfClash` (which checks every agent holding the row). Both answer 409 naming the agent. **Add a third write path and you must call it too**; being application-level, it also has a small race two concurrent adds could slip through, which costs a confusing export and is fixed by a rename.
- **A connector name is a LABEL, not a slug** — anything except control characters, trimmed, 1–64 chars, matching what Claude.ai accepts. It used to be a slug for one reason: the name was pasted into shell commands metro generated, where `my server` parsed as two arguments. Those commands and `api/install.ts`'s `shellArg` are gone, so the reason went with them. Control characters stay out because the name is still a JSON key — it is the `mcpServers` key the CLI prints.
- **A stored url keeps the shape it was given** (`connectorUrlText`). `new URL('https://host').toString()` appends a trailing slash — WHATWG normalisation, not a metro decision — so the helper strips it when the path is root and there is no query, and leaves every real path alone. The OAuth `resource` still uses the NORMALISED `url.toString()`: it must match between authorization and refresh, so do not "fix" that one to match.
- **Membership edits are STAGED, and only `Save` writes.** `AgentPicker` (from a connector: which agents hold it) and `AddConnectors` (from the agent page: which connectors it holds) both hold the chosen ids in local state and compute an add/remove diff on submit (`setAgentConnectors` applies it in order, adds then removes), so a mis-click costs nothing. Both keep `staged` as `string[] | null` and fall back to what the server says (the `connector_ids` on `GET /api/agents`), which is what makes a reopened modal show fresh data rather than a stale snapshot.
- **`ConnectorChooser` is the body only — no `Modal`** — a searchable checkbox list that `AddConnectors` wraps for the agent page's `Add connectors` button. It round-trips the full selection and therefore removes as well as adds; zero selected is valid.
- **An AGENT is the unit of authorization, and it HOLDS its connectors** (`db/agent-connectors.ts`, `daemon/agent-connector-api.ts`). Collections were that unit from `0014` to `0018` and are GONE: `0019_agents_own_connectors` (hand-written, one-way — rolling back means restoring a backup) creates `agent_connectors` (`agent_id` → `agents.id` cascade, `connector_id` → `connectors.id` cascade, `unique(agent_id, connector_id)`), moves the ONE production collection that had to survive — `Internal` (`tnlSpfBErt0`) — onto the existing agent `Tony` (`bMcXH2uERTe`), then drops `collection_items` and `collections`. **It mints no agents.** Every other collection (`Support`, `MCI Group`) is simply dropped: the connectors stay in the project, held by nobody, until someone adds them from an agent's page — Less's explicit call. The move is a guarded `INSERT … SELECT` (the agent must exist and sit in the connector's project, `ON CONFLICT DO NOTHING`), so on any database without that agent — a fresh one, the test one — it is a no-op rather than a failed deploy; verified on a real Postgres 16 both ways. The item rows cascade on BOTH sides, so deleting a connector or an agent removes the membership rather than leaving a dangling row.
  - **Adding a connector re-checks that the caller owns the AGENT (`ownedAgentOrThrow`) AND that the connector is in that agent's project (`connectorNameIn`)** — otherwise a caller could paste somebody else's connector id onto their own agent and read it through an agent token. A foreign id is a flat 404. Adding twice is idempotent (the unique violation is swallowed), and every write answers the agent's new `{id, name, connectorIds}`.
  - Routes are `GET`/`POST /api/agents/<id>/connectors`, `DELETE /api/agents/<id>/connectors/<connectorId>` and `POST /api/agents/<id>/code` — the last mints the pairing code, which is why code minting is an AGENT operation and no account-wide or per-collection code exists. **`handleAgentConnectorRequest` is mounted BEFORE `handleAgentApiRequest` in `session-apis.ts`** because `agent-api.ts` answers 404 for any sub-resource it does not know; `test/agent-connector-api.test.ts` pins that it claims exactly these paths and leaves `/api/agents`, `/<id>` and `/<id>/key` alone.
  - In the UI, membership is edited from BOTH ends: a connector's kebab has *Add to agent* (`AgentPicker`, one checkbox per agent of the project), and the agent page has a Connectors section (`AgentConnectors`) with *Add connectors* and a per-row *Remove from agent*. There is no Collections page. `#/authorize` is the agent chooser `metro login` sends you to and `#/authorize/<agentId>` is the one-agent card `metro start` prints; both mint the same `ma_` code, and `RunLocally` on the agent page mints it too.
  - Every mutation goes through `refreshConnectors`/`refreshAgents` in `api/queries.ts` rather than an ad-hoc `invalidateQueries`, because deleting a connector changes every agent's `connector_ids` through the cascade — `refreshConnectors` therefore invalidates the agents and stations queries too. **`GET /api/agents` carries `connector_ids` per agent** (`connectorIdsByAgent`, one query for the whole list), which is what the agent page, the picker and the authorize page read; nothing in the UI fetches `/api/agents/<id>/connectors` one agent at a time.
- **NO API returns a connector credential to a browser, and the UI cannot render one.** This REVERSES the earlier relaxation that re-served the stored header value to its owner: `connectorPayload` carries no `secret`, no `bearer`, no `expiresAt` and no `json`, on the list route and the detail route alike, so an XSS or an open devtools window has nothing to take. `apps/ui/src/api/install.ts` and `ConnectorInstall.tsx` are DELETED with it — there is no Add-to panel and no per-client install command any more.
  - **The credential-bearing `mcpServers` block is served to a CLI SESSION ONLY.** `signSession` takes an optional `via` claim, `/api/cli/claim` mints `via: 'cli'`, and `handleList` attaches `json` only when `session.via === 'cli'`. A wallet sign-in in the browser can never carry that claim, so the boundary is the token TYPE, not the route — the same session that renders the page cannot read the credentials. `test/connector-api.test.ts` pins both directions, including that the browser response contains neither the secret nor the string `mcpServers`.
  - **The CLI read serves NO vendor credential any more.** `GET /api/cli/mcp` returns relay entries only — `connectorNamesByIds` reads id+name, `relayServersJson` builds `{"metro.box <name>": {type, url: <base>/relay/<id>, headers: {Authorization: Bearer <the caller's own agent or run token>}}}` — so nothing credential-shaped rests in any config on any machine, and a copied block never goes stale (token refresh happens at the relay, per request). `listFreshConnectorsByIds` and `withFreshToken` are deleted with the old export; refresh now lives in `db/connector-relay.ts` behind the single-flight map.
  - Consequence: a CLI session minted BEFORE this landed has no `via` and gets no `json`. The CLI answers with `NotSignedIn` ("run `metro login` again") rather than a shape error, which is why it moved to `0.1.0-beta.18`.
- **The route MUST stay in `handlePreMcpRoutes` before `handleMonitorRequest`**, which claims all of `/api/*` and never falls through. `connectorApi` is the optional 5th positional parameter of `startWebhookServer`/`handleRequest`/`handlePreMcpRoutes`; do NOT fold it into `AgentApiDeps`.
- Migration `0010` adds the table. Migrations apply themselves on deploy — see Migrations below.
- **Adding a connector lands on its page.** The modal's button is `Add`; on success it closes and routes to `#/connector/<id>`, and the OAuth callback does the same for a freshly created row instead of returning to the list. An OAuth server now answers **201 with the stored row AND an `authorizeUrl`**, not the old 202-with-no-row: the row is written first and its id goes into `beginOAuth`, so the callback takes the RECONNECT path (an UPDATE) rather than inserting, which is what keeps it off `unique(project_id, name)` on collections. Note a `window.open` after that await is popup-blocked, the click's gesture having been spent — which is why the create flow assigns the same tab.
- **A connector has its own page** (`#/connector/<id>`), served by `GET /api/connectors/<id>`. That route carries the tool catalog AND the OAuth `bearer`/`expiresAt`; the LIST deliberately carries neither, so one page load does not ship every tool — or every access token — of every connector.
- **`signIn` is the three-state the page's button reads**, derived by `signInState` in `db/connector-config.ts`: `connected` when `config.auth.kind === 'oauth'`, `disconnected` when the row is marked `config.oauth` but holds no tokens, `null` for header and no-auth rows, which get no button because they have no session to end. The `config.oauth` flag is what keeps a disconnected OAuth row distinguishable from a genuinely credential-less one; `readConfig` back-fills it from the presence of tokens, so rows written before it existed read as `connected` with no migration.
- **`POST /<id>/disconnect`** clears the tokens and keeps the row. **`POST /<id>/connect`** re-runs OAuth for a row that already exists: `PendingAuth` carries a `connectorId`, and the callback UPDATES through `reconnectConnector` instead of inserting — inserting would collide with the collection name unique and 409. The callback returns the browser to `#/connector/<id>` rather than the list when it carries an id.
- **Tools group into TWO buckets, read-only and write/delete** (`connector-tools.ts`), matching what Claude.ai shows. `classifyTool` returns `read` only when the server declares `readOnlyHint: true`; everything else — including a tool with no `annotations` at all — is `write`. That asymmetry is deliberate and is the safe direction: `readOnlyHint` defaults to FALSE and `destructiveHint` defaults to TRUE, so silence means "assume it writes", never "assume it is safe". The tool NAME is never an input, in either direction; a test pins that `delete_everything` with no annotations is not read-only AND that it is not called destructive on the strength of its name. `isDestructive` keeps the finer spec distinction (read-only → false, `destructiveHint: false` → false, otherwise true) for the row badges. Annotations are HINTS and MCP says clients must treat them as untrusted unless the server is trusted — the page says so, and nothing on any auth path reads them.
- **A stored catalog is read with `readStoredTools`, NEVER `toToolList`.** They take different shapes: `toToolList` reads the WIRE, where a tool carries `annotations` and its kind is derived; `readStoredTools` reads a row, where the kind was already derived at check time and no `annotations` field exists. Re-deriving on read silently classified every tool as `write`, because `classifyTool(undefined)` is `write` — the correct kinds were in the database the whole time and only the read destroyed them. `test/connector-tools.test.ts` pins the round trip AND pins that the wire reader flattens it, so the two cannot be swapped back.
- **`tools/list` is PAGINATED.** `listTools` follows `nextCursor` (10 pages max, stopping on a repeated cursor). Reading only the first page silently under-reports a big server, which is what the original probe did.
- **The probe asks for `2025-11-25` and falls back to `2025-06-18`**, retrying ONLY on `ConnectorNotMcp` — a redirect, an unreachable host or a 401 is version-independent and must not double-hit the host. Later frames echo the version the SERVER chose, not the one we asked for. The newer version is what makes `serverInfo.icons` reachable at all.
- Icons are `serverInfo.icons[].src`, https only (`safeIconSrc`). The daemon still records one on every check, but **the UI no longer renders it**: almost no server publishes one, so nearly every row fell through to a favicon guess and then to a letter, which read as broken rather than absent. `ConnectorIcon` is deleted; connector rows and the connector page are text-only. The field stays on the wire, unused, for whoever wants to try again.
- The URL policy and the error classes live in `connector-url.ts` now (`ConnectorVerifyError`, `ConnectorUnauthorized`, `ConnectorNotMcp`), re-exported from `connector-verify.ts` so existing importers are unaffected.
- **OAuth connect flow** (`oauth-discovery.ts`, `oauth-client.ts`, `oauth-pending.ts`, `connector-oauth.ts`). A server that answers `initialize` with 401/403 and NO credential offered throws `ConnectorUnauthorized`, and `POST /api/connectors` answers **202 `{status:'oauth`, authorizeUrl}`** instead of an error; the UI sends the browser there. A credential that WAS offered and rejected stays a 400 — never start OAuth over a rejected token.
  - **A 401 is not the only sign that a server wants OAuth, and on its own it misses real servers.** Gmail's cloud MCP (`https://gmailmcp.googleapis.com/mcp/v1`) answers an unauthenticated `initialize` AND `tools/list` with 200 — it only needs the token for tool CALLS — so the `ConnectorUnauthorized` path never fires and the row was stored as no-auth with no Connect button. `advertisesOAuth` fixes that by asking the RFC 9728 resource metadata whether it names an `authorization_servers`, and `oauthCapable` sets `config.oauth` from it at create AND at re-check, so a mis-classified row heals on Refresh tools list. It never DOWNGRADES (`config.oauth || …`), so a transient probe failure cannot take the button away from a connector that was signed in. It is only asked when the row holds no credential; a header-auth row is left alone.
  - **Detecting it does not mean metro can sign in to it.** Registration is DCR only, and Google publishes no `registration_endpoint` — so Gmail shows Connect, and Connect answers with `oauth-client.ts`'s "does not accept client registration" 400. Reaching Google needs a pre-registered client id, which is a different mechanism from anything on this path today.
  - **An issuer with a PATH puts `.well-known` before it, not after** (`authServerMetadataUrls`). RFC 8414 §3.1 inserts the suffix between host and path, so PlanetScale's issuer `https://mcp.pscale.dev/mcp/planetscale` publishes at `/.well-known/oauth-authorization-server/mcp/planetscale`. `wellKnown()` overwrites `pathname` and so only ever asked the ROOT, which 404s — every path-bearing issuer failed with "publishes no OAuth metadata Metro can use" even though it published plenty. The candidate list now tries the two path-aware forms, the OIDC legacy `<path>/.well-known/openid-configuration`, then the root forms. The resource-metadata side (`resourceMetadataUrls`) always did this correctly; only the authorization-server side was wrong.
  - Discovery is RFC 9728 then RFC 8414: `/.well-known/oauth-protected-resource` (path-aware form FIRST, then root) → `authorization_servers[0]` → `/.well-known/oauth-authorization-server`, falling back to `openid-configuration`. **Every discovered url goes back through `parseConnectorUrl`**, so the SSRF boundary covers the OAuth hops too, not just the MCP one.
  - The client is registered per connector by **Dynamic Client Registration** (RFC 7591) with `token_endpoint_auth_method: 'none'`. PKCE is S256 and mandatory; the verifier never leaves metro.
  - **`GET /api/connectors/callback` is the one route on this surface that is NOT session gated** — the browser arrives from the authorization server with no Authorization header. It authenticates by holding the unguessable `state`, which is a single-use key into an IN-MEMORY pending map (`oauth-pending.ts`, 10-min TTL, 100 max, unref'd sweeper). The map is what keeps the client secret and the PKCE verifier off the wire. `takePending` consumes on EVERY path including the error one, so a state cannot be replayed.
  - `returnTo` is checked by `validateReturnTo` (`session-config.ts`, the web UI host allowlist SIWE shares) — before anything is registered, and the callback always redirects the user back (`?connector_error=…#/connectors` on failure) rather than leaving them on a JSON page.
  - Tokens live in `config.auth` as `{kind:'oauth',…}`. A re-check (and the relay) refreshes them when they are within **five minutes** of expiry (`REFRESH_SKEW_MS`, raised from one minute for the relay) and **persists the refreshed pair**; a `refresh_token` the server declines to rotate is carried forward. The relay degrades to a not-yet-expired stored token when a proactive refresh fails, but a FORCED refresh (after an upstream 401) that fails is 424, never a silent stale retry.
- **An exported server name is `metro.box ` + the connector's name.** The prefix was removed once and DELIBERATELY brought back with the relay (Less's explicit call): now that every exported url points at metro's relay rather than the vendor, the prefix states where the traffic goes. The name is still a JSON key, never parsed, never on an auth path. **Rename is the way to disambiguate** — `POST /api/connectors/<id>/rename` takes `{name}`, runs it through the same `connectorName` validation as create, and 409s only when the new name would collide on an agent that holds the connector — a project-wide duplicate is allowed since `0016`.

### Sign-in is Sign-In with Ethereum, and the identity is the wallet address

- **There is no Google login any more** (`google-oauth.ts`, `google-auth.ts`, the `GOOGLE_OAUTH_*` secrets and `/auth/google/*` are gone). `GET /auth/siwe/nonce` mints a single-use nonce (`siwe-nonces.ts`: viem's `generateSiweNonce`, in memory, 10-min TTL, 500 max, unref'd sweeper — the `oauth-pending.ts` pattern); `POST /auth/siwe/verify {message, signature}` runs `verifySiweLogin` (`siwe-auth.ts`) and answers `{session, address}`. No redirect and no `return_to`: the page keeps the token from the response body, which is why `consumeFragment` and the `#session=` handoff are gone from the UI.
- **`verifySiweLogin` refuses in this order**: not a 65-byte hex signature (400) → not an EIP-4361 message carrying address, domain, nonce, uri and version 1 (400) → a domain that is not a web UI host (`allowedSiweDomain`: `metro.box`, `localhost`/`127.0.0.1` with any port, `*--metro-ui.netlify.app`; 400) → a uri on another host than the domain (400) → viem's `validateSiweMessage` (domain, nonce, `expirationTime`/`notBefore`; 400) → a nonce unknown, expired or already used (400 — the nonce is consumed HERE, so a bad signature still spends it) → `verifyMessage` recovering another address (401). **EOAs only**: `verifyMessage` is viem's offline recover, so a smart-contract wallet (EIP-1271) is refused with a message saying so. `test/siwe.test.ts` signs real messages with a viem private key and pins every branch and the routes.
- **The session subject is the lowercase address.** `SessionClaims`, `AgentClaims`, `RunClaims`, `ApiSession` and `RequestIdentity` carry `subject`, never `email`. `userIdForSubject` (`db/users.ts`) resolves an address against `users.address` and anything else against `users.email`, which is what keeps every session, agent token and run token minted before the cutover valid — no machine had to re-pair. `/api/cli/claim` and `/api/cli/session` still send the subject under the wire key `email` as well as `subject`, because the published CLI (`beta.31`) reads `email`; the CLI redesign retires that key.
- **Every `…ForEmail` became `…ForUser`**, and its first argument is the session subject. `/api/session` answers `{subject}`; the agent list answers `subject` too.
- **Members are invited by address** (`POST /api/projects/<id>/members {address, role}`; `ensureUserByAddress` creates the row and `ensureDefaultProject` its Personal project). The members list carries `address` and `email`, both nullable; the UI shows the address shortened and falls back to the email only for pre-SIWE rows.
- **Migration `0020_users_address`** (hand-written, one-way) adds `users.address` UNIQUE, makes `email` nullable, maps `fabien@bonustrack.co` (the owner of the `Snapshot` project that holds every agent and connector; `fabien@snapshot.org` only ever owned an empty Personal project and goes with the rest) to `0xef8305e140ac520225daf050e2f71d5fbcc543e7`, then removes every user without an address together with their projects, agents, stations, connectors and memberships, in FK order (stations first, since they carry no FK; then agents, connectors, members, projects, users). A `DO` block refuses to run when users exist and none got an address, so a typo in that email aborts the deploy instead of emptying the database. Less's call: the other accounts were not wanted. Verified on a real Postgres 16 with production-shaped fixtures.
- **The UI** offers three kinds of wallet (`auth/wallet-options.ts` composes the list, `test/wallet-options.test.ts` pins it): every wallet announced through EIP-6963 (or a bare `window.ethereum`), **WalletConnect** through Reown AppKit, and **Coinbase Wallet** through its SDK — the same three Snapshot's UI leads with, modeled on `@snapshot-labs/lock`'s connectors but deliberately NOT a dependency on lock (its root export is types-only, the connectors are reachable only through the Vue entry, and it drags thirdweb, starknet, sequence and the Safe SDKs in as hard dependencies). `auth/wallet.ts` loads `@reown/appkit` and `@coinbase/wallet-sdk` by dynamic import on the click, so neither is in the initial bundle; AppKit is created ONCE per page (`createAppKit` twice registers its web components twice) in core mode with no adapter, `open()`ed, and the `eip155` provider taken from `subscribeProviders` with `MODAL_CLOSE` as the refusal; every connector hands back `{provider, address, release}` and the login page calls `release()` in a `finally`, so a WalletConnect pairing or Coinbase session lives exactly as long as one signature. **WalletConnect uses Snapshot's Reown project id by default** (`DEFAULT_WC_PROJECT_ID` in `auth/wallet.ts`, the same id the Snapshot UI ships, Less's call), and `VITE_WC_PROJECT_ID` overrides it; `walletChoices` hides the button only when the id resolves to an empty string. Signing is viem's `createWalletClient(custom(provider))` over whichever provider came back. `api/siwe.ts` builds the message with `createSiweMessage` (domain `location.host`, uri `location.origin`, chain 1, ten-minute expiry). The footer and members list render `shortAddress` and the blockie seed is the address. The login page carries no warning text (Less had the lost-wallet note removed); the README states the account model instead.

### Agent API (`daemon/agent-api.ts`)

- `GET`/`POST /api/agents`, `DELETE /api/agents/<id>`, `POST /api/agents/<id>/key`, plus the account sub-resource in `daemon/account-api.ts`.
- Gated by the session JWT only — **never an agent key.** An agent key cannot reset itself.
- Shared plumbing in `daemon/api-http.ts`; every status-carrying error extends `ApiError`. `apiFailure` maps exactly `AgentAdminError` and `StationAttachError` to their status and everything else to a logged 500.
- **`GET` also returns per-agent liveness** — `connected` (a live GET stream is attached) and `last_seen` — derived from the session registry via `agentLiveness()`, injected as the `liveness` dep because `daemon/` must not import `mcp/`. It is gated on `owned` exactly like the key: the connection state of somebody else's agent is not yours to see. This is the signal for the documented deploy ceiling — a client whose stream died reads `connected: false` while still making tool calls.
- **`GET` also returns each agent's `connector_ids`**, through the `connectorIds` dep (`connectorIdsByAgent`, one `IN` query for the whole list), so the UI never has to read `/api/agents/<id>/connectors` per agent.
- **`GET` returns the agent's key VALUE** (plus `?token=` endpoint and paste-ready command) for agents the session OWNS, and lists nothing else. The exposure is gated TWICE and **both gates must stay**: the list query selects only (`id`,`name`,`owner_id`), `selectKeyRows` re-reads `key` for owned ids ONLY, and `agent-api.ts` re-checks `agent.owned` before serialising. `AgentRow` has no `key` field, so the assembly step cannot serve a key it was not handed.
- `toAgentSummaries` derives `owned` and the key exposure from ONE predicate (`ownerId !== null && r.ownerId === ownerId`) so they cannot drift. **The null guard is load-bearing** — without it a caller with no `users` row would be handed every operator-provisioned row as owned.
- Ownership resolves `owner_id` from the DB per request, not from the JWT, so a new agent appears without re-login.
- DELETE is owner-only by id: not-yours / unknown / `owner_id IS NULL` → 404; still-attached accounts → 409. `ownedAgentOrThrow` is shared by delete, attach and key reset so their predicates cannot drift.
- `gatherAccountsForAgents` stamps each account with its owning `agentId` for the UI. That is display metadata on the `/api/agents` path only — `scopeAccountsByAgent` decides visibility. The MCP `list_accounts` tool still calls plain `gatherAccounts`.

### The paste-ready command (`mcpAddCommand`)

`claude mcp add --transport http metro "http://127.0.0.1:8420/mcp?token=<key>"` — mirrors the Browserbase shape byte for byte.

- **The url is ALWAYS the loopback one (`LOCAL_MCP_ENDPOINT`), held or not.** It used to switch: `mcpEndpoint()` (the hosted base) for an agent metro runs, loopback only once a runtime held it. Less's explicit call to make it unconditional. The known cost is accepted and is NOT a bug: an agent that has not been claimed by `metro start <id>` is served by metro, not by loopback, so the command as shown answers nothing until you run the daemon on the machine you paste it into. `mcpEndpoint()` still builds the hosted url for the list payload's `endpoint` field.
- **No `--scope user`**, so it registers only for the pasting directory. Less's explicit call; do NOT "fix" it. `--transport` stays spelled out for the same reason.
- **The server name is the constant `metro` for every agent** (#124), never the agent name or a slug. Only `?token=` differs. That constant is also what makes the line safe whatever is in `agents.name` — a name with a space used to paste as a broken two-word server. Known consequence: two metro agents in one Claude Code config collide on the second add. Accepted — it is a collision in the pasting person's own config, and nothing on the auth path reads this string.

### Attaching station accounts

- `POST /api/agents/<id>/accounts/start` is the **ONLY** route that writes `accounts`.
- **No `accounts` row exists unless the credential has been demonstrated to work.** Every station is verified against the real provider BEFORE the row is written: discord-bot `GET /users/@me` plus the `/applications/@me` Message Content flags, telegram-bot `getMe`, xmtp opens a real inbox with the key it just generated. Well-formed is not enough — a generated secp256k1 key is well-formed by construction.
- The xmtp check runs OUT OF PROCESS (`Bun.spawn`, key over stdin, never argv/env, 90s cap) because `@xmtp/node-sdk` v6 exposes no `close()`, so an in-daemon client would hold the MLS SQLite handle for the daemon's life and fight the train. It verifies into the SAME db3 the train will use and stores that path in `config.dbPath`, so the train reuses the verified installation instead of burning one of the inbox's ten. On a failed write, `discard()` deletes the db3 and its sidecars. Refusals run through `withoutKey`.
- `account_id` is ALWAYS server-generated (`a<agentId>-<8 hex>`), never from the body — (`station`,`account_id`) is a global PK, so a caller-chosen id would collide across owners and leak which ids exist.
- Duplicate bot tokens are refused 409 (two telegram-bot accounts sharing a token make the whole train refuse to boot).
- **No API returns a stored station credential** — the one-time `secret` in the 201 is the only time a generated XMTP key is shown. The single deliberate exception is the webhook endpoint url (see the webhook station).
- **Interactive attach** (`daemon/attach-session.ts`): telegram and whatsapp cannot finish in one request, so `start` answers `status:'pending'` with an `as_<22 base64url>` id, and the client polls, posts `/step`, or `DELETE`s. `ATTACH_ID_RE` is disjoint from every station name, which lets one route table serve both shapes.
  - `AttachSessions` is IN MEMORY ONLY. It holds the live provider client and hands the finished config straight to the write; no credential reaches a view or poll response.
  - `authorize` runs `ownedAgentOrThrow` BEFORE any provider client is created.
  - 5-min pending TTL, 1-min settled, 2 per agent, 40 per daemon, 15s unref'd sweeper; expiry/cancel/`stop()` all call `driver.cancel()`.
  - Login modules live in the STATION packages and are pulled in by DYNAMIC import, so `@mtcute/bun` and Baileys are not loaded at boot.
  - The whatsapp driver closes its pairing socket BEFORE the train boots with the same creds, or the two fight. Baileys' `connection: 'close'` with 515 right after pairing is a REQUIRED restart, not a failure.
- After a write, `reloadAccountsFromDb()` re-reads Postgres and rewrites the account files and maps. `writeStations` rewrites a train stub only when its CONTENT changes (`writeIfChanged`) — the supervisor watches that directory and an unconditional rewrite would restart EVERY station on every attach. Reactivation is `TrainSupervisor.requestReload(name)`, sharing the fs watcher's debounce map so the two collapse into one restart; `stopTrain(name)` is the detach-the-last-account path.

### Monitor transport (`monitor/api.ts`)

Live-only `GET /api/tail` SSE (no replay), `POST /api/call/:train/:action`, `GET /api/health`. Same `authenticate()` and `allowedAgents()` as `/mcp`, so it grants nothing the Channel does not. Enabled iff the daemon holds a credential at all (`hasAnyKey()` or `METRO_SESSION_SECRET`); otherwise the whole `/api/*` surface 404s. `/api/health` stays in front of the auth gate — its body is what `/health` already serves unauthenticated. **Keep it minimal: no history, ring buffer or claims.**

Do NOT reintroduce a `color-mix` or a hand-picked hex — the sidebar used to blend `bg` with `inputBg` and landed on a tone the palette never defines, which is what made it read warm. Only three background tones exist in practice (`surfaceColor` maps `surface`/`sunken`/`toolbar` to `bg` and only `raised` to `inputBg`), so the sidebar is `inputBg` and anything that must sit on top of it uses `borderColor` as a fill. One exception stands: the pairing QR pins the kit's LIGHT-scheme tokens because a themed QR in dark mode cannot be scanned.

- **Loading indicators wait 100ms before their first paint** (`loading-delay.ts`). Both mount only while something is in flight and unmount when it lands, so each times its own appearance and no call site has to know.
- **One `CountBadge`, and it is the kit's badge system, not a hand-rolled pill.** `resolveBadgeStyle` (`@stage-labs/kit/badge`) supplies background, readable foreground and font token; the fill is `palette.border` so it matches the kebab. `beside="title"` opts into `OPTICAL_NUDGE` — geometric centring measured correct against BOTH the line box and the cap height, yet still read HIGH beside a page title, because a word like "Connectors" is mostly x-height. The nudge lands it between cap and x-height centre. That is an optical judgement, reached by rendering variants and looking at them; section headings (`ToolList`) take no nudge. Do NOT re-add a private badge beside it — `ToolList` had one and it is gone.
- **A connector row is ONE line** — favicon, name, host — the tools/sign-in summary having been dropped. Sign-out state shows as a greyed title, a **Connect** button (`size="md"` = 40px, matching `.kebab-lg`), and a sort that pushes disconnected rows last (`connectorsInOrder`: a stable sort returning a NEW array, so the query cache is never sorted in place). **Disconnect lives in the kebab and is red**, on the list and on the connector page.
- **`Connect` must open its tab SYNCHRONOUSLY on the click.** `window.open` after the `await` is popup-blocked — the gesture is spent, the same reason the add-connector modal cannot open a tab after its POST. The handler opens a blank tab first and assigns `location` once the authorize url arrives, falling back to the same tab when the popup was blocked outright.
- **The favicon is Google's `s2/favicons`, asked for the REGISTRABLE domain.** `baseDomain` strips subdomains against a public-suffix list (`mcp.example.co.uk` → `example.co.uk`), because `mcp.snapshot.box` 404s where `snapshot.box` answers. An unknown domain returns a real **404**, so `onError` is a clean signal and falls back to a lettered tile — the old `/favicon.ico` guess had no such signal, which is what made `ConnectorIcon` read as broken and got it deleted. The tile pins the kit's LIGHT-scheme `bg-light`, the same exception the pairing QR takes: a favicon carries no theme, and Snapshot's is black-on-transparent, invisible on a dark surface. Rendered at 16px, fetched at 32. Known cost: it discloses each connector's domain to Google, mitigated only by `referrerPolicy="no-referrer"`.
- **There is NO mono font anywhere, and `variant="mono"` is not a thing any more.** GT America is the only family; `ui.tsx` resolves `fontFamily` from weight alone. The variant was already a no-op by then — an explicit `size` beat `resolveTextSize`, and `mono` maps to the DEFAULT text role — so the prop only ever swapped the family. `FONT_MONO`, `--metro-font-mono` and the `.markdown code` mono rule went with it.
- **`.kebab` carries NO border, and that is load-bearing.** Its border was the same colour as its background (and as its hover), so it never rendered — but it made the button 42px against the kit Button's fixed 40px, a visible misalignment no amount of `align-items: center` can fix. - **The kit Button sets `alignSelf: 'flex-start'`** (`button.styles.ts`), so in a centred row it sits at the top of the content box rather than the middle. Its `style` prop merges after the base, which is the one place to override it — `CENTER_SELF` in `ConnectorRow`.
- Every page gets `paddingBottom: 64` from `Shell`, against `paddingTop: 24`, so content never ends flush with the viewport.
- **Inline style objects in JSX are a LINT ERROR** (`no-restricted-syntax` in `stage.config.js`, `**/*.tsx`, selector `JSXAttribute[name.name=/[Ss]tyle$/] > JSXExpressionContainer > ObjectExpression`). Reach for the kit's `Box` props first — `gap`, `padding`/`margin` (`{x,y,top,…}`), `flex`, `minWidth`/`maxWidth`, `width`/`height`, `radius`, `background`, `surface`, `border` (`{bottom:{width,color}}`) — which is most of what a style object was ever used for; `surface="raised"` is the token for `palette.inputBg`. The rule bans the LITERAL, not the prop, so a NAMED constant is the sanctioned escape for what the kit has no prop for: `SHRINK` and `GROW` in `theme.ts` (flexShrink/flexGrow + `minWidth: 0`, which is what makes `numberOfLines` ellipsize), and a local const for anything computed (`ScrollView`, `Animated.View`, a portal's position, a raw `div`/`img`). Note this does NOT mean the rendered DOM loses inline styles — react-native-web emits `Box` props as inline style either way; the rule is about what the source says.
- **`apps/ui/public/fonts/*.woff2` are the only binary assets and the only files the MIT `LICENSE` does not cover.** The UI renders **GT America** (Regular for body, Medium for the heavier role) and NOTHING else — the two Calibre `.woff2` files are deleted, and `test/fonts.test.ts` pins that no `Calibre*` file remains in `public/fonts`. Nothing imports either face — `index.css` names them by url and Vite copies `public/` verbatim. Each file is its own single-face family at `font-weight: normal`.
  - **`index.css` declares FOUR faces, and the two that look redundant are not.** `GT-America-Regular` and `GT-America-Medium` are what `theme.ts` names, but the kit hardcodes `Calibre-Medium`/`Calibre-Semibold` in six places (`text.styles.ts`, `tokens.ts`, `control.styles.ts`, `title.tsx`, `tabs.tsx`). Metro's `Text`/`Button`/`Input` wrappers override the family, so those are covered; anything unwrapped — `Title`, `Tabs`, `Select`, `Dialog` — is not. The `Calibre-*` blocks therefore remain as ALIASES pointing at the GT America files. Delete them and unwrapped kit components silently drop to system sans. `test/fonts.test.ts` pins all four faces, the preload target, and that no `Calibre*` binary ships.
  - GT America is licensed to Snapshot Labs, like Calibre before it. Neither is covered by the repo's MIT `LICENSE`; do not copy either face into another project.

| telegram | yes | all seven | Telegram **user account** (MTProto via `@mtcute/bun`). Config `{session, apiId, apiHash}`. ToS/ban risk; the session is a full-account secret; single-writer. Dormant until an account exists. |
| discord-bot | yes | all seven + thread/pin/typing/presence/voice | Voice via `@discordjs/voice`. |
| whatsapp | yes | `send`/`reply`/`react`/`unreact`/`edit`/`delete` (no `read`) | Real user account via Baileys. See below. |
| webhook | **no** | none (inbound-only) | See below. |

Allowlists resolve via account-store `allowlistEnv`: `<STATION>_ONLY_ACCOUNTS` restricts, `<STATION>_ACCOUNTS` configures (`XMTP_`, `TELEGRAM_BOT_`, `TELEGRAM_`, `DISCORD_BOT_`, `WHATSAPP_`).

Every station's `accounts` action reports `handle` + `url` for the UI. All of them swallow a failed identity lookup into `null`, so a blank handle means the provider call failed (e.g. a revoked telegram-bot token) — the daemon knows the reason and currently shows none. Worth fixing.

### whatsapp

Package `baileys` (`@whiskeysockets/baileys` is the OLD name; both publish `7.0.0-rc*`). Config `{phone}`; the Baileys auth blob lives in the SAME `accounts.config` jsonb under `config.credentials`, spread into the account file by `materialize.ts` — **the train opens no pg connection.** `useAccountAuthState` holds creds + Signal keys in memory and never writes creds back (`saveCreds` is a no-op; Signal sessions re-establish on demand). Pairing survives deploys and volume loss. Fails loud if the blob is missing. Two writers of the creds: `scripts/login.ts` and a web-UI attach session; the running train writes nothing.

- **Exactly two key types are durable, and the reason is 463.** Baileys 7 attaches a trusted-contact token (`tctoken`) to every 1:1 send, and WhatsApp answers a 1:1 send without one with `ack error 463` — it counts as reaching out to a stranger and time-locks the account. The token is issued to us BY the contact and Baileys' own index-pruning assumes that store is persisted, so an in-memory-only store is the 463 back on every deploy, each refusal deepening the lock. `src/token-store.ts` persists `tctoken` + `lid-mapping` (the PN ↔ LID index the token is filed under) to `~/.metro/whatsapp-tokens-<account>.json`, 0600, debounced 1s, seeded back on boot. Losing the file degrades to the old behaviour, never to a failure. **Do NOT extend this to `session`/`pre-key`/`sender-key`/`identity-key`/`app-state-sync-key`/`device-list`** — `creds` carries the pre-key counters and is still never written back, so persisting half a Signal state is worse than persisting none.
- **A message key is not synthesizable** (`src/keys.ts`). In a GROUP the address is (`remoteJid`, `id`, `fromMe`, **`participant`** = the original author), and a key correct in a 1:1 is wrong in a group in exactly that field: with `participant` missing, Baileys and WhatsApp's own clients fill it from the REACTION's sender, so the reaction resolves to a message that does not exist — accepted, ACKed, rendered nowhere. 1:1 worked by luck. The fix is a per-account bounded LRU (`makeKeyCache`, 4000) filled from EVERY `messages.upsert` (before the `fromMe` filter — our own sends must be in it) and from the key `sendMessage` returns, reused VERBATIM, which also sidesteps lid-vs-phone address spaces. The cache dies with the train, so `react` on a group message this connection never saw FAILS LOUD (`whatsapp_unknown_message`) rather than reporting success for a send that displays nothing. Do NOT "simplify" any of these back to a constructed key.
- **A refused send is an error, and the verdict is read off the raw socket** (`src/ack.ts`). `sendMessage` resolving only means the stanza left the socket; the verdict arrives as `<ack class="message" error="…">`. `send` waits `METRO_WHATSAPP_ACK_WAIT_MS` (5000, `0` disables) and THROWS — `whatsapp_account_restricted` for 463 (naming the timelock, `retryable: false`), `whatsapp_send_refused` otherwise. No ack inside the window is still reported as sent: the absence of a verdict is not a verdict. **The hook must STAY on `sock.ws`** (`CB:ack,class:message`) — Baileys re-emits the same ack through the BUFFERED emitter, and a stuck buffer eats it; `ws` frames bypass the buffer. `messages.update` is kept as the delivery log.
- **Inbound media** covers all five types (plus the `viewOnce`/`ephemeral`/`documentWithCaption` wrappers). `kind` is six-way, not five: WhatsApp ships a voice note and an mp3 both as `audioMessage`, distinguished ONLY by `ptt`, so a kind derived from the mime cannot tell them apart — the station's kind rides on the payload and wins. `mimetype` is stripped of parameters or the cache file gets `.bin`; a node with no `fileName` gets one synthesised from the SAME `extFromMime` the cache name uses. `reuploadMedia` is wired in as Baileys' `reuploadRequest`, which recovers a file WhatsApp already expired from its CDN.
- **The ceiling is `MAX_ATTACHMENT_BYTES` (100 MiB default, `METRO_ATTACH_MAX_BYTES`), metro's, not WhatsApp's** — between 100 MiB and WhatsApp's 2 GB document limit metro is the thing refusing. It refuses honestly and for free: every media node declares `fileLength`, so the size is asserted before a byte is fetched. The download timeout is metro's too (`withIdleTimeout`), because Baileys 7 typechecks a `signal` and then drops it.
- `sock.end()` is `async` in Baileys 7 and must be awaited.
- **A second Baileys client on live credentials is an OUTAGE, not a test** — the sockets share one device identity, the newest wins, and Signal state diverges. Verify inbound media against a local `mmg.whatsapp.net` in a private mount namespace instead. ToS/ban risk: use a dedicated number.

### webhook

`hasAccounts: true, hasTrain: false` — an endpoint is an `accounts` row, so it is OWNED by one agent and scoped like any other station.

- **Attach:** `{"station":"webhook"}`. No provider exists to verify, so `prepareWebhook` mints a `webhookId` and a `secret`, stores `{secret, webhookId, createdAt}` in `config`, and puts the finished `endpoint` straight on the 201's `identity`.
- **The url names the `webhookId`, NEVER the `account_id`.** That is why the second id exists: `account_id` is `a<agentId>-<8 hex>`, so a public url built from it would publish the internal agent id to every provider it is pasted into. `webhookId` is 19 random digits (`newWebhookId`) and carries nothing. The PK, the agent map key and the event line all stay `webhook/<account_id>`; `findEndpointByWebhookId` is the only lookup the route may use.
- **Inbound:** `POST /api/webhooks/<webhook_id>/<token>`. **The whole URL is the credential** — no signature header, deliberately: an HMAC is a real gate but most providers cannot compute one, and the header was what made this unusable. The token is 48 CSPRNG bytes base64url compared with `timingSafeEqual`; everything that is not an exact match is a flat 404, including an `account_id` in the id position and a row missing either field. `GET` is a 200 readiness probe with no event; anything else 405.
- **The route MUST stay in `handlePreMcpRoutes` BEFORE `handleMonitorRequest`** or the monitor router swallows it. `webhook-station.test.ts` boots WITH a `monitorCall` and asserts `/api/tail` still 401s while the hook 200s — the only way that bug is visible.
- The token never reaches a log or the event: `webhookEntry` is handed `hookPath(id)`, not `req.url`.
- **This is the ONE place the no-API-returns-a-station-credential rule is relaxed.** `inCoreAccounts` re-serves the full url to the owning agent on every `GET /api/agents`, because a url you cannot retrieve is useless — you paste it into a provider days later. The blast radius differs in kind: a bot token or XMTP key controls an account on someone else's network, this one only posts events INTO its own agent. Scoped by the same `scopeAccountsByAgent`, surfaced as `endpoint` rather than `url` so the row's external-link button never makes a credential clickable, and masked behind Reveal/Copy in the UI.
- **Delivery needed TWO fixes.** Dropping the `station === 'webhook'` check in `inbound.ts` was necessary but NOT sufficient: `classifyEvent` types an external webhook as `{type:'system'}` and `routable` only routed `msg`/`react`, so an attached endpoint answered 200, emitted, and reached NOBODY. `system` is routed now, safe because that branch is its only producer in the workspace.
- The note (`channels/webhook-note.ts`) carries the pretty-printed body — the summary line alone tells an agent nothing — capped at `MAX_BODY_CHARS` 8 KiB with the dropped count named, plus an ALLOWLIST of headers, never the whole map: a delivery's `authorization`, `cookie` and signature must not land in the agent's context.
- Two consequences of routing a `system` event: `handleEvent` does NOT set `lastLine` for one (that is `knownLine`, where an approval prompt goes, and a webhook line has no `send` verb), and `handlePermissionReply` runs only for `msg`, so a body containing `yes abcde` can never answer a pending request.
- `listEndpoints` reads the materialized `~/.metro/webhook-accounts.json`, not the pre-account `webhooks.json` (warned about once at boot by `warnOnLegacyWebhooks`).

## Projects own everything

- **A PROJECT is the unit of ownership. Nothing belongs to a user except the project itself.** `agents.project_id`, `connectors.project_id` (and, until `0019` dropped them, `collections.project_id`) replaced `owner_id`/`user_id` in `0015`; stations follow their agent and connectors are held by agents through `agent_connectors`. `users` now only identifies a person and owns projects.
- `projects` (`id`, `name`, `owner_id` → `users.id` restrict, `is_default`) and `project_members` (`project_id` cascade, `user_id` restrict, `role`, `unique(project_id, user_id)`).
- **Roles gate the PROJECT, not its contents.** `admin` and `member`; any member manages that project's agents and connectors, only an admin renames it or manages members, and only the OWNER deletes it. The owner cannot be demoted or removed, and a `is_default` project cannot be deleted at all — `ensureUserWithProject` mints one named `Personal` on first sign-in.
- **`memberAccessOrThrow` is the single access predicate** (`db/projects.ts`) and everything else goes through `projectIdOrThrow`. A project you are not a member of is a flat **404**, identical to one that never existed, so the route is not an existence oracle.
- **Reads and creates take `?project=<id>`; everything else resolves the project FROM THE ROW.** `listAgents`/`createAgent` and `listConnectors`/`createConnector` require the query param (400 without it). `ownedAgentOrThrow` and `ownedConnectorOrThrow` look the row up by id and then assert membership of ITS project, so a rename or delete needs no project on the wire and cannot be pointed at the wrong one.
- **`db/users.ts` exists to break an import cycle.** `projects.ts` needs user lookup and `agent-admin.ts` needs membership; leaving `ensureUserByAddress`/`userIdForSubject`/`normalizeAddress`/`isUniqueViolation` in `agent-admin.ts` made the two import each other, which madge rejects. For the same reason `ensureUserByAddress` does NOT create the default project — `ensureUserWithProject` (in `projects.ts`) composes the two, and only the sign-in path calls it.
- **`0015` is hand-written, and it must stay that way.** `drizzle-kit generate` emits bare `DROP COLUMN`s that would throw away every ownership link. It creates a `Personal` project per existing user, backfills agents/connectors/collections from the old owner, sends any orphaned agent to the earliest user's default project, and only then sets `NOT NULL` and drops the old columns. **There is no down migration: once deployed, rolling back means restoring a backup.**
- **The MCP auth path is untouched.** An agent's key still resolves straight to its agent id with no user or project involved, so connected clients and the CLI are unaffected by any of this — only the web API became project-scoped.
- In the UI the project is IN THE ROUTE (`#/<projectId>/connectors`), never a stored preference, so a link identifies what it shows. `#/settings` (appearance) and `#/authorize` stay user-level. **`Dashboard` redirects to a project ONLY for `kind: 'none'`** — it used to redirect whenever the selection carried no project id, which silently bounced `#/authorize`, `#/settings` and `#/docs/setup` to `#/<projectId>`. `rememberedProject` (in `api/projects.ts`, shared with the authorize page) falls back to the last used project and then the default one, which is what makes `#/` land somewhere.
- **`#/authorize` renders OUTSIDE the shell** — a centred card like the login page, returned by `Dashboard` before `Frame` and never by `AgentPanel`. It defaults to the last used project and lists that project's agents straight away, with `Change project` to switch; `#/authorize/<agentId>` (the url `metro start` prints) is the same card for one agent and skips the chooser. The selection kind is `authorize` with `id: string | null`.

## Running the daemon locally (`metro start <agentId>`)

The daemon can run on the user's own machine so **no message content passes through metro's servers**. Credentials still live in the hosted Postgres — this is a PORTABILITY and message-privacy change, not credential custody. Say it precisely: *your messages do not pass through Metro's servers*; **not** *Metro cannot read your messages*, which is false while metro holds your bot tokens.

- **Metro NEVER runs a messenger station. Local only, and there is no fallback.** `pgSource` filters `MOVABLE_STATIONS` out unconditionally, held or not, so the hosted daemon materializes webhook and nothing else. A messenger station does not run anywhere until a machine claims the agent, and that is deliberate: a hosted fallback would silently put the operator back on the message path, which is the property this whole design exists to remove.
- **`StationSource` is the whole seam** (`db/materialize.ts`): `() => Promise<LoadedAgent[]>`. `pgSource` reads Postgres, `httpSource` reads `GET /api/run/config`. `materializeFrom`/`reloadFrom` are source-agnostic; `materializeFromDb`/`reloadAccountsFromDb` are thin pg wrappers holding the two pg-only concerns (the `DATABASE_URL` guard and `closeDb`). **There is no "local mode" branch below that seam** — that is what stops hosted and local forking.
- **Linked mode is selected by `METRO_RUN_TOKEN` alone** and is never inferred. `runtimeConfigFromEnv()` returns null without it and boot takes `materializeFromDb()`.
- **File mode is the third `StationSource`, and it is opt-in: `METRO_MODE=local`.** `db/file-source.ts` reads every `<METRO_AGENTS_DIR, default ~/.metro/agents>/<name>/agent.json` — `{version: 1, id, name, key, owner, stations[]}` — and validates it loudly with the file path in every error: 11-character ids, the agent-name rule (`AGENT_NAME_RE`, now in `db/ids.ts` so the file reader and `createAgentForUser` share it), an `mk_` key, a lowercase owner address, known station names, and no id or key shared by two files. Precedence at boot is run token → `DATABASE_URL` → `METRO_MODE=local`; with none of the three the daemon still fails loud on the missing `DATABASE_URL`, on purpose — a hosted deploy that lost its secret must not boot empty and green. File mode is the one source allowed to materialize ZERO agents (`materializeFrom(source, { allowEmpty: true })`), because a fresh machine has no agent until something creates one, and `stationRunsHere` counts it as local so messenger stations run here. Nothing reloads the files yet: that arrives with the routes that write them. `test/file-source.test.ts` pins the parser, the uniqueness rules and the empty case.
- **`materializeFrom` throws on ZERO AGENTS, not zero stations.** An agent whose stations all moved local is legitimate; the old count-stations check would crash-loop the hosted daemon the moment the last agent moved.
- **A held agent's key is refused by metro.** `pgSource` returns it with `key: null`, so a client still pointed at `mcp.metro.box` gets a clean 401 rather than an empty session it might mistake for working.
- **A held agent is served by exactly one daemon, but its rows are still VISIBLE.** `pgSource` returns a held agent with its accounts intact and **`key: null`**: the null key keeps `agents.key` out of the hosted key map, so a client pointed at the wrong daemon gets a clean 401. The accounts stay because the agent/name/allowlist maps are what the panel's attribution reads; stripping them made every held agent's stations vanish from metro.box, which shipped once. Hosted not RUNNING those stations is `stationRunsHere` in `writeStations`, not an empty account list.
- **`typ: 'run'` is a THIRD token type.** It is the only token `GET /api/run/config` accepts (a session JWT and an agent token are both refused there), and since `0019` it is ALSO accepted wherever an agent token is (`agentIdentity`: `/api/cli/*`, `/relay/*`), so the machine running the agent reads its connectors with no second sign-in; it is refused on every session-gated route. `test/run-api.test.ts`, `test/cli-pair-api.test.ts` and `test/relay.test.ts` pin the directions. **The lease is fenced on those routes too** (`assertLease` in `api-http.ts` → `fenceRuntime`): a run token whose machine was taken back (`DELETE /api/agents/<id>/runtime`) answers 401 on `/api/cli/*` and `/relay/*` before any upstream contact, so taking an agent back really cuts that machine off instead of leaving its token live until expiry. `/api/run/config` is the one route that deliberately serves a stored station credential — to a token that authorizes exactly one agent, minted only by that agent's owner.
- **The config read IS the heartbeat.** There is no separate heartbeat route; the poller already reads every 30s.
- **`MOVABLE_STATIONS` is every station EXCEPT webhook**, enforced on the READ, so a station attached after the claim is silently withheld rather than half-running. The CLAIM (`/api/run/claim`, `blockedStations` dep → `blockedStationsFor`) is refused outright (409, naming the stations, code spent) for an agent holding a webhook, because the bus is in-process and `supervisor.call` answers `no train named '<x>'` — an agent split across two daemons is broken, not degraded. It cannot be refused at MINT time any more: one `ma_` code serves `metro login` too, which a webhook agent is entitled to.
  - **webhook is the ONE station that can never be local**, and it is structural: `POST /api/webhooks/<id>/<token>` is called by third parties, and the url is re-derived from the daemon's public base, so a local daemon would hand out `http://127.0.0.1:…` for deliveries that keep landing on Fly.
  - **xmtp IS local**, and the cost is one installation per machine, not per restart: `config.dbPath` is HOME-relative (`~/.metro/xmtp-production-<hex>.db3`) and `expandHome` resolves it against the LOCAL home, so the first boot on a machine registers an installation and every later boot reuses that db3. An inbox allows ten; `bootAccount` prints a one-line warning the first time a machine spends one so it is never silent. Machine CHURN is what would exhaust it — revoking an installation costs a non-renewable identity update (256 cap) — which is why a stable server is fine and a fleet of short-lived boxes is not. If churn ever becomes real, add a `fetchInboxStates` precheck that refuses near the limit.
  - **whatsapp treats `connectionReplaced` as TERMINAL** (`terminalReason`, `packages/whatsapp/src/client.ts`). It used to fall through to an immediate reconnect, so two daemons on one device identity evicted each other in a tight loop — a full login from a new IP per iteration, which is exactly the traffic shape a 463 timelock punishes. The lease should prevent two, but this makes an accidental double-run survivable instead of destructive.
- **There is NO fallback.** On 401/403/409 the poller stops every train and does not retry — `RuntimeRevoked` is terminal. An unreachable metro is the other branch: back off, change nothing, keep relaying. Getting those two backwards is the bug.
- **The lease has no epoch and needs none.** Runtime ids are unique and a reclaim always mints a new one, so `agents.runtime_id === token.rt AND revoked_at IS NULL` is a complete fence. Reclaim is a human action (`DELETE /api/agents/<id>/runtime`), never a timer — automatic reclaim on a station where overlap is destructive is a scheduled outage.

## Database / multi-agent (Postgres + Drizzle)

**The DB is the ONLY runtime account source** — nothing reads station secrets from the environment.

Four tables in `db/schema.ts`. BOTH foreign keys point at `users.id` `ON DELETE RESTRICT` — `agents.owner_id` and `connectors.user_id` (a user who still owns either cannot be deleted); `stations` references its agent by a plain text column with no FK.

**Every id is an 11-character base64url string** (`db/ids.ts`, `newId()` = 8 CSPRNG bytes, `ID_RE = /^[A-Za-z0-9][A-Za-z0-9_-]{10}$/`) — YouTube's shape, 64 bits, URL-safe. The first character is forced alphanumeric by REROLLING, and that is load-bearing: base64url yields a leading `-`/`_` about 3% of the time, which `ACCOUNT_ID_RE` rejects and which is hostile as a filename or CLI argument. `id` is the FIRST column of every table; `0011` recreates each table to get that physically, since `ALTER TABLE ADD COLUMN` appends.

**Ids are opaque, never parsed.** They carry no type prefix and no embedded agent, so nothing may infer ownership from an id's text — `stations.account_id` used to be `a<agentId>-<hex>` and no longer is.

- `users` — `id`, `address` UNIQUE (the lowercase wallet that signs in), `email` UNIQUE but nullable (only rows from before SIWE carry one). One row per person, created on first wallet sign-in.
- `agents` — `id` (the real identity, the only thing scoping compares); `name`, a display label with NO unique index since `0007`, so it may repeat across and within owners and differ only in case; `owner_id` nullable (NULL = operator-provisioned); `key` nullable text UNIQUE.
- `stations` (was `accounts` until `0011`) — `id` PK; `agent_id`; `station` **plain text, not a pg enum**, so a new station needs no migration (adding `webhook` needed none); `account_id`; `allowlist` text[] DEFAULT `['*']`; jsonb `config`. `unique(station, account_id)` keeps the old PK's global-uniqueness invariant. The `StationName` union is TS-only, via `$type`.
- **`stations.account_id` is NOT the primary key and its values were NOT re-minted by `0011`.** It is the station's public handle: it appears in `metro://<station>/<account_id>` lines an agent already holds, and in `~/.metro/whatsapp-tokens-<accountId>.json`. Re-minting it would orphan that token store and bring back the `463` timelock.
- **The materialized per-station files are still `~/.metro/<station>-accounts.json`.** That name is a contract with the station packages (`packages/*/src/accounts.ts` defaults) and with the `*_ACCOUNTS_FILE` env vars — the table rename must NOT rename them.
- `connectors` (added by `0010`) — `id`; `user_id` → `users.id`, so a connector is owned by the PERSON and no agent id appears on the path; `name`; `url`; `transport` plain text (`http` today, `sse` reserved), `ConnectorTransport` TS-only via `$type`; jsonb `config` = `{auth, createdAt, verified}`, ISO strings, no timestamp column. **No unique on the name** — see Connectors above.

There is NO `keys` table since `0009`, no `credentials` column and no `whatsapp_auth` table. `allowlist` is a first-class column (relay-only, stripped from the train files); `owner` and every heterogeneous secret live in `config`, which materialize passes through to the train files. DB deps (`drizzle-orm`, `postgres`, dev `drizzle-kit`) live ONLY in `apps/mcp`; config is `apps/mcp/drizzle.config.ts`, generated SQL `apps/mcp/drizzle/`.

### Writers and loading

- `db/agent-admin.ts` (users + agents), `db/account-attach.ts` (stations), `db/connectors.ts` (connectors) and `db/whatsapp-login.ts` are the ONLY writers. `db/materialize.ts` is read-only against the DB, and it never reads `connectors` — nothing about a connector is materialized to disk or to a train.
- `ensureUserByAddress` is `INSERT … ON CONFLICT DO NOTHING RETURNING id`, re-SELECTing the winner when a concurrent first login wins the race, so two simultaneous logins settle on one row and neither 500s.
- **`isUniqueViolation` (`db/users.ts`) walks the `cause` chain.** drizzle-orm ≥ 0.44 wraps every driver failure in a `DrizzleQueryError` whose `PostgresError` sits in `cause`, so a bare `err.code === '23505'` never matches and every "swallow the duplicate" path answered 500 instead — the old collections add did exactly that in production. Verified against a real Postgres; `test/unique-violation.test.ts` pins the wrapped shape.
- `createAgentForUser` validates the name (`/^[A-Za-z0-9][A-Za-z0-9_-]{1,31}$/`, trimmed, **never lowercased**), mints the key and inserts agent + key in ONE statement, with no duplicate-name check of any kind. It registers the key only when the daemon is not `METRO_AGENT`-pinned.
- **Keys are stored PLAINTEXT.** `GET /api/agents` re-serves the key to its owner, so hashing would break that and turn `authenticate()` into a DB lookup. Don't "fix" it in passing.
- No per-owner agent cap and no sign-in domain allowlist — sign-up is open to any Ethereum wallet by design. Don't reintroduce `METRO_MAX_AGENTS_PER_OWNER` or `METRO_SIGNIN_DOMAINS`.
- `deleteAgentForUser` **does not cascade into `accounts`**: an agent with rows is refused 409 and the owner detaches them first, so deleting an agent can never destroy a live station credential in one click. It deletes in one transaction (re-asserting `owner_id` in the WHERE) then `unregisterAgentKey(id)`, so the key 401s on the next request without a restart — evicting from the DB alone is not revocation. It never touches `users`.
- `materializeFromDb()` runs once at boot before `supervisor.start()`, writes the per-station account files (`writeSecure` 0600) and train stubs, and **throws on missing `DATABASE_URL` or an empty DB** — one path, fails loudly. Trains read those files; none opens a pg connection.
- `METRO_AGENT` (an 11-character agent id) restricts a daemon to one agent; must match `ID_RE` and exist, or boot throws. Unset loads all — and since #129 several agents hold the daemon concurrently, so one daemon per agent is no longer required for liveness.
- xmtp config is `{privateKey}`; the legacy `{mnemonic, derive}` HD form is GONE and a row still carrying it fails validation at boot. `mnemonic`/`derive`/`seed` stay in the UI's `SECRET_KEY_PATTERN` redaction list so an unconverted row can never render its seed.

### Migrations

**Migrations apply themselves on deploy, via `release_command` in `fly.toml` — NOT at boot.** Fly runs `bun --filter @metro-labs/mcp db:migrate` (i.e. `drizzle-kit migrate`) in a temporary machine holding the app's secrets BEFORE the new version is released. It is the same command you run by hand, so there is one code path, not two.

- **`release_command` replaces `CMD` but NEVER overrides `ENTRYPOINT`.** This is why the Dockerfile ends in `CMD ["bun", "/app/apps/mcp/src/server.ts"]` and must NOT go back to `ENTRYPOINT`. With an `ENTRYPOINT` the release machine runs `bun server.ts <release command>` — `server.ts` ignores argv, so it boots a SECOND daemon against an empty `/data` (a fresh XMTP installation, burning an install slot) and never exits, timing the deploy out. This actually happened once; do not reintroduce it.
- **The failure semantics are the whole point of choosing `release_command` over a boot-time `migrate()`.** A non-zero exit ABORTS the deploy and the old machine keeps serving. The same migration at boot would throw before `markDaemonReady()`, which the crash guard turns into `exit 1` — a crash-loop, i.e. an outage caused by the migration itself. Do not move this to `boot.ts`. Verified: unreachable DB, empty and unset `DATABASE_URL` all exit 1; a re-run with nothing pending exits 0 and applies nothing.
- **`drizzle-kit` is a runtime `dependency`, not a devDependency** — `bun install --frozen-lockfile --production` (Dockerfile) would otherwise leave it out of the image and the release command would fail. It is ~10 MB. Moving it back to devDependencies breaks every deploy.
- **`bun --filter` is load-bearing**: it sets cwd to `apps/mcp` so `drizzle.config.ts` and its relative `out: './drizzle'` resolve. The release machine's cwd is `/app` (the Dockerfile `WORKDIR`), where neither exists.
- The daemon itself still never migrates, and `materializeFromDb()` still throws on an empty DB — a deploy whose release command failed never reaches it.
- `test/migrate.test.ts` pins journal integrity only (every entry has its `.sql`, contiguous and ordered `when`, no orphan `.sql`). There is no Postgres in the suite; the DB behaviour above was verified by hand against a real one staged at `0009`.

## Deploy & Ops

- **Merging to `main` auto-deploys to Fly.** Don't merge unfinished work. Land via PR; the repo squash-merges (`(#NNN)` suffix).
- **Every deploy is a real outage** — 40–90s observed, and it kills the GET stream of every connected MCP client permanently (see the ceiling above). Tell the user to reconnect metro afterwards.
- Fly app `metro`, region `iad` (`fly.toml`). `auto_stop_machines=false`, `min_machines_running=1`, `shared-cpu-1x`/1gb, `metro_data`→`/data`. Env: `HOME=/data`, `METRO_TRAINS_DIR=/app/apps/mcp/trains`, `METRO_HTTP_HOST=0.0.0.0`, `METRO_LOG_LEVEL=info`.
- **Single-writer XMTP:** only ONE instance may write the MLS inbox. A second burns the 10-install / 256-update budget, and exhaustion is a permanently dead inbox. This is why `min_machines_running=1` and machines never auto-stop. Never run a second prod writer.
- `HOME=/data` puts the MLS db3s on the mounted volume so they survive deploys — that durability is why XMTP stays on Fly.
- No Docker entrypoint script: `ENTRYPOINT` runs `bun /app/apps/mcp/src/server.ts` directly, and materialize generates the stubs. `acquireLock` reclaims a stale lock from an ungracefully-killed instance so a restart never boot-loops, while a genuinely-live metro still makes the second instance exit.
- **`DATABASE_URL` is the ONLY required Fly secret.** Optional: `METRO_PUBLIC_URL`, `METRO_AGENT`. Station secrets live in the DB. The channel allowlist is the per-account `allowlist` column, not an env var.
- Reconnect reality: the channel GET stream is held open by a 15s SSE-comment keepalive. On reconnect the relay replays from the bounded ring — best-effort, bounded to `BUS_BUFFER_MAX`, not guaranteed across a long disconnect.

## Working discipline

- **Verify, then act.** Confirm claims against the code (rg/Read) before changing or asserting. Most "obvious" facts here have load-bearing exceptions.
- Don't flag code as dead without an `rg` search proving zero references across the workspace, including the exports map and the station registry.
- The full gate must be green before you propose a PR.
- Branch off `main`, open a PR, land via PR. For stacked PRs, beware `--delete-branch` deleting a dependent PR's base.
