# CLAUDE.md

## What Metro is

Metro is a relay that bridges chat networks (XMTP, Telegram, Discord, generic webhooks) to an MCP server. Runs as one always-on Fly process; serves MCP in-process over HTTP; supervises one subprocess ("train") per configured station. Inbound chat messages become MCP events for an agent to act on; the agent's outbound tool calls fan back out to the right network.

## Monorepo layout

Bun workspaces (`bun@1.3.9`): `apps/*`, `packages/*`.

- `apps/mcp` — the core. Package `@metro-labs/mcp`, bin `metro-daemon` → `./dist/server.js`. Source dirs:
  - `src/mcp/` — generic MCP core: server, tool dispatch, the `str()` helper (`str.ts`). No per-channel transport logic.
  - `src/channels/` — Channel transport: the `InboundRelay` (`inbound.ts`) that turns bus events into `notifications/claude/channel` MCP notifications. Depends on core (`mcp/str.js`), not vice-versa.
  - `src/monitor/` — the lightweight live Monitor transport (`api.ts`): SSE tail + call/health endpoints.
  - `src/daemon/` — boot, HTTP server, tunnel/endpoints, train supervisor, logging, errors, secure-fs, protocol, the in-process event bus.
  - `src/stations/` — station registry, types, runtime, account-store, attachments, lines, messaging-normalize.
- `packages/*` — seven station packages: `@metro-labs/xmtp`, `@metro-labs/telegram`, `@metro-labs/telegram-user`, `@metro-labs/discord`, `@metro-labs/whatsapp`, `@metro-labs/line`, `@metro-labs/webhook`.

Flow: inbound network message → station → in-process bus → MCP event for the agent. Outbound: agent MCP tool call → station verb → network. The daemon hosts both the MCP server and the stations in one process; the bus connects them.

## Commands / the gate

- `bun install` — install. CI and Docker use `bun install --frozen-lockfile`; always commit `bun.lock` changes or CI/deploy breaks.
- Local run: `bun apps/mcp/src/server.ts` (`server.ts` is just `import './daemon/boot.js'`). Prod and `start` run TS from source — `dist/` is built only by the gate's `build` task and is not used at runtime.
- The gate: `build` + `test` run through turbo; `typecheck`, `lint` (eslint), `knip`, `madge` run through `stage` (`@stage-labs/config`). Run the full set (`bun run build && bun run typecheck && bun run lint && bun run knip && bun run madge && bun run test`) before any PR; gate must be green.
- Single package: run the same scripts inside the package (e.g. `bun --filter @metro-labs/mcp test`).
- Tests: `apps/mcp` test script is `tsc --noEmit && bun test test/`; the real command runs with `METRO_STATE_DIR="$(mktemp -d …)"`. The turbo `test` task `dependsOn ["^build"]` so a core (`apps/mcp/src`) edit invalidates the station packages' cached test results. Run the full `bun test` suite — don't assert an exact test count.
- madge runs via `stage madge` (`@stage-labs/config`), configured through `stage.config.js`.

## Conventions (strict `@stage-labs/config` preset — HARD constraints)

- No comments in source. None. Don't add explanatory comments.
- No escape hatches: no `eslint-disable`, no `@ts-ignore`/`@ts-expect-error`, no `any` casts to dodge types.
- **`no-floating-promises` runs with `ignoreVoid: false`** (tightened over the preset in `stage.config.js`). `void somePromise()` is NOT a way to float a promise here — it was the eslint-sanctioned suppression that let the v157 crash be written and pass lint. Every promise must be `await`ed or end in a `.catch()` that LOGS; a bare `void` on a promise is a lint error. `void p.catch(h)` still passes but the `void` is noise — drop it.
- Size caps enforced by lint: `max-lines` per file (counts blanks + comments) and function-length limits. Split files instead of suppressing.
- tsconfig is strict; ESM. Import specifiers MUST carry explicit `.js` extensions (`./tunnel.js`, not `./tunnel`).
- Errors: throw real errors; surface messages via the shared `errMsg` helper and `TrainError` (`@metro-labs/mcp/train-error`). Don't swallow.
- Logging via the shared `log` (`@metro-labs/mcp/log`) — not `console`.
- Imports from core use the exports map, e.g. `@metro-labs/mcp/log`, `/train-error`, `/secure-fs`, `/events`, `/lines`, `/endpoints`, `/trains/protocol`, `/stations/types`, `/stations/station-runtime`, `/stations/account-store`, `/stations/attachments`, `/stations/messaging-normalize`. Station packages: `.` → `src/station.ts` (station def), `./train` → `src/index.ts` (train entry).

## Architecture notes

- In-process bus (`src/daemon/events.ts`): inbound flows station → bus → MCP event in one process. It is a bus, not a journal — no on-disk persistence/history. It keeps a small bounded in-memory ring buffer (`BUS_BUFFER_MAX = 500`) keyed by a monotonic `busSeq`; the Channel relay (`src/channels/relay.ts`) tracks the highest contiguously-delivered `busSeq` and replays missed events on transport rebind so the Claude channel does not drop messages across reconnects. Bounded + in-memory only — do NOT add an on-disk journal/history.
- Static seam: stations are wired through the registry in `src/stations/`; core dispatches generically over station defs (verbs/attachment modes), no per-network branching in core.
- Tolerated package cycle: there is a known dependency cycle between core and station packages. It is intentional and tolerated — do NOT "fix" it; madge is configured around it.
- Six out-of-process trains (XMTP, Telegram, Telegram-user, Discord, WhatsApp, Line) + webhook handled in-core (no subprocess; `hasAccounts: false`). The telegram-user, whatsapp, and line trains only spawn when an account of that station is configured. Line is a hybrid: its train handles OUTBOUND (push API) only, while INBOUND arrives via an in-core webhook route (`daemon/line-webhook.ts`, mounted on the shared HTTP server before the MCP auth gate) — the route reads the materialized `line-accounts.json` for the per-account `channelSecret`, verifies `X-Line-Signature` (base64 HMAC-SHA256, fail-loud), parses the events array, and emits inbound `MetroEvent`s directly onto the bus.
- Permission replies (human-in-the-loop): a pending MCP `permission_request` is relayed to chat as `yes <request_id>` / `no <request_id>`; `inbound.ts` matches the chat reply with `PERMISSION_REPLY_RE = /^\s*(y|yes|n|no)\s+([a-km-z]{5})\s*$/i`. The 5-char-code format is a contract with the relayed prompt — never change one side only.
- Self-serve agent API (`daemon/agent-api.ts`): `GET`/`POST /api/agents`, `DELETE /api/agents/<id>`, plus the account sub-resource routed to `daemon/account-api.ts` (`POST /api/agents/<id>/accounts/start`, `DELETE /api/agents/<id>/accounts/<station>/<account_id>`). Mounted in `handlePreMcpRoutes` **before** the monitor router (which claims all of `/api/*`) and before the MCP auth gate. Anything else under `/api/agents/` is a 404 from this handler, so the monitor router never sees it. Shared request plumbing (CORS, `sendJson`, `apiSession`, `readJsonBody`, `apiFailure`) lives in `daemon/api-http.ts`; every status-carrying error extends `ApiError` (`daemon/api-error.ts`): `AgentAdminError` and `StationAttachError` both do, and `apiFailure` maps exactly those to their status and everything else to a logged 500. Gated by the Google session JWT (`Authorization: Bearer` or `?token=`), never by an agent key. Its DB access is injected from `boot.ts` (`AgentApiDeps`) exactly like `metroCall`, so `daemon/` never imports `mcp/` — keep it that way or madge breaks. `GET` returns the agent's key VALUE (plus its `?token=` endpoint and paste-ready `claude mcp add` command) for agents the session **owns**, and nothing at all for everything else — a `GOOGLE_EMAIL_AGENTS` grant comes back `owned: false` with `key`/`endpoint`/`command` all `null`. Those three are flat fields on the agent, exactly the shape `POST /api/agents` returns, because an agent has AT MOST ONE key since `0009`. Re-serving is possible only because `agents.key` is plaintext (see below); the exposure is gated TWICE and both gates must stay: `listAgentsForEmail`'s list query selects only (`id`,`name`,`owner_id`) and `selectKeyRows` re-reads the `key` column for owned ids ONLY, so a granted agent's secret never leaves Postgres, and `agent-api.ts` re-checks `agent.owned` in `keyPayload` before serialising. `AgentRow` has no `key` field at all, so the assembly step cannot serve a key it was not separately handed. `toAgentSummaries` is the pure, unit-tested assembly step; the `owned` boolean and the key exposure are derived from ONE predicate (`ownerId !== null && r.ownerId === ownerId`) so they cannot drift apart. That null guard is load-bearing: a caller with no `users` row resolves to `ownerId === null`, and without it `null === null` would hand every operator-provisioned row to a stranger as owned. Ownership is `agents.owner_id` (⊕ the `GOOGLE_EMAIL_AGENTS` grant) resolved from the DB per request: the session email is turned into a `users.id` on every call, NOT read from the JWT, so a freshly created agent shows up without re-login and an old session minted before `0008` keeps working. The scope set handed to `gatherAccounts` is `agents.id`s, never names. `boot.ts` wires that dep to `gatherAccountsForAgents` (`mcp/accounts.ts`), which scopes as before and then stamps each surviving account with the `agentId` that owns it, so the UI can render accounts UNDER their agent instead of in one global list. That stamping is on the `/api/agents` path only: the MCP `list_accounts` tool still calls plain `gatherAccounts` and its output shape is unchanged. It is display metadata, not an authorisation step: `scopeAccountsByAgent` remains the thing that decides which accounts are visible at all. DELETE is owner-only and addressed by id: not-yours or unknown → 404, `owner_id IS NULL` → 403 (a grant lets you SEE an operator row, never delete it), still-attached `accounts` rows → 409. `POST /api/agents/<id>/key` resets that agent's key and is owner-only through the SAME `ownedAgentOrThrow`, so its authorisation cannot drift from delete's or attach's: not-yours or unknown → 404, `owner_id IS NULL` → 403. It answers 200 with the new `key`/`endpoint`/`command` built by the same `credentials()` helper `POST /api/agents` uses, so the shapes cannot diverge; the key value is never logged. It is a session-JWT route like every other one here — an agent key cannot reset itself.
- The paste-ready command (`mcpAddCommand`, `daemon/agent-api.ts`) deliberately mirrors the Browserbase one byte for byte in shape: `claude mcp add --transport http <server-name> "<endpoint>?token=<key>"`. There is NO `--scope user`, which means `claude mcp add` falls back to its **local** default and registers the server only for the directory the line was pasted in. That is Less's explicit call to match the Browserbase convention, made knowing the scope consequence, so do NOT "fix" it back to `--scope user`. `--transport` stays spelled out in full rather than `-t`, for the same reason. The server name is the **constant `metro`** for every agent, never the agent name and never a slug derived from it (#124, Less's explicit call): only the `?token=` differs from one agent to the next, so `mcpAddCommand` takes the key alone. That constant is also what makes the emitted line safe whatever is in `agents.name` — the earlier `mcpServerName` sanitiser existed because a DB name with a space would paste as `claude mcp add --transport http Ada Lovelace "<url>"`, which the CLI accepts with a SUCCESS message and registers as a broken server named `Ada` pointing at `Lovelace`; with a fixed token the agent name never reaches the command at all, so the sanitiser is gone. The known consequence: two metro agents added to the SAME Claude Code config now collide on the second `claude mcp add`, because both are called `metro`. That is accepted (one agent per machine is the common case), it is a collision in the pasting person's own config rather than ours, and it is never a scoping question because nothing on the auth path reads this string — so do NOT "fix" it back to a per-agent name or add a suffix.
- Attaching station accounts (`daemon/account-api.ts` + `db/account-attach.ts` + `stations/attach.ts`): `POST /api/agents/<id>/accounts/start` is the ONLY route that writes `accounts`. Ownership is `ownedAgentOrThrow`, **the same function `deleteAgentForEmail` uses**, so the attach predicate cannot drift from the delete predicate; a `GOOGLE_EMAIL_AGENTS` grant (`owned:false`) gets 403 and can never attach or detach. `stations/attach.ts` owns the per-station credential check and returns `{ config, identity, secret?, discard? }`. **The invariant is that no `accounts` row exists unless that credential has been demonstrated to work**, so every station is verified against the real provider BEFORE the row is written: discord `GET /users/@me` + the `/applications/@me` Message Content flags, telegram `getMe`, and xmtp opens a real inbox with the key it just generated (`stations/attach-xmtp.ts` → `@metro-labs/xmtp/verify`). Well-formed is NOT enough: a generated secp256k1 key is well-formed by construction, which is precisely why it has to be registered before it is stored. The xmtp check runs OUT OF PROCESS (`Bun.spawn('bun run …/verify.ts')`, key over stdin, never argv/env, 90s cap) because `@xmtp/node-sdk` v6 exposes no `close()`/`releaseDbConnection()`, so an in-daemon client would hold the MLS SQLite handle for the daemon's whole life and fight the train over the same db3, which is the single-writer rule. It verifies into the SAME `~/.metro/xmtp-production-<16 hex>.db3` the train will use and stores that path in `config.dbPath`, so the train reuses the verified installation instead of burning a second of the inbox's ten (measured: same db3 gives the same `installationId`, a fresh db3 gives a new one). If the write fails after a good check, `prepared.discard?.()` deletes the db3 + `-wal`/`-shm`; `account-api.ts`'s `storeAccount` is the only caller. Refusal messages are run through `withoutKey` so a provider message can never echo the generated key back. `prepareAccount` is injected as `deps.prepareAccount`, and its xmtp verifier is a second injected param, so the route and the station check are both testable without touching the network. `account_id` is ALWAYS server-generated (`a<agentId>-<8 hex>`), never taken from the body, because (`station`,`account_id`) is a global PK and a caller-chosen id would both collide across owners and leak which ids exist. Duplicate bot tokens are refused 409 (two telegram accounts sharing a token make the whole train refuse to boot). **No API ever returns a stored station credential**: the one-time `secret` in the 201 body is the ONLY time the generated XMTP key is shown, and `GET /api/agents`'s `agents.key` exposure was deliberately NOT extended to `accounts.config`.
- Interactive attach (`daemon/attach-session.ts` + `stations/attach-interactive.ts` + `@metro-labs/telegram-user/login` + `@metro-labs/whatsapp/login`): `telegram-user` and `whatsapp` cannot finish in one request, so `POST .../accounts/start` answers `status:'pending'` with an `as_<22 base64url>` attach id, and the client polls `GET .../accounts/<attachId>`, posts `.../step` with a `code` or `password`, or `DELETE`s to abandon. `ATTACH_ID_RE` is disjoint from every station name, which is what lets one route table serve both `/accounts/<attachId>` and `/accounts/<station>/<accountId>`. `AttachSessions` is IN MEMORY ONLY, never persisted: it holds the live provider client (the thing holding the credential in flight), hands the finished config straight to the `accounts` write, and never puts a credential on the view or in a poll response. `authorize` runs `ownedAgentOrThrow` BEFORE any provider client is created, so a grant cannot even start a Telegram login it would not be allowed to store. 5-minute pending TTL, 1-minute settled TTL, 2 sessions per agent, 40 per daemon, a 15s unref'd sweeper, and expiry/cancel/`stop()` all call `driver.cancel()` to tear the client down. The login modules live in the STATION packages (the station owns its library) and are pulled in by DYNAMIC import so `@mtcute/bun` and Baileys are not loaded into the daemon at boot. The whatsapp driver must close its pairing socket BEFORE the train boots with the same creds, or the two connections fight; `finish()` closes it first, then reports. Baileys sends `connection: 'close'` with 515 right after pairing, which is a REQUIRED restart with the same in-memory creds, not a failure.
- The daemon is now a writer of `accounts`, but ONLY through `db/account-attach.ts` (mirroring the `db/agent-admin.ts` and `db/whatsapp-login.ts` (the operator `scripts/login.ts` path) precedent). `materialize.ts` still never writes the table. After a write, `reloadAccountsFromDb()` re-reads Postgres, rewrites the per-station account files and the agent/allowlist/key maps, and `pruneStations` blanks the account file + removes the train stub for a station whose last account just went away; boot's `materializeFromDb()` keeps its old behaviour (empty DB → throw, then `closeDb`). `writeStations` rewrites a train stub only when its CONTENT changes (`writeIfChanged`), because the supervisor watches that directory and an unconditional rewrite would restart EVERY station on every attach. Reactivation goes through `TrainSupervisor.requestReload(name)`, which schedules `handleSourceChange` on the SAME debounce map the fs watcher uses, so an explicit reload and the watcher's own event collapse into one restart instead of two; `stopTrain(name)` is the detach-the-last-account path.
- The UI is NOT an MCP client any more (#113). `apps/ui/src/mcp/client.ts` was deleted: at the time the daemon ran ONE `mcp.Server` on ONE transport and `rebindDecision` rebound it on every `initialize`, so a browser MCP client stole the live agent's session on every page load. Sessions are per-identity now (see below) and a same-scope browser client would take that identity's session rather than everybody's, which is still not a thing the panel should do. The UI uses `fetch('/api/agents')`. Do not reintroduce an MCP client in `apps/ui`. Layout is two panes: the left sidebar is the agent list and nothing else, and EVERYTHING agent-specific (accounts, attaching a new one, MCP endpoint, API key, the `claude mcp add` line, delete) belongs to the selected agent in the main pane. Attach/detach controls render only when `agent.owned` is true, matching the server's predicate; the UI hiding them is convenience, `ownedAgentOrThrow` is the enforcement. Accounts must never render globally; the pairing is structural, never inferred. An account with no `agentId` is shown under no agent; the one exception is a session that can see exactly ONE agent, where every returned account is by construction that agent's, which is what keeps a new UI usable against an older daemon.
- `apps/ui/public/fonts/Calibre-{Medium,Semibold}.woff2` are the ONLY binary assets in the repo and the ONLY files the MIT `LICENSE` does not cover — they are a commercial Klim Type Foundry face under Snapshot Labs' own licence. Do not copy them into another repo and do not delete them as "unused" (nothing imports them; `src/index.css` names them by url and Vite copies `public/` verbatim into `dist/`). The kit hardcodes the family NAMES `Calibre-Medium` and `Calibre-Semibold` and never sets a `fontWeight`, so each file is declared as its own single-face family at `font-weight: normal` — one `Calibre` family at 500/600 (which is how `packages/tune` does it in `sx-monorepo`) would match nothing here. `apps/ui/test/fonts.test.ts` guards the declaration and the css↔file path pairing; see `apps/ui/README.md` § Fonts for why there is no `local()` source.
- `agents.key` is the ONLY credential. `METRO_MCP_HTTP_TOKEN` was retired: there is no env bearer, no `{kind:'key'}` identity, and **no unscoped principal anywhere in the daemon**. Since `0009` an agent has AT MOST ONE key and a key belongs to AT MOST ONE agent: `agents.key` is a nullable text column with a UNIQUE constraint (NULLs are distinct, so any number of agents may have no key, but no two may share one). That 1:1 is what makes a bare `?token=<key>` unambiguous with no agent selector in the url. `db/key-map.ts` keeps ONE index: SHA-256(key) → agent id. It holds no plaintext key at all — the id → key index and its `keyForAgent` reader were removed once `attach-serve.ts` stopped putting the agent's key in attachment urls, so nothing in the daemon needs a key back out of an agent id. `materialize.ts` fills it at boot and `createAgentForEmail` registers a new key live. `authenticate()` order is: key map (→ `{kind:'agent', agentId}`) → session JWT (→ `{kind:'google', agentIds}`). No token, or a token in neither, is a 401 — a daemon with nothing configured is CLOSED, not open. `allowedAgents()` is the single place that turns an identity into a scope set — it returns a `Set<number>` of agent ids and NEVER `undefined`; use it, don't re-derive. Key RESET is `POST /api/agents/<id>/key` → `resetAgentKeyForEmail` (`db/agent-admin.ts`). One column cannot hold an old and a new key at once, so a reset is a hard cutover with NO overlap window, deliberately: one `UPDATE agents SET key = … WHERE id = … AND owner_id = … RETURNING id` (the same owner re-assertion the delete uses, 0 rows → 404, retried on `23505` so the UNIQUE constraint cannot be tripped), then `rotateAgentKey(id, key)` — which is `unregisterAgentKey` + `registerKey` in ONE synchronous call, so the map never holds two live keys for one agent and never holds none. Order is load-bearing: the row commits, THEN the map swaps, THEN the new key goes out in the response, so the new key is never advertised before it works and the old one never outlives the response. `registerKey` alone is NOT a rotation — it adds a hash without evicting the old one, which is exactly the two-live-keys bug `rotateAgentKey` exists to prevent, and `key-map.test.ts` pins that. The new key is registered only when this daemon serves that agent (`daemonServesAgent`, i.e. unpinned or `METRO_AGENT` == the id); the eviction is UNCONDITIONAL, because a pinned daemon that skipped the eviction would keep honouring a key its owner just revoked. Revocation is not complete until the live MCP session is gone too: `boot.ts` composes the DB reset with `closeAgentSession(id)` (`mcp/index.ts` → `SessionRegistry.closeScope`), which closes the session whose scope key is that agent's (`sessionScopeKey({kind:'agent', agentId})`) and ends its standalone GET stream AT THE WIRE — an attached SSE stream authenticated once with the old key would otherwise keep receiving that agent's traffic forever, because a stream does not re-authenticate. The per-identity `ReplayLedger` survives in the registry LRU, so the client reconnecting with the new key still gets anything that arrived while it was disconnected. A Google session over the SAME single agent shares that scope key and is closed with it; a multi-agent Google session is NOT, deliberately — the JWT is a separate credential and a key reset revokes the key, not the sign-in.
- ONE scope predicate, three transports (`db/agent-scope.ts`). `lineTargetDenied(allowed, args, station?)` resolves `args.line` to `station/accountId` → agent id and denies anything outside the scope set; it also denies an `args.account` override that would re-route to another agent's account, which is the hole a line-only check leaves open because stations resolve `account ?? line`. `mcp/index.ts`'s `scopeDenied` and the Monitor's call gate are both that one function, so they cannot drift. `stationFullyScoped` is the extra rule for a call that names NO line (`accounts`): allowed only when every account of that station is in scope, which is a no-op while one agent owns a station and a hard 403 the moment a second agent joins it. `eventInScope` is the delivery filter for EVERY inbound egress, and it FAILS CLOSED: an event whose line maps to an agent goes only to that agent, and an account-station line (the `STATIONS` list in `db/schema.ts`) whose account maps to NO agent goes NOWHERE. The old `agentId === undefined || …` fail-open handed a whatsapp account with a stale accounts file and no DB row to every tail, so it is gone; the deliberate, narrow carve-out that remains is by STATION, not by lookup failure — a line on a station that has no accounts at all (`webhook`, local `metro://claude/…`) is not agent-owned traffic and still goes to every authenticated tail, which is what `monitor.test.ts`'s ownerless-event assertion pins. An unparsable line reaches nobody. This cannot black-hole traffic at boot: `boot.ts` awaits `materializeFromDb()` (which throws on an empty DB) before `createMetroMcp()` and `startWebhookServer()`, and `setAgentMap` swaps the map in one assignment rather than clearing it, so there is no window in which the map is transiently empty while requests are being served — and if it ever were empty, `key-map.ts` would be empty too and every request would 401 before reaching a scope check. The Monitor tail applies it per subscriber; the Channel applies it through `ChannelOwner` (`mcp/channel-owner.ts`), which records the identity that authenticated the currently-attached standalone GET stream — that stream is the wire notifications actually go out on, so it, not the transport, is the thing that decides scope. `ChannelRelay` consults it in `deliver()`; an out-of-scope event is WITHHELD, not dropped — it is removed from `pending` so the bounded ring buffer replays it to its real owner on the next attach. With no stream attached nothing is deliverable at all (`inScope` is false for every line), which is what keeps an event alive until a session exists to receive it instead of writing it into a transport with no reader. `streamBelongsTo` (now one definition with the session key: both are `sessionScopeKey` equality) survives as the last-line guard on a stream takeover — a GET that would replace a session's live stream from a different scope is a flat 409 — which is unreachable while routing is correct and is exactly why it is there. The permission relay (`mcp/permission-relay.ts`) re-checks `owner.inScope(relay.knownLine)` before pushing a tool-approval prompt to chat: `knownLine` is per-session state now, and the re-check stays because a prompt is Claude's tool name + input preview.
- **SSE resumption is a SECOND egress and must be scoped separately** (the v146 leak; #127 gated only `ChannelRelay.deliver()`, which is a real gate that the resumption path simply does not pass through). `serveStandaloneGet` replays the `BoundedEventStore` straight to whoever presents a `Last-Event-ID`, before the sink is bound and without ever consulting `ChannelRelay` — so the leak produced NO relay log line at all, neither `notify … replay true` nor `withheld`, which is the signature to look for. There is ONE `_GET_stream` and one session for the whole daemon, so one client's cursor addresses another client's frames by construction: agent B's `initialize` adopts the session, agent A's reconnect adopts it back (`rebindDecision`), and A's stale cursor then names B's buffered frames. The fix scopes the buffer itself: `storeEvent` records the frame's `meta.line` AND the `ChannelOwner` scope in force when it was stored (`scopeOf` is a REQUIRED `BoundedEventStore` dep — there is no permissive default), and `replayEventsAfter` takes the reconnecting identity's scope as a REQUIRED option and re-checks every frame through `mcp/frame-scope.ts` → the same `eventInScope`. `scope: undefined` replays NOTHING, which is what the SDK's own (unreachable, because `isStandaloneGet` intercepts every SSE GET before `transport.handleRequest`) call site would get. A line-carrying frame is judged by its line; a frame with no line (the permission notification) is judged by its recorded owner scope, so it still resumes to the session it was generated for and to nobody else. Withholding at replay does NOT consume the frame — the store is a buffer, not a queue, so the rightful owner's own reconnect still replays it, and the bus ring buffer is the independent path that re-delivers anything never delivered at all. `test/egress-scope-matrix.test.ts` crosses ONE case table against ALL FOUR egresses (channel live, channel bus replay, SSE resumption, monitor tail); add a new egress to that table or the next one will leak exactly the same way. Both gates are KEPT and are now redundant by construction (#129 gave every identity its own event store, so a cursor cannot name another identity's frames in the first place) — that redundancy is the point, this class has already recurred once, so do NOT remove either gate on the grounds that isolation makes it unreachable.
- **Per-identity MCP sessions** (#129). A session is `mcp/session.ts`'s `McpSession` and it owns EVERYTHING that used to be a module-level singleton: its own `mcp.Server`, its own `StreamableHTTPServerTransport`, its own standalone `_GET_stream` sink, its own `ChannelOwner`, its own `BoundedEventStore`, its own `InboundRelay` and its own `ChannelRelay` with its own bus subscription. `mcp/session-registry.ts` holds them in TWO indexes filled together — session id → session, and scope key → session — so a lookup by either cannot drift from the other. The scope key (`mcp/session-route.ts`, `sessionScopeKey`) is the SORTED agent id set, not the identity object: an `agents.key` and a Google session over the same one agent are the SAME session, which is deliberate and is the same equality `streamBelongsTo` already used for keeping a stream across a rebind. There is at most ONE live session per scope key: a second `initialize` from the same identity supersedes the first (its own client's business), a second identity does not touch it (the thing that used to break). `rebindDecision` is GONE, and with it adopt-anything: `routeSession` returns `use` for a session id the caller already owns, a flat 404 `Session not found` for one somebody ELSE owns, and `create` with `adoptId` ONLY for an id nobody owns — which is what keeps the daemon-restart resumption (`test/mcp-session-restart.test.ts`) working without letting one identity name another's session. `initialize` never adopts the presented id. **Adoption is silent to the client, so an adopted session MUST be told the tool schema may have moved**: the client presents the id it already had, gets a 200, and never re-`initialize`s, which means it never re-fetches `tools/list` and keeps whatever schema it cached when its process first connected — across every deploy, for the life of that Claude Code process. That is how #135's `data` attachment source stayed invisible to an agent for an hour after it shipped: her client was still advertising the pre-#135 two-source schema, so inline bytes were not failing, they were unofferable, and `url` looked like the only thing that worked. The server therefore declares `capabilities.tools.listChanged` and sends ONE `notifications/tools/list_changed` to a session whose schema may have moved — not to a session the client initialized itself, which has just listed the tools anyway. **The notice is armed by a schema SIGNATURE, not by the adoption flag** (#141): `toolSchemaSignature()` (`tool-dispatch.ts`) is a memoized hash of the served `toolList()`, `McpSession.issuedSchema` records the signature the session was issued (the current one for a self-initialized session, `undefined` for an adopted one, because what an adopted client cached is genuinely unknown), and `schemaNoticeDue` is simply `issuedSchema !== toolSchemaSignature()`. That is the daemon telling rather than guessing, and it keeps working if the tool list ever stops being compile-time static — today it cannot change in-process, so adoption is the only way a live session can hold a stale schema, which is exactly why #137 gated on it and got the right answer for the wrong reason.
  - **Arming it is not delivering it, and delivery was the actual #137 bug.** #137 fired the notice only from `bindSink`, i.e. only onto the standalone `_GET_stream`. A real client does not have one when it matters: the MCP SDK client opens that GET exactly ONCE, right after `notifications/initialized`, and its reconnect budget is `maxRetries: 2` at 1s and 1.5s (`client/streamableHttp.js`) — a Fly deploy is ~16s of connection-refused, so both retries burn inside the outage and the stream is gone for the life of that client process. The client keeps its session id, keeps POSTing tool calls, metro adopts it (`session: opened` with the SAME id), `schemaNoticeDue` goes true — and nothing is ever sent, because `bindSink` never runs again. Worse, the SDK server silently DISCARDS a notification with no `relatedRequestId` when `_GET_stream` is absent (`webStandardStreamableHttp.js`: "Stream is disconnected - event is stored for replay, nothing more to do"), so there is no error and no log line either. Measured with a real SDK client against a real daemon across a simulated deploy: zero notices, on both a 0.5s and a 16s outage.
  - **So the notice rides whichever egress the client is actually reading.** `deliverSchemaNotice` takes the send function: `announceToolSchema` passes `server.sendToolListChanged()` on a standalone-GET bind (guarded by `streamAttached` so it cannot be spent on a dead stream), and `registerToolHandlers`'s `SchemaNotice` hook passes `extra.sendNotification` from inside the `tools/call` handler, which the SDK routes onto THAT request's own SSE response stream. A streamless adopted client therefore learns the schema moved on the response to its very next metro tool call. A `tools/list` request settles the notice WITHOUT sending one (`markCurrent`) — the client is holding the current schema by definition, and notifying there would be a refetch loop. `issuedSchema` is updated only once the send RESOLVES, so an undelivered notice stays armed for the next opportunity instead of being consumed by a drop; an `announcing` latch keeps two concurrent tool calls from both sending. Pinned in `test/schema-notice-without-stream.test.ts` (adopted-with-no-stream gets it on a tool call, gets it only once, `tools/list` settles it silently, self-initialized never gets it) alongside the original `test/mcp-session-restart.test.ts` pair. **The ceiling is real and worth knowing: the daemon cannot reach a client that is neither streaming nor calling.** If a client's GET stream is dead it is also receiving no inbound chat at all, and nothing server-side can fix that — only a `/mcp` reconnect or a client restart re-opens it. The session id is minted by the registry and handed to the transport as its `sessionIdGenerator`, so it is known before the first request is handled rather than read back off the transport afterwards. Lifetime: an idle session with no attached stream is reaped after `SESSION_IDLE_MS` (10min) by a 60s unref'd sweeper, `MAX_SESSIONS` is 64 and the ceiling evicts the least-recently-used STREAMLESS session (and refuses with a 503 rather than dropping a live one). Replay bookkeeping is per identity, not global: the registry keeps a bounded LRU of `ReplayLedger`s (`{startAt, delivered}`) keyed by scope key and hands the SAME ledger to each successive session of that identity, which is what makes a message that arrived while an agent was disconnected survive its reconnect AND its full re-initialize; a scope that has never connected starts at the `startInbound()` watermark, exactly the boot-time watermark the single relay used. A displaced or superseded stream is now closed at the WIRE: `RawGetSink.close()` clears the keepalive, drops the SDK `_streamMapping` entry, releases the sink and calls `res.end()`, and it is also wired in as the SDK stream entry's own `cleanup`, so `transport.close()` ends the response too. Before this, `dropStream()` only set `rawGetSink.closed = true` and the displaced client got no bytes, no EOF and no keepalive until its own idle timeout (~90s observed). `InboundRelay` state is per session for the same reason: `knownLine`, `allowedLines`, `seenEvents` and `pendingPermissions` are one instance per identity, so one agent's chat reply can no longer answer another's tool-approval prompt. The dedupe key (`channels/dedupe.ts`) keeps stripping the account segment — that is what collapses ONE agent's two accounts sitting in the same conversation, which is why it exists (#2) — but is now prefixed by the OWNING agent id, so two AGENTS on the same conversation id with the same station-native `messageId` no longer suppress each other. Do NOT re-collapse any of this into a singleton, and do not assume "one session" anywhere: `test/session-concurrency.test.ts` drives two agents over real HTTP at once and is the file that fails first if you do.
- **Scoping is by `agents.id`, never by name.** `agent-map.ts` maps `station/accountId → agent id` (`agentIdForAccount`) and keeps a separate id → name map used ONLY for the display label `MetroEvent.agent` (`agentForLine`). `key-map.ts` maps SHA-256(`agents.key`) → agent id, and the session JWT carries `agent_ids`. `agents.name` has NO uniqueness at all since `0007` (it is a display label, stored with the casing the person typed), so a name comparison anywhere in an authorisation path is a cross-owner leak, and it will NOT be a type error — both are strings. The one place a name is still looked up is the `GOOGLE_EMAIL_AGENTS` grant, and that query is pinned to `owner_id IS NULL` so an operator grant can never resolve to an agent somebody owns. That pin is the whole safety argument and it predates `0007`: Postgres treats NULLs as distinct in a unique index, so `owner_email IS NULL` rows were NEVER constrained by the old (`owner_email`,`name`) index and a grant could always match several rows. `operatorAgentIdsByName` returns all of them and the session is scoped to all of them: over-broad visibility of operator rows, never a key (grants are `owned: false`, so `key`/`endpoint`/`command` are null) and never a delete (403). If that ever needs tightening, the fix is to let `GOOGLE_EMAIL_AGENTS` carry ids, not to re-add a unique index. Grant entries match the stored name byte for byte, casing included.
- REMOVED / don't resurrect: `history.jsonl`, on-disk journal/outbox, the Codex integration (dropped in #16). Don't reintroduce these. The old read-only HTTP "Monitor dashboard" (ring-buffer/backlog replay, `/api/state`, claims/owner-mode filtering) was removed in #40 — do NOT bring those parts back. A deliberately-scoped **lightweight Monitor transport** was reintroduced (`monitor/api.ts`): live-only `GET /api/tail` SSE (no replay), `POST /api/call/:train/:action`, `GET /api/health`, mounted before the MCP auth gate. It authenticates with the SAME `authenticate()` as `/mcp` (an `agents.key` or a session JWT, `?token=` or Bearer) and scopes with the SAME `allowedAgents()`, so it grants a credential nothing the Channel does not already grant it. It is enabled iff the daemon holds a credential at all (`hasAnyKey()` or `METRO_SESSION_SECRET`); otherwise the whole `/api/*` surface 404s exactly as it did when the env token was unset. `/api/health` deliberately stays IN FRONT of the auth gate: its body is the same `version`/`uptime` snapshot the unauthenticated `/health` already serves on the same port, so gating it would buy nothing. Keep it minimal — no history/ring buffer/claims.
- Attachment serving (`daemon/attach-serve.ts` + `daemon/attach-owner.ts`) is scoped by the OWNING agent, not by a shared secret. `withAttachmentUrl` in `http.ts` resolves the event's line to an agent id (`agentIdForLine`) and hands it to `attachmentEventUrl`; minting the url writes TWO sidecars next to the cached attachment (`writeSecure`, 0600): `<cachefile>.owner` (the agent id) and `<cachefile>.grant` (`daemon/attach-grant.ts`, a JSON `{token, agentId, mintedAt}` whose `at_<43 base64url>` token is 32 CSPRNG bytes). The `?token=` in the url is THAT per-attachment token, never the agent's key, so the advertised link keeps working in a bare `curl` while carrying no credential that is good for anything else. Minting is idempotent for the same owner — an existing grant is reused rather than replaced — so re-emitting an event does not silently break a link already delivered. `/attach` takes TWO paths and both re-check the `.owner` sidecar first: the presented token matches that attachment's own grant (compared with `timingSafeEqual`, and the grant's `agentId` must equal the recorded owner), OR the caller authenticates as an identity whose scope contains the owner. Everything else — an unknown owner, an unreadable sidecar, another attachment's token, another agent's key — is a flat 401, never a serve. The ONE thing that answers 404 is a name that is not cache-shaped at all (`CACHE_NAME_RE` fails), decided before `authorized()` runs: that answer depends only on the request string and never on what is on disk, so it leaks nothing, and it is what an operator who pastes the ORIGINAL filename (`horse.mp3`) rather than the cache name now gets. A cache-shaped name stays a flat 401 whether or not it exists, deliberately — the cache name is `msg_<station messageId, first 16 alnum>_<index>.<ext>`, so on discord it is derived from a snowflake that anyone in the channel can already see, and a distinguishable "gone" vs "not yours" would turn `/attach` into an existence oracle over another agent's traffic keyed on public ids. Do not "improve" that 401 into a 404. The capability path FAILS CLOSED: no `.grant` file means no token can ever match, so the only way in is an owner-scoped credential. The sidecar lives in the same durable cache dir as the file, so a deploy does not invalidate links already handed out. `CACHE_NAME_RE` cannot match a `.owner` or `.grant` path (two dots), so the sidecars are unservable by construction. A key reset therefore no longer breaks attachment links: the link's authority is its own token, which the reset does not touch. The one exception is transitional — urls minted BEFORE this change carry the agent key verbatim and die with the first reset, which is the intended way to kill them. Since #129 the Channel is no longer one shared session, so the link is only ever delivered onto the owning identity's own stream.
- **Outbound attachment sources** (`stations/attach-resolve.ts` + `stations/attach-inline.ts` + `stations/attach-resolve.ts`'s `fromUpload`). An attachment on `send` names EXACTLY ONE of `upload`, `data`, `url` or `path`; two is an error and so is none. `upload` is the route for anything real (see the upload endpoint note below); the other three all have a constraint that rules them out for the normal case. The old `hasRef` filter that swallowed a source-less entry is GONE, because dropping it and still answering `sent: text` is exactly the #134 dishonesty. `path` is resolved on the DAEMON host (the tool description now says that in as many words, because callers reasonably assumed their own machine); `url` is fetched by the daemon and must therefore be publicly reachable, which is why it is unusable for a confidential file; `data` is base64 carried inline in the MCP request. **`data` is for TINY files only, and the binding limit is not the daemon's.** `MAX_INLINE_BYTES` is enforced at the daemon, but upstream of it the base64 has to pass through the MODEL'S OUTPUT to get into the tool call at all, and a model cannot emit tens of thousands of characters of base64 verbatim. Lisa measured the practical ceiling at roughly **10 KB** (a small xlsx went; a PDF and an image did not) — three orders of magnitude below the 8 MiB cap, which is why #135 shipped believing the daemon cap would bind and it never does. The earlier #135 note that `data` is "the only form that works for a file on the caller's machine" was true when it was written and is now WRONG: `upload` is that form, and `data` survives only as the tiny-file shortcut that needs no second round trip. Inline is capped at `MAX_INLINE_BYTES` = **8 MiB of DECODED bytes, per attachment AND per send** — the running total is what stops a multi-attachment call from reaching the transport. The number is derived, not picked: `MCP_BODY_MAX` (`mcp/index.ts`) is 32 MiB and a body over it is a bare `413 payload too large` before any tool code runs, so the tool cap has to sit far enough under it (8 MiB decoded is 10.67 MiB of base64) that the explicit limit-naming error always fires FIRST. Do not raise one without the other. base64 is validated strictly (alphabet, whole quanta, and a decoded-length equality check) because `Buffer.from(x, 'base64')` silently drops junk and a silently-corrupt attachment reported as sent is the same class of bug as #134. Strict is not the same as unforgiving: `splitInlineData` strips a `data:<mime>;base64,` prefix before validation and adopts that mime when `mime` is omitted (an explicit `mime` still wins), because a client that base64s a local file commonly hands over the whole data url and refusing it costs a round trip for nothing — a `data:` url with no `;base64` parameter is still refused, since its payload is percent-encoded text rather than bytes. Inline bytes land in a per-attachment `mkdtemp` dir (0700) under `os.tmpdir()` as a 0600 file and NEVER in `attachDir()`: that cache is durable (`HOME=/data` on Fly) and is the only thing `/attach` can serve, so a confidential inline file must not go there. `ResolvedAttachment.temp` carries the dir and `cleanupAttachments` removes it — `handleSend` calls it in a `finally` (success, station error and under-report alike) and `resolveAttachments` calls it on its own partial-failure path before rethrowing. Stations still only ever see a local file, so no inline base64 crosses the train stdin pipe (`drainLines` would drop a call line over `STDOUT_LINE_MAX` = 4 MiB in silence and leave the daemon waiting out the 60s call timeout); xmtp's own 190 KiB non-image refusal is untouched and still fires first on that station.
- **The upload endpoint** (`daemon/upload-store.ts` + `daemon/upload-api.ts` + `mcp/upload-tool.ts`), the fourth attachment source and the only one fit for a real file. The problem it solves is that all three older sources fail for a DIFFERENT reason: `path` resolves on the daemon host, `url` needs the file to be public, and `data` has to transit the model's output. The bytes therefore go over HTTP, straight from the caller's disk to the daemon, never through an MCP message. **This means one step needs a SHELL and there is no way around it**: an MCP tool call is model output by construction, so any MCP-only route puts the bytes back through the model. `create_upload` (the MCP tool) does everything a shell is not needed for — it mints the slot and hands back a ready-to-run command — but pushing the bytes is `curl`. A subagent has a shell; an orchestrator-only main loop does not, and its move is to delegate the ONE command and keep the `upload_id`, because the slot belongs to the metro AGENT, not to whoever ran the command.
  - Two ways in, both ending in the same owned slot. `POST /api/uploads?name=&mime=` with the file as the raw body, authenticated by the agent's own key (the SAME `authenticate()`/`allowedAgents()` `/api/tail` and `/attach` use) — the owner is the single agent in scope, or `?agent=<id>` when a Google session covers several. Or `create_upload` → `PUT /api/uploads/<id>?token=<ut_…>`, where the ticket is the only credential on the wire, so the agent key never reaches a shell command or a process list. `DELETE /api/uploads/<id>` drops a confidential file early instead of waiting out the TTL. Mounted in `handlePreMcpRoutes` BEFORE the monitor router (which claims all of `/api/*`), exactly like `agent-api.ts`; anything else under `/api/uploads/` is a 404 from this handler.
  - **Ownership and the grant are #130's, not a parallel copy.** `attach-owner.ts` and `attach-grant.ts` were generalised to path-based primitives (`recordOwner`/`ownerOf`, `issueGrant`/`readGrant`/`grantAllowsPath`) with the old cache-name functions kept as thin wrappers, so an upload's `.owner` and `.grant` sidecars are written and checked by the same code that guards `/attach`. `/api/uploads/<id>` takes the same TWO paths `/attach` does and fails closed the same way: the presented token matches that slot's own grant AND the grant's `agentId` equals the recorded owner, OR the caller authenticates as an identity whose scope contains the owner. Everything else is a flat 404 (not 401 — an upload id is an unguessable capability, so a distinguishable "exists but not yours" would be an oracle). At `send` time `fromUpload` re-checks the owner against `allowedAgents(currentIdentity())`, passed IN as `ResolveOptions.allowed` — `stations/` must not import `mcp/`, so the scope is a parameter, and `allowed === undefined` resolves NOTHING. Same message for expired, never-pushed, unknown and not-yours.
  - **Transient by construction, never in the durable cache.** Uploads live in `uploadDir()` (`METRO_UPLOAD_DIR ?? $TMPDIR/metro-uploads`, 0700) as `<id>` + `<id>.owner` + `<id>.meta` + optional `<id>.grant`, all 0600. NOT in `attachDir()`, which is durable on `/data`, has no reaper, is already 202 MB, and is the only thing `/attach` can serve — a confidential upload must not become a servable url. `UPLOAD_TTL_MS` is 30 minutes, expiry is read from `.meta` on EVERY lookup (so an expired upload is dead before any reaper runs), and `startUploadReaper()` sweeps every 60s from `boot.ts` with one sweep at start, which is what collects files stranded by a crash. `UPLOAD_ID_RE` (`up_` + 22 base64url) is the traversal guard and also makes the sidecars unaddressable, since an id can hold no dot. A send does NOT consume the upload — a `send` that times out has usually succeeded, so a retry must still work, and the TTL is the thing that reclaims it.
  - **The ceiling is 64 MiB per file, plus a 512 MiB daemon-wide live budget.** It is no longer bounded by the model, so it is derived from three things instead: the bytes stream from the socket to a `.part` file with a running counter and are `rename`d into place only on completion, so RSS is flat and a torn upload is never visible; it must stay under `MAX_ATTACHMENT_BYTES` (100 MiB) so the limit-NAMING error fires before the generic size error; and it clears the largest ceiling any metro station will accept (the Telegram Bot API's 50 MB document limit), so metro is never the thing that refuses a file a station would have carried. Over-size is refused from the `content-length` header BEFORE a byte is written where the client declares one; a chunked body with no `content-length` is caught by the running counter, which then DRAINS rather than throws out of the `for await` — throwing there destroys the socket in Bun's `node:http` and the client hangs forever with no response (measured: `curl` waited out 90s). Draining is capped at `DRAIN_MAX` = 2x. Do not "simplify" the drain back into a throw. **Removing the `.part` on a failed push belongs to `streamToSlot`, not to its callers**: only the `POST` path mints the slot and can drop the whole thing on error, so when the cleanup lived in `handleCreate` a chunked over-size `PUT` against a `create_upload` ticket (the primary advertised route) left a ~64 MiB `.part` behind, charged it to the 512 MiB live budget for the full TTL, and wedged that slot at a 409 `already being written` on every retry — the `wx` open is what makes an orphan `.part` permanent rather than merely wasteful. `drainInto` therefore owns the write and `streamToSlot` `rm`s the `.part` on any throw, so both routes clean up identically and a refused push leaves the slot reusable.
- **An inbound attachment that could not be fetched is `attachmentFailed`, not silence.** A station emits `attachmentSaved` (`contentType`, `attachmentFor`, `index`, `attachmentPath`, `mime`, `name`, optional `kind`) when the bytes land, and `attachmentFailed` (same correlation fields plus `reason`) when they cannot. Both go through ONE correlator, `InboundRelay.mediaCtxFor`, so a failure consumes the pending slot exactly like a success: it takes the buffered caption, marks its index, and clears the 15s `flushPendingFallback` timer once every attachment is accounted for. That timer stays and is still the right answer for a download that never came back at all, but it is the WRONG answer for one that was refused outright — "could not be fetched in time" blames the clock for a 100 MiB limit — and a station that knows must say so at once. Failure notes carry the caption, the sender and the message id like any other media note, and deliberately advertise NO `url` and NO `local_path`, because there is no file. `saveStreamToCache` (`stations/attachments.ts`) is the streaming sibling of `saveBufferToCache` for the same reason `upload-store.ts` streams: bytes go to a `.part` with a running `assertAttachmentSize` counter and are `rename`d in only on completion, so RSS is flat on a 100 MiB file and a refused or torn save leaves neither a half file nor an orphan `.part`. Only whatsapp emits `attachmentFailed` today; discord, telegram, telegram-user and xmtp still fall through to the timeout, and moving them over is a follow-up, not a rewrite.
- **Nothing in the relay path is fatal** (the v157 outage). One `mcp.notification()` that could not be written took the whole daemon down — exit 1, machine reboot, ~16s of outage on every station at once — because `bufferAttachments`'s 15s fallback timer discarded its promise with a bare `void` and `flushPendingFallback` is the ONE `InboundRelay` entry point that does not run inside `ChannelRelay.deliver`'s try/catch. The trigger is ordinary: a client that re-`initialize`s (a stream resume, a supersede, an idle reap, a key reset) closes the old session's `mcp.Server`, and its already-armed orphan timer then fires against `_transport === undefined` → `Error('Not connected')`. **A notification failing because a client vanished is normal and must never be fatal.** Three layers, all kept: the timer `.catch()`es and logs; `ChannelRelay.enqueue` terminates its `chain` with a `.catch()` so one failed step can neither escape nor poison the chain for the rest of that session's life; and `daemon/crash-guard.ts` installs process-level `unhandledRejection` + `uncaughtException` handlers as the FIRST statement in `boot.ts`. The guard is deliberately asymmetric on ONE flag: before `markDaemonReady()` (the last line of `main()`) a crash still `log.fatal`s and exits 1, because a daemon with no HTTP server should crash-loop visibly rather than linger as a zombie for Fly's health check to reap; after ready it logs at `error` with the error, its type, its stack and a per-kind counter, and keeps relaying. `uncaughtException` is treated the same as a rejection on purpose — a sync throw out of a timer or an event handler is one failed event, not a corrupt heap, and `/health` on the shared HTTP server is the independent backstop that still gets a genuinely wedged process restarted. The fatal path does NOT go through pino: it writes one pino-shaped JSON line with `logFatalSync()` (`daemon/log.ts` → `writeSync(2, …)`). `pino.destination(2)` is a SonicBoom with `sync: false`, and `process.exit` right after a `log.fatal` truncates it — measured, and `stream.flushSync()` does NOT fix it, because SonicBoom leaves `_writingBuf` behind whenever an async write is already in flight, which made the loss intermittent (1 run in ~4). A terminal record must be written synchronously or it is not written. `test/never-fatal-notify.test.ts` pins the timer against a real closed SDK `Server` and `test/crash-guard.test.ts` drives the process-level behaviour through real subprocesses, which is the only honest way to assert it. The keepalive `res.write`s in `mcp/raw-get-stream.ts` and `monitor/api.ts` are the same class in sync form (a write to a destroyed socket throws) and are now guarded + close the stream.
- **Outbound attachment reporting is derived, never asserted** (#134, tightened in #135). `handleSend` resolves every attachment in core (`stations/attach-resolve.ts`) and then compares what came back against `atts.length` through ONE predicate, `assertDelivered` in `mcp/call-tools.ts` — applied to BOTH `sendForwarded` (the response's `attachments` array) and `sendNative` (the `station.sendAttachments` return), because a native station skipping one used to under-report with a success. Fewer labels than attachments is an error, never a success. Each station's label list must be built INSIDE the loop that actually pushes, appended only after the push resolves, and derived from the same branch that chose the send verb — never `map`ped over the input array, which is what let telegram-user report full success for a partial send (`attachments.map((a) => a.kind ?? 'file')`) and made the count guard unreachable on that one station. telegram-user's `buildInputMedia` therefore returns `{media, kind}` from one branch, discord builds its labels in `send-files.ts`'s `appendFiles` as it appends to the FormData, and `xmtpSendAttachments` labels through the shared `kindOf` so an mp3 is `audio` rather than `file`. `apps/mcp/test/send-attachment-honesty.test.ts` crosses the drop/partial/complete cases against EVERY station's line, and each station package has its own send-loop test; add a station to both or the next divergence is invisible again. Discord takes paths with no names, so `normalizeDiscord` carries `attachmentNames` alongside `files`/`attachmentKinds` — without it a url-sourced file arrives named after its internal cache file (`msg_out0xxdejy0x4_0.mp3`) instead of `horse.mp3`.

## Deploy & Ops

- Auto-deploy on `main`: merging to `main` deploys to Fly. Don't merge unfinished work.
- Fly app `metro`, region `iad` (`fly.toml`). `auto_stop_machines=false`, `auto_start_machines=false`, `min_machines_running=1`, `shared-cpu-1x`/1gb, mount `metro_data`→`/data`. Env: `HOME=/data`, `METRO_TRAINS_DIR=/app/apps/mcp/trains`, `METRO_HTTP_HOST=0.0.0.0`, `METRO_LOG_LEVEL=info`.
- Single HTTP port: `internal_port=8420`. Port is `webhookPort()` = `Number(process.env.METRO_WEBHOOK_PORT) || 8420` — 8420 is an overridable default, not a constant. Serves MCP, webhooks, and health.
- /health coupling: `daemon/http.ts` serves `GET /health` and `/healthz` — 200, unauthenticated, checked BEFORE the MCP auth gate. Body is `{status:'ok',version,uptime}` (uptime = `Math.round(process.uptime())` seconds; version = `npm_package_version ?? '0.1.0-beta.15'`). Fly health-check hits `GET /health` (interval 30s, timeout 5s, grace 45s). Breaking/gating this route → machine marked unhealthy → outage. A test guards it; keep it passing.
- Single-writer XMTP: only ONE instance may write the XMTP/MLS inbox. A second writer burns the 10-install / 256-update budget (exhaustion = permanently dead inbox). This is why `min_machines_running=1` and machines never auto-stop/start. Never run a second prod writer.
- No Docker entrypoint script: the Dockerfile `ENTRYPOINT` runs `bun /app/apps/mcp/src/server.ts` directly. `METRO_TRAINS_DIR=/app/apps/mcp/trains` so the boot-generated stubs resolve `@metro-labs/*` from `apps/mcp/node_modules` with no symlink. The daemon creates its own dirs; `acquireLock` (`paths.ts`) reclaims a stale lock from an ungracefully-killed prior instance (self/pid-1/dead, or on Linux a live pid whose `/proc` cmdline isn't metro) so a restart never boot-loops, while a genuinely-live metro still makes the second instance exit.
- MCP reconnect reality: the MCP channel GET SSE stream is kept open by a 15s SSE-comment keepalive in `src/mcp/raw-get-stream.ts`. On reconnect the Channel relay replays events from the bounded in-memory ring buffer (busSeq > last contiguously-delivered) — recovery is best-effort and bounded to the last `BUS_BUFFER_MAX` events, not guaranteed across a long disconnect or a buffer overflow.

## Database / multi-agent (Postgres + Drizzle)

- DB is the ONLY runtime account source — nothing reads station secrets from the environment. Three tables in `src/db/schema.ts`. `accounts` references its agent by a plain `agent_id` int with NO foreign key; the ONE FK in the schema is `agents.owner_id` → `users.id` `ON DELETE RESTRICT` (added by `0008`, and RESTRICT was Less's explicit call: a user who still owns an agent cannot be deleted). `users` (`id` serial PK, the owner identity; `email` text UNIQUE and always lowercased through `normalizeEmail`; one row per person, created on first Google sign-in), `agents` (`id` serial PK — the real identity, the ONLY thing scoping compares, `name` a plain display label with NO unique index since `0007` dropped the (`owner_email`,`name`) one added by `0006`, so it may repeat across owners, within one owner, and differ only in case; `owner_id` nullable int → `users.id`, and NULL owner_id = operator-provisioned; `key` nullable text UNIQUE, the agent's ONE API key, added by `0009` when it replaced the `keys` table), `accounts` (`agent_id`, `station` text — plain text, not a pg enum, so new stations need no schema migration; TS-only `StationName` union via `$type` — `account_id`, `allowlist` text[] (DEFAULT `'{*}'` = `['*']` allow-all), jsonb `config` for the station connection secrets + optional `owner` + extras; PK (`station`,`account_id`)). There is NO `keys` table since `0009`, NO `credentials` column and NO `whatsapp_auth` table — the Baileys auth blob lives in `accounts.config` under `config.credentials`, exactly like every other station secret (see below). `allowlist` is a first-class column (relay-only, stripped from the train files); `owner` and the heterogeneous secrets (token/mnemonic/privateKey/session/apiId/apiHash/derive/dbPath) live in `config` — materialize passes `config` through to the per-station train files (trains read `cfg.owner`). Drizzle-kit config `apps/mcp/drizzle.config.ts`, generated SQL in `apps/mcp/drizzle/`. Deps live ONLY in `apps/mcp` (`drizzle-orm`, `postgres`, dev `drizzle-kit`) — station packages never add the DB deps.
- WhatsApp auth needs NO DB path in the train: the creds blob rides along in `config.credentials`, which `materialize.ts` already spreads into the whatsapp account file (`{ id, ...config }`) like any other secret — the whatsapp train opens NO pg connection at all (drizzle stays entirely in `apps/mcp`). The Baileys glue is `packages/whatsapp/src/auth-state.ts` (`useAccountAuthState(credentials, accountId)`): `accounts.ts` carries `credentials` on the `WhatsAppAccount` record, the client passes it in, and it loads the stored `{ creds, keys }` blob (`BufferJSON`-encoded jsonb), holds creds + Signal keys in memory, and never writes the creds back — `saveCreds` is in-memory only, Signal sessions re-establish on demand. The one exception is the trusted-contact token cache (`tctoken` + `lid-mapping` → `~/.metro/whatsapp-tokens-<account>.json`, see the station row); it is a local file and NOT a DB write. The running train (and `materialize.ts`) never write the accounts table; the creds are written either by the manual `scripts/login.ts` through `@metro-labs/mcp/db/whatsapp-login`, or by a web-UI attach session through `db/account-attach.ts`. Fails loud if the blob is missing — no file fallback, DB is authoritative.
- The daemon writes `users` + `agents` through `db/agent-admin.ts` and `accounts` through `db/account-attach.ts`; those two modules plus `db/whatsapp-login.ts` are the ONLY writers, and `db/materialize.ts` is read-only against the DB. `db/agent-admin.ts`: `ensureUser(email)` is the users writer: `INSERT … ON CONFLICT (email) DO NOTHING RETURNING id`, and when the insert returns no row (a concurrent first login won the race) it re-SELECTs the winner's id, so two simultaneous first logins for one email settle on ONE row and neither 500s. It is called on the Google callback path (`completeCallback` → `deps.ensureUser`) AND from `createAgentForEmail`, which is what keeps a session minted before `0008` working without a re-login. `resolveUserId` is the pure, unit-tested insert-then-lookup step. `createAgentForEmail` validates the name (`/^[A-Za-z0-9][A-Za-z0-9_-]{1,31}$/`, trimmed, NEVER lowercased; the casing the person typed is the casing that is stored and displayed), mints the key and inserts the agent WITH its key in ONE statement (no duplicate-name check of any kind), and calls `registerKey` **only when the daemon is not `METRO_AGENT`-pinned** (`servesEveryAgent()`) — a pinned daemon's boot materialize would drop that key anyway, so registering it would make the key work until the next restart and then silently stop. Keys are stored PLAINTEXT — `GET /api/agents` re-serves the key to its owner and `attach-serve.ts` mints attachment urls with it, so hashing `agents.key` would break both and would turn `authenticate()` into a DB lookup. Don't "fix" it in passing. There is NO per-owner agent cap and NO sign-in domain allowlist — sign-up is open to any verified Google account by design (#113 review); don't reintroduce `METRO_MAX_AGENTS_PER_OWNER` or `METRO_SIGNIN_DOMAINS`.
- `deleteAgentForEmail(email, granted, id)` is the delete path, and it **still does not cascade into `accounts`**: an agent with `accounts` rows is refused 409 and the owner detaches them one at a time first (`DELETE /api/agents/<id>/accounts/<station>/<account_id>`, or SQL), which keeps deleting an agent from ever destroying a live station credential in one click and makes it impossible for materialize to stand up a station for a deleted agent. It deletes the `agents` row in ONE transaction (the delete re-asserts `owner_id` in its WHERE; dropping the `keys` table also dropped the separate delete that used to precede it), then `unregisterAgentKey(id)` evicts BOTH key-map indexes so the key 401s on the next `/mcp`, Monitor or `/attach` request without a restart. There is no env copy to clear any more, and the delete no longer `RETURNING`s the key value at all. Evicting from the DB alone is not revocation — the map is the thing `authenticate()` reads. It never touches `users`: deleting your last agent does not delete your account.
- Loading model (deliberately small, subprocess-safe): `db/materialize.ts` is the single DB module — it opens the client (`db/client.ts`), reads agents+accounts, and WRITES the per-station account files (`~/.metro/<station>-accounts.json`, via `writeSecure` 0600) + the train stubs. It runs once at boot (`boot.ts`, before `supervisor.start()`). The station trains read those files through the account-store's file path — including the whatsapp train, whose creds now ride in `config.credentials` in that same file, so it opens NO pg connection (above). `materializeFromDb()` throws on missing `DATABASE_URL` or empty DB — one path, fails loudly. The docker entrypoint no longer generates stubs; materialize does.
- `METRO_AGENT` (numeric agent id) restricts a daemon to one agent; must be a positive integer that exists or boot throws; unset loads all. `applyAgentKey` is GONE with the env token: a lone agent's key is already in the key map, and it authenticates as that agent, scoped to the only agent the daemon serves. Inbound is tagged with the owning agent via `db/agent-map.ts` — materialize sets both in-memory maps (`station/accountId → id` and `id → name`) in the same process as the tagger, and `agentForLine` in `http.ts` resolves the id to a name for the `MetroEvent.agent` label only. Inbound delivery is FILTERED by owner (see `eventInScope` above), so one daemon serving several agents no longer hands one agent's chat traffic to another. Since #129 they are also multiplexed into separate CONCURRENT MCP sessions (see the per-identity sessions note above), so two agents can hold the daemon at once and neither displaces the other; one daemon per agent is no longer required for liveness.
- xmtp account config is `{ mnemonic, derive }` OR `{ privateKey }` (`packages/xmtp/src/accounts.ts`) — the identity secret lives in the DB, no env `MNEMONIC` path. The DB is populated directly by the operator; `drizzle.config.ts` is outside `src/**` and auto-detected by knip's drizzle plugin.
- Deploy is Fly-only. `DATABASE_URL` is the ONLY required Fly secret; everything else is optional: `METRO_PUBLIC_URL` (base URL for attachment links; unset → tunnel hostname, else attachments are surfaced by local path only), `METRO_AGENT` (pin one agent). The channel allowlist is NOT an env var — it is the per-account `allowlist` text[] column (DEFAULT `['*']` = allow all senders; set a specific array to restrict). Station secrets live in the DB, not on Fly. `HOME=/data` (the mounted volume) so the XMTP MLS db3s land at `/data/.metro/xmtp-production-<id>.db3` and survive deploys — that durability is why XMTP stays on Fly (single machine + single-attach volume).

## Working discipline

- Verify, then act: confirm claims against the code (rg/Read) before changing or asserting. Most "obvious" facts here have load-bearing exceptions.
- Don't flag code as dead/unused without an `rg` search proving zero references across the workspace (including the exports map and station registry).
- Gate-green: full turbo gate must pass before you propose a PR.
- PR/merge: branch off `main`, open a PR, land via PR. Merging to `main` auto-deploys. For stacked PRs, beware `--delete-branch` on merge deleting the base of a dependent PR.
