# CLAUDE.md

## What Metro is

A relay bridging chat networks (XMTP, Telegram, Discord, WhatsApp, Threema) to an MCP server, run **on the user's own machine** (`metro serve`). One always-on process serves MCP over HTTP and supervises one subprocess ("train") per station with a train. Inbound network message → station → in-process bus → MCP event. Outbound: agent tool call → station verb → network. A separate, much smaller app (`apps/api`, `@metro-labs/api`) deployed on Fly as `api.metro.box` (renamed from `mcp.metro.box` on 2026-09-05 at Less's request; the old name keeps its certificate for a while) runs NO station: it serves wallet sign-in, the vault (sealed agent bundles) and `/health`, and that is all metro.box is. The page at `https://metro.box` (`apps/ui`, Netlify) manages one local daemon at a time. `docs/LOCAL-FIRST.md` is the design; every step of it has shipped.

## Monorepo layout

Bun workspaces (`bun@1.4.0` — the relay REQUIRES ≥1.4: Bun 1.3.9's HTTP clients, fetch and `node:http` alike, never tear down an aborted upstream connection, so every relayed stream whose client vanished would leak a live vendor socket; `ci.yml` passes `bun-version: '1.4.0'` to the shared workflow and the Dockerfile pins the same): `apps/*`, `packages/*`.

- **One kernel, two deployables, six trains, one launcher, one page** (the layout since 2026-09-09; the measured case is at https://claude.ai/code/artifact/1f541c31-f3e2-4cb2-9dd6-8a896d5a6c47).
- `packages/core` — `@metro-labs/core`, the kernel every process shares: `log`, `events`, `ids`, `secure-fs`, `is-record`, `protocol`, `train-error`, `lines`, `station-names`, `str`, `endpoints` and `stations/{types,station-runtime,account-store,attachments,messaging-normalize}`. **It imports nothing from the workspace, carries no HTTP and no policy**, and is the ONLY thing a station package may import.
- `packages/http` — `@metro-labs/http`, how a metro server authenticates and answers a request: `cors`, `api-http`, `api-error`, `signed-identity`, `identity-key`, `identity-registry`, `return-to`, `mode-api`. Imports only `core`. It exists so viem and `@noble/curves` never reach a station process.
- `apps/api` — `@metro-labs/api`, **api.metro.box**: the vault, the server list, `/api/mode`, `/health`, and the only Postgres in the repo (`src/db/`, `drizzle/`, the `release_command`). 448 lines. No station, no MCP, no gateway.
- `apps/daemon` — `@metro-labs/daemon`, what `metro serve` runs on a box, one directory per domain:
  - `boot/` — `boot.ts`, `crash-guard`, `paths` (state dir, trains dir, the lock), `connect-hint`, `local-owner`. May import anything.
  - `routes/` — `http.ts` (the server and the mount ORDER), `session-apis`, `local-mode` (wires every API's deps), `identity`, `session`. Imports the surfaces; nothing imports it back except `boot`.
  - `agents/` — `api`, `accounts-api`, `bundle`, `admin`, `account-attach`, `map` (line → agent), `keys` (SHA-256(key) → agent), `scope` (the one scope predicate), `files` (the agent.json source), `file-admin` (the writes).
  - `stations/` — `registry`, `attach*`, `materialize`, `supervisor`, `supervisor-io`, `train-call`, `attach-session`, `runtime-deps`.
  - `connectors/` — `api`, `store`, `model`, `config`, `verify`, `tools`, `url`, `json`, `oauth*`, `relay`, `relay-target`, `cli-api` (the `mcpServers` block).
  - `mcp/` — the MCP server, at `/` and `/mcp`. `channels/` — bus events into `notifications/claude/channel`; `mcp` imports `channels`, never the reverse. `gateway/` — `/gateway` and the Model API. `monitor/` — the tail transport.
  - `claude/` (`api`, `files`, `settings`, `login`), `terminal/` (`api`, `tickets`, `socket`), `files/` (`attach-serve`, `attach-grant`, `attach-owner`, `upload-api`, `upload-store`), `net/` (`tunnel`), `server/` (`control`, `machine`, `update`).
  - **The law, checked by madge**: a domain imports `core`, `http` and other domains only at named seams (`agents/scope`, `stations/registry`, `stations/train-call`, `files/attach-serve`); no domain imports `boot/` or `routes/`; `agents/` and `stations/` never import `mcp/` (deps are injected from `boot.ts`). There is no `db/` any more: the four Postgres files went to `apps/api`, the fifteen on-disk agent-state files to `agents/` and `connectors/`.
  - **There is no `METRO_MODE` and no hosted branch.** Every daemon is local; `isLocalMode()`, `stationRunsHere`, the optional vault/servers APIs and `test/local-runtime-imports.test.ts` all went with the split.
- `apps/ui` — the control panel (Vite + react-native-web + `@stage-labs/kit`).

The Model page is the way to Bedrock now. `claude-settings.ts` (`settingsConflicts`) and `provider-flags.ts` stayed because `metro claude` uses them.

The port is `--port`, else `METRO_WEBHOOK_PORT`, else 8420. **`metro serve` hands the daemon its own path as `METRO_CLI_BIN` and respawns the daemon whenever it exits with code 75** (`RESTART_CODE`, `spawnPlan` takes a plan FACTORY so `METRO_VERSION` is re-read from the package on disk): that is how the page's Update button works, see `/api/update`. `metro update --check` prints `{current, latest, newer}` and installs nothing. Foreground only; the daemon itself prints the metro.box connect link. **Funnel is not optional: `metro serve` ALWAYS sets `METRO_TUNNEL=tailscale` plus `METRO_TAILSCALE_BIN`** (Less, 2026-09-05: "We always need tailscale tunnel anyway"; `findTailscale`: `tailscale` on PATH, else the macOS app's `/Applications/Tailscale.app/Contents/MacOS/Tailscale`, then `tailscale status --json` must say `BackendState: Running` with `Self.Online` not `false` (a machine removed from the tailnet keeps saying Running while its rename and its funnel go nowhere, seen on Suzy 2026-09-09), or the error says how to install and `tailscale up`; `--tunnel` in any spelling is refused with "--tunnel is gone"), and the DAEMON does the rest — see the tunnel bullet under Deploy & Ops. `--owner` is needed on the first start of a box only; `.owner` remembers it. **The machine's name on the tailnet is generated by metro** (Less, 2026-09-05: "Can we have some autogenerated address?"): `src/node-name.ts` keeps `metro-<6 chars>` in `<agents dir>/.node` and, when `tailscale status --json`'s `Self.DNSName` does not start with it, runs `tailscale set --hostname <name>` once (a refusal prints the command to run by hand) and then waits up to 30s (`METRO_NODE_RENAME_WAIT_MS`) for `tailscale status` to report the new name before the daemon starts, else warns and goes on (beta.80; Suzy, 2026-09-09: the daemon started at once, its funnel came up announcing the old `ip-172-31-25-236` name, and neither name ever resolved in public DNS), so the Funnel address is `https://metro-xxxxxx.<tailnet>.ts.net`, named after neither the agent nor the box. **A `.node` written before the first start is kept** (beta.100): `NAME_RE` accepts `metro-` plus 1 to 40 lowercase letters, digits and dashes, which is how the page's AWS launcher knows a box's address before it exists; a held name outside that shape is replaced by a generated one. `test/serve.test.ts` pins the arguments and the environment.
  - **Stop, Start and Restart from the page** (Less, 2026-09-06: "start a server serve command from the UI, and stop it"; beta.67). The daemon exits **76** (`HOLD_EXIT` in `boot.ts`) on `POST /api/stop` and 75 on `POST /api/restart` (`server/control.ts`, owner-signed, 400 when `METRO_CLI_BIN` is unset because nothing would bring the daemon back); `spawnPlan` (`runtime.ts`) treats 76 as **park**: `holdUntilStart` (`src/hold.ts`) writes the serve lock with the PARENT pid, binds a stub on the daemon's own host:port, runs its own foreground `tailscale funnel <port>` (restarted 2s after an exit; the daemon's funnel died with the daemon, and without one the public address would go dark, which is the whole point) and prints `metro is stopped. Holding …`. The stub answers `GET /api/mode` with the usual fields plus `stopped: true`, `POST /api/start` (200 `{starting: true}`, UNAUTHENTICATED by construction: the CLI carries no crypto library, and starting is what the supervisor does after a crash anyway; the daemon is closed by construction), `/health` 503, and everything else 503 `{error, stopped: true}`, all with the daemon's CORS headers. On start it kills its funnel with SIGINT and WAITS for it to exit, closes the stub, removes the lock (else the child's `acquireLock` would see a live metro pid and exit 0) and respawns through the plan factory; SIGINT/SIGTERM (Ctrl-C, `metro stop`, which reads that lock) end `metro serve` with 0. **A parent older than beta.67 does not know 76**: the first Stop after updating from ≤beta.66 exits `metro serve` entirely, a hand restart. `test/hold.test.ts` runs the stub, the lock and a fake `tailscale` over real HTTP; `test/runtime.test.ts` pins the loop.

It refuses while a `metro serve` holds the lock and runs the same preflight as serve (owner, bun, tailscale). **On a box that already has the unit it prints `already installed` and touches nothing** (beta.78; before that it printed the lock refusal, because the service's own `metro serve` holds the lock, seen on Lisa 2026-09-09), and `metro stop` on such a box adds that the service restarts the daemon in a moment, naming `systemctl stop metro` (or `launchctl bootout gui/<uid>/box.metro.serve`) as the way to keep it stopped (`serviceStopHint`). `uninstall` and `status` are the other verbs. This is what makes Stop/Start from the page complete: the parent survives reboots, and a shell is needed for the install only. Anything but Linux and macOS is refused by name. `test/service.test.ts` pins the files and the commands against fake deps.
  - **The npm package ships NO vendor SDK, and the daemon runs from a per-user runtime store** (`src/runtime-install.ts`). `packages/cli/package.json` has no `dependencies` at all; `scripts/stage-runtime.mjs` copies metro's own sources into `runtime/node_modules/@metro-labs/*` and writes `runtime/stations.json`, a manifest of `core` (the daemon's vendor deps minus `drizzle-kit`/`drizzle-orm`/`postgres`) and one dependency map per station, read from the workspace `package.json`s. `prepareRuntime()` runs before EVERY spawn (the plan factory, so a `metro update` respawn re-syncs): it copies the staged `@metro-labs/*` (the daemon, `core`, `http` and the six stations) into `~/.metro/runtime/node_modules/@metro-labs` when `runtime.json` changed, writes `~/.metro/runtime/package.json` with the core plus the SDKs of the channels found in `~/.metro/agents/*/agent.json` (`localStations`), and runs `bun install --no-summary --no-progress` there ONLY when that file differs from the last installed one (the `node_modules/.metro-installed` marker; a failed install leaves no marker, so the next serve retries). The daemon then runs **`<store>/server.ts`, a one-line shim staged by `stage-runtime.mjs`** (`import './node_modules/@metro-labs/daemon/src/server.ts'`, copied into the store on every sync; `daemonEntry` in `runtime.ts` falls back to the package path for a dir with no shim) with `METRO_TRAINS_DIR=<store>/trains`, `METRO_RUNTIME_STORE` and `METRO_RUNTIME_MANIFEST`; a `sources` dir with no `stations.json` (a from-source `METRO_RUNTIME_DIR`) runs in place with neither. `METRO_RUNTIME_STORE` overrides `~/.metro/runtime`. `@xmtp/node-bindings` alone is 263 MB unpacked (seven platform binaries in one tarball), which is why an agent without XMTP must never download it. **A channel attached AFTER boot installs its SDK on the daemon side**: `stations/runtime-deps.ts` `ensureStationDeps(station)` (a no-op without both env vars, so from-source and Docker never touch it) runs the same compare-and-`bun install` for the known accounts plus the new station, and is called at the top of `prepareAccount`, before an interactive attach's driver import (`attach-session.ts`) and before `syncStations` reloads a train (the Restore path). The two installers write byte-identical `package.json`s, so neither ever undoes the other's work. `apps/daemon/test/runtime-deps.test.ts` and `packages/cli/test/runtime-install.test.ts` drive both against a fake `bun` on PATH; `packages/cli/test/runtime-deps.test.ts` pins the manifest against the workspace. **The `beta.52` → `beta.53` step is the one update that needs a hand restart**: the old serve loop respawns its own plan, which expects the SDKs inside the npm package that `beta.53` no longer carries. **Since beta.78 the path a running `metro serve` spawns is the shim, so moving or renaming the daemon package changes one staged line and never strands a box again** (beta.77 did exactly that: the old parent respawned `@metro-labs/mcp/src/server.ts`, which the new store no longer held, and both boxes went dark until a hand `metro serve`). `bun run smoke` (`scripts/smoke.sh`) codifies the three hand checks a layout change needs: boot from a fresh runtime store, boot `apps/api` alone without a database, and reproduce the Dockerfile's filtered install and boot from it.
  - **`metro tail <agent-id>` follows the LOCAL daemon's `/api/tail` and prints one JSON event per line** (`src/tail.ts`). It exists as the Monitor-tool ingress for Claude Code — `Monitor({command: 'metro tail <id>', persistent: true})` delivers events into a session that is ALREADY running, which the experimental Channels flag cannot — and it is loopback-only by construction (`localUrl()`). The key comes from `METRO_AGENT_KEY`, else the agent file (a refused `METRO_AGENT_KEY` is terminal, never retried; a refused file key is re-read once). Reconnects with 1s/2s/5s backoff (reset after a healthy stream), treats 90s of silence as a dead socket (the tail keepalive comes every 25s), and stdout carries ONLY event JSON — every status line goes to stderr, because Monitor treats each stdout line as an event.

## The Claude Code plugin (`plugin/`, repo-as-marketplace)

**The plugin ships inside the npm package and the daemon installs it** (Less, 2026-09-10: "Can the plugin be part of the NPM package maybe? So we dont deal with bonustrack/metro or custom update all the time?"). `stage-runtime.mjs` copies `plugin/` and the root `.claude-plugin/marketplace.json` into `runtime/marketplace/` and **stamps the staged `plugin.json` version with the CLI's own version**, so every publish is a new plugin version and `claude plugin update` always has something to move to (the "version did not move" bug class is gone by construction); `prepareRuntime` copies `marketplace/` into the store with the sources. At boot, after `markDaemonReady`, `claude/plugin-install.ts` `ensureMetroPlugin` finds `claude` (`PATH`, else `~/.local/bin/claude`, the native installer's home; none means `skipped`, nothing touched), reads `claude plugin marketplace list --json`, **replaces a `metro` marketplace that is not the store's path** (the GitHub one every box had: `remove` then `add <store>/marketplace`, which lists as `source: directory`), then `claude plugin install metro@metro -y --scope user` when absent or `marketplace update` + `plugin update -y` when `claude plugin list --json` reports another version, and `syncPluginServers()` runs after so the fresh install's `.mcp.json` is filled at once. Every `claude` call is logged, a refusal is a `failed` outcome with the reason, never a throw, and a from-source run (no `METRO_RUNTIME_STORE`) skips it. **So `metro update` and the page's Update button carry the plugin**, and after either the running session needs `/reload-plugins --force`. The repo still doubles as a marketplace (root `.claude-plugin/marketplace.json` lists `./plugin`) for anyone installing by hand, but no box needs `bonustrack/metro` any more. **`plugin/` is NOT a workspace package** — it ships committed plain-Node `.mjs` (no build, no deps) because a plugin install is a snapshot. `test/plugin-install.test.ts` drives the whole ladder against a scripted `claude`.

- **`plugin/.claude-plugin/plugin.json`'s `version` MUST move with any change under `plugin/`.** Claude Code installs a plugin into `<claude dir>/plugins/cache/<marketplace>/<plugin>/<version>/` and `claude plugin update` compares version numbers, so code that changes under an unchanged version NEVER reaches a machine that already installed it: `claude plugin update` answers `already at the latest version` and the stale copy keeps running. That happened: the version said `0.2.0` from 2026-09-03 while the code changed five times after it, including the commit that retired the hosted paths, so Tony's cached helper still printed a hosted-era `metro login` JWT on 2026-09-10 and the daemon's relay refused all twelve connectors with a silent 401 (`identify` answers 401 without logging, which is why the journal showed nothing). A machine stuck that way needs `claude plugin uninstall metro@metro` then `install`, since an update alone will not move it.
- **The plugin is a client of the LOCAL daemon, like the CLI.** `bin/metro-plugin.mjs` reads `~/.metro/agents/*/agent.json` (`METRO_AGENTS_DIR`; `METRO_AGENT` picks one by name or id when several), calls `http://127.0.0.1:<METRO_WEBHOOK_PORT or 8420>/api/cli/mcp` with the agent key, and `/metro:refresh` rewrites the plugin's `.mcp.json`. There is no `/metro:login` and no credentials file any more.
- **A rewritten `.mcp.json` needs `/reload-plugins --force`, not a plain `/reload-plugins`.** Measured on Tony, 2026-09-10, on Claude Code 2.1.261: with the daemon writing every copy correctly, a plain reload reported the plugin reloaded and `/mcp` kept the OLD servers through a rename and a delete, while `--force` picked both up at once, in the running session. So a plain reload reuses a cached manifest and `--force` re-reads the plugin from disk. Two earlier notes here were wrong in opposite directions: one said a plain reload was enough, the next said only a restart was. A restart works too, and is not needed. This is why the skill ends by telling the user to run `/reload-plugins`, and why the committed `.mcp.json` placeholder is `{}`.
- **The generated `.mcp.json` carries NO credential**: entries are `{type, url: <local relay>, headersHelper: node "${CLAUDE_PLUGIN_ROOT}/bin/metro-plugin.mjs" headers}` — the helper prints `Bearer <agent key>` fresh from the agent file on every connect. With no agent on the machine it prints `{}` and the relay answers 401.
- **The `metro.box ` name prefix is STRIPPED inside the plugin** (`serverEntries`): plugin servers are already namespaced (`plugin:metro:<name>`), so the prefix would only mangle tool names. The raw `metro mcp` export keeps it.
- A plugin UPDATE overwrites the install dir, resetting `.mcp.json` to `{}` — `/metro:refresh` regenerates it.

## Commands / the gate

- `bun install`. CI and Docker use `--frozen-lockfile`; always commit `bun.lock` or CI/deploy breaks.
- Local run: `bun apps/daemon/src/server.ts`. Prod runs TS from source — `dist/` is built by the gate only, never used at runtime.
- **The gate, all of it, before any PR:** `bun run build && bun run typecheck && bun run lint && bun run knip && bun run madge && bun run test`. Must be green.
- Tests set `DYLD_FALLBACK_LIBRARY_PATH=/usr/lib` (prebuilt `@xmtp/node-bindings` links a nix libiconv; without it the gate is red on darwin only) and `METRO_STATE_DIR="$(mktemp -d …)"`. Run the whole suite; don't assert an exact test count.
- **Tests that boot the HTTP server pick a port in 10000–29999, BELOW Linux's ephemeral range (32768–60999).** They used 20000–39999, and the CI runner's own outbound sockets landed on the chosen port often enough to fail `attach-serve` on a docs-only commit. `webhookPort()` reads `Number(env) || 8420`, so port 0 cannot be requested through the env; keep the range, do not "simplify" it to 0.
- turbo's `test` `dependsOn ["^build"]`, so a core edit invalidates the station packages' cached results.
- **Train stubs live in `trainsDir()` (`boot/paths.ts`): `METRO_TRAINS_DIR`, else `apps/daemon/trains` beside the source (gitignored, and lint-ignored in `stage.config.js`). NOT `~/.metro/trains`.** A stub is a bare `import '@metro-labs/<station>/train'`, which only resolves under a tree that holds the workspace `node_modules` — the repo, or the CLI's runtime dir, which sets the env explicitly — so the old home-dir default made every train of a from-source run die with `Cannot find module`. Fly's `METRO_TRAINS_DIR=/app/apps/daemon/trains` is now simply the default spelled out. It is read lazily so a test can point it at a temp dir in `beforeEach`, and every test that materializes MUST, or it writes stubs into the checkout. `materializeFrom` also prunes at FIRST boot, not only on reload: the supervisor spawns every `*.ts` in that dir, so a stub left by an older configuration crash-looped until the first reload happened to run `pruneStations`.

## Conventions (strict `@stage-labs/config` — HARD constraints)

- **No comments in source. None.**
- No escape hatches: no `eslint-disable`, `@ts-ignore`/`@ts-expect-error`, or `any` casts to dodge types.
- **`no-floating-promises` with `ignoreVoid: false`** (tightened in `stage.config.js`). `void p` is a lint error — it was the sanctioned suppression that let the v157 crash pass lint. Every promise is `await`ed or ends in a `.catch()` that LOGS.
- `max-lines` per file and function-length caps. Split files instead of suppressing.
- Strict tsconfig, ESM. Import specifiers carry explicit `.js` extensions.
- Throw real errors; surface via `errMsg` and `TrainError`. Don't swallow.
- Log via the shared `log`, not `console`.
- Core imports go through the exports map (`@metro-labs/core/log`, `/events`, `/lines`, `/stations/types`, …). Station packages: `.` → `src/station.ts`, `./train` → `src/index.ts`.

## Architecture

### Bus and stations

- **In-process bus** (`packages/core/src/events.ts`): a bus, not a journal. Bounded in-memory ring (`BUS_BUFFER_MAX = 500`) keyed by monotonic `busSeq`; `channels/relay.ts` tracks the highest contiguously-delivered seq and replays missed events on rebind. **Do NOT add an on-disk journal or history.**
- **Static seam:** stations are wired through `stations/registry.ts`; core dispatches generically over station defs. No per-network branching in core.
- **Tolerated package cycle** between core and station packages. Intentional — do NOT "fix" it; madge is configured around it.
- **`Station` carries TWO independent booleans: `hasAccounts` and `hasTrain`.** They were once conflated (`hasAccounts: false` meant "no subprocess"); webhook is the one station where they differ (`true`/`false`). `hasTrain` decides the subprocess:
  - `materialize.ts`'s `STATION_TARGETS.webhook.trainImport` is `null`, so `writeStations` writes the account file but no stub, and `pruneStations` blanks the file without `rmSync`ing a stub that never existed.
  - `boot.ts`'s `syncStations` returns before touching the supervisor.
  - `mcp/accounts.ts` reads webhook's accounts in-core (`inCoreAccounts`) instead of calling an absent train — which is also why webhook can never appear in `unavailable`.
  - The Monitor's `/api/call/:train/:action` is a flat 400 for it; `list_members` refuses on `!hasAccounts || !hasTrain`.
- telegram and whatsapp trains spawn only when an account of that station exists.
- **The LINE station was removed.** No `line` package, no `line` in `STATIONS` — a leftover `line` row in `accounts` crashes `materialize.ts` at boot. Drop those rows before deploying.

### Sessions, identity and scope

- **`agents.key` is the ONLY credential.** No env bearer, no unscoped principal anywhere. Since `0009` an agent has at most one key and a key belongs to at most one agent (`agents.key` nullable text UNIQUE), which is what makes a bare `?token=<key>` unambiguous with no agent selector.
- `agents/keys.ts` keeps ONE index: SHA-256(key) → agent id, no plaintext. `authenticate()` order: key map → session JWT. Neither is a 401 — **a daemon with nothing configured is CLOSED, not open.**
- `allowedAgents()` is the single place turning an identity into a `Set<number>`; it never returns `undefined`. Use it, don't re-derive.
- **Scoping is by `agents.id` (an opaque 11-char string), never by name.** `agents.name` has no uniqueness since `0007`, so a name comparison in an auth path is a cross-owner leak and will NOT be a type error. Do not reintroduce a name-keyed grant.
- **Key reset** (`POST /api/agents/<id>/key` → `resetAgentKeyForUser`) is a hard cutover with no overlap window: `UPDATE … WHERE id = … AND owner_id = …` (0 rows → 404, retried on `23505`), then `rotateAgentKey` = unregister + register in ONE synchronous call, so the map never holds two live keys or none. Order is load-bearing: row commits → map swaps → new key goes out. `registerKey` alone is NOT a rotation — it adds a hash without evicting the old one, which `test/key-map.test.ts` pins. Registration is skipped on a `METRO_AGENT`-pinned daemon that doesn't serve the agent; **eviction is unconditional.** `boot.ts` composes the reset with `closeAgentSession(id)`, since an attached SSE stream never re-authenticates.
- **Per-identity MCP sessions** (`mcp/session.ts`). `McpSession` owns everything that was once a module-level singleton: its own `mcp.Server`, transport, `_GET_stream` sink, `ChannelOwner`, `BoundedEventStore`, `InboundRelay`, `ChannelRelay` and bus subscription.
  - `mcp/session-registry.ts` holds two indexes filled together (session id → session, scope key → session) so a lookup by either cannot drift.
  - The scope key (`sessionScopeKey`) is the SORTED agent id set, not the identity: an `agents.key` and a browser session over the same agent are the SAME session.
  - At most one live session per scope key. A second `initialize` from the same identity supersedes; a second identity does not touch it.
  - `rebindDecision` is GONE. `routeSession` returns `use` for an id the caller owns, a flat 404 for one somebody else owns, `create` with `adoptId` only for an id nobody owns. `initialize` never adopts.
  - Lifetime: idle streamless sessions reaped after `SESSION_IDLE_MS` (10min) by a 60s unref'd sweeper; `MAX_SESSIONS` 64, evicting the LRU **streamless** session and refusing with 503 rather than dropping a live one.
  - `ReplayLedger`s live in a registry LRU keyed by scope key, so a message that arrived while an agent was disconnected survives reconnect AND full re-initialize.
  - `InboundRelay` state (`knownLine`, `allowedLines`, `seenEvents`, `pendingPermissions`) is per session, so one agent's chat reply cannot answer another's approval prompt. The dedupe key still strips the account segment (that is what collapses one agent's two accounts in one conversation) but is prefixed by the owning agent id.
  - Do NOT re-collapse any of this into a singleton. `test/session-concurrency.test.ts` drives two agents over real HTTP and fails first if you do.
- **Adoption is silent, so an adopted session must be told the tool schema may have moved.** Armed by a schema SIGNATURE, not the adoption flag: `toolSchemaSignature()` is a memoized hash of `toolList()`, `issuedSchema` is the signature the session was issued (`undefined` when adopted), and `schemaNoticeDue` is `issuedSchema !== toolSchemaSignature()`.
  - **Arming is not delivering.** The notice rides whichever egress the client is actually reading: `announceToolSchema` on a GET bind (guarded by `streamAttached`), or `extra.sendNotification` from inside the `tools/call` handler, which the SDK routes onto that request's own response stream. `tools/list` settles it silently (`markCurrent`) — notifying there is a refetch loop. `issuedSchema` updates only once the send RESOLVES; an `announcing` latch stops two concurrent calls both sending. Pinned in `test/schema-notice-without-stream.test.ts` and `test/mcp-session-restart.test.ts`.
  - **The ceiling: the daemon cannot reach a client that is neither streaming nor calling.** The SDK client opens its GET stream once, retrying twice at 1s and 1.5s; any deploy outage exceeds that and the stream is gone for the life of that client process. Such a client keeps making tool calls and receives no inbound chat at all. Only a `/mcp` reconnect or client restart fixes it. **Tell the user to reconnect after every deploy.**

### One scope predicate, every egress (`agents/scope.ts`)

- `lineTargetDenied` resolves `args.line` → agent id and denies anything outside the scope set, including an `args.account` override that would re-route to another agent's account (stations resolve `account ?? line`, which is the hole a line-only check leaves). `mcp/index.ts`'s `scopeDenied` and the Monitor's call gate are that one function.
- `stationFullyScoped` covers a call naming no line (`accounts`): allowed only when every account of that station is in scope.
- **`eventInScope` is the delivery filter for EVERY inbound egress and FAILS CLOSED.** An account-station line (the `STATIONS` list in `apps/api/src/db/schema.ts`) whose account maps to no agent goes NOWHERE. An unparsable line reaches nobody.
  - The remaining carve-out is by STATION, not by lookup failure: a line on a station with no accounts at all (local `metro://claude/…`) still reaches every authenticated tail. **Do NOT remove it wholesale** — `metro://claude/…` depends on it.
  - `webhook` is IN `STATIONS`, so an endpoint reaches its owning agent and nobody else.
- **Four egresses, one case table** (`test/egress-scope-matrix.test.ts`): channel live, channel bus replay, SSE resumption, monitor tail. **Add a new egress to that table or it will leak.**
- **SSE resumption is a separate egress.** `serveStandaloneGet` replays `BoundedEventStore` before the sink is bound and without consulting `ChannelRelay`, so gating the relay alone left a real leak with no log line at all. `storeEvent` records the frame's `meta.line` and the `ChannelOwner` scope in force; `replayEventsAfter` takes the reconnecting scope as a REQUIRED option and re-checks every frame through `mcp/frame-scope.ts` → the same `eventInScope`. `scope: undefined` replays NOTHING. Withholding does not consume the frame — the store is a buffer, not a queue. Both gates are kept and are redundant by construction; **do not remove either** on the grounds that isolation makes it unreachable.
- The Channel applies scope through `ChannelOwner` (`mcp/channel-owner.ts`), which records the identity that authenticated the currently-attached GET stream — that stream is the wire, so it decides scope. An out-of-scope event is WITHHELD, not dropped, so the ring buffer replays it to its real owner. With no stream attached nothing is deliverable, which keeps events alive rather than writing them into a transport with no reader.
- `streamBelongsTo` is the last-line guard on a stream takeover (409); unreachable while routing is correct, which is why it stays.
- `permission-relay.ts` re-checks `owner.inScope(relay.knownLine)` before pushing an approval prompt, because a prompt is Claude's tool name and input preview.

### Never fatal

- **Nothing in the relay path may kill the daemon** (the v157 outage: one unwritable `mcp.notification()` took every station down). A notification failing because a client vanished is normal.
- Pinned by `test/never-fatal-notify.test.ts` (against a real closed SDK `Server`) and `test/crash-guard.test.ts` (through real subprocesses, the only honest way). Three layers, all kept: the `flushPendingFallback` timer `.catch()`es and logs; `ChannelRelay.enqueue` terminates its chain with a `.catch()` so one failure cannot poison the chain; `boot/crash-guard.ts` installs `unhandledRejection` + `uncaughtException` as the FIRST statement in `boot.ts`.
- The guard is asymmetric on one flag: before `markDaemonReady()` a crash exits 1 (a daemon with no HTTP server should crash-loop visibly); after ready it logs at `error` with a per-kind counter and keeps relaying. `/health` is the independent backstop for a genuinely wedged process.
- The fatal path does NOT go through pino — `logFatalSync()` writes one pino-shaped line with `writeSync(2, …)`, because `pino.destination(2)` is async and `process.exit` truncates it (`flushSync()` does not fix it).
- Keepalive `res.write`s in `raw-get-stream.ts` and `monitor/api.ts` are the same class in sync form: guarded, and they close the stream.

### Attachments

- **Inbound:** a station emits `attachmentSaved` when bytes land and `attachmentFailed` (same correlation fields plus `reason`) when they cannot. Both go through ONE correlator (`InboundRelay.mediaCtxFor`), so a failure consumes the pending slot exactly like a success and clears the 15s fallback timer. That timer is right for a download that never returned and wrong for one refused outright. Failure notes advertise no `url` and no `local_path` — there is no file. Only whatsapp emits `attachmentFailed` today; the rest still fall through to the timeout.
- `saveStreamToCache` streams to a `.part` with a running `assertAttachmentSize` counter and `rename`s on completion, so RSS stays flat and a refused save leaves neither a half file nor an orphan.
- **Serving** (`files/attach-serve.ts` + `attach-owner.ts` + `attach-grant.ts`) is scoped by the OWNING agent, not a shared secret. Minting a url writes two 0600 sidecars beside the cached file: `.owner` (agent id) and `.grant` (`{token, agentId, mintedAt}`, `at_<43 base64url>`, 32 CSPRNG bytes). The `?token=` is that per-attachment token, never the agent's key. Minting is idempotent for the same owner, so re-emitting an event does not break a delivered link.
  - `/attach` takes two paths, both re-checking `.owner` first: the presented token matches that attachment's own grant (`timingSafeEqual`, and the grant's `agentId` must equal the recorded owner), OR the caller authenticates as an identity whose scope contains the owner. Everything else is a flat 401.
  - The ONE 404 is a name that is not cache-shaped (`CACHE_NAME_RE`), decided before `authorized()` — it depends only on the request string. A cache-shaped name stays 401 whether or not it exists: cache names derive from public ids (a discord-bot snowflake), so a distinguishable "gone" would be an existence oracle. **Do not "improve" that 401 into a 404.**
  - Fails closed: no `.grant` means no token can match. Sidecars are unservable by construction (`CACHE_NAME_RE` cannot match two dots).
- **Outbound sources** (`stations/attach-resolve.ts`, `attach-inline.ts`): exactly ONE of `upload`, `data`, `url`, `path`. Two is an error and so is none — the old filter that swallowed a source-less entry is gone, because dropping it and answering `sent: text` is the #134 dishonesty. Each resolved attachment logs `send: attachment source` with its kind (`upload`/`data`/`url`/`path`, beta.78): the evidence for whether `data` and `path` are used before either is cut.
  - `path` resolves on the DAEMON host; `url` must be publicly reachable; `data` transits the model's output. `upload` is the only one fit for a real file.
  - **`data` is for TINY files.** `MAX_INLINE_BYTES` is 8 MiB decoded, per attachment and per send — derived so the limit-naming error fires before `MCP_BODY_MAX` (32 MiB) answers a bare 413. Don't raise one without the other. But the binding limit is the model, not the daemon: the practical ceiling is roughly **10 KB**, three orders of magnitude below the cap.
  - base64 is validated strictly (alphabet, whole quanta, decoded-length equality) because `Buffer.from(x, 'base64')` silently drops junk. `splitInlineData` strips a `data:<mime>;base64,` prefix and adopts that mime when `mime` is omitted; a `data:` url without `;base64` is refused.
  - Inline bytes land in a per-attachment `mkdtemp` (0700) under `os.tmpdir()`, **never `attachDir()`** — that cache is durable and is the only thing `/attach` serves. `cleanupAttachments` runs in a `finally` on success, station error and under-report alike. Stations only ever see a local file, so no base64 crosses the train stdin pipe — `drainLines` would drop a call line over `STDOUT_LINE_MAX` (4 MiB) in silence.
- **The upload endpoint** (`files/upload-store.ts` + `upload-api.ts` + `mcp/upload-tool.ts`). Bytes go over HTTP from the caller's disk to the daemon, never through an MCP message. **One step needs a SHELL and there is no way around it** — an MCP tool call is model output by construction. `create_upload` mints the slot and returns a ready-to-run command; pushing bytes is `curl`. An orchestrator-only main loop should delegate the one command and keep the `upload_id`; the slot belongs to the metro AGENT, not whoever ran it.
  - Two ways in: `POST /api/uploads?name=&mime=` with the raw body, authenticated by the agent's key (owner is the single agent in scope, or `?agent=<id>`); or `create_upload` → `PUT /api/uploads/<id>?token=<ut_…>`, where the ticket is the only credential on the wire. `DELETE` drops a confidential file early.
  - **The advertised PUT url must name the daemon that minted the slot.** Slots live in the minting daemon's `uploadDir()` (per-machine tmp, never `/data`), so `publicBaseOrDefault()` resolves `METRO_PUBLIC_URL`/tunnel first, then its own `http://127.0.0.1:<webhookPort()>`. Every daemon is local, so the old hosted fallback to `https://api.metro.box` is gone: a slot always lives on the daemon that minted it. **Inbound takes the same branch:** `attachmentUrl` falls back to the loopback base too, so inbound media notes always advertise a working `/attach` url.
  - Ownership reuses #130's primitives, not a copy. Same two paths as `/attach`, failing closed the same way, but everything else is a flat **404** — an upload id is an unguessable capability, so "exists but not yours" would be an oracle. At `send` time `fromUpload` re-checks the owner against `allowed`, passed IN as a parameter (`stations/` must not import `mcp/`); `allowed === undefined` resolves NOTHING.
  - **Transient by construction:** `uploadDir()` (0700), never `attachDir()`. `UPLOAD_TTL_MS` 30 min, expiry read from `.meta` on EVERY lookup, `startUploadReaper()` sweeping every 60s with one sweep at start. `UPLOAD_ID_RE` (`up_` + 22 base64url) is the traversal guard and makes sidecars unaddressable. A send does NOT consume the upload — a timed-out `send` has usually succeeded, so a retry must work.
  - **64 MiB per file, 512 MiB daemon-wide live budget.** Under `MAX_ATTACHMENT_BYTES` (100 MiB) so the naming error fires first, and above the largest station ceiling (Telegram's 50 MB) so metro never refuses a file a station would carry. Over-size is refused from `content-length` before a byte is written; a chunked body is caught by the running counter, which **DRAINS rather than throws** — throwing there destroys the socket in Bun's `node:http` and the client hangs forever. Drain capped at `DRAIN_MAX` = 2x. Do not "simplify" it back into a throw.
  - `streamToSlot` owns removing the `.part` on failure, not its callers: the `wx` open makes an orphan permanent, wedging that slot at 409 for the full TTL.
- **Outbound reporting is derived, never asserted** (#134). `handleSend` compares what came back against `atts.length` through ONE predicate, `assertDelivered`, applied to both the forwarded and native paths. **Fewer labels than attachments is an error, never a success.** Each station's label list must be built INSIDE the loop that pushes, appended only after the push resolves, and derived from the branch that chose the verb — never `map`ped over the input array, which is what let telegram report full success for a partial send. `test/send-attachment-honesty.test.ts` crosses drop/partial/complete against every station's line; add a station to it and to the package's own send-loop test.

### Human-in-the-loop

A pending MCP `permission_request` is relayed to chat as `yes <request_id>` / `no <request_id>`; `inbound.ts` matches with `PERMISSION_REPLY_RE = /^\s*(y|yes|n|no)\s+([a-km-z]{5})\s*$/i`. The 5-char format is a contract with the relayed prompt — never change one side only.

Built 2026-09-07 after Tony answered "Not addressed to me" to a Discord reply to its own message (the `mentionsBot` flag the agent's rule named had never existed in metro; nothing about DMs, mentions or reply targets reached the model). **Core decides, stations only report facts they get for free** (`channels/addressed.ts` `addressedBy`, `replyMeta`; wire fields `is_private`, `mentions_self`, `reply_to_self` on `TrainEvent`, mapped to `isPrivate`/`mentionsSelf`/`replyToSelf` on `MetroEvent` only when literally true). ### Connectors (`connectors/store.ts`, `daemon/connector-*.ts`)

A connector is a **verified bookmark for a remote MCP server** kept on the daemon, plus the paste-ready `mcpServers` block. The daemon stores it (`<agents dir>/connectors.json`, `{id, name, url, transport, config}`, 0600), proves it answers, and **RELAYS its MCP traffic through `/relay/<connector-id>`**: the vendor credential is injected per request and never reaches Claude Code's config, the browser, or metro.box. The relay holds no MCP session of its own (pure passthrough), gives connectors no MCP tool and puts nothing on the bus.

- **The relay** (`connectors/relay.ts`, `RelayApiDeps.identify` = `keyIdentity` in `local-cli-api.ts`: bearer or `?token=` → `agentIdForKey`): `POST`/`GET`/`DELETE /relay/<id>`, mounted in `handlePreMcpRoutes` (outside `/api/*`). Anything but the agent key is 401; an unknown connector id is a flat 404. **The caller's key is stripped before anything goes upstream**; only `accept`, `content-type`, `mcp-session-id`, `mcp-protocol-version`, `last-event-id` pass through, plus the injected credential (stored header, or `Bearer <accessToken>` refreshed single-flight by `localRelayTarget` and persisted to the file). **Status discipline: the daemon's 401 means only the daemon's credential.** An upstream 401/403 triggers ONE forced refresh and ONE retry; still refused → **424** `{error, reconnect}`. A row with no stored credential forwards BARE (lazy-auth servers are real). **The OAuth degradation ladder ends BARE, not refused.** Upstream 3xx is refused (502). POST bodies buffered (8 MiB), responses piped with drain backpressure, SSE keepalive comments (`METRO_RELAY_KEEPALIVE_MS`, 25s); client disconnect aborts upstream via `res` 'close' AND `res.socket` 'close', both guarded by `!res.writableEnded` — never `req` 'close'.
- **A connector on the daemon is held by every agent, full stop** (2026-09-07, QW-3): the per-agent hold list is GONE with its routes (`/api/agents/<id>/connectors`), `localHoldEverywhere` and the picker; `connector_ids` on `GET /api/agents` is every connector, the bundle ships every connector, the relay serves any connector id to any agent key, and the agent file's `connectors` key is read tolerantly (bad entries dropped, never fatal) and no longer written: an on-disk key kept only so old files still parse. **A connector name is unique on the daemon** (409 at create and rename), because it is the `mcpServers` key.
- **A row normally requires a real MCP `initialize` — with ONE deliberate exception**: a server that demands OAuth is stored UNVERIFIED (`auth: none`, `oauth: true`) so it exists whether or not you finish signing in. **`parseConnectorUrl` is a security boundary**: on a local daemon `allowLocalConnectors(true)` relaxes it (http, loopback and private hosts are the point there); every frame is `redirect: 'manual'` and a 3xx is refused. Raw `fetch`, never the SDK `Client`. **No stdio, ever.**
- **A remote 401 is the daemon's 400, never its 401** (`ConnectorVerifyError` is always 400): 401 is reserved for a missing or invalid session, which `apps/ui/src/api/client.ts` turns into a sign-out. On re-verify it is `200 {ok:false, reason}`.
- **A connector name is a LABEL, not a slug** — anything except control characters, trimmed, 1–64 chars. **A stored url keeps the shape it was given** (`connectorUrlText`); the OAuth `resource` uses the NORMALISED `url.toString()`.
- **No API returns a connector credential to a browser**: `connectorPayload` carries no `secret`, `bearer`, `expiresAt` or `json`. The `mcpServers` block comes from `GET /api/cli/mcp` with the AGENT KEY (`handleLocalCliRequest`, mounted in `session-apis.ts`), and it names only the daemon's relay urls with `Bearer <key>`.
- **Tools group into read-only and write** (`connector-tools.ts`): `classifyTool` is `read` only on `readOnlyHint: true`, silence means write. **A stored catalog is read with `readStoredTools`, NEVER `toToolList`.** `tools/list` is PAGINATED (10 pages max). The probe asks for `2025-11-25` and falls back to `2025-06-18`, retrying ONLY on `ConnectorNotMcp`.
- **OAuth connect flow** (`oauth-discovery.ts`, `oauth-client.ts`, `oauth-pending.ts`, `connector-oauth.ts`): RFC 9728 then RFC 8414 discovery, path-aware `.well-known` forms first; DCR only (a server with no `registration_endpoint`, like Google, shows Connect and refuses on Connect); PKCE S256; `GET /api/connectors/callback` is the one unauthenticated route on this surface, keyed by the single-use `state` in an in-memory map; the callback lands on the daemon's own public base (loopback or tunnel) and redirects back to `#/<host>/connector/<id>`. `advertisesOAuth` sets `config.oauth` at create and re-check and never downgrades. Tokens live in `config.auth`, refreshed within five minutes of expiry and persisted.
- **Each connector is its OWN MCP server in Claude Code, and the daemon keeps that list current** (Less, 2026-09-10: "we need a way so MCPs are separated, but also that can be live updated", rejecting the beta.85 aggregate). **Claude Code learns its MCP servers at session start and nothing can inject one mid-session** — no config re-read, no dynamic server helper, and `/mcp`'s Reconnect re-dials known servers without re-reading config (Claude Code docs, checked 2026-09-10). The ONE live path is `/reload-plugins`, which in an interactive session connects and disconnects a PLUGIN's servers while keeping the connections of servers whose config did not change. So: `connectors/plugin-sync.ts` writes the `.mcp.json` of every metro plugin under `<claude dir>/plugins` (a bare map of servers, the shape a plugin root takes). **It SEARCHES rather than assuming a layout** (`pluginRootsUnder`, 5 levels, dotdirs and `node_modules` skipped, 8 roots max), and the reason is the one that cost an evening on 2026-09-10: **an INSTALLED plugin is served from `<claude dir>/plugins/cache/<marketplace>/<plugin>/<version>/`, and `<claude dir>/plugins/marketplaces/<marketplace>/plugin/` is only the marketplace CHECKOUT, which Claude Code does not read for MCP servers** (`installed_plugins.json` records the `installPath`). ## The vault (step 3 of `docs/LOCAL-FIRST.md`)

**Vocabulary: a user reads "channel"; the code, the files, the wire and this document say `station`.** The page's labels, routes (`#/<host>/channels`, `#/<host>/channel/<id>`), the CLI usage text and the README prose were renamed on 2026-09-04 at Less's request; identifiers, JSON keys (`stations`), `metro://<station>/…` lines and the MCP payloads were NOT, because they are on-disk and wire contracts (agent files, vault bundles, existing tool schemas). Do not rename those without a migration.

metro.box stores each agent's stations, connectors and their credentials as ONE CIPHERTEXT BUNDLE per agent, sealed in the browser to a key derived from the owner wallet, and can open none of it.

- **Hosted side** (`apps/api/src/db/vault.ts`, `apps/api/src/vault.ts`, table `vaults` (`0021_vault`, renamed from `vault` by `0025_vaults` for the plural every other table has): `id` = the agent id, `owner` = the VAULT IDENTITY (below), `name`, `stations` jsonb of station kinds for the directory, `envelope` jsonb, `synced_at` ISO text): `GET /api/vault` lists the identity's entries WITHOUT envelopes, `PUT /api/vault/<agentId>` upserts, `GET`/`DELETE /api/vault/<agentId>` read and drop one. **There is NO metro.box sign-in on this path** (Less's call: the user is already signed in to their daemon and must not be asked again). Each request carries the same signed header every local API takes, `Authorization: Metro <address> <unix ms> <signature>` over `metro-auth\n<METHOD> <path>\n<at>` (`packages/http/src/signed-identity.ts`, viem's `verifyMessage`, five minutes of skew), and the recovered address IS the owner. The vault identity is an Ethereum account derived in the browser from the SAME EIP-712 signature that derives the encryption key (`HKDF(signature, salt "metro", info "vault-secp256k1")` → `privateKeyToAccount`), so anyone who could forge it could also decrypt, and nothing weaker guards the rows. Not-yours and unknown are the same 404. `parseVaultInput` refuses an envelope that is not `v: 1`, not for that agent id, or whose `key.recipient` is not an address, and caps it at `ENVELOPE_MAX` (2 MiB; the route reads bodies up to that plus 64 KiB, which is why `readJsonBody` takes a `max`). The server never sees a wallet signature, a key or a plaintext. Consequence: rows written before this change (owner = the wallet address) are unreachable; re-sync once.
- **Local side** (`agents/bundle.ts`, local daemons only): `GET /api/agents/<id>/bundle` answers the owner with the PLAINTEXT bundle `{version: 1, agent: {id, name, key, stations: [{station, id, allowlist, config}]}, connectors: [{id, name, url, transport, config}]}` (`readLocalAgentFile` + `readLocalConnectors`), and `POST /api/agents/restore` takes that same shape (`parseBundle`, 2 MiB) and writes it through `localImportAgent` (same merge rules as an import: same id refreshes in place) and `localImportConnectors`, then reloads the stations. Mounted through `SessionApis.bundleApi`, before the agent api which 404s unknown sub-resources. **Plaintext credentials cross the wire only between the page and the daemon it manages** (loopback or the daemon's own tunnel), never to metro.box.
- **Browser side** (`apps/ui/src/vault/crypto.ts`, `auth/identity.ts`; `@noble/curves` for the curve, WebCrypto for HKDF and AES-GCM): the owner wallet signs ONE EIP-712 message, `domain {name: "metro", version: "1"}`, type `EncryptionKey {purpose: string, keyVersion: uint256}`, message `{purpose: "encryption-key", keyVersion: 1}`; `HKDF-SHA256(signature bytes, salt "metro", info "secp256k1", 48 bytes)` mapped to a scalar is the wallet's **secp256k1** private key (Ethereum's curve, the ECIES shape XMTP used for its wallet-derived key bundles; Less asked for Ethereum-based encryption). Each seal mints a random 32-byte data key, encrypts the bundle JSON with AES-256-GCM (AAD = agent id), and wraps the data key to the wallet: ephemeral secp256k1 keypair, ECDH x-coordinate, `HKDF(shared, salt "metro-wrap", info ephemeralPub || recipientPub)`, AES-256-GCM with AAD = the recipient address. The envelope is `{v: 1, keyVersion, agentId, nonce, ciphertext, key: {recipient, recipientPublicKey, ephemeralPublicKey, nonce, ciphertext}}`, base64url throughout. Opening checks `key.recipient` against the signing wallet FIRST, so the wrong wallet fails by name and never by a decryption error. **The derived private key lives only in the browser for the duration of one action** and nothing is cached or registered; the same signature reproduces it anywhere. `signInTo` refuses a wallet that is not the daemon's owner (`/api/mode` owner) before asking for the signature. `test/vault-crypto.test.ts` pins the round trip, the wrong-wallet refusal, tampering and the typed data.
- **Flows**: *Sync with Metro* on the agent page (`SyncAgent`): the stored identity → `GET /bundle` from the local daemon → seal → signed `PUT /api/vault/<id>`. *Restore from Metro* on an empty daemon (`RestoreAgent`): the stored identity → signed `GET /api/vault` lists → pick → signed `GET /api/vault/<id>` → open → `POST /api/agents/restore`. No wallet prompt at all after sign-in, no metro.box session anywhere.
- **Deviation from the design note, accepted**: the wallet signs ONCE per action; the double-signature determinism check is not done. A non-deterministic signer (an ERC-1271 contract wallet, some MPC wallets) would derive a different key at restore and fail with "sealed for <address>, not for the wallet you signed with" or "could not be opened", never silently.

### Sign-in is ONE EIP-712 signature, and every request after it is signed by a derived key

There is no SIWE, no nonce, no session JWT and no `.session-secret` any more (Less, 2026-09-04: "replace SIWE completely with the EncryptionKey"). The owner wallet signs the vault's `EncryptionKey` typed data ONCE (`domain {name: "metro", version: "1"}`, `EncryptionKey {purpose: string, keyVersion: uint256}`, `{purpose: "encryption-key", keyVersion: 1}`; the daemon's copy is `packages/http/src/identity-key.ts`, the page's `vault/crypto.ts`, and `test/identity.test.ts` on both sides pins the SAME vector: signature → identity `0xfbd1…f3d7`). That signature is the master secret: the page derives from it the vault encryption key (`HKDF(sig, "metro", "secp256k1")`) AND the request-signing identity (`HKDF(sig, "metro", "vault-secp256k1")` → `privateKeyToAccount`), keeps `{address, signature}` in `localStorage` (`metro.identity`, `auth/identity.ts`) and re-derives on load, so the user is never asked to sign again on that browser. Known trade-off, accepted: a script that can read that origin's storage can decrypt the vault; the same script could already drive the daemon with the old session.

- **Registration is the only time the signature leaves the browser**: `POST /auth/identity {signature}` (`routes/identity.ts`, local daemons only). The daemon verifies it with viem's `verifyTypedData` against `.owner` (403 `this machine belongs to another wallet`, 403 while no owner, 400 when not a 65-byte hex), derives the identity address the same way and records `identity → owner` in an IN-MEMORY map (`packages/http/src/identity-registry.ts`). Nothing is persisted: after a restart the first signed request 401s, the page re-registers from its stored signature and retries once (`api/client.ts` `call`), which the user never sees. A 401 from any other origin (metro.box) is never retried that way.
- **Every request is signed**: `Authorization: Metro <identity address> <unix ms> <EIP-191 signature>` over `metro-auth\n<METHOD> <path>\n<at>` (`packages/http/src/signed-identity.ts` `signedIdentity`, five-minute skew, path without the query). `apiSession(req)` is now ASYNC and returns `{subject}` from the registry, so every session-gated API awaits it; the subject is the owner wallet. The hosted vault verifies the same header and takes the recovered identity address AS the owner, with no registration. **EOAs only**, as before.
- `/mcp`, the Monitor, uploads and attachments authenticate with AGENT KEYS only (`authenticate(req)`, no config); a `Metro` header never opens them and a `?token=` never carries an identity. `RequestIdentity` still has the `session` kind (a multi-agent scope) with no producer left: `test/egress-scope-matrix.test.ts` keeps it as the wide-scope reader, so it stays until that matrix is reworked.
- **The UI**: `Login.tsx` `signInTo` connects the wallet, signs, derives and stores; no daemon is involved at sign-in (see the server list bullet under The UI for how each daemon learns the identity). `App.tsx` loads the stored identity on boot (`loading` → `login`/`unlocked`); a lock clears it. There is no token prop anywhere: `call(init)` reads `activeIdentity()` and signs, so `fetchStations()`, `createConnector(input)`, `useSessionQuery()` and friends take no credential. Sync and Restore no longer show a wallet list: `SyncAgent` seals with the stored identity on one click, `RestoreAgent` lists the vault as soon as it opens. Tests install an identity with `test/identity-fixture.ts`.
- Daemon tests sign with `test/identity-helper.ts`: `auth(method, urlOrPath, who)` where a string `who` is a subject registered on the fly (`identityFor`, deterministic account per subject, re-registered on every call because `identity.test.ts` resets the registry) and an account is signed as-is (unregistered → 401). The ownership tests keep their ada/bob subjects that way.

Gated by the session JWT only — **never an agent key.** An agent key cannot reset itself.

### The paste-ready command (`mcpAddCommand`)

`claude mcp add --transport http metro "http://127.0.0.1:8420/mcp?token=<key>"` — mirrors the Browserbase shape byte for byte.

### Attaching station accounts

- `POST /api/agents/<id>/accounts/start` is the **ONLY** route that writes a station into an agent file (`localAttachAccount`), and `DELETE …/accounts/<station>/<account_id>` the only one that removes it.
- **No account exists unless the credential has been demonstrated to work.** Every station is verified against the real provider BEFORE the write (`stations/attach.ts` `prepareAccount`): discord-bot `GET /users/@me` plus the `/applications/@me` Message Content flags, telegram-bot `getMe`, xmtp opens a real inbox with the key it just generated. The xmtp check runs OUT OF PROCESS (`Bun.spawn`, key over stdin, 90s cap) because `@xmtp/node-sdk` exposes no `close()`; it verifies into the SAME db3 the train will use and stores that path in `config.dbPath`. On a failed write `discard()` deletes the db3.
- The account id is server-generated, never from the body. Duplicate bot tokens are refused 409. A webhook station is refused on a local daemon (400, its url would have to be public).
- **No API returns a stored station credential** on its own; the bundle route hands the whole agent to the owner for sealing.
- **A station account can be switched OFF without deleting it** (Less, 2026-09-10: "make it possible to disable a Station without having to delete it"): `stations[].enabled` in the agent file (absent = on, so every existing file is unchanged), carried by `LoadedAccount.enabled`, the bundle and the vault. `writeStations` keeps a disabled account in the agent map (it stays known, owned and visible on the page, with `enabled: false` on its row from `accountEnabled` in `agents/map.ts`) but leaves it out of the account file, so the train never runs it and a station whose accounts are all off gets no train at all through the same pruning as a deleted one. `PUT /api/agents/<id>/accounts/<station>/<account_id>/enabled {enabled}` (`localSetAccountEnabled`) flips it and, unlike the allowlist, DOES go through `syncStations`, because the train must drop or pick up the account. The page shows a `Disabled` pill in the channel list and on the station page, with a Disable / Enable button beside the kebab (`components/ToggleAccount.tsx`). A disabled account's credentials stay exactly where they were, which is the whole point: enabling it again is one click, not a sign-in.
- **The per-account allowlist is edited from the station page** (Less, 2026-09-10; `agents/allowlist.ts`, `agents/senders.ts`, `PUT /api/agents/<id>/accounts/<station>/<account_id>/allowlist`, `GET …/senders`). `normalizeAllowlist` trims, drops blanks, dedupes case-insensitively, caps 500 entries of 200 plain characters, and collapses to `['*']` when the list is empty or names `*`, so "allow nobody" cannot be expressed by accident. **An allowlist change refreshes the maps only** (`reloadAgents` = `reloadFrom(fileSource)`, never `syncStations`): the filter lives in the daemon (`senderAllowed` in `mcp/session.ts`), so restarting a train would reconnect WhatsApp and XMTP for nothing. `GET …/senders` offers what the bus ring has seen on that account (`recentSenders`, newest first, `self`/`unknown` and other accounts excluded), which is what turns an opaque id into a name on the page; it is bounded by `BUS_BUFFER_MAX` and empty on a fresh daemon. The account rows carry `allowlist` (`mcp/accounts.ts`), and the page shows Anyone / Only these senders with the seen list one click away (`components/Allowlist.tsx`), plus a per-station line saying where that station's sender id comes from (`WHERE_TO_FIND`: a Telegram numeric id or @userinfobot, a Discord id through Developer Mode, a WhatsApp `<number>@s.whatsapp.net`, an XMTP inbox id and not a wallet address). **A row whose `allowlist` is null hides the editor**, which is both an unmapped account and a daemon too old to have the route.
- **Interactive attach** (`stations/attach-session.ts`): telegram and whatsapp cannot finish in one request, so `start` answers `status:'pending'` with an `as_<22 base64url>` id, and the client polls, posts `/step`, or `DELETE`s. `AttachSessions` is IN MEMORY ONLY. `authorize` runs the owner check BEFORE any provider client is created. 5-min pending TTL, 1-min settled, 2 per agent, 40 per daemon. Login modules live in the STATION packages and are pulled in by DYNAMIC import. The whatsapp driver closes its pairing socket BEFORE the train boots with the same creds; Baileys' `connection: 'close'` with 515 right after pairing is a REQUIRED restart, not a failure.
- After a write, `reloadFrom(fileSource)` rewrites the account files and maps; `writeStations` rewrites a train stub only when its CONTENT changes (`writeIfChanged`), and `TrainSupervisor.requestReload(name)` shares the fs watcher's debounce map.

### Claude Code sessions, memory and settings (local daemons only)

`claude/files.ts` reads Claude Code's own files on the machine the daemon runs on — `<claude dir>/projects/<encoded cwd>/<session>.jsonl` transcripts and `<…>/memory/*.md` — where the claude dir is `METRO_CLAUDE_DIR`, else `CLAUDE_CONFIG_DIR`, else `~/.claude`. `claude/api.ts` serves them read-only to the OWNER session on `GET /api/claude/projects`, `/sessions?project=`, `/sessions/<id>?project=&offset=&limit=`, `/memory?project=` and `/memory/<name>.md?project=` (mounted through `SessionApis.claudeApi`, local mode only, so a hosted daemon 404s). Names are validated before any path is built (`PROJECT_RE`, `SESSION_RE`, `MEMORY_RE`; `.` and `..` refused; the URL is split BEFORE decoding so an encoded slash never becomes one). A project's `cwd` comes from the newest transcript's first line, a session's title from the last `ai-title` line in the file's tail, else the first real user prompt in its head (`readEdge` reads 64 KiB at either end, never the whole file, for lists). A transcript page streams the file once, keeps `user`/`assistant` lines that are not `isSidechain`, drops `thinking` content (kept as a marker), `<task-notification>`/`<system-reminder>` noise and unknown blocks, caps text at 20 KB, tool input at 4 KB and tool results at 8 KB, and paginates by kept-entry offset. The UI (`Sessions`, `Memory`, `Transcript`, `ClaudeProjects`, routes `#/<project>/sessions[/<claude project>[/<session>]]` and `#/<project>/memory[/<claude project>[/<file>.md]]`, sidebar rows on a local daemon) is LIVE: lists and memory refetch every 5s, and the transcript view opens on the LAST page and polls `offset=<seen total>` every 4s to append new turns while Claude works, with `Show earlier` paging backwards. `test/claude-api.test.ts` drives it against a fixture claude dir.

**Skills are the second thing this surface writes** (Less, 2026-09-10, pointing at claude.ai's Skills panel: "a way to add / remove / edit skills. With a left sidebar menu"). `claude/skills.ts` lists `<claude dir>/skills/*/SKILL.md` plus, for every Claude project whose `cwd` still exists, that project's `.claude/skills/*/SKILL.md`; each entry carries the frontmatter `name` and `description`, the folder name, the scope, the path and the mtime, and a directory without a `SKILL.md` is not a skill. `GET /api/claude/skills` lists them with the PLACES a new one can go, `GET/PUT /api/claude/skills/<id>` read and write one, `POST /api/claude/skills {name, scope, text?}` creates one from a template, and `DELETE` removes the skill's whole FOLDER. **The id is `<place>:<name>` and is resolved by looking it up in that same listing**, never by building a path, so traversal is impossible by construction and an unknown id is a flat 404; the page percent-encodes it, the daemon decodes it. A create validates the name against `SKILL_NAME_RE` (lowercase letters, digits and dashes, 64 chars) before it becomes a directory, refuses a name already taken (409) and an unknown place (404); a write refuses empty text (400), a file over `SKILL_MAX` (256 KiB) and a `seenAt` that no longer matches (409), and is atomic like the settings write. The delete asserts the folder is named after the skill before `rmSync`. **The settings files are the one thing this surface WRITES** (Less, 2026-09-08: "a new tab to be able to see the claude code settings JSON (and make it editable)"). `claude/settings.ts` lists `<claude dir>/settings.json` (always, even when it does not exist yet) plus, for every Claude project whose `cwd` still exists, that project's `.claude/settings.json` and `.claude/settings.local.json` — **project files are listed only when they exist**, so the list stays short and truthful. `GET /api/claude/settings` returns them with their text; `PUT /api/claude/settings/<id>` writes one. **The id is resolved by looking it up in that same listing, never by building a path**, so traversal is impossible by construction and an unknown id is a flat 404. A save is refused unless the text parses as a JSON OBJECT (400), is refused when the file changed on disk since the page read it (409, the body carries the `seenAt` the listing gave), and is written atomically (temp file then rename) with the mode the file already had, or 0644 for a new one — **never `writeSecure`**, which would force 0600 on `~/.claude` and on a project's shared `.claude`. A file over `SETTINGS_MAX` (256 KiB) is listed with `editable: false` and empty text rather than truncated, and refuses the write, because the alternative is silently overwriting a file with a truncation of itself. `test/claude-settings.test.ts` drives the whole surface over real HTTP against a fixture whose project cwd really exists.

### The model gateway (`apps/daemon/src/gateway/`, local daemons only)

Built 2026-09-07 at Less's request ("a new sidebar item Model which allows me to change the model used in Claude Code using the daemon system, Bedrock, Codex or OpenRouter, without breaking anything"). **Claude Code on the box talks to the daemon, and the daemon decides where inference goes**: `metro claude` sets `ANTHROPIC_BASE_URL` to `http://127.0.0.1:<port>/gateway` (see the CLI section), and the gateway (`gateway.ts`, mounted in `handlePreMcpRoutes` right after `/health`, so before every other router; `SessionApis.gateway`, local mode only) serves the Anthropic Messages format there. Auth is the agent key in `x-metro-key` (`agentIdForKey`), never `Authorization`: Claude Code keeps its own login in `Authorization`, and the daemon's port is public through Funnel, so the header is what stops a stranger. **The agent key's blast radius grew with it**: the key that already opens `/mcp` and the relay now also spends the owner's Bedrock, OpenRouter and ChatGPT credit through `/gateway`, and a key reset revokes that too. The route is decided PER REQUEST from `<agents dir>/model.json` (`model-config.ts`, 0600, `{version: 1, provider, bedrock: {region, apiKey, model}, openrouter: {apiKey, model}, codex: {model, auth: {accessToken, refreshToken, idToken, accountId, email, plan, savedAt} | null}}`), so the Model page switches a running session on its next request, no restart.

- **Three providers, resolved by `resolveRoute`**: a model id with an explicit prefix (`bedrock:<id>`, `openrouter:<id>`, `anthropic:<id>`, typed as `/model bedrock:eu.anthropic.claude-sonnet-4-6` inside a session) goes there for that request; a plain id goes to the page's provider. `anthropic` forwards to `api.anthropic.com`, and **with no key on the Model page it is VERBATIM**: the path with its query (`/v1/messages?beta=true`), every request header except hop-by-hop ones, `accept-encoding` and `x-metro-key` (`forwardedHeaders`), and the body BYTES as received (re-serialised only to strip an explicit prefix), so `anthropic-beta` with the OAuth capability, `cache_control`, `context_management`, `output_config` and whatever a later release adds all pass untouched, which is what the gateway compatibility guide demands; **A key stored on the page changes exactly two things** (Less, 2026-09-08, who also asked for a claude.ai subscription sign-in; that half is NOT built, see the note at the end of this section): `anthropicHeaders` drops `authorization`, drops every `anthropic-beta` naming `oauth` (an API key must not carry the OAuth capability) and sets `x-api-key`, and `defaultModelFor` pins `anthropic.model` — except for a SMALL model (`isSmallModel`, `/haiku/i`), which is passed through as asked, so Claude Code's background chores and a subagent pinned to Haiku are not silently upgraded to the pinned model and its price. With no key the request is untouched, which is what every existing box does. ### whatsapp

Package `baileys` (`@whiskeysockets/baileys` is the OLD name; both publish `7.0.0-rc*`). Config `{phone}`; the Baileys auth blob lives in the SAME `accounts.config` jsonb under `config.credentials`, spread into the account file by `materialize.ts` — **the train opens no pg connection.** `useAccountAuthState` holds creds + Signal keys in memory and never writes creds back (`saveCreds` is a no-op; Signal sessions re-establish on demand). Pairing survives deploys and volume loss. Fails loud if the blob is missing. Two writers of the creds: `scripts/login.ts` and a web-UI attach session; the running train writes nothing.

- **Exactly two key types are durable, and the reason is 463.** Baileys 7 attaches a trusted-contact token (`tctoken`) to every 1:1 send, and WhatsApp answers a 1:1 send without one with `ack error 463` — it counts as reaching out to a stranger and time-locks the account. The token is issued to us BY the contact and Baileys' own index-pruning assumes that store is persisted, so an in-memory-only store is the 463 back on every deploy, each refusal deepening the lock. `src/token-store.ts` persists `tctoken` + `lid-mapping` (the PN ↔ LID index the token is filed under) to `~/.metro/whatsapp-tokens-<account>.json`, 0600, debounced 1s, seeded back on boot. Losing the file degrades to the old behaviour, never to a failure. **Do NOT extend this to `session`/`pre-key`/`sender-key`/`identity-key`/`app-state-sync-key`/`device-list`** — `creds` carries the pre-key counters and is still never written back, so persisting half a Signal state is worse than persisting none.
- **A message key is not synthesizable** (`src/keys.ts`). In a GROUP the address is (`remoteJid`, `id`, `fromMe`, **`participant`** = the original author), and a key correct in a 1:1 is wrong in a group in exactly that field: with `participant` missing, Baileys and WhatsApp's own clients fill it from the REACTION's sender, so the reaction resolves to a message that does not exist — accepted, ACKed, rendered nowhere. 1:1 worked by luck. The fix is a per-account bounded LRU (`makeKeyCache`, 4000) filled from EVERY `messages.upsert` (before the `fromMe` filter — our own sends must be in it) and from the key `sendMessage` returns, reused VERBATIM, which also sidesteps lid-vs-phone address spaces. The cache dies with the train, so `react` on a group message this connection never saw FAILS LOUD (`whatsapp_unknown_message`) rather than reporting success for a send that displays nothing. Do NOT "simplify" any of these back to a constructed key.
- **A refused send is an error, and the verdict is read off the raw socket** (`src/ack.ts`). `sendMessage` resolving only means the stanza left the socket; the verdict arrives as `<ack class="message" error="…">`. `send` waits `METRO_WHATSAPP_ACK_WAIT_MS` (5000, `0` disables) and THROWS — `whatsapp_account_restricted` for 463 (naming the timelock, `retryable: false`), `whatsapp_send_refused` otherwise. No ack inside the window is still reported as sent: the absence of a verdict is not a verdict. **The hook must STAY on `sock.ws`** (`CB:ack,class:message`) — Baileys re-emits the same ack through the BUFFERED emitter, and a stuck buffer eats it; `ws` frames bypass the buffer. `messages.update` is kept as the delivery log.
- **Inbound media** covers all five types (plus the `viewOnce`/`ephemeral`/`documentWithCaption` wrappers). `kind` is six-way, not five: WhatsApp ships a voice note and an mp3 both as `audioMessage`, distinguished ONLY by `ptt`, so a kind derived from the mime cannot tell them apart — the station's kind rides on the payload and wins. `mimetype` is stripped of parameters or the cache file gets `.bin`; a node with no `fileName` gets one synthesised from the SAME `extFromMime` the cache name uses. `reuploadMedia` is wired in as Baileys' `reuploadRequest`, which recovers a file WhatsApp already expired from its CDN.
- **The ceiling is `MAX_ATTACHMENT_BYTES` (100 MiB default, `METRO_ATTACH_MAX_BYTES`), metro's, not WhatsApp's** — between 100 MiB and WhatsApp's 2 GB document limit metro is the thing refusing. It refuses honestly and for free: every media node declares `fileLength`, so the size is asserted before a byte is fetched. The download timeout is metro's too (`withIdleTimeout`), because Baileys 7 typechecks a `signal` and then drops it.
- `sock.end()` is `async` in Baileys 7 and must be awaited.
- **A second Baileys client on live credentials is an OUTAGE, not a test** — the sockets share one device identity, the newest wins, and Signal state diverges. Verify inbound media against a local `mmg.whatsapp.net` in a private mount namespace instead. ToS/ban risk: use a dedicated number.

### threema

Package `packages/threema`, `@metro-labs/threema` (Less, 2026-09-10: "create a new package for Threema station? Integrate it on the UI and everywhere like other stations"). A **Threema Gateway ID in end-to-end mode**: the ID (`*ABCDEFG`), its API secret and the private key from the key file Threema hands out when the ID is created. Config `{gatewayId, secret, privateKey, callbackId, callbackToken, createdAt}`; the key is stored as the bare 64 hex characters (`parsePrivateKey` strips the `private:` prefix). A basic-mode ID cannot be attached: Threema would hold the key, so nothing end-to-end is left, and the form asks for a key such an ID never had.

- **Attach verifies three things with Threema before the write** (`packages/threema/src/verify.ts`, run IN THE DAEMON with `node:crypto` only, so the daemon never loads the SDK): `GET /credits` proves the ID and secret (401 is "Threema rejected that Gateway ID or API secret"), `GET /pubkeys/<id>` returns the public key the Gateway holds for the ID, and it must equal the X25519 public half of the pasted private key (`publicKeyOf`, a PKCS#8-wrapped `createPrivateKey`; `test/verify.test.ts` pins that node and tweetnacl derive the same key). `prepareThreema` (`stations/attach.ts`) then mints a `callbackId` (19 digits, `newWebhookId`) and a `callbackToken` (48 CSPRNG bytes, base64url), and the identity carries the callback url plus the credit balance. The UI form is three fields (`gatewayId` plain, `secret` and `privateKey` masked; `test/attach.test.ts` lists `gatewayId` among the plain ones because people write to it).
- **Inbound is a Threema callback on the daemon's PUBLIC address**: `POST /api/threema/<callbackId>/<callbackToken>` (`routes/threema-callback.ts`, mounted right after the webhook route, so BEFORE the monitor router; `test/threema-station.test.ts` asserts `/api/tail` still 401s). The url is built with `publicBaseOrDefault()` like `hookUrl`, shown once after attach (`AttachedAccount`) and again on the station page as `callback`: `mcp/accounts.ts` `withCallbackUrl` rebuilds it from the `callbackId`/`callbackToken` the train's `accounts` answer carries and strips the token from the row, the same relaxation the webhook endpoint has (a url that only posts INTO its own agent). The route checks the path token (`tokenMatches`; `stations/threema-callbacks.ts` reads the materialized `threema-accounts.json`), requires the seven fields Threema always sends (`from, to, messageId, date, nonce, box, mac`, form-encoded, 64 KiB cap, `nickname` optional) and forwards them to the train through `forwardTrainCall('threema', 'callback', …)`. **Status discipline**: a train that is down answers 503 so Threema retries (three times over five minutes); a train that REFUSES (bad MAC, wrong recipient, undecryptable) answers 400 so it stops; `GET` is a 200 readiness probe; anything unroutable is a flat 404. `readBody`/`BodyTooLargeError` moved to `routes/body.ts` so this route and `http.ts` share them without a cycle.
- **The private key never leaves the train.** `src/actions.ts` `callback` checks the MAC FIRST (HMAC-SHA256 over `from+to+messageId+date+nonce+box` keyed by the API secret, `timingSafeEqual`, before any network call, so a forged post costs one HMAC), fetches the sender's public key (`/pubkeys`, cached per train lifetime), opens the NaCl box (`tweetnacl`: Curve25519, XSalsa20, Poly1305; PKCS#7 padding of 1 to 255 random bytes, and `unpad` refuses a last byte of 0 or past the end) and reads the type byte: `0x01` text is an inbound `msg` on `metro://threema/<account>/<THREEMAID>` from `metro://threema/<account>/user/<THREEMAID>` (`from_name` is the sender's push nickname, `is_private` always); `0x80` delivery receipt with status 3 or 4 (thumbs up or down) is a `react` event (👍/👎) targeting each acknowledged message id, other statuses are acknowledged and dropped; `0x90` typing is dropped; every other type (files, location, polls, groups) is logged and acknowledged as `ignored:0x..` so Threema does not retry. Message ids are the 16-hex strings of Threema's 8-byte ids, lowercased.
- **Outbound is `send_e2e`**: `send` seals `0x01 + utf8` for the recipient's public key under a fresh 24-byte nonce and posts `from, to, nonce, box, secret` form-encoded; the answer is the message id, remembered in a bounded set (`SENT_MAX` 2000) so a later quote of it reports `reply_to_self`. **A `reply` is a Threema quote v2**: the text becomes `> quote #<messageId>\n\n<text>`, and an inbound text of that shape is read back as a reply (`unquote`). Text only, `MAX_TEXT_BYTES` 3500 (the Gateway caps a box at 4000 bytes and answers 413 past it), `attachmentMode: 'none'`, verbs `send` and `reply`. Gateway refusals map to `TrainError`s by status: 401 `threema_unauthorized`, 402 `threema_no_credits`, 404 `threema_unknown_id`, 413 `threema_message_too_long`, 400 `threema_bad_recipient`, anything else `threema_gateway_error` (retryable when 5xx). The train logs the credit balance at boot.
- **Not carried, by the protocol or by choice**: emoji reactions, edits and deletes (the Gateway has no such message types; the receipt thumbs are the only reaction), files and media, delivery receipts back to the sender (each would cost a credit), and groups (a Gateway ID receives group messages only in groups it created itself with a ☁️-prefixed name; not built). `Line.parseThreema` accepts 8-character user ids and `*` plus 7 gateway ids; the allowlist entry for a sender is their Threema ID (`WHERE_TO_FIND.threema`). `THREEMA_GATEWAY_URL` overrides `https://msgapi.threema.ch` for a fake Gateway.
- `packages/threema/test/{crypto,verify,actions}.test.ts` pin the box, the padding, the MAC, the quote, the attach checks and both directions of the train against a stubbed `fetch`; `apps/daemon/test/threema-station.test.ts` pins the attach, the route over real HTTP and the account rows.

### webhook

`hasAccounts: true, hasTrain: false` — an endpoint is an `accounts` row, so it is OWNED by one agent and scoped like any other station.

- **Attach:** `{"station":"webhook"}`. No provider exists to verify, so `prepareWebhook` mints a `webhookId` and a `secret`, stores `{secret, webhookId, createdAt}` in `config`, and puts the finished `endpoint` straight on the 201's `identity`.
- **The url names the `webhookId`, NEVER the `account_id`.** That is why the second id exists: `account_id` is `a<agentId>-<8 hex>`, so a public url built from it would publish the internal agent id to every provider it is pasted into. `webhookId` is 19 random digits (`newWebhookId`) and carries nothing. The PK, the agent map key and the event line all stay `webhook/<account_id>`; `findEndpointByWebhookId` is the only lookup the route may use.
- **Inbound:** `POST /api/webhooks/<webhook_id>/<token>`. **The whole URL is the credential** — no signature header, deliberately: an HMAC is a real gate but most providers cannot compute one, and the header was what made this unusable. The token is 48 CSPRNG bytes base64url compared with `timingSafeEqual`; everything that is not an exact match is a flat 404, including an `account_id` in the id position and a row missing either field. `GET` is a 200 readiness probe with no event; anything else 405.
- **The route MUST stay in `handlePreMcpRoutes` BEFORE `handleMonitorRequest`** or the monitor router swallows it. `webhook-station.test.ts` boots WITH a `monitorCall` and asserts `/api/tail` still 401s while the hook 200s — the only way that bug is visible.
- The token never reaches a log or the event: `webhookEntry` is handed `hookPath(id)`, not `req.url`.
- **This is the ONE place the no-API-returns-a-station-credential rule is relaxed.** `inCoreAccounts` re-serves the full url to the owning agent on every `GET /api/agents`, because a url you cannot retrieve is useless — you paste it into a provider days later. The blast radius differs in kind: a bot token or XMTP key controls an account on someone else's network, this one only posts events INTO its own agent. Scoped by the same `scopeAccountsByAgent`, surfaced as `endpoint` rather than `url` so the row's external-link button never makes a credential clickable, and masked behind Reveal/Copy in the UI.
- **Delivery needed TWO fixes.** Dropping the `station === 'webhook'` check in `inbound.ts` was necessary but NOT sufficient: `classifyEvent` types an external webhook as `{type:'system'}` and `routable` only routed `msg`/`react`, so an attached endpoint answered 200, emitted, and reached NOBODY. `system` is routed now, safe because that branch is its only producer in the workspace.
- The note (`channels/webhook-note.ts`) carries the pretty-printed body — the summary line alone tells an agent nothing — capped at `MAX_BODY_CHARS` 8 KiB with the dropped count named, plus an ALLOWLIST of headers, never the whole map: a delivery's `authorization`, `cookie` and signature must not land in the agent's context.
- Two consequences of routing a `system` event: `handleEvent` does NOT set `lastLine` for one (that is `knownLine`, where an approval prompt goes, and a webhook line has no `send` verb), and `handlePermissionReply` runs only for `msg`, so a body containing `yes abcde` can never answer a pending request.
- `listEndpoints` reads the materialized `~/.metro/webhook-accounts.json`.

## The daemon (what `metro serve` runs)

- **`StationSource` is the whole seam** (`stations/materialize.ts`): `() => Promise<LoadedAgent[]>`. `fileSource` (`agents/files.ts`) reads every `<METRO_AGENTS_DIR, default ~/.metro/agents>/<name>/agent.json` — `{version: 1, id, name, key, owner, stations[], connectors[]}` — and validates it loudly with the file path in every error: 11-character ids, the agent-name rule (`AGENT_NAME_RE` in `packages/core/src/ids.ts`), a url-safe key of 16–128 chars, a lowercase owner address, known station names, no id or key shared by two files. `materializeFrom(fileSource, { allowEmpty: true })` runs at boot (a fresh machine has no agent yet); every station runs here, always: the hosted service is its own app (`apps/api`) with no stations at all.
- **A local daemon is administered through the routes above, backed by files** (`routes/local-mode.ts` builds its `SessionApis`, `agents/file-admin.ts` does the writes). `GET /api/mode` answers `{mode: local, owner, project: 'localdaemon', version}`. Agents are created as `<agents dir>/<name>/agent.json` (key registered in the same call so `/mcp?token=` works at once), every write is followed by `reloadFrom(fileSource)` plus a supervisor reload (`syncStations` in `boot.ts`).
- **Restore writes through the same merge rule an import used**: `localImportAgent` with a same-id agent rewrites the file in place (the bundle's stations win by `station/id`, stations attached here and absent from the bundle are kept, the key is re-registered); a different agent with the same name is 409. `localImportConnectors` upserts `connectors.json` by id.
- At boot a local daemon prints the `https://metro.box/#/<host:port>` link (`connectLink`; `METRO_UI_URL` overrides the UI base), the `ssh -L` line, and the owner line (`Only <owner> can sign in.` or the `--owner` reminder). `connect-hint.ts` holds the three hints.
- **xmtp on a machine costs one installation per machine, not per restart**: `config.dbPath` is HOME-relative (`~/.metro/xmtp-production-<hex>.db3`) and `expandHome` resolves it locally, so a restore on the SAME box reuses the installation while a brand-new box spends one of the inbox's ten. **whatsapp treats `connectionReplaced` as TERMINAL** (`terminalReason`), so an accidental double-run is survivable instead of a 463 timelock loop.
- `test/file-source.test.ts`, `test/file-admin.test.ts`, `test/local-mode-api.test.ts` (a real wallet signature over HTTP), `test/local-connectors.test.ts` (a fake MCP server on loopback, end to end) and `test/bundle-api.test.ts` pin it.

## Database (Postgres + Drizzle, `apps/api` only)

**Postgres lives only in `apps/api`.** The daemon has no `drizzle-orm`, `postgres` or `drizzle-kit` dependency at all, so the boundary is a package rather than an assertion; the old `local-runtime-imports` test that walked the static graph is gone with it. `STATIONS`/`StationName`/`ConnectorTransport` live in `packages/core/src/station-names.ts` (`apps/api/src/db/schema.ts` re-exports them), `normalizeAddress` in `packages/core/src/address.ts`.

**Two tables** in `apps/api/src/db/schema.ts`, and the hosted daemon reads nothing else (`0023_drop_users` dropped `users`: with SIWE gone nothing wrote it; `0024_servers` added the server list; `0025_vaults` renamed `vault` to `vaults`):

- `vaults` — `id` (the agent id), `owner` (the identity address, indexed), `name`, `stations` jsonb (station kinds, for the Restore list), `envelope` jsonb (the sealed bundle), `synced_at` ISO text. `apps/api/src/db/vault.ts` is its only writer; not-yours and unknown are the same 404.
- `servers` — `id` (an 11-char id), `owner` (the identity address, indexed), `host`, `name` (nullable), `added_at`; unique on (`owner`, `host`). `apps/api/src/db/servers.ts` is its only writer, reached from `apps/api/src/server.ts` like the vault.

**Every id is an 11-character base64url string** (`packages/core/src/ids.ts`, `newId()`, `ID_RE`) with the first character forced alphanumeric by rerolling. Ids are opaque, never parsed.

**Gone in `0022_local_only`** (hand-written, `DROP TABLE IF EXISTS` in FK order: `agent_connectors`, `runtimes`, `stations`, `connectors`, `agents`, `project_members`, `projects`): every plaintext station row, connector row and key that metro.box ever held, the runtime leases, and the projects and members model. Their code went with them: `db/projects.ts`, `db/runtimes.ts`, `db/runtime-admin.ts`, `db/agent-connectors.ts`, `db/whatsapp-login.ts`, the pg halves of `agents/admin.ts`, `connectors/model.ts`, `connectors/relay-target.ts`, `stations/materialize.ts` and `agents/account-attach.ts`, `daemon/run-api.ts`, `runtime-source.ts`, `agent-import.ts`, `import-api.ts`, `agent-pair.ts`, `pair-codes.ts`, `cli-pair-api.ts`, `project-api.ts`, the agent and run token functions of `daemon/session.ts` and `agentIdentity`/`assertLease` of `api-http.ts`. **Do not reintroduce a plaintext credential table on metro.box; the vault is the only store and it is ciphertext.** DB deps (`drizzle-orm`, `postgres`, `drizzle-kit`) live ONLY in `apps/daemon`; config is `apps/daemon/drizzle.config.ts`, generated SQL `apps/daemon/drizzle/`. `drizzle-kit generate` cannot be used and there is no `db:generate` script (the snapshots, none newer than `0014`, were deleted on 2026-09-07, QW-1): migrations are hand-written with a journal entry.

### Migrations

**Migrations apply themselves on deploy, via `release_command` in `fly.toml` — NOT at boot.** Fly runs `bun --filter @metro-labs/mcp db:migrate` (i.e. `drizzle-kit migrate`) in a temporary machine holding the app's secrets BEFORE the new version is released. It is the same command you run by hand, so there is one code path, not two.

- **`release_command` replaces `CMD` but NEVER overrides `ENTRYPOINT`.** This is why the Dockerfile ends in `CMD ["bun", "/app/apps/daemon/src/server.ts"]` and must NOT go back to `ENTRYPOINT`. With an `ENTRYPOINT` the release machine runs `bun server.ts <release command>` — `server.ts` ignores argv, so it boots a SECOND daemon against an empty `/data` (a fresh XMTP installation, burning an install slot) and never exits, timing the deploy out. This actually happened once; do not reintroduce it.
- **The failure semantics are the whole point of choosing `release_command` over a boot-time `migrate()`.** A non-zero exit ABORTS the deploy and the old machine keeps serving. The same migration at boot would throw before `markDaemonReady()`, which the crash guard turns into `exit 1` — a crash-loop, i.e. an outage caused by the migration itself. Do not move this to `boot.ts`. Verified: unreachable DB, empty and unset `DATABASE_URL` all exit 1; a re-run with nothing pending exits 0 and applies nothing.
- **`drizzle-kit` is a runtime `dependency`, not a devDependency** — `bun install --frozen-lockfile --production --filter @metro-labs/api` (Dockerfile) would otherwise leave it out of the image and the release command would fail. **The filter is load-bearing too**: it installs only the hosted app and the two packages it imports, 68 packages and 168 MB against 1.5 GB for the whole workspace, and the image copies only `apps/api`, `packages/core` and `packages/http`, so no station SDK and no daemon source ever ship to Fly. It is ~10 MB. Moving it back to devDependencies breaks every deploy.
- **`bun --filter` is load-bearing**: it sets cwd to `apps/daemon` so `drizzle.config.ts` and its relative `out: './drizzle'` resolve. The release machine's cwd is `/app` (the Dockerfile `WORKDIR`), where neither exists.
- The daemon itself still never migrates, and `materializeFromDb()` still throws on an empty DB — a deploy whose release command failed never reaches it.
- `test/migrate.test.ts` pins journal integrity only (every entry has its `.sql`, contiguous and ordered `when`, no orphan `.sql`). There is no Postgres in the suite; the DB behaviour above was verified by hand against a real one staged at `0009`.

## Deploy & Ops

- **Merging to `main` auto-deploys to Fly.** Don't merge unfinished work. Land via PR; the repo squash-merges (`(#NNN)` suffix). Every deploy is a brief outage of the page's sign-in and the vault; the hosted daemon runs no station, so no chat is affected.
- Fly app `metro`, region `iad` (`fly.toml`). `auto_stop_machines=false`, `min_machines_running=1`, `shared-cpu-1x`/1gb, `metro_data`→`/data`. Env: `HOME=/data`, `METRO_TRAINS_DIR=/app/apps/daemon/trains`, `METRO_HTTP_HOST=0.0.0.0`, `METRO_LOG_LEVEL=info`. **`DATABASE_URL` is the ONLY required Fly secret.** `METRO_VERSION` is unset there, so the hosted `/api/mode` reports `dev`; only a local daemon's version (passed by `metro serve`) is shown on the page.
- **Single-writer XMTP** is a rule for each machine running an agent: only ONE process may write an MLS inbox; a second burns the 10-install / 256-update budget. That is why `metro serve` refuses a second instance and why two boxes must never run the same agent.
- **One tunnel, Tailscale Funnel** (`net/tunnel.ts`, `tunnelWanted()` → `Tunnel(funnelDriver(port), onUrl)`; the driver struct stays so tests can fake it; the child is restarted 2s after an exit, killed with SIGINT on shutdown so a foreground `tailscale funnel` restores the node's serve config, and if no address appears within 20s the child's own output is logged at warn so Tailscale's "Funnel is not enabled, visit https://login.tailscale.com/f/funnel?node=…" reaches the operator; a restart backs off 2s → 30s). **`listener already exists for port 443`** (seen on Suzy, 2026-09-05) means the node already holds a serve config: the driver's `adopt` first asks reality: the node name from `tailscale status --json` (`Self.DNSName`) is resolved at 1.1.1.1/8.8.8.8 and probed at `/api/mode` THROUGH THAT PUBLIC ADDRESS (`node:https` with the name as SNI, 5s cap; from the box itself the name resolves over MagicDNS straight to the node, so a tailnet-only serve would pass a plain fetch) and, when it answers `mode: local` with this daemon's own owner, that address is USED instead of respawning (a frozen or foreground funnel from another terminal does not show in `funnel status`, seen on Suzy and Tony, 2026-09-05); only then is `tailscale funnel status` read, and a tailnet-only serve or another port is logged at error with `tailscale serve reset` as the fix. **An adopted Funnel is watched** (`watchAdopted`, every `METRO_TUNNEL_WATCH_MS` = 30s, `ADOPTED_MISSES` = 2 consecutive failed probes): when it stops answering, the daemon publishes its own and logs `the Funnel this daemon adopted no longer answers; publishing our own`. Lisa, 2026-09-09: a hand-run `metro serve` was suspended with Ctrl-Z and `metro stop`ped, which killed its daemon but left its foreground `tailscale funnel` orphaned in the tmux shell; the service daemon that followed adopted that funnel twice, and `tmux kill-session` then took the funnel down while the daemon it fronted kept running unreachable until a restart. **`METRO_TUNNEL=tailscale` is the PERSISTENT address** (Less, 2026-09-05, after weighing tailcat, a metro.box relay and WebRTC): `tailscale funnel <port>` in the foreground publishes `https://<machine>.<tailnet>.ts.net` (443, or `:8443`/`:10000`), a name that survives restarts, updates and reboots, reachable from any browser with nothing on the laptop; `funnelUrlIn` picks it out of the "Available on the internet:" block, and the link is announced ONLY once the name resolves at 1.1.1.1 OR 8.8.8.8, over IPv4 OR IPv6 (`resolvesPublicly`; each resolver is asked on its own because one resolver's negative cache must not veto the other, and Tailscale publishes the AAAA record minutes before the A, seen on Suzy 2026-09-05): Tailscale publishes a Funnel name in public DNS only after Funnel is approved for the tailnet and the node's cert exists, and a browser that asks before that caches the NXDOMAIN for minutes (seen on Suzy, 2026-09-05: the page said "No Metro daemon answered" at a name ts.net's own servers did not know yet). It needs Tailscale installed and signed in on the daemon's box and Funnel enabled once on the tailnet; the browser's TLS session terminates ON THE BOX (the node holds its own certificate; Funnel's relays forward by SNI and never decrypt), which is stronger than the quick tunnel, where Cloudflare terminates TLS. Funnel is on every Tailscale plan, the free Personal one included. `test/tailscale-funnel.test.ts` drives it against a fake `tailscale`. The cloudflared quick tunnel is GONE (Less, 2026-09-05: a temporary domain has no place); a box with no Tailscale has loopback and `ssh -L`. It runs `cloudflared --no-autoupdate tunnel --url http://127.0.0.1:<port>` with no account, reads the `https://<words>.trycloudflare.com` address out of cloudflared's stderr banner (`quickTunnelUrlIn`), keeps it as module state (`currentTunnelUrl()`), and, ONLY once the name resolves at Cloudflare's own resolvers (`resolvesAtCloudflare`, 1.1.1.1/1.0.0.1, polled every 3s for up to 3min, then announced anyway with a warning), calls the `onUrl` hook `boot.ts` passes, which prints `publicConnectHint`. The wait is deliberate: a fresh `trycloudflare.com` name takes ~50s to appear, and a browser that asks the SYSTEM resolver before that poisons its negative cache for minutes. **`publicBaseUrl()` is `METRO_PUBLIC_URL`, else the live tunnel address**. A missing binary (`ENOENT`) is logged once and NOT retried — the CLI checks first.
- Reconnect reality: the channel GET stream is held open by a 15s SSE-comment keepalive. On reconnect the relay replays from the bounded ring — best-effort, bounded to `BUS_BUFFER_MAX`, not guaranteed across a long disconnect.

## Working discipline

- **Verify, then act.** Confirm claims against the code (rg/Read) before changing or asserting. Most "obvious" facts here have load-bearing exceptions.
- Don't flag code as dead without an `rg` search proving zero references across the workspace, including the exports map and the station registry.
- The full gate must be green before you propose a PR.
- Branch off `main`, open a PR, land via PR. For stacked PRs, beware `--delete-branch` deleting a dependent PR's base.
